cover
02 / 16
SLCR / SLCR
要件をグラフへ［日本語］
要件（仕様）を長文ではなく「グラフ」として保持し、validatorで検証できる形にして、エージェント・人・CIが同じ根拠で動けるようにする標準です。
背景キーワード：context rot（文脈劣化） / compounding drift（誤読の蓄積）
problem
03 / 16
読むだけで崩れる
仕様のズレ
長い要件文書は、誤読・取りこぼし・理解の揺れを生みやすく、時間とともにズレが蓄積します（context rot / compounding drift）。
起きること
誤読・取りこぼし

AI/人が読むときに、必要な根拠まで届かない。

結果
実装との乖離

「コードが何を満たすべきか」が曖昧になりやすい。

metaphor
04 / 16
読む最小単位
sliceで切り出す
SLCRは「要件（REQ）＋必要な周辺文脈」だけを、切り出した“slice”としてエージェントに渡します（全仕様を読ませない）。
中心
REQ

満たすべき要求。

関係
refines / 階層

位置づけと導入経路。

補助
依存 / 用語

誤解を減らす最小根拠。

Slice（スライス）＝必要情報の最小パッケージ（日本語注記：スライス）。
architecture
05 / 16
要件をグラフで持つ
ツリー表現→内部グラフ
要件はセクション／要件／受け入れ基準（AC）／用語などの構造として、YAML/JSON/TOMLで表しつつ、内部的にはグラフとして管理します。
入力（記述）
Markdownではなく構造体

セクション・REQ・AC・用語を分離して保持。

内部（実行）
グラフで辿れる

slice抽出や依存関係の参照を一貫化。

process
06 / 16
合否を判定する
AC→validatorで検証
各受け入れ基準（acceptance criteria, AC）をコード近傍のvalidatorで証明し、要件と実装のズレを検出します。
配置
.validators.slcr.toml

validatorの宣言・紐づけを管理。

判定軸
満たす／満たさない

“仕様が満たされたか”を機械的に評価。

enumeration
07 / 16
3つの状態
satisfied / unsatisfied / unknown
slcr checkは各要件を分類し、unknownは“失敗”ではなく「検証未整備（coverage gap）」として扱います。
判定
satisfied

validatorが受け入れ基準を満たす。

判定
unsatisfied

受け入れ基準が満たされない。

判定
unknown

検証できるvalidatorが未存在。

distinction
08 / 16
重要度で運用を変える
MUST / SHOULD / MAYを統制
モダリティに応じて、unknown/unsatisfied/警告の扱いを段階化し、CI運用で厳格度を調整できます。
MUST
失敗＝止める

MUST / MUST NOTは失敗扱い。

SHOULD
警告＝管理

警告（warning）として扱える。

MAY
情報

情報（info）として運用。

例：CIで --deny-warnings により運用を締められる。
process
09 / 16
CIで“仕様どおり”を再現
checkをコマンド化
「does the code do what the spec says?」を、slcr checkとしてCIで実行可能にし、継続開発でも一貫性を維持しやすくします。
基本
要件単位の評価

各REQのACをvalidatorが判定。

運用
JSON出力・差分検知

レンダリング差分（--expect-no-diff）で更新漏れを検知。

architecture
10 / 16
組み込みではなく宣言
pinned toolsで再現性
validatorはSLCRに内蔵された固定ツールではなく、SLCR.tomlで宣言してpinされた外部ツールを使う設計です。
狙い
環境依存を抑える

ツール更新による挙動差を減らす。

現実
tools記述は必要

ディスクリプタ作成コストが発生する。

evidence
11 / 16
人間にも同じ根拠
slcr renderでMarkdown生成
人が読むために、同じグラフからMarkdownを生成します。さらに、--expect-no-diffで生成結果の差分を使って仕様更新漏れを検出します。
一致
読む仕様＝参照仕様

エージェントが参照する根拠とズレにくい。

検出
差分で漏れを発見

レンダリング差分が“更新の取りこぼし”のサイン。

comparison
12 / 16
導入の勝ち筋と注意点
validator前提の運用設計
SLCRは検証志向が強い一方、validatorの粒度・保守・運用ガバナンスが弱いと“unknownが残る”リスクがあります。
勝ち筋
unknownを減らす計画

coverage gapを減らすため、validatorを先に整備。

注意点
仕様品質・粒度の設計

ACの粒度ガイドやチーム合意がないと誤実装の余地が残る。

closing
13 / 16
まとめ
要件を検証可能に
SLCRは「グラフで要件を管理」し、「validatorでACを検証」し、「unknownを検証未整備として可視化」して、長期の仕様運用を現実に落とします。
