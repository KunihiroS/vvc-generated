Microsoft MXC
02 / 16
Agent安全を“境界”で作る
Execution Containers
AIエージェントがファイル・ネットワーク・複数アプリにまたがる時、最大の課題は“権限の事故”。MXCは実行時にOSが境界を強制し、ポリシーで囲い込みます。
（英語用語）containment=実行境界 / least privilege=最小権限 / observability=監視・可視化
Problem
03 / 16
事故は“権限”から始まる
自由が強すぎる
AIエージェントにユーザーと同等の権限を与えると、モデルの判断や生成コード、プラグイン挙動が意図を超えてしまい、情報漏えい・業務停止のリスクが上がります。
意図超え
生成コードが想定外のファイルや外部先へ到達
被害拡大
“信用”に依存する設計だと封じ込めが弱い
運用負担
最小権限ポリシー作成が難しく、拒否過多になりがち
見えにくさ
何へアクセスしたかが追えないと改善できない
Core Idea
04 / 16
OSが“勝手”を止める
Policyが 境界になる
MXCは、開発者/IT管理者が許可する資源を宣言し、実行時にOSが境界を強制します。これで“見た目は合理的でも、権限外はできない”形に変えられます。
宣言（policy）指定
許可するファイル・ネットワーク宛先・アプリ範囲などを定義
強制（enforcement）実行時
OSが境界を適用し、エージェントの権限自己拡張を遮断
Architecture
05 / 16
境界の対象は広い
ファイル / アプリ / ネット
MXCの境界は単一機能ではなく、ファイル・ネットワーク・複数アプリにまたがるアクセスへ及びます。攻撃や事故の“入口”を複数面で抑えるのが狙いです。
Files領域
参照/更新を許可した範囲のみ（例：ユーザーDocumentsの遮断など）
Network接続
任意のネット接続を遮断し、許可した宛先だけに制限
Apps実行
必要なアプリ/機能の実行を許し、不要な実行面を閉じる
Modes
06 / 16
最小権限を作るための“段階”
Learning → Permissive → Enforcement
最小権限ポリシーは最初から完璧に当てるのが難しいため、MXCは3モードで現実的に作ります。
i. Learning学習
拒否されたアクセスも記録し、活動の実態を観測（activity report）
ii. Permissive許可的
計測・調整を進めつつ、業務停止を避ける運用寄りの段階
iii. Enforcement強制
ポリシー通りに実行を制御（拒否・制御が“運用の本番”に近づく）
ポイント：拒否の観測→許可の絞り込み→強制へ、という移行が前提。
Governance
07 / 16
“宣言”と“制約”を分ける
開発者 × IT の 分業
MXCポリシーは開発者の宣言と、IT組織の管理側制約を分離します。これにより、企業ごとの姿勢に合わせて運用できます。
開発者（policy作成）定義
必要な資源（ファイル・ネット宛先など）をエージェント側から宣言
IT（組織制約）運用
Intune等で追加制約、承認/評価の方針を適用し安全に回す
Identity
08 / 16
“人”と“エージェント”を切り分ける
Identity（帰属）で 影響範囲を絞る
エージェント活動をユーザーと区別することで、セキュリティチームは“人の操作”ではなく“エージェントの振る舞い”として評価・遮断できます。
帰属（attribution）識別
ローカルIDまたはEntra連携の身元に紐づけて区別
侵害時の設計隔離
不正・不具合エージェントの影響を、従業員全体へ拡がりにくくする狙い
Observability
09 / 16
“見える化”が最小権限の前提
活動レポートで 学習
Learning/Permissiveの段階では、エージェントが実際にどの資源へアクセスを試みたかがレポートとして残ります。これが最小権限ポリシー作成の材料になります。
何を試したか
ファイル・ネット宛先などのアクセス試行を把握
拒否の理由
境界に引っかかった操作を観測し調整へ
段階移行
拒否観測→許可絞り込み→本番強制へ
改善ループ
監視・更新を回せないと“境界の質”が上がらない
FAQ要旨：Learning/Enforcementの違いは“観測あり/なし”の位置づけ。
Comparison
10 / 16
信用ではなく“強制”へ
Trust型 vs Boundary型
MXCの本質は、エージェントを“信用する/しない”に寄せず、実行時に境界をOSが強制する点です。
Trust型典型
許可の判断がモデル/コードに依存し、事故時の封じ込めが弱くなりがち
Boundary型（MXC）狙い
必要資源以外をOSレベルで遮断し、権限外行動を構造的に防止
補足：隔離強度はバックエンド/ティアで異なる可能性があるため、防御レベルは設計と選択次第。
Risks
11 / 16
“万能ではない”を前提にする
許可範囲が広いと リスク残る
MXCは隔離・境界強制でリスクを下げますが、万能な保証ではありません。最小権限ポリシーの設計と継続的な見直しが不可欠です。
ポリシー誤設定失敗
許可範囲が広いと、境界内での悪用や被害が残り得る
運用の欠落監査
監視・更新・学習→強制移行が回らないと、安全は積み上がらない
影響範囲粒度
identity/帰属の粒度やログ保持など、運用設計の確認が必要
性能/コスト現場
導入・保守・監査・性能影響は、実運用で見積もりが必要
Usage
12 / 16
エージェント接続の現実
対応は製品に 依存
入力文では、GitHub Copilot、OpenClaw、OpenAI Codex、Replit等でMXCサポートがある/今後予定とされています。ただし“どの機能がどの程度”対応かは個別確認が必要です。
Copilot例
MXCと連携するケースが言及
Codex / Replit例
サポートまたは予定が言及
OpenClaw例
サポートの言及
また、session containerの分離はWindowsに限定される可能性があるため、利用OS制約も前提に。
Closing
13 / 16
結論：境界＋監視＋運用
MXCは“足回り”を 整える
MXCの強みは、OSが実行時に境界を強制し、Learning/Permissive/Enforcementと観測レポートで最小権限へ寄せられる点です。技術導入だけでなく、ポリシー設計・移行・監視改善のプロセスが回るかが成否を左右します。
Your next check次の確認
許可範囲（最小権限）・ログ/監査・Entra/identityの粒度・ログ保持・移行運用を設計する
