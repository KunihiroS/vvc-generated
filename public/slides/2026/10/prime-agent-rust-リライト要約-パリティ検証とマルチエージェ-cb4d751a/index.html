02 / 16
Prime Agent Rewrite

Rustへ

TypeScript版の Prime Agent を Rust へ“ゼロから書き直し（rewrite）”し、マルチエージェント運用の品質と性能を同時に引き上げた取り組みを要点整理します。
Key idea
パリティ（同等性）を崩さず改善する
Bilingual: Parity（同等性）
Quality gates
TUI差分 / セッション差分 / プロトコル差分
Verification（検証）を設計の中心に
読み終えると「何を・なぜ・どう検証して・何が良くなったか」が1枚ずつ繋がる構成です。
PROBLEM
03 / 16
移行の理由

課題顕在化

TypeScript版は提供の速さが武器だった一方、実行時エラーの検知不足や、単一イベントループ上での重処理による応答性低下、GCコストが運用課題になりました。
Robustness
実行時例外の検知が弱い
Responsiveness
イベントループ競合
Resource cost
GC・JSランタイムのオーバーヘッド
結論として「速度」だけでなく、運用の安定性（安全・効率・予測可能性）が移行の主因です。
METAPHOR
04 / 16
移行の難所

同等性の橋

言語を置き換えるだけではなく、「見た目・挙動・通信」の実質的な一致＝パリティ（同等性）を渡りきった状態で速くする必要があります。
Parity（同等性）
画面・セッション・プロトコルを一致させる
目的は“実用上同じ”を機械的に担保
Orchestration（調停）
複数エージェント協調で自己改善を回す
役割分離＋検証込みワークフロー
ここが本質：速さの前に、正しさの橋（検証）がないと改善が崩れます。
ARCHITECTURE
05 / 16
検証設計

三層パリティ

実装の互換（機能・挙動・プロトコル）を守るために、TUI差分・セッションログ差分・プロトコル差分の複数検証を用意しました。
TUI diff
端末レンダリング一致（見た目）
Human-in-the-loopを減らす狙い
Session diff
会話・モデル呼び出しの整合
入力→同一セッションを確認
Protocol diff
デーモンのメッセージ型整合
通信の差異を潰す
単一のテストではなく、失敗しやすい層から順に“割れ目”を塞いでいます。
PROCESS
06 / 16
失敗→修正ループ

検証込み自律

自動翻訳ではなく、パリティ検証ごとに失敗→差分情報→修正へ戻るループ前提で自律ワークフローを成立させています。
Cycle
失敗 → 差分 → 修正
検証結果が次の修正を指示
Risk control
品質低下リスクを抑制
“改善”が“劣化”にならない
ここでの主役はモデルそのものより、検証で差分を回収する仕組みです。
ORCHESTRATION
07 / 16
役割分離

偏りを遮断

実装担当と検査・検証担当を分離し、別モデル・別文脈・新しい Prime Sandbox で検証して確認バイアスを減らします。
Implementer
実装（書く）
変更の責任範囲を限定
Reviewer
検査（見る）
別モデル/文脈
Verifier
検証（機械的に確かめる）
新Sandboxで再実行
自己改善は強いが危険でもあるため、「見張り」を同じ棚に置かない発想です。
ENUMERATION
08 / 16
FSMの工場化

手順の型

ルートエージェントがタスクをトポロジカルに並べ、Planner/Implementer/Reviewer/Verifier の固定パターンを FSM 的に回すことで、手順の再利用性を狙います。
Topology
手順を“並ぶべき順”として配置
計画→実装→検査→検証
Outcome
技術的負債を減らし長期運用へ
同種開発の再現性を上げる
“動く”だけでなく、“同じ品質で回し続ける”ためのオーケストレーションです。
EVIDENCE
09 / 16
性能の獲得

ヒルクライム

ベンチマークを目的関数に置き、パリティ検証を壊さない条件付きで改善探索（ヒルクライム）を行い、結果のノイズを抑えて評価しています。
Objective
ベンチマークを“良さ”の指標に
Constraint
パリティ維持を条件にする
正しさ優先
Experiment
ノイズが大きい結果を比較から除外
実験設計への配慮
改善の探索が恣意的にならないよう、“測って絞る”形にしています。
COMPARISON
10 / 16
Rustの伸び

コスト削減

Rust版は、入力までの時間（cold/warm）、メモリ使用量、インストールサイズなどで大きな改善を示し、マルチエージェントのストレステストにも耐えました。
Latency
cold / warm の入力時間が改善
Memory
メモリ使用量を削減
Footprint
インストールサイズが縮小
“速くなる”は自明ではなく、待機・メモリライフサイクル改善が中心と示唆されています。
DISTINCTION
11 / 16
一般化への注意

比較の罠

性能数値は自社カスタム実行スイートでの計測であり、外部比較には条件差の可能性があります。結論の断定より、ベンチマーク条件の確認が必要です。
Benchmark validity
入力条件・評価基準が統一されない恐れ
Need more data
失敗ケース頻度・種類、セキュリティ観点、障害時復旧分布
つまり「良さそう」だけでなく、導入判断のための観測指標が要ります。
CLOSING
12 / 16
今後の道筋

evals加速へ

リライト後の“基盤が整った状態”で能力向上と評価（evals）を加速し、Prime Intellect のエコシステムへより密に統合していく方針です。
Roadmap
能力向上＋ evals（評価）を加速
Integration
Prime Intellect へ統合を強化
Platform
Windowsネイティブ対応（ベータ）
配布・導入手順も提示
次は“改善の回転”を上げつつ、“測り方”をより汎用にしていくフェーズです。
