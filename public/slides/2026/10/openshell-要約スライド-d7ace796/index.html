02 / 16
安全を後付けしない
OpenShell 要約
自律AIエージェントが「ファイル・ネットワーク・API・資格情報」を扱うときに、ポリシーを実行時強制と形式的検証で守るランタイムです。
入力はREADME相当の要約で、実装の網羅性・性能・失敗時挙動などの一次情報は不足しています。断定より、書かれている範囲の解釈と追加確認点を整理します。
problem
03 / 16
なぜ危ない？
制御なき 能力
自律AIエージェントは強力ですが、能力が増えるほど「データ漏えい」「不用意な通信」「権限の過剰付与」のリスクも増えます。
Risk / 脅威
秘密情報やファイルを参照・流出
情報漏えい（Information Leakage）
Risk / 脅威
許可していない外部へ通信
不用意なネットワーク（Unintended Network）
Risk / 脅威
資格情報（クレデンシャル）を不適切に利用
権限乱用（Credential Misuse）
Risk / 脅威
ポリシー微修正で安全が崩れる
変更起因事故（Change-induced Incident）
metaphor
04 / 16
守る仕組み
二重の 関門
OpenShellは「実行時の強制（カーネルレベル）」と「変更前の検証（formal verification）」を組み合わせ、危険な抜け道を減らします。
Door 1 / 関門
Sandbox隔離 + 実行時監視・制御
Kernel-level enforcement
Door 2 / 関門
ポリシー変更前に形式的検証 → 承認待ち
Policy formal check
architecture
05 / 16
どこを制御する？
カーネル 強制
エージェントをサンドボックスで動かし、カーネルがファイルアクセス・システムコール・ネットワーク接続を制御し、通信はポリシーチェックを通過します。
File / ファイル
読み書きの範囲を実行時に制限
Syscall / 呼び出し
許可されない処理を遮断
Network / 通信
接続先をポリシーで判定
Web検索情報では seccomp に加え Landlock LSM、ネットワーク名前空間の言及もあるため、「どのLinux機構で何を制御するか」の確認価値があります。
process
06 / 16
変更の扱い
形式的 検証
ポリシー変更を適用する前に形式的検証を行い、危険な新規アクセス（例：資格情報付きで到達可能なホストの増加）をフラグして人のレビューへ回します。
1. Verify / 検証
意図しない権限拡大を検出
formal verification
2. Review / 承認
フラグ時は承認者の介入が必要
human-in-the-loop
具体的なフロー（どの変更がどれだけブロックされるか）や、偽陽性/偽陰性の運用はREADME要約だけでは不明です。
distinction
07 / 16
重要な設計
資格情報 非露出
エージェントは実際の資格情報を見ず、承認済みエンドポイント向け要求にだけOpenShellが資格情報を追加します。
Agent / エージェント
資格情報にアクセスしない
no secret exposure
OpenShell / ランタイム
承認済み先への要求に限り付与
policy-gated credential injection
ただし「盗めない」とは断言できません。メモリ保護・ログ混入・失敗時挙動・プロセス間通信の扱いは追加確認が必要です。

クラスタ運用前提
Kubernetes 連携
Helmでゲートウェイをデプロイし、CNIはNetworkPolicyを強制できる必要があるとされています。つまりクラスタ側の分離設計が成立条件です。
Deploy / 配置
Helmでgatewayを導入
Enforce / 強制
NetworkPolicyが実際に効くCNI
Web検索情報では、NetworkPolicyが「作られるだけ」で強制されない場合に回避リスクがあるとされます（ingress/egress両方の強制が論点）。

運用と監査
テレメトリは 限定
テレメトリは匿名で運用カテゴリと件数に限定し、ファイルパス・プロンプト・資格情報などは収集しないと説明されています。無効化手段も明示されています。
Collected / 収集
匿名の運用カテゴリ・件数
privacy-preserving metrics
Not collected / 非収集
資格情報、ファイルパス、プロンプト等
no secrets & no content
正確な送信データ項目や保持期間は「Telemetry」ドキュメント確認が確実です。

Only sandbox

OpenShell
