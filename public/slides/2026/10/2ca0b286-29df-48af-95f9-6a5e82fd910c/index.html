Laminar / Observability
02 / 18
AIエージェント観測

Laminar

LLMやAIエージェントの実行を、トレース・Signals・evalsとして集め、SQLとUIで改善につなげます。

Problem
03 / 18
見えない挙動

デバッグが重い

AIエージェントは「どのLLM呼び出しで詰まったか」「どの状態変化が原因か」を追いにくいことが多いです。結果として、失敗の再現や改善の優先度付けが遅れます。

Metaphor
04 / 18
三つで観測

ログでは足りない

Laminarは「呼び出し履歴（トレース）」「重要な状態変化（Signals）」「評価（evals）」を分けて記録します。単一ログより、原因究明と改善の道筋が立てやすくなります。

Architecture
05 / 18
中核コンポーネント

Tracing / Signals / Evals

Tracing
スパン（span）で記録し、LLM呼び出しや流れを追跡
（traces / トレース）
Signals
状況を平易な文章で記述し、詰まり・失敗を検知
（signals / シグナル）
Evals
評価を可視化し、改善サイクルを回す
（evaluation / 評価）
Query
06 / 18
SQLで分析

“あとで聞ける”

収集したトレース・イベントを、SQLで問い合わせる設計です。UIでの確認だけでなく、条件抽出して要因を切り分けられます。

SDK
07 / 18
最小コード導入

OpenTelemetryネイティブ

計測の入り口
OpenTelemetryネイティブのトレースSDKで開始（例：スパン収集）
（OpenTelemetry / 標準計測）
言語
TypeScript / Python クライアントで接続しやすい
（clients / クライアント）
Self-host
08 / 18
現場の現実

Docker Compose

運用はDocker Composeを前提に段階的な構成選択ができます。まずは軽量スタックで動かし、必要に応じて本番向けへ寄せる流れです。

Config
09 / 18
プロバイダ切替

.envで制御

Gemini / OpenAI互換 / AWS Bedrock / Azure AI Foundry を想定し、.envで切替します。AIプロジェクトの変更（モデル・ベンダー）に追従しやすい前提です。

オプトアウトあり

セルフホストでも
匿名のusage telemetry収集が起こり得る
（usage telemetry / 利用テレメトリ）
停止

（disable / 無効化）
Distinction
11 / 18
実務で効く差

運用論点が明記

機能紹介に留まらず、セルフホストで詰まりやすい具体論（再作成・ディスク回収・TTL）まで扱います。導入後の“安定稼働”に寄与します。

ClickHouse
12 / 18
設定変更の罠

再作成が必要

理由（要点）
ClickHouseの設定変更は、適用するためにClickHouseコンテナの再作成が必要
（re-create / 再作成）
Data retention
13 / 18
“無効化”の落とし穴

既存データは残る

無効化
内部テレメトリログ無効化は書き込み停止になり、既存テーブルは残る
（stop write / 書き込み停止）
回収
ディスク回収のためTRUNCATEが提案される（ただし注意が必要）
（TRUNCATE / 切り詰め）
TTL
14 / 18
テーブル変形

TTLでリネーム

TTL適用によりテーブルがサフィックス付きでリネームされる可能性があります。削除・回収操作は、サフィックス付きテーブルの有無を確認してから行うのが安全です。

References
15 / 18
読む順番

判断に必要

公式README（主）
観測対象（Tracing / Signals / Evals）、セルフホスト手順、クリックハウス運用注意
補足確認
LLMプロバイダ設定、テレメトリ仕様（送信粒度/保持/暗号化範囲）、権限・データ保持ポリシー

要点：Laminarは「AIエージェントの実行を継続観測し、デバッグ・改善・評価を回す」ための基盤です。ただし導入判断は、テレメトリの実仕様とデータ保持・運用リスクを追加調査して確定してください。
