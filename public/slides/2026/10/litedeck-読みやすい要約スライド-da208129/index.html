02 / 16
SSHを一画面に

LiteDeck要約

SSH接続だけでサーバ管理をGUI化し、導入負担を抑えつつ「実行内容の可視化」と安全策を重視するエージェントレス運用ツールです。
核 / Core（エージェントレス）
サーバに基本インストール不要（常駐しない）。
統合 / Unify
ファイル・編集・サービス/プロセス/コンテナ・監視・端末・AI連携を1画面へ。
PROBLEM
03 / 16
運用は往復地獄

何がつらい？

SSH運用は、監視・編集・再起動・ログ確認を行き来しがちで、確認漏れや誤操作の温床になります。特にAI連携では「何を変えたか」が見えにくくなりがちです。
誤操作
確認が抜けると復旧コストが増える。
監査性
誰が/何を/いつ—の追跡が難しい。
AIの境界
AIが行う変更が“見えない”と事故が増える。
METAPHOR
04 / 16
一枚の管制図

GUIで可視化

LiteDeckは、SSHでできる操作を同一画面に集約し、実行結果を“手触りのあるログと差分”として見せます。AIが絡む場合も、対象範囲を限定して安全域を作ろうとしています。
見える化 / Visibility
Command Log・diff・（対象に限る）Undo。
安全域 / Boundary
「LiteDeck経由で行われた変更」に限定して可視化/復元。
※ “全部の変更”ではありません。対象外の経路がある点が重要です（後で詳述）。
ARCHITECTURE
05 / 16
常駐なしの接続

SSHで実現

エージェントレス設計により、サーバ側へデーモンを追加せず、開いているSSHポートを使ってファイル操作・情報取得・実行を行います。実行可能な範囲は、SSH経由でOSが提供する手段に依存します。
クライアント側
同一画面で操作と監査をまとめる。
サーバ側
追加インストールは原則不要（前提：SSH稼働）。
依存 / Depend
systemdやサービス形式、WindowsはOpenSSH中心。
EVIDENCE
06 / 16
diffとログ

監査の道具

LiteDeckの中核の考え方は「何を実行したか」をCommand Logとして残し、ファイル更新ではdiffや復元（Undo）で変更を追えることです。AI連携でも同じ思想を維持すると読み取れます。
Command Log
実行した内容を追跡しやすくする。
diff / Undo
元ファイル保持にもとづく復元（対象範囲に限る）。
加えて、sudo等の昇格は勝手に要求せず、必要時に確認する安全思想が強調されています。
DISTINCTION
07 / 16
AIの範囲限定

MCP境界

AI（MCP連携）は「LiteDeck経由で行われた作業」に対してのみグラフ化・Undo対象になるとされています。つまり、別経路（例：AIが自前でSSH実行）で変えた内容は、可視化/復元の対象外になり得ます。
対象 / Target
LiteDeck経由の変更（diff・Undoが効く領域）。
対象外 / Outside
LiteDeck外のSSH実行や直接改変（見えない可能性）。
MCP（Model Context Protocol）: AIが“ツール”を呼ぶための枠組みとして扱われることが多い用語です（ここでは連携概念）。
PROCESS
08 / 16
安全は設計＋運用

誤操作を抑える

sudo等は無断で実行せず確認フローを置く設計思想があります。さらに「署名の代替ではないSHA256チェック」など、初期配布の安全性に関する注意も明記されています。
権限 / Privilege
必要時に確認（勝手に昇格しない方針）。
監査 / Audit
Command Log・diffで変化を追跡。
配布 / Release
初期は無署名、SHA256は署名の代替ではない。
ENUMERATION
09 / 16
監視も統合

CPU〜GPUまで

LiteDeckは監視を統合し、CPU/メモリ/ディスク/ネットワークに加えてNVIDIA GPU（Jetsonを含む）も扱う導線があります。Jetsonボードは少なくとも「読む（read）」対象として言及されています。
標準 / Standard
CPU・メモリ・ディスク・ネットワーク。
強み / Focus
NVIDIA GPU（Jetson）監視を狙う。
ただし、対応条件（必要コマンド、権限、JetPack/ドライバ要件）は読み取れる断片だけでは断定できません。
COMPARISON
10 / 16
OS前提が効く

対応は二系統

入力からは、クライアントはmacOS/Windows/Ubuntu、サーバはLinux（systemd、Ubuntu/Debian/Raspberry Pi等）とWindows（OpenSSH server）が中心と読めます。Windowsサーバではタブ/機能が一部未整備の記載もあります。
Linux / systemd
サービス管理・プロセス/状態の取得と相性。
Linux / 軽量
Ubuntu/Debian/Raspberry Pi等。
Windows / OpenSSH
一部機能が未整備の可能性。
DISTINCTION
11 / 16
限界を誤解しない

Undoの範囲

復元できるのは「ファイル内容」など、可視化対象に限定される可能性があります。さらに、AIがLiteDeck外経路で変更した場合は追跡/復元が効かない恐れがあります。
できる / Yes
LiteDeck経由のファイル変更はdiff/Undoの対象になり得る。
できない / No
LiteDeck外の変更、プロセス停止・再起動等の影響は残る可能性。
導入前に、削除・kill等の不可逆操作は“検証用環境”で挙動確認する姿勢が重要です。
PROCESS
12 / 16
導入判断チェック

あなたの要件

LiteDeckが刺さるのは「SSH中心」「常駐物を増やしたくない」「操作の監査性が欲しい」現場です。一方、AI連携やGPU監視は前提条件の検証が必要になります。
向くケース
エージェントレス方針／diff・ログ重視／運用を統合したい。
要検証
Jetson GPUの検出条件／MCPの境界運用／無署名配布の社内手順。
MCPは一般にツール呼び出しに起因するリスク（プロンプトインジェクション等）が議論されるため、隔離やガバナンス設計が推奨されます。
