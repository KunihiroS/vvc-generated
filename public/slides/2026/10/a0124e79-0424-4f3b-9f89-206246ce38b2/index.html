COVER
02 / 17
Era（Eon）で“企業丸ごと”生成
Era（Eon）
MCP / ベンダーAPI互換で、複数SaaSにまたがる整合した1社（同一人物・同一顧客・同一案件）をシミュレートし、エージェントのテスト・ベンチマークに使えるようにします。
日本語補足：企業合成（企業丸ごとを作る）/ ライブ扱い（読み書きで検証）
PROBLEM
03 / 17
“ダミー”では足りない
整合性
単発の疑似データだと、Salesforce / Slack / Jira / Zendesk などで同じ人物・同じ顧客が一致しません。結果として、横断ワークフローの推論や検証が崩れます。
Issue 1 / 問題
ID・関係（顧客/案件/出来事）がサービス間でズレる
Issue 2 / 問題
読めるだけで書き戻し検証が弱い（テストが完結しない）
狙い：テストが「それっぽい」ではなく同一企業として成立すること。
METAPHOR
04 / 17
会社は“つながり”
Identity
Eraが作るのは、レコードの束ではなく会社という物語です。Slackにいる同じ社員が、JiraにもSalesforceにも同じ存在として現れます（同一アイデンティティの一貫性）。
Same Person / 同一人物
社員（User）
Same Customer / 同一顧客
顧客（Account）
Same Event / 同一出来事
出来事・履歴（時系列）
結論：エージェント評価を「横断前提」に寄せられる。
ARCHITECTURE
05 / 17
“生成→接続→双方向”
MCP/互換
生成したシミュレート企業を、MCPサーバー／API互換の接続口で読み書き可能にします。書き込み→ベンダーRESTクライアントで読み戻し、という整合した流れを狙います。
Step 1 / 生成
業種・規模・対象顧客・接続先を入力して企業データセットを作成
Step 2 / 検証
MCP経由の操作結果をREST側で読み戻し、状態の一貫性を確認
補足：単なるモックではなく、テスト対象を“稼働状態”として扱う発想。
ENUMERATION
06 / 17
作成入力は5問
入力
企業生成はコンソールで5問に答えるだけで開始できます。CLIでも業種・会社規模・対象システムなどを指定して作成できます。
Console / コンソール
5問入力で生成開始（業種・規模・シナリオ・接続先など）
CLI / 自動化
業種・規模・接続対象をパラメータ化し、反復生成に対応
運用イメージ：研究だけでなくCI（継続的テスト）へ落としやすい構造。
EVIDENCE
07 / 17
現実っぽい分布
Shapes
取引規模・顧客規模・チケット数などは一様ノイズではなく、対数正規分布やheavy-tailed（重い尾）など現実的な形を取る設計です。
Transaction / 取引
規模（重い尾を想定）
Customer / 顧客
企業規模（分布に合わせる）
Tickets / チケット
件数（生成の偏りを再現）
狙い：エージェントが「ありがちな雑なデータ」に適合しすぎるのを抑える。
EVIDENCE
08 / 17
品質課題もテスト化
Mess
重複、欠損っぽい行、プレースホルダ等の意図的な汚れを混ぜられます。さらに、欠陥の種類と置換された値をマニフェストで宣言します。
Quality Benchmark / ベンチ
検出器（detector）が何を見つけるべきかを定義可能
Fairness / 公平
欠陥パターンが“隠れノイズ”にならず、評価前提を共有できる
二面性：現実性は上がるが、過適合の点は追加検証が必要。
ARCHITECTURE
09 / 17
時間の現実性
Time
タイムスタンプは各人の勤務週・タイムゾーンに基づいて割り当てられます。休暇や異動なども勤務実態のルールで織り込み、いつ何が起きたかを整合させます。
Timestamps / 時刻
勤務週・タイムゾーン反映
Vacation / 休暇
稼働可能性を制約
Transfers / 異動
履歴ルールで整合
効果：調査・調停（いつ/なぜ）系タスクで説得力が出る。
PROCESS
10 / 17
ライブオーバーMCPで確認
Loop
エージェントがMCP経由で書き込み・操作を行い、その結果をベンダーAPI経由で読み戻します。同一テナント状態を共有するため、更新を含む業務プロセスの検証に向きます。
Write / 更新
MCP経由で操作（例：チケット/コメント/レコード更新）
Read / 確認
REST側で読み戻し、同じ会社状態で整合性チェック
期待値：読み取りだけで終わらない“業務の実行可能性”を評価。
DISTINCTION
11 / 17
“企業”の根拠
Why Company
単なるダミーではなく、複数システムにまたがって同一の登場人物・同一の関係が再現されます。さらに勤務時間に合わせた時刻配置や、人事履歴ルール、同一テナント状態の読み書きが根拠になります。
Same Graph / 関係
社員⇄顧客⇄案件⇄出来事が崩れない
Same Reality / 時間
勤務・休暇・異動のルールに従う
Same State / 状態
テナントの読み書きで整合を確認
結論：評価に必要な“前提”を会社単位で担保する。
COMPARISON
12 / 17
導入判断の注意点
Check
この資料だけでは、検証指標の定義・閾値・生成条件・比較プロトコル、またベンダーAPIの制約再現度が不明です。導入前に「整合性保証」「シナリオ網羅性」「汚れの多様性」「互換範囲」を追加確認すべきです。
Before / 事前
ID/参照キー/更新反映の厳密さを確認
During / 運用
汚れに“過適合”しない評価設計（第三者再現性）を検証
セキュリティ観点：資料は“実人物なし”を強調。ログ/監査や出力取り扱いは運用で要確認。
