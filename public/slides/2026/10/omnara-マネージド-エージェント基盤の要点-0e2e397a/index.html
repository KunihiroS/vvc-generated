COVER
02 / 16
運用のための基盤
Omnara 概観
Omnaraは、モデル（LLM）と実行環境（マシン/サンドボックス）とツールを管理し、状態を保存しながらAIエージェントを運用するためのセルフホスト可能なマネージド基盤です。
PROBLEM
03 / 16
エージェント運用が難しい
実装だけでは足りない
チャット型の“その場応答”ではなく、ツール実行・承認・再開・監査・外部連携まで含めると、運用設計が別問題になります。
Durable state
障害や再起動後の継続（再開性）
Governance
権限/承認で安全に制御（ガバナンス）
Integration
Slack/GitHub等へ“つなぐ導線”
METAPHOR
04 / 16
制御プレーン
エージェントを“サービス化”
Omnaraは推論（inference）そのものより、エージェントを動かす“制御プレーン/運用基盤”を提供する思想です。運用（状態・権限・連携）を主役にします。
あなたの構成
構成ファイル（例：agent.yaml）/ API / CLI
プラットフォームの仕事
状態保存・承認・イベント・外部連携
ARCHITECTURE
05 / 16
分離設計
モデル×実行環境×ツール
モデル（LLM）と実行環境（あなたのマシン/複数ベンダーのサンドボックス）とツールを分離し、同じ形式で起動できます。
モデル
OpenAI/Anthropic互換など（後述）
実行環境
マシンプール/サンドボックス
ツール/指示
指示（instruction）＋ツール実行
EVIDENCE
06 / 16
止まっても進む
durable state（耐久状態）
ワーカーはステートレスでも、各ステップの記録（状態）をPostgreSQLに保存するため、停止・再起動後の再開が可能だと説明されています。
保存先
PostgreSQL（ステップ履歴/状態）
運用効果
クラッシュ後の継続、トラブルシュート
DISTINCTION
07 / 16
安全の要
権限と承認
ツール実行を「即時」「人の承認要求」「ブロック」に設定でき、プラットフォームがその方針を強制してエージェントを制御します。
即時（Allow）
承認なしで実行
承認要求（Approve）
人がOKするまで待機
ブロック（Deny）
実行を拒否
※安全性の最終品質は、どのツールをどう許可するかという運用設計に依存します（README情報の限界も後述）。

通知/連携

10 / 16
自社で持つ
セルフホスト前提
セルフホスト時はエージェント履歴や状態を自分のPostgreSQLに保存でき、クラウドではOmnara側に保存されAPIで参照する形になります。
セルフホスト
PostgreSQL：履歴/状態を自社でクエリ可能（evals等へ）
クラウド
Omnara側に保存：API経由で参照
COMPARISON
11 / 16
ベンダーロックを緩める
Claude/OpenAIとの違い
Claude Managed AgentsやOpenAI Agents APIが「特定ベンダーのモデル中心」なのに対し、Omnaraは「モデルと実行基盤を選べる」ことを強みとして打ち出しています。
他のマネージド
モデル中心（ベンダー寄りの制約）
Omnara
モデル＋実行基盤を選択、状態データを自社DBで扱える

12 / 16
注意点もある
README以上が必要
公式READMEの抜粋だけでは、セキュリティ実装の境界（監査ログ粒度、秘密情報対策、サンドボックス隔離の実態等）は断定できず、追加ドキュメント確認が必要です。
設定リスク
ローカルデフォルトが不安全と明記される可能性
権限の実装
境界の堅牢性はSECURITY.md等で要確認
隔離の実態
性能/コスト/残存データ/ネット制限など
CLOSING
13 / 16
導入の要点
“運用できる土台”
Omnaraは、耐久状態（PostgreSQL）、権限/承認、外部連携、任意のモデル/実行環境を揃え、エージェントをプロダクション運用に寄せた設計が強みです。ただし本番では安全設定・ログ・隔離を実地で検証しましょう。
評価しやすい点
再開性（durable state）、監査可能性（記録の所在）
導入前に確認
権限設計、秘密情報、保持/復元、サンドボックス境界（SECURITY.md等）
