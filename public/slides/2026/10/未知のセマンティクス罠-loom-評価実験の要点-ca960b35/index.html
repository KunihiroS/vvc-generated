自信ある説明、でも危ない
見抜けるか
Loom のような小型言語では、外見が分かりやすくても内部の意味（セマンティクス）が罠になります。

評価の核心

エージェントが危険を「認識し、説明し、設計/コードで回避」できるか。

不足しているもの

尤度の高い文章や筋の良い説明だけでは、正しいと判定できない。

“success” ≠ “safe”成功≠安全
metaphor
04 / 16
取引は成功/失敗が鍵
状態は戻る
スマートコントラクトは、失敗なら状態が戻り、成功なら反映されます。この前提がセマンティクス罠で揺らぎます。

期待

失敗 → ロールバック。

罠の発想

「失敗が起きた」と見えるまでコミットさせる。

結果

本来作れない値/権限が通過する。

Runtime semantics matters実行時意味論が本体

実装させるもの
Asset と AMM
エージェントには、資産（asset）を扱うインターフェースと、それを用いた定数積スワップ（AMM 的な swap）の実装が求められます。

狙い

状態遷移・呼び出し解決・権限が絡む箇所で、罠が露出するようにする。

追加要件

アクセス制御（認証）も実装対象に含め、署名者や権限の取り扱いを検査する。

goal: avoid interface-matched attacksインターフェース適合攻撃を想定

動いても、全てドレイン
失敗の裏取り
エージェントがセマンティクス罠を見落とした契約は、適応された攻撃（grader がインターフェースに合わせて改変）で実際に全てドレインされました。

外見

実装は「正しそう」に見える。

攻撃側

インターフェース適合で罠を突く。

観測

資産がドレインされ、危険が顕在化。

text likelihood ≠ runtime safety文章のもっともらしさ≠安全
enumeration
07 / 16
3種類のランタイム危険
何が 罠か
評価は「3種類の危険（署名者保持・ディスパッチ差し替え・deferred failure）を正しく認識できたか」を見ます。

(i) signer / 権限

想定外に signer や権限が保持される。

(ii) dispatch / 解決

動的ディスパッチの解決が差し替え可能。

(iii) deferred failure

失敗（panic）が「評価されるまで」失敗せず、そのままコミットし得る。

スコア

完全認識のみ加算、部分認識は加点なし。

認識の完全性が鍵認識≠推測
distinction

“高努力”は万能ではない
effort上げても 固定
effort（max effort など）を上げても、特定の危険（例：dispatch差し替えや deferred failure）では改善が一貫しないモデルがありました。

観測

試行回数増でも、疑うべき方向がないと成果が伸びない。

示唆

必要なのは計算量より「前提化された検証設計」。

more tokens ≠ better safety増量≠安全化

dispatch で設計が変わる
失敗回避の 実験
dispatch 実例では、前提ログや検証を通じてモデルが設計を変える様子が描写されています。説明要求より「検証設計要求」が効きうる、という方向性が示唆されています。

なぜ効く

仕様に書かれていない挙動差を、観測で潰しに行ける。

限界

それでも実務レベルの厳密安全が自動達成されるとは限らない。

recognition ≠ remediation認識≠修正

実務向け結論
自信より検証
未知課題で信頼性を上げる鍵は、「前提を検証可能に明文化し、実験で確かめる」アプローチです。ただし一般化と安全完全性は別問題として残ります。

効いたこと

ASSUMPTIONS.md による前提ログ→実験増→未記述危険の発見。

残る課題

モデル/ハーネス多様性・他脆弱性クラス・網羅性は限定的。

combine: logs + tests + attacks + reviewログ＋テスト＋攻撃＋レビュー
