タブではなく、権限

Chromeタブ（画面の区切り）をアクセス対象にしても、安全性が自動的に担保されるとは限りません。問題の核心は「資格（認証）境界がどこに宿るか」です。

03 / 16
デモは“便利”でも

危険になり得る

「ChatGPTがタブを覗ける」系のデモは、見た目はスコープ制御のように見えても、セキュリティ設計の誤解を生みます。境界評価は“観測（見る）”より“実行（できる行為）”で行うべきです。

誤解
タブ＝認証境界 / credential boundary
実態
認証・権限は profile（cookie jar / セッション）に宿る

何が境界になるか

境界の置き場所

境界は「このタブだけ見せる」ではなく、「どのプロファイル／セッションで／何のゲートを通して実行するか」で設計・検証すべきです。

観測側
読む（タブ内容の取得）
実行側
アクション（購入・送信・削除・設定変更…）
権限の所在
同一 profile の cookie jar
必要な制約
ブラウザ/API/プロキシによる強制（強いinvariant）
evidence
06 / 16
“パスワード無し”でも

認証済みが成立

モデルがパスワード文字列を見なくても、ブラウザはセッションCookieや認可情報を自動で付与してリクエストを成立させ得ます。つまり「視界」と「権限」は一致しません。

見えない
モデルがパスワード欄の文字列を取得しない
起きる
cookie jarが付与され、認証済み通信が成立
Confused deputy（責任ある振る舞いの錯誤）に近いズレが起こり得る
distinction

read-onlyは万能ではない

“読む”が“やる”を呼ぶ

「このタブだけ読む」「タグ付けしたタブのみ使用」は、しばしば指示への“期待”に依存します。遵守が信頼（同一信頼ドメイン）に寄っていると、境界ではなく制約の気分になり得ます。

制約の形
Only use this tab（指示）
検証の弱さ
執行側が同一権限なら越境可能
必要条件
技術的に強制するinvariant

08 / 16
境界の“証明”は実験

カナリアテスト

境界が実在するかは、設計図より敵対的な検証で確かめる必要があります。許可されていない側に目印（canary）を置き、観測・越境できないことを確認します。

準備
禁止側に canary（目印）を埋める
実験
許可された範囲から敵対的にアクセス試行
判定
観測・操作ができない → 境界が機能
目的
“越境できない不変条件”を確認
enumeration
09 / 16
運用が壊れる点

監査ログの不足

何を許されたか／どのプリンシパルとして実行されたかがログに残らないと、事後に境界違反を判断しにくくなります。さらにログが“何を見たか”中心だと、権限行使の文脈が欠けがちです。

典型
閲覧（タブ/範囲）ログ中心
欠落しがち
実行（購入/送信/削除等）の認可文脈
結果
監査で“何が許可されていたか”が追えない
影響
再発防止・原因究明が遅れる
“evidenceとしての監査”には境界の不変性が必要
comparison
10 / 16
低リスク例の転用

“ソファ比較”→

決済操作へ

タブ内の軽い閲覧（例：ソファ比較）が、管理権限や決済操作へ転用されると致命的になり得ます。脅威モデルのスコープ（何ができるか）とデモのスコープ（何を見せるか）が一致していない点が警戒ポイントです。

デモの範囲
読むだけ / 比較するだけ（見た目の限定）
転用の範囲
購入・送信・削除・設定変更（side effect）
evidence

期待と実態

モデルが“見えているように見えない”形で状態（口座残高、業務情報、メール等）へアクセスすると、ユーザーの同意の理解と実態がズレます。境界が説明可能であることが重要です。

倫理
同意（understanding）のギャップ
プライバシー

要点
境界を説明し、運用で確認可能にする
“できること”の明示が、技術以上に効く場面がある

安全設計の結論

推測ではなく

検証へ

プロファイル分離は必要条件になり得ますが、それだけで十分とは限りません。ブラウザ同期、パスワードマネージャ拡張、OSキーチェーン、デバッグポート、ローカル連携など“別経路”も確認対象です。

必要
プロファイル/セッションの分離（cookie jarの分離）
不足
別経路で権限が横流しする可能性
確認
API権限・プロセス分離・デバッグ/同期経路・監査ログ
方法
canaryテスト等の敵対的検証でinvariantを確かめる
closing
13 / 16
読むだけの安心をやめる

境界は実行権

タブをスコープしても、プロファイルのセッション権限が共有されるなら“認証境界”になりません。安全性は「どのプリンシパルで／どのゲートで／どの行為まで」成立するかを、ログと敵対的テストで確かめることです。

I. 評価軸
観測ではなく実行（行為と認可）
II. 境界場所
profile / session / capability boundary
III. 確認
canaryテスト + 監査ログの文脈保持
End.
