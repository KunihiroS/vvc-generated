意思決定を“型”で返す
Decisions API
テキスト/画像を評価し、アプリが扱える形式（predicate・choice・score）で返す高速APIです。分類・ルーティング・優先順位付けを確率と一緒に設計できます。

確率（0〜1）／カテゴリ選択／段階スコア

判断が必要
画像・問い合わせ
アプリは「破損の有無」「どの部署に回すか」「深刻度はどこか」のような判断を日常的に必要とします。 しかし文章生成では、後続処理に使える“安定した型”が手に入りにくい課題があります。

Example

Example

Need
閾値でルーティング/レビュー制御

結果は“機械のため”
人の推論→運用
Decisions APIは、モデルの推論を「アプリ仕様の型」に変換して返します。 そのため、表示だけで終わらず、次の処理（振り分け/優先度/確認キュー）へ直結します。
predicate
真偽条件の確率
choice
固定選択肢から分類
score
順序付き段階評価
ARCHITECTURE
05 / 16
APIの入出力
POST /v1/decisions
リクエストは主に model / input / questions の3要素で構成されます。questionsの各質問には unique name を付け、レスポンスの answers 配列がそのnameを返します。
model: "gpt-6-luna"
input: { text: "..." , image: { ... } }
questions: [
  { name: "damage", type: "predicate", ... },
  { name: "department", type: "choice", ... },
  { name: "severity", type: "score", ... }
]
ENUMERATION
06 / 16
3タイプの質問
predicate / choice / score
目的に合わせて質問タイプを選び、出力形式がアプリのデータモデルにそのまま収まるようにします。
i. predicate（述語）
「破損があるか」「関連があるか」など真偽条件を確率で
ii. choice（選択）
「部署」「カテゴリ」のように順序なしの固定集合から1つ
iii. score（段階）
「軽微・中・重大」など順序付きレベルを確率分布で評価
Key
文章生成ではなく、ワークフロー処理向けの型
EVIDENCE
07 / 16
確率分布が来る
thresholdで運用
predicate/choice/scoreはいずれも確率（0〜1）を基に、choice/scoreでは候補やレベルへの確率分布と confidence が返ります。 そのため、誤検知（false positive）と見逃し（false negative）のコストに応じて閾値を調整できます。
predicate
条件が成り立つ確率（真偽に近い判断）
choice / score
候補/レベルごとの確率分布＋confidence
Outcome
ルーティング、フィルタリング、レビュー優先度
Design
アプリ側で“過不足のない”境界を作る
DISTINCTION
08 / 16
scoreは“連続っぽい”
丸めが必要
scoreは各レベルの確率分布から、数値インデックスを使った確率加重平均で算出されます。そのため、境界をまたぐ中間的な値（例：1.1のような値）になり得ます。
Interpret
確率加重平均 → 中間値が出る
Action
数値を丸めるか、連続値のまま使うか決める
For routing
例：thresholdで「人手確認」に回す基準を作る
Takeaway
“スコアをどう扱うか”が設計の一部
PROCESS
09 / 16
画像はdata URL限定
前処理が要る
画像はbase64のインライン data URL のみ対応で、HTTP/HTTPS URLや file_id入力は不可です。 そのため、画像取得→base64化→サイズ/遅延の管理を導入要件として織り込む必要があります。
Not supported
HTTP/HTTPS URL、file_id
Required
base64のインライン data URL
Impact
データ量増加→トークン/性能への影響を見積もる
Mitigation
リサイズ/圧縮/前処理を検討（必要なら自動化）
COMPARISON
10 / 16
棲み分けが鍵
Decisions vs Responses
Decisions APIは、確率・選択肢・段階スコアなど“意思決定の型”を高速に返すことが焦点です。Responses APIは、Structured Outputs やツール呼び出しのように“自分のJSONスキーマに沿った生成”が必要な場合に向きます。
Decisions
分類/評価（predicate・choice・score）中心
Responses
Structured Outputs（任意スキーマ）中心
When to choose
運用に回す“判断材料”が欲しいならDecisions
Rule of thumb
意思決定の分類/評価 → Decisions

DISTINCTION
12 / 16
良い点/注意点
運用可能性 vs 検証不足
私見では、Decisions APIは推論結果をアプリ判断ロジックへ“そのまま接続”できる設計で、分類・検品・ルーティングに非常に相性が良いです。 一方、抜粋だけでは精度（accuracy）や失敗モード、confidenceの校正（calibration）など検証情報が不足しており、導入前の評価が必要です。
Practical
確率/型出力 → 運用に乗せやすい
Technological
gpt-6-lunaのみ／v1/decisions／画像data URL限定
Risk / Safety
誤検知/見逃しコストで閾値設計が変わる
Operational
confidenceで人手確認キュー制御は可能
CLOSING
13 / 16
導入は“セット”で
閾値×画像×評価
結論として、Decisions APIは高速評価器として有力ですが、(1)自社データでの閾値最適化、(2)失敗モード観察、(3)画像前処理と性能評価、をセットで進めるべきです。 こうすれば運用品質を最短で立ち上げられます。
i. Threshold
誤検知/見逃しコストに合わせて境界を設計（閾値設計）
ii. Failure
失敗パターンを記録し、質問タイプ/入力設計を調整
iii. Images
base64 data URL前提でリサイズ/圧縮・遅延を検討
