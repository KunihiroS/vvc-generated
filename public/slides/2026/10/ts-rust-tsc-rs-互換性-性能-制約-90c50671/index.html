Rustでtsc互換

ts-rust

TypeScriptコンパイラ（tsc/言語サーバ）をRustへ移植した実験的ツール tsc-rs / ts-rust が、現実でどれだけ使えるかを「互換性・性能・制約」で整理します。
problem
03 / 16
単なる置換ではない

互換性

TypeScriptはコード変換だけでなく、型推論・型検査・言語サーバ機能まで担います。 だから“互換”は「文法だけ」ではなく、型チェック結果やエラー出力の挙動の近さまで含みます。
さらにベンチマークは環境依存（実行手順・ウォームアップ・オプション）で差が出るため、測定条件もセットで読む必要があります。
architecture
04 / 16
上流を固定

Pinning

ts-rustはMicrosoft TypeScriptの特定コミットに固定（pin）し、その時点のGo版と比較して整合性を示します。 「いつのTypeScriptを再現しているか」を明確にしている点が互換性検証の根拠です。
主張
Go版と同じテスト群をほぼ完全にパス
根拠の形
言語サーバ・APIのオラクル集合でも一致

Effect

比較は「Effect向け診断（codes 377xxx系）」を内蔵するかどうかで変わる、とされています。 つまり“必要な処理を1回で完結できるか”が速度差に直結します。

07 / 16
完全一致ではない

7.1-dev

一部のケースではTypeScript 7.1.0-dev相当の追加チェックが混ざり得て、tsc 7.0.2との差分がエラー出力に現れる、と注意されています。 そのため「tscのバージョン/差分の理解」が前提になります。
観測
VS Code / Sentryで追加エラーが出る可能性
解釈
“tscそのもの”ではなく、7.1-dev相当の差分を含むことがある

Known problems

条件付き

既知の問題は「どんな構成で出るか」が整理されています。 導入判断では、あなたのリポジトリ構成が該当するかを最初に確認するのが安全です。
i. モノレポ
出力ファイル到達経路が絡み、TS6059が出やすい
ii. project refなし
tsc -bで旧/欠損出力参照が起き、TS2305/TS2307が起こり得る

運用影響

メモリ

長時間の編集や特定のワークロードではメモリ増加が起き得る、とされています。 “速い＝常に軽い”とは限らないため、エディタ連続利用の体感も要確認です。
リスク
編集が長いほどメモリが増える可能性
対策
あなたの実運用でCI/ローカル検証（ウォッチ/IDE含む）

置換の現実

Drop-in？

README抜粋では、テストした実プロジェクトではドロップイン置換に近い（作者主張が強い）一方で、既知の問題とバージョン差分が明確に書かれています。 よって“完全保証”ではなく、“構成依存で差分確認が必要”が安全な読み方です。
期待値
テスト集合では整合しやすい
注意点
モノレポ/tsc -b/project ref/7.1-dev差分でズレが出得る

11 / 16
導入チェック

最短手順

導入の近道は「あなたの構成で差分を潰すこと」です。 少なくともモノレポとproject reference周り、そしてIDE長時間利用を先に確認しましょう。
i. 構成
モノレポ/出力到達経路（TS6059）を確認
ii. ビルド
tsc -bとproject reference有無（TS2305/TS2307）
iii. 運用
IDE連続利用でメモリ増加を観測

結論（読み替え）

使える可能性

入力データからの印象は「互換性と性能の両面で相当前進しているが、インストールや運用は不確実で、差分は起こり得る」です。 だから段階導入（対象範囲を絞った検証）で価値を取りに行くのが現実的です。
強み
上流pin＋テスト一致＋実プロジェクトの速度計測
弱み
既知の条件付き問題、7.1-dev差分、環境依存
