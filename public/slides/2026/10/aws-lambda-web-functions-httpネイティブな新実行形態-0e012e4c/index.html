04 / 14

HTTP ネイティブ

Lambda Web Functionsは、既存のExpress/Fastify/Hono/Next.js等を「コードを書き換えず」にLambda上で動かすことを目指します。起動時に AWS_LAMBDA_HTTP_ENDPOINT を使い、listen先だけLambdaに合わせます。
対応イメージ
Express / Fastify / Hono / Next.js 等
“サーバを作る”発想のまま
最小差分
listen先をLambda用ホスト/ポートへ
構造より起動設定の調整
EXECUTION MODEL
05 / 14

同時実行と CPU課金

Web Functionsはイベント駆動ではなくHTTPネイティブとして動き、1環境が複数リクエストを同時に処理します（最大128同時リクエスト/環境）。課金はアクティブCPUに基づくため、I/O待ちが多い処理で親和性が期待されます。
同時性
最大128同時リクエスト/環境
ポート待ち受け前提
課金
アクティブCPUに基づく
待ち時間は有利になり得る
向き/注意
DB/API待ちに強い可能性
計算負荷は要実測
“一般論”は検証前提
MULTI-REGION
06 / 14

レイテンシ ルーティング

複数リージョンを指定するとコードが複製され、単一のグローバルURLから呼び出し元に近いリージョンへ振り分ける仕組みを自動設定します。運用側で「どこへデプロイするか」「遅延調整」を個別設計せずに済むのが利点です。
配布
指定リージョンへ複製して配置

到達先

(レイテンシベース)
URL一本で最適化

段階配信は revision で

リビジョンはイミュータブルなスナップショットで、エンドポイントはリビジョンへルーティングします。さらに revision weights で割合指定でき、カナリア相当の段階的切替をCLIから実行可能です。

CLOUDFRONT
08 / 14

CDN × 動的

CloudFrontと統合し、静的コンテンツはCDNキャッシュ、動的処理はWeb Functionsへ振り分ける構成が組みやすいとされています。OAC（Origin Access Control）連携でプライベートオリジン呼び出しのパターンも紹介されます。
役割分担
静的：CloudFrontキャッシュ
動的：Web Functions
最適化しやすい分業
プライベート化
OACで制御し、エンドポイント直接公開を抑制
セキュリティ設計の余地
MIGRATION
09 / 14

“listenだけ”の 差

既存Expressは大きくは同じで、起動設定として AWS_LAMBDA_HTTP_ENDPOINT のホスト/ポートを app.listen に渡す前提が示されています。つまり移行は「イベント関数へ書き換え」ではなく「起動先の差」です。
環境変数
AWS_LAMBDA_HTTP_ENDPOINT を取得
提供される接続情報
変更点
app.listen の host/port を切替
コード構造は維持しやすい
※具体のコード差分はアプリ構成に依存しますが、主旨は「HTTPサーバとしての形を保つ」ことです。
CHOICE
10 / 14

Event vs Web vs MicroVM

イベント関数はキュー消費や他AWSサービス起点など「イベント処理」に向きます。Web FunctionsはHTTPで複数同時リクエストを扱うWebアプリ/APIバックエンドに向く、という整理が提示されています。
Event Functions
イベント起点の処理
キュー/サービス連携向け
Lambda Web Functions
HTTPネイティブのWeb/API
同時リクエスト前提
MicroVM
別の実行モデル枠
要件に応じて比較対象
実装・運用の選択は、同時性、外部I/O比率、状態管理（セッション等）の設計要否で決めます。
