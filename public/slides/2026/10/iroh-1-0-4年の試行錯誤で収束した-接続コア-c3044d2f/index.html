COVER
01 / 12
4年で収束した、接続の安定化
iroh 1.0
iroh 1.0 は「とにかくつながる」ことに一点集中して、4年間の試行錯誤から“接続コア”へ絞り込まれたネットワーク基盤だ（接続確実性／つながる率の最適化）。
Core idea / 核
エンドポイントID（公開鍵）でダイヤルし、hole punching で到達する
Transport / 通信
QUIC（quinn）＋ TLS（rustls）
Identity / 識別
BLAKE3 検証ストリーミング（内容＝ハッシュ）
PROBLEM
02 / 12
P2Pの最大壁
NAT越え
P2Pは「相手は見えているのに、直接つながらない」が頻発する。特に NAT（構内機器の番地変換）越えは環境依存で、成功率が揺れる。
What’s required / 必要条件
相手を“公開鍵ID”で指し示し、確実に接続を成立させる（接続確実性＝最優先）
What’s hard / 難所
hole punching は成功率がネットワーク条件に左右されるので、“理想P2P”だけでは足りない
PROCESS
03 / 12
互換→不満→転換
IPFS互換
初期のirohは IPFS 互換（Rust実装）を狙ったが、大容量ブロブ転送の不満などから、現実用途に合わない依存が増えていった。
Early choice / 初期選択
IPFS互換へ寄せる（相互運用の期待）
Observed issue / 問題
デルタチャットのような“狭いが厳しい”用途で非効率／依存過多
結果：互換より「用途と制約に最適化」する方向へ pivot（方針転換）した。
ARCHITECTURE
04 / 12
土台は“実装可能性”から
QUIC×BLAKE3
ネットワーク層は短期間でデモ成立が必要だったため、Rustで扱いやすいQUIC実装（quinn）を採用。内容指向では BLAKE3 検証を活かす設計へ寄せた。
Transport / 運搬
QUIC（quinn）
Verification / 検証
BLAKE3 検証ストリーミング
Target / 目標
再開可能（制約：ディスク／ネットワーク）
例：krakensync のような試作で「ストリーミング検証」を早く確かめた。
DISTINCTION
05 / 12
互換を捨てた理由
軽量化
デバイス移行時のデルタチャットのような現実用途に合わせて、IPFS互換へのこだわりを止めた。結果として設計はより軽量で高性能になった。
Shift / 変化
完全にQUICベースへ（互換より整合性／効率）
Stable properties / 安定の核
エンドポイント＝Ed25519公開鍵／軽量な検証ストリーム
ここで一貫しているのは「制約に対する最適解を選ぶ」姿勢だ。
EVIDENCE
06 / 12
標準は捨てない
TLS維持
QUIC（RFC 9000）の役割分担により、認証・暗号化はTLS（rustls）を維持する流れになった。さらに raw public key のような改善で不満点を解消していった。
Why TLS / 残した理由
QUICの仕様上の位置づけと、証明・認証の整合
How to improve / 改善の方向
rustls側の raw public keys 対応タイミングで移行（手触り改善）
Noiseへの置換も誘惑として語られるが、最終的には標準との整合を優先した。
DISTINCTION
07 / 12
交渉は軽く
ALPN
プロトコル交渉（ストリームの扱い決定）では ALPN TLS拡張を使う方針になった。毎回ハンドシェイクする方式よりオーバーヘッドが小さい。
Goal / 目的
素早く合意（交渉）し、余計なコストを抑える
Trade-off / トレードオフ
ClientHello中のALPNは観測され得る
Possible future / 将来
Encrypted ClientHello などで対策余地
「暗号化されないのが不安」という論点は、脅威モデル確認と今後の対策可能性として扱われる。
PROCESS
08 / 12
成功率が主役
hole punching確実化
NAT越えは環境依存なので、純粋P2Pにこだわらず成功率を優先する。必要なら中継サーバ（リレー）でフォールバックする。
When it works / 成功時
穴あけを素早く成立させ、直接接続を狙う
When it fails / 失敗時
企業ネットワークなどではリレーで転送（到達性＝最優先）
また、tailscale的な考え方に近い方向で実装を進めた（より高い到達率を狙う）。
PROBLEM
09 / 12
やりすぎは品質を壊す
API肥大化
機能が増えるほど、全APIを全方位で品質保証するのが難しくなる。利用者が実際に必要としていた共通部分は「エンドポイントIDでのダイヤル」と「確実なhole punching付き接続」だった。
Observed / 見えたこと
共通需要＝接続の中心機能
Decision / 決断
“バッテリー同梱”から「接続」に絞る（他機能は別クレートへ）
このスコープ縮小が、ワイヤ形式とAPIの安定化（=1.0）につながった。
EVIDENCE
10 / 12
1.0で固定したもの
接続ワイヤ
iroh 1.0 では、長期運用できる形で「接続を成立させる最小コア」を安定化した。結果として、開発者が扱うべき境界が明確になる。
Stable / 安定
ワイヤ形式（接続のやり取りの骨格）
Stable / 安定
API（接続中心に収束）
Stable / 安定
エンドポイントID（Ed25519公開鍵）＋直接到達戦略
さらに、ステータス管理（canary等）や変更管理の観点も整えた。
DISTINCTION
11 / 12
“やらない”にも意味
採用しない
1.0に入れなかった案は、ロードマップとして明示されている。鍵アルゴリズムの可変やポスト量子署名への全面対応などは、現時点では先送りされた。
Key algo change / 鍵
Ed25519以外の可変は、pkarr等との整合の都合で採用しなかった
Post-quantum / PQ
ポスト量子署名への全面対応は、1.0のスコープ外に整理
ただしワイヤ形式の鍵エンコードは key agnostic で、将来拡張の道は残している。
CLOSING
12 / 12
結論：接続の成功確率へ
最小コアへ
iroh 1.0 は「理想より成功確率」「汎用より制約適合」「機能より境界の明確化」で収束した。あなたの用途でも同じ前提（成功率重視・制約あり）なら、接続コアを中心に組み立てる判断がしやすい。
Design rule / 指針
hole punching成功率を最優先し、必要ならリレーでフォールバック
Dev impact / 影響
APIを縮退（接続に集中）し、品質と安定性を担保しやすくした
