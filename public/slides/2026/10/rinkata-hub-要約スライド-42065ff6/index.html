Cover
02 / 14
共有基盤で、意図から証跡へ
Rinkata Hub
AIエージェントの作業を「ゴール→仕様→意思決定→完了証拠」まで追跡するための、single source of truth（正）の場所を目指す。
Problem
03 / 14
文脈のズレが痛い
AI運用の落とし穴
エージェントは自律的に進められる一方、前提の取り違え・文脈の捏造・手戻りが起きやすい。さらに、なぜそうなったかや完了の根拠が散らばると、後から検証できない。
リスク i
前提の取り違え / 文脈の捏造
リスク ii
手戻り（仕様・判断が再確認不能）
リスク iii
証拠不足（品質・監査・説明が弱い）
Architecture
04 / 14
正は一か所
ゴール中心の共有メモリ
Rinkata Hubは、Knowledge/Idea/Work/Decision/Evidenceを「Hubが正」として一元化し、エージェントと人間の前提を揃える。作業の根拠（仕様・決定・証拠）を参照させ、文脈のズレを抑える狙い。
Hubが管理する
Goals / Specifications / Decisions / Evidence / Knowledge
エージェントの動き
知識ベース参照→作業→成果の証拠を記録→知識へ書き戻し
Metaphor
05 / 14
迷子を防ぐ地図
意図は“記憶”、証拠は“足跡”
Ideaから受け入れ基準（acceptance criteria）を付与し、後工程の認識齟齬を減らす。Workの完了時にはテストやスクリーンショット、PRなどのEvidenceを残し、なぜ成立したかを追える。
Idea
ノート→整形→acceptance criteria（受入れ基準）
Work
作業の実行（人/AIが進める）
Evidence
テスト / スクショ / PR などの完了証拠
Flow
06 / 14
ゴール→完了まで
一気通貫のトレーサビリティ
入力データの主張からは、Hubは「意図（ゴール）を起点」に、意思決定と完了証跡までを連結して管理する。これにより、レビュー・検証がしやすい状態を作ろうとしている。
i. 共有の意図
Goalsを基準に、仕様と判断の土台を揃える
ii. 意思決定
Decisionを記録し、何を選んだかを残す
iii. 作業
Workを進める（Hub参照で文脈を維持）
iv. 完了証拠
Evidenceを自動収集・記録し、受入れ可否を追跡
Evidence
07 / 14
“動いた”を残す
証跡で品質と説明責任
完了した作業はKnowledgeに自動追加され、古くなるドキュメント問題を軽減する狙いがある。証跡（テスト、スクショ、PRなど）により、監査性・品質確認・説明可能性を強める可能性。
証拠の種類
テスト / スクリーンショット / PR
得られる効果
監査性・品質確認・説明責任
鍵になる点
書き戻しの粒度・形式（入力では不明）
※ Japanese: 証跡（evidence）＝「完了の根拠」
Governance
08 / 14
人が“要る場所”を可視化
承認ポイントを明示
意思決定が人間介入を必要とする場合、呼び出しできる設計が示されている。複数エージェント並行時のボトルネックを減らし、責任の所在を運用で整えやすくする。
強調点
Decisionで“判断が必要な場面”を見える化
ただし不明
誰が最終承認者か / 承認強制の条件 / 例外処理
※ Japanese: ガバナンス（governance）＝「運用統制」
Limits
09 / 14
方向性は良いが
追加確認が必要
入力だけでは、導入手順・権限設計・エージェント安全性/ガードレール・セキュリティ/コンプライアンス・統合範囲（GitHub以外）が確定できない。評価には技術仕様とリスク情報が不足している。
Security
外部送信の可能性 / アクセス権 / 脆弱性対策
Reliability
誤動作時のリカバリ / 証跡の十分性
Integration
CI/CD / チケット管理 / Slack等との接続
※ Japanese: ここが埋まらないと、効果は“示唆”止まりになる
Opinion
10 / 14
慎重に、でも期待
結論：有望＋検証必須
理念は「仕様と根拠でエージェントを縛り、品質・説明可能性・ドキュメント鮮度・統制を改善」にあると理解できる。特にEvidence→Knowledgeの更新設計は筋が良いが、導入判断には権限・セキュリティ・統合・証跡の保証を追加確認すべき。
期待できる軸
意図の固定 / トレーサビリティ / ナレッジ鮮度
必ず確認したい軸
権限管理 / 保存・削除 / 監査ログ粒度 / 事故時対応
Closing
11 / 14
次に聞くべきこと
評価チェック
導入判断のために、あなたの開発フロー（チケット管理・CI/CD・レビュー体制・現状のドキュメント）を前提に優先確認項目を絞るのが有効。
i. 権限
誰が何にアクセス / 書き込みできるか
ii. 証跡の保証
Evidenceの参照性・改ざん耐性（監査ログ含む）
iii. 統合
GitHub以外（CI/CD・チケット・レビュー）への接続範囲
この3点が分かれば、「理想の効果」が「現場で再現できるか」を判断しやすくなる。
