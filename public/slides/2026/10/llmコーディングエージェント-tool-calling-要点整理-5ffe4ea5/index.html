Overview
02 / 17
最小実装の設計思想
LLM×ツール呼び出し
LLMを「コーディングエージェント」として動かす要点を、Python 1ファイルの最小構成に沿って整理する。 往復ループ（モデル⇄ツール実行）と、安全のための失敗設計が中心。
Bilingual（用語）: coding agent（コーディングエージェント） / tool calling（ツール呼び出し）
Problem
03 / 17
口だけだと無理
“実行”が要る
ただ質問するだけのチャットでは、調査・編集・テスト実行まで完結できない。 そこで「ツールを呼んで結果を返す」仕組みが必要になる。
モデル側
ツール呼び出し要求（指示）
ホスト側
実処理（ファイル/コマンド）＋結果返却
Key idea: モデルは直接PC処理をしない（分離でデバッグ容易）。
Architecture
04 / 17
1ターン=1往復
ツールループ
各ステップは「HTTPリクエスト1回」。モデルの応答にtool callがあれば、ホストが該当関数を実行して会話に追記し、再度APIへ投げる。
i
会話入力 → モデル応答
ii
tool call 判定
iii
実行結果を tool/role で返す
tool_call_idが欠けると次のAPIリクエストが拒否される（ループ継続性に直結）。

読む→直す→確かめる
例としてFizzbuzzのバグ（range上限の取り違え）を、read_file→テスト実行→edit_file→再テストで直す流れを示している。
観察
read_file（コード確認）
検証
run bash（tests実行）
修正
edit_file（old→new置換）
再検証
テスト再実行
失敗時はエラー内容を会話に返し、モデルが次の手を考え直せる。

06 / 17
曖昧を拒否
edit_fileの要件
edit_fileは「oldがファイル内にちょうど1回存在」を要求する。diffの見た目合わせより安全に“誤編集”を抑える。
条件
oldが完全一致
条件
出現回数=1
方針
曖昧なら失敗→やり直し
Bilingual: diff（差分） / exact-match（完全一致）

run_toolは例外を捕捉し、エラー文字列を会話メッセージとして返す。モデルは“失敗理由”を読んで次の探索や修正に移れる。

対処

Safety
08 / 17
制限と確認
安全策の要点
safe_pathでワークスペース外のファイルアクセスを拒否し、書き込みやbash実行には確認プロンプトを挟む。 ただし“最小限”であり万能ではない。
ファイル
safe_path（外部拒否）
操作
write/editは確認
実行
bashは確認（--yesで無効化）
Bilingual: sandbox（隔離環境）/ confirmation（確認）

Comparison
10 / 17
--yesは危険
GATEDと誤運用
確認（GATED）があることで事故を抑えるが、--yesで省略すると書き込みやbash実行の抑止が弱くなる。 bashはホスト権限で動くため、誤指示の被害が直撃する。
通常
確認あり（止められる）
--yes
確認が省略
結果
危険度が上がる（特にbash）
Bilingual: risk（リスク） / hazard（危険）
