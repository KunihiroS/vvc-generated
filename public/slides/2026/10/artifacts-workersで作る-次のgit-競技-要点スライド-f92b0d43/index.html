Artifacts × Workers
02 / 18
次のGitを“競技”で作る

Build the next Git

CloudflareはArtifacts（Gitと会話できる版管理基盤）をオープンベータにし、Workersと組み合わせて「エージェント時代の次のGit」を開発者競技で具現化します（開発者向け・誰でも参加可能）。
Problem
03 / 18
人が増える前に、エージェントが増える

衝突とレビューが変わる

何百〜何千のAI/自律プログラム（エージェント）が同じコードベースに同時変更を入れると、コンフリクト、レビュー、変更理由（なぜ）追跡の設計が根本から変わります（Agent era）。
従来寄り（前提）
人中心で、単一フローの変更をブランチ/PRで協業。
次の前提（要求）
並列エージェントが“書き続ける”ため、衝突・統合・監査を運用設計する。
Metaphor
04 / 18
Gitは“保存”ではなく“調整”へ

保存から調停へ

「差分を持つ」だけでは不十分で、誰がいつ何を・なぜ更新したかをつなぎ、次工程（ビルド/検証/デプロイ）へ流すための調整レイヤが必要になります。
i. 生成
多数エージェントが変更を作る。
ii. 統合
衝突（コンフリクト）と合意形成を扱う。
iii. 運用
レビュー・検証・根拠（なぜ）を残し続ける。
Architecture
05 / 18
Artifactsが“基盤プリミティブ”になる

土台はArtifacts

Artifactsは、リポジトリ作成/フォーク、バージョン付きストレージ、Git操作をプログラム的に扱える形で提供し、上に載せる“調整層”を参加者に委ねます（エージェントが理解できる構造）。
基礎API（概念）
プログラムによるリポジトリ作成・フォーク／Git操作を扱うための構造。
スケール前提
Gitと会話できる版管理基盤として、大規模リポジトリに合わせた設計。
Architecture
06 / 18
Workersが“次工程”を自動化する

Workersで接続する

Artifactsの更新をトリガにして、自動ビルド/デプロイ/プレビュー生成や、イベント駆動のレビュー・CI起動を組み立てられます（event-driven pipeline）。
Build
Artifactsへpush →ビルド実行。
Deploy
本番ブランチへデプロイ。
Review/CI
変更イベント → レビューやCI起動。
Comparison
07 / 18
“GitHubの延長”ではない

PR UIの延長では足りない

目標は「GitHubにエージェントを足す」ではなく、複数エージェント同時変更を前提に、協調・衝突・レビュー・意図保持を再考することです。
GitHub寄り
人が主に操作し、単一変更フロー中心。
この競技が狙う
同時並行で変更が発生し続ける設計に最適化。
Core Question
08 / 18
解くべき“上位の設計”

次のGitの問い

競技では、Artifacts＋Workersの土台の上に、エージェント同時開発に最適化した調整レイヤをどう作るかが主題になります。
i. 衝突（コンフリクト）
同時変更をどう整合させるか。
ii. レビュー
大量・並列の結果をどう評価するか。
iii. “なぜ”の保持
変更理由（intent）をどう紐づけるか。
iv. 次工程への接続
ビルド/検証/デプロイへどう流すか。
Evidence
09 / 18
運用障壁を下げる仕組み

実運用へ寄せる

管轄指定（jurisdiction）で法令・契約の不確実性を抑え、操作量・プル/プッシュ・エラー率などのメトリクス可視化でボトルネック検知をしやすくします。
Jurisdiction
EU/USなどの管轄指定で運用リスクを抑制。
Observability
操作数、プル/プッシュ、エラー率を可視化。
競技が“デモ”に留まらず、運用段階へ踏み出すための要点として位置づけられています。

FAQ
13 / 18
“なにができる？”をFAQで圧縮

ArtifactsとWorkersの役割分担

ArtifactsはGitと会話できる版管理・リポジトリ操作の基盤、Workersはイベント/自動化でパイプラインをつなぎます（役割が分離される）。
Artifacts（基盤）
Gitと会話できるバージョン付きファイルシステム／プログラムによる作成/フォーク／エージェント文脈の保存に適した構造。
Workers（自動化）
pushやイベントをトリガにビルド/デプロイ/プレビュー生成、レビューやCIワークフローを起動。
用語補助：意図（なぜ）＝intent（インテント）／変更理由の追跡＝traceability（トレーサビリティ）
Takeaway
14 / 18
強みと注意点：参加者の設計地帯

土俵は用意、勝ち筋は設計

強みはArtifacts×Workersの具体性（イベント連携、管轄指定、メトリクス、課金モデル）で、注意点は評価基準・運用/安全の詳細が読み取りにくい点です。
強み
エージェント成果物を次工程へ接続する土台がある／運用に寄せた要素が揃う。
注意点
衝突時挙動・“なぜ”の妥当性・性能/安全/整合性・監査/権限の具体が不明確。
結論：デモだけでなく、並列競合・ログ・コスト・権限の設計まで含めて差別化が必要です。
