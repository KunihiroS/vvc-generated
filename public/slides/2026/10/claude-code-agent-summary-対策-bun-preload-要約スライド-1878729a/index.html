Claude Code / 対策概要
02 / 14
表示のための無駄？

agent_summaryを止める

Claude Code がバックグラウンドのエージェントごとに行う定期要約（agent_summary）を、Bun の --preload で無効化する非公式対策と、その背景・効果を整理します。
Problem
03 / 14
定期要約が回る

何が起きる？

agent_summary は、バックグラウンドの各エージェントについて「直近の行動」を 3〜5語で要約し、エージェント一覧のステータスを更新するために定期的に動くとされています。
頻度（目安）
約 30 秒間隔
用途（主張）
会話モデル入力ではなく、表示更新
Evidence
04 / 14
“表示”にもコスト

OpenTelemetryで見る

提示内容では、query_source=agent_summary のリクエストが全体のコスト割合に無視できない規模で含まれる、という根拠が示されています。
見える化
query_source 属性で分類
注意点
ここでの “cost_usd” は推定（請求そのものではないことがある）
Approach
05 / 14
止めるのはタイマー

仕組み

対策は agent_summary のネットワーク呼び出しを直接止めるのではなく、setTimeout/setInterval をラップして「要約用のタイマー発火」だけを無害化し、結果として side query を止めます。
入力点
Bun --preload
フック対象
timer callback
狙い
agent_summary 実行の抑制
Process
06 / 14
アンカーで判定

検出ロジック

提示された実装は、Function.prototype.toString の結果に含まれるアンカー文字列を手掛かりに「要約タイマーだけ」をマッチさせて無効化する方式です。
マッチ条件
アンカー文字列（文字列内の目印）
副作用（この方式の性質）
内部実装変更に弱い（後述の silent failure へ）
Effect
07 / 14
得るもの / 捨てるもの

何が変わる？

この対策で期待されるのは agent_summary のリクエストが消えることですが、その代わりに表示側の情報が更新されなくなる点が明記されています。
観測（期待）
OpenTelemetry で query_source=agent_summary がゼロ
UI/可視性（影響）
エージェントのステータス更新停止／SDK進捗要約が止まる可能性
Risk
08 / 14
壊れ方が厄介

silent failure

アンカー文字列に依存するため、Claude Code のアップデートでタイマー構造やログ文字列が変わると、フックが効かず要約が復活する可能性があります。
原因
文字列・コールバック形式の変更
症状
気づきにくいまま agent_summary が再開（再課金・再消費のリスク）
Verify
09 / 14
毎回チェック

Verify手順

READMEは、OpenTelemetryで agent_summary がゼロになっているか等を用いた検証（Verify）を、アップデートのたびに行うことを推奨しています。
確認1
agent_summary リクエスト有無
確認2
ステータス更新の停止
確認3
期待する副作用が継続
Decision
10 / 14
導入基準を決める

判断ポイント

コスト削減に合理性がある一方、非公式な挙動変更・アップデート脆弱性・可視性低下を許容できるかで適否が分かれます。
向く条件
検証（Verify）を毎回できる／表示要件が軽い
慎重条件
チーム運用で監視が必要／更新検証コストを避けたい
Closing
11 / 14
まとめ / take away

結論

agent_summary は表示更新用途の定期要約とされ、Bun preload でタイマー発火を潰せば query_source=agent_summary を抑えられる可能性があります。
メリット（要点）
トークン消費・レート制限余力の節約（推定コストの削減）
デメリット（要点）
表示の可視性低下＋アンカー依存の silent failure リスク（Verify必須）
