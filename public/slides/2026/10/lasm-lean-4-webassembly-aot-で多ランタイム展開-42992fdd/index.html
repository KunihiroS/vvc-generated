01 / 11
LeanをAOTで配る

Lasm in Production

Lean 4のプログラムをWebAssemblyへ事前（AOT）コンパイルし、Node・サーバレス・Edge・WASI・ブラウザへ展開するための開発基盤です。

Problem
02 / 11
証明と実行のズレ

安心の範囲

「Leanで証明した性質」と「デプロイ後の実行時に本当に同じ振る舞いが起きるか」は別問題です。特にサーバレス/Edge/ブラウザでは、実行環境の制約が増え、境界の前提が崩れやすくなります。

Core Idea
03 / 11
AOTで閉じる

実行時にLeanを要請しない

Lasmは、デプロイ後にLeanモジュールのロード・評価・コンパイル等を行わない設計を中核にします。つまり「AOT成果物だけ」で振る舞いを完結させ、運用の不確実性を減らします。

Architecture
04 / 11
多ランタイム接続

One Code Many Runtimes

同一のLeanコードベースを、Nodeサーバからサーバレス関数・Edge・WASI・ブラウザまで現実のホストへ載せることを目指します。

Node（サーバ）
ファイル/ソケット/プロセス等、比較的リッチな機能が使える前提。
Edge / ブラウザ / WASI
単一スレッド、プロセス/ソケットなし等、IO前提が変わる。
Trust
05 / 11
証明は強いが全てではない

分割された保証

Lasmの信頼モデルは「証明できる部分」と「テスト/前提で担保する部分」を分けます。Conduit（RealWorld）では、その境界が明示されています。

証明（Proof）
117の定理など、認可/検証/整合性（モデルに沿う性質）を保証。
未証明領域
SQLやJSONテキスト、並行性、JSランタイム統合などはテスト寄り。
Evidence
06 / 11
Conduitの数字

117 theorems

ConduitはLeanでの形式的保証を、API仕様（認可・ページング・検証）やデータ表現（JSON/Markdown安全性）に反映します。

Auth
認可（authorization）の整合性を定理化。
Paging
ページング（ページ分割）仕様の検証。
Safe Text
JSON/Markdownの安全性をモデル化。
AOT Rules
07 / 11
後から動かない

実行時の禁止

READMEでは、デプロイ後に「Leanのモジュールロード・評価/コンパイル・REPL的挙動・カーネル利用・プラグイン動的ロード」等を行わない（禁止）方針が明記されています。

No Runtime Lean
実行時にコンパイラ/評価器へ依存しない。
AOT Completeness
成果物だけで性質を維持する前提。
Constraints
08 / 11
同じコードでも前提が違う

ホスト差が設計を決める

Nodeはスレッド/ファイル/ソケット/プロセス等を含み、Edgeやブラウザ等は単一スレッドで制約が大きい、といった差があります。したがってIOの前提を先に設計する必要があります。

Node
比較的自由なIO（例：ファイル/ソケット/プロセス）。
Edge / Browser / WASI
単一スレッド中心・プロセス/ソケットなし・ファイル制約。
JS Boundary
09 / 11
型境界とコスト

@[js] が性能にも効く

Leanからnpm関数を呼ぶときは@[js]でバインディングを宣言します。各呼び出しは境界を跨ぐため、細粒度の呼び出しが性能に影響し得ます（計測例として24µs）。

宣言（Binding）
型変換・呼び出し境界を明示し、整合性チェックへ。
設計（Coarse-grain）
多回呼びを避け、粗粒度にまとめる工夫が重要。
Decision
10 / 11
導入判断の軸

向く / 向かない

Lasmは「証明可能な仕様を中心に据え、外部境界をテストと前提で管理する」場面に強いです。逆に、動的評価や柔軟なランタイム拡張を前提にする設計とは相性が悪くなります。

向く
仕様（認可/検証/整合性）をLeanで定式化して保証したい。
AOTで完結し、境界（SQL/JSON/並行性）も管理できる。
向かない
実行時にLeanを評価・拡張したい（REPL/動的コンパイル等）。
JS境界の細粒度呼び出しが支配的なアーキテクチャ。
Closing
11 / 11
要点まとめ

AOT×境界設計

Lasmは、Leanの厳密さをWeb/サーバレスの現実に持ち込むための基盤で、実行時にLeanを使わないAOT方針と、証明/テストの信頼境界を前提として設計されます。

① 安心の作り方
証明できる性質は証明し、境界は分割して扱う。
② 運用の不確実性
実行時Lean排除で、動的崩れのリスクを抑える。
③ 性能の現実
JS境界（@[js]）の呼び出しコストを意識する。
