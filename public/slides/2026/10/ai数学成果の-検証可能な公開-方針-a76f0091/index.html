02 / 16
検証可能性へ
数学×AI公開
AIが数学の新結果を出したとき、「雰囲気」ではなく第三者が追試・検証できる形で公開する方針を整理します。
Key idea / 要点
検証可能な根拠（Lean形式化など）と運用ルール（更新・引用）を“最初から”用意する。
Focus / 焦点
GitHub公開、論文運用、Lean（形式的証明）、compute/試行統計までを透明化。透明性（透明性・再現性）
対象：研究コミュニティ / 一般理解
Japan / English termあり
PROBLEM
03 / 16
“信じてね”問題
検証の欠落
AIの数学成果は、もっともらしく見えても誤りが混ざり得ます。そのとき第三者が確認できないと、進展が止まります。
Risk / 懸念 i
文章の証明だけだと誤りの検出が遅れる（または不可能）。
Risk / 懸念 ii
“更新される前提”が不明だと、古い版に引用が固定される。
Risk / 懸念 iii
探索コスト（compute）や試行規模が不明だと、評価・比較ができない。
METAPHOR
04 / 16
チェック工程
証明を“レシピ化”
人間が読む“文章”だけでなく、機械が追える“手順（形式化）”まで落とすと検証が前に進みます。
層 / Layer 提供物 第三者の確認
直観（intuition） 要約・説明 理解の助け、ただし保証は限定的
根拠（evidence） GitHub公開・根拠資料 追跡可能性が上がる
検証（verification） Lean形式化（formal proof） 機械チェックで正しさを強く支える
ARCHITECTURE
05 / 16
公開の設計図
三つの柱
方針の核は、(i)公開と運用、(ii)Leanによる形式化、(iii)透明性情報（推論要約・compute推定など）を束ねることです。
I. Public / 公開
GitHubで成果共有＋改訂・引用プロトコル
II. Formal / 形式化
Leanで証明を計算機検証可能に（追試の入口を作る）
III. Transparent / 透明化
推論の要約、計算コスト推定、試行統計を追加開示
補足：独立助言グループ（Institute for Advanced Study）の推奨に基づくベストプラクティス志向。
PROCESS
06 / 16
更新前提の運用
改訂・引用のプロトコル
結果は固定物ではなく改訂され得るため、論文更新と引用方法を最初から明文化して、追跡可能性を確保します。
What / 何を
論文の更新手順、引用のしかた、参照の整合性。
Why / なぜ
再現性（reproducibility）と追跡可能性（traceability）を上げるため。
ポイント：公開は“開始”で、コミュニティが正しく参照できる状態にしておく。
EVIDENCE
07 / 16
機械検証の核
Lean形式化
AIの証明をLean（形式化言語）で記述すると、計算機が検証できる形に近づき、誤り検出の強度が上がります。
Lean / 概念
証明をルールに沿って記述し、機械がチェックする。
Benefit / 効果 i
“もっともらしさ”から“機械的検証”へ。
Benefit / 効果 ii
数学者が改良・拡張しやすい基盤になる。
ENUMERATION
08 / 16
透明性の中身
追加で出す情報
単に結果だけでなく、「何をどれだけ試したか」「どれだけ計算したか」を示す情報を公開する計画です。
推論の要約（例）
推論の要約を10本（複数要約として提示）。
compute / 計算資源
ChatGPT Proの“思考”時間相当として計算コスト推定を表す。
試行統計
試行した問題数などの統計。
平均値（言及）
平均で約3時間相当の計算に相当、という説明。
COMPARISON
09 / 16
“読み物” vs “検証”
何が変わる？
公開方針を比較すると、従来は説明中心だったのに対し、今回は検証可能な根拠（Lean・運用）と評価材料（compute/試行）が前面に出ます。
従来寄り 今回方針
i 根拠 文章の証明 GitHub＋Lean形式化（機械チェックへ）
ii 参照方法 暗黙/後追い 改訂・引用プロトコルを明示
iii 評価材料 計算コストは不明 推論要約、compute推定、試行統計を追加開示
DISTINCTION
10 / 16
要約は証明じゃない
透明性の“範囲”
推論の要約（要約/summary）は理解の導線になり得ますが、それ自体が検証（verification）を保証するわけではありません。
Summary（要約）
研究者が理解するための補助。
Verification（検証）
中心はLean形式化や公開根拠に基づくチェック。
安全な見方：要約＝補助、検証＝形式化（または同等の第三者確認手段）。
DISTINCTION
11 / 16
“相当”の解釈
compute推定
compute推定は比較・評価に役立ちますが、前提条件が不明だと厳密な再現（exact reproduction）は保証しにくい可能性があります。
目的 / Use
探索コスト見積もり、価値比較、資源効率評価。
注意 / Caveat
“相当”は環境差（モデル設定等）で一致しない可能性。
鍵 / Key
バージョン、設定、実行ログ粒度などの前提公開。
EVIDENCE
12 / 16
第三者レビューの現実
独立検証の論点
公開されても、独立専門家がどこまで検証を完了したかは別問題になり得ます。ここはコミュニティ側の関与が重要です。
懸念 / Concern
外部検証が十分でない可能性（例：Advisory Groupが未完了という指摘）。
見るべき / Watch
形式化の範囲・品質、推論要約と検証根拠の整合、前提の明確さ。
CLOSING
13 / 16
次の確認点
結論：制度化の方向
この方針は、AIの数学成果を「科学的透明性・検証可能性」の要件に近づける試みです。今後は“どこまで・どの品質で”形式化され、独立検証が進むかが焦点になります。
強み / Strength
GitHub運用＋Lean形式化＋透明性情報の組み合わせ。
弱点 / Gap
形式化範囲・推定前提・要約の結びつきの詳細不足。
注視 / Follow
形式化の深さ、再現性条件、独立レビューの進捗。
Japanese: 形式化（keishikika）／透明性（tōmeisei）
