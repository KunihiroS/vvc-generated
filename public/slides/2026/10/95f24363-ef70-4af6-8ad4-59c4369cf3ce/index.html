YARA-L Authoring Skill
02 / 17
一気通貫で“作る→検証→整える”
YARA-L支援
YARA-L 2.0検知ルールを、生成だけで終わらせずレビュー・チューニング・変換まで前提にした“エージェント用スキル”を整理します。
ポイントは、linterによる形式品質向上と、しかし“最終保証ではない”という設計思想です。
対象：Google Security Operations（SecOps）で使う検知ルール言語 YARA-L。参照UDMやoutcome集計も絡む前提で読み解きます。
READ DECK
Problem
03 / 17
それっぽさは不十分
品質問題
YARA-Lルールは“文法が通る”だけでは運用品質を保証しません。SecOps側の検証・実データでのチューニングが必要です。
形式ミス
ルールエディタが拒否する形式・セクション順・未接続変数・欠落要素など
誤検知要因
参照UDMの選び方、条件の置き方、集計閾値、absenceや正規表現の扱い
結論：linter/コンパイルの合格は入口。検知率・誤検知率の実測と改善が本丸です。
NO AUTO PROMISE
Core
04 / 17
出力は“ルール以外”も
一気通貫
このスキルは、AIにYARA-L 2.0を作らせるだけでなく、検証・チューニングに必要な周辺成果物まで返す設計です。
生成
meta / outcome / $risk_score を含む完全なYARA-L 2.0ルール
検証
UDMフィールド検証リスト、参照リスト/データテーブル雛形、tests
調整
誤検知源（最も起こりやすい2つ）と抑制チューニング案
さらに、提出前の形式品質を上げるオフラインlinter（構造チェック）を同梱。
RULE + TEST
Workflow
05 / 17
入力→変換→品質ゲート
流れ
脅威説明やATT&CK、Sigma、SPL/KQLなどを起点にYARA-Lへ落とし込み、最後はlinterで形式品質を確認します。
入力（例）
ATT&CK / Sigma / SPL / KQL / 脅威説明
変換（要点）
検知ロジック要約→meta/outcome/$risk_score→UDM参照設計→テスト作成
オフラインlinter
エディタが拒否しやすい形式・整合性・欠落を事前に検出
人のレビュー
lintの合格でもSecOps側で必ず検証が必要（設計上の前提）
“生成の自動化”ではなく、“レビューを組み込む支援”として位置づけられています。
HELP, NOT MAGIC
Outputs
06 / 17
必要物が揃う
成果物
返ってくるのは“ルール本体”だけではありません。検知の根拠・検証・調整を回すための材料が含まれます。
要約
検知ロジックを1文で要約（レビュー時の理解コストを下げる）
完全ルール
meta / events / match / outcome などの構造一式（$risk_score含む）
UDM検証
パーサ側で確認すべきUDMフィールド一覧（例：// VERIFY:が出る領域）
テスト
should fire / should not fire（期待通りに当たる/当たらない確認）
加えて、参照リストやデータテーブルの雛形（サンプル行含む）も作成対象。
REVIEW READY
Lint
07 / 17
lint＝保証ではない
注意点
オフラインlinterは“形式品質を上げるゲート”です。しかしREADMEは、lintクリーン＝SecOpsで必ず動く、と言っていません。
lintが見る範囲
構造・セクション整合・未接続変数・集計欠落・absence欠落・危険な正規表現等
lintが保証しない
実コンパイル/実イベント実行環境の一致、UDM参照の最終解釈、データ分布による精度
結論：Rules Editor / SecOps APIでの実検証を前提に“導入リスクを下げる”もの。
GATE, NOT PROOF
UDM
08 / 17
“// VERIFY:”の意味
不確実性
UDMフィールドの埋まり方はパーサ（解析器）で変わり得るため、確実でない箇所は“// VERIFY:”として明示されます。
なぜ
解析器がイベントをどう解釈し、どのUDMへマッピングするかが一様ではない可能性
対処
現場のイベントサンプルで、実際に参照UDMが埋まるか検証する
この設計により“自動で正解になる”前提を避け、現場検証を導線化しています。
VERIFY FIRST
Comparison
09 / 17
“生成AI”との差
自動化の境界
このスキルは“文法・構造をそれっぽく書かせる”だけではなく、誤検知要因の想定やテスト、参照データ雛形まで含めて実務に寄せています。
単発生成
ルール文の形は揃うが、検証・根拠・チューニング手段が不足しがち
YARA-L Authoring Skill
UDM検証・should fire/should not fire・誤検知源2つ・参照テーブル雛形まで作る
ただし、精度の最終保証はデータと運用設計（通知/抑制/評価）に依存します。
ASSIST, NOT GUARANTEE
Risk
10 / 17
生成の限界
精度の不確実性
生成AIの出力は文法・構造には強くても、“データ分布に対する精度”は保証しにくいのが前提です。
入力品質
Sigma/SPL/KQL等の解釈・前処理・技術紐づけが精度を左右
イベント実値
参照UDMの実データ、相関有無、頻度分布が結果を変える
運用設計
アラート抑制（例：7日間停止）や評価設計が“見え方”を左右
よって“起点として優秀”でも、効果測定（検知率/誤検知率）を省略すると危険です。
MEASURE
Operational
11 / 17
運用は段階投入
検証計画
READMEにはプレースホルダ置換と、運用開始後のアラート停止期間を設けた検証が明記されています。
プレースホルダ
製品名/テーブル名/参照リスト等を置換しないと、意図しないマッチや無効化の原因
抑制期間
例：7日間アラート停止で、誤検知・検知漏れの実測→調整ループへ
結論：自動生成→即本番ではなく、評価→再チューニングを前提に組み込む。

不足情報
README文面だけでは、linterの網羅率・SecOps APIでの実検証手順・性能面の指標がどれほど示されているか不明です。
linter網羅率

SecOps APIでの確認フロー、期待する出力・失敗時の切り分け
性能指標
性能（例：集計/正規表現コスト）やベンチマークの有無
ベストプラクティス
誤検知抑制の“再現性ある運用パターン”がどこまで整理されているか
導入時は追加調査し、“どこまでを自動化し、どこを人手で担保するか”を明確にするのが安全。
DUE DILIGENCE
Takeaway
13 / 17
結論
導入の軸
このスキルの価値は“周辺工程を同梱した支援”にあります。linterは入口の品質ゲートであり、精度保証ではないため、実データで検証してチューニングする前提で使うべきです。
強み
UDM検証・tests・誤検知源2つ・参照雛形まで“レビュー可能な形”で出す
注意
lintクリーン＝SecOpsで動作/期待精度とは限らない（環境差・データ差）
運用
プレースホルダ置換＋抑制期間で実測→再チューニング（検知率/誤検知率）
次アクション：自組織のイベントサンプルとUDMマッピングで、// VERIFY:領域から優先検証。
