MongoDB / AI Agent
02 / 16

データ基盤の再設計

AIで“行動”する時代

生成して答えるAIから、観測して実行するエージェントへ。必要になるデータ要件（鮮度・検索・状態・統制）が、運用データ層の設計を変える。

Problem
03 / 16

答え→操作

要求が反転する

従来は「情報を渡して回答」すれば足りることが多い。エージェントは「正しい行動」を求めるため、参照データと検索・状態・権限が性能と同じくらい重要になる。

観測→検索→推論
状況を見て文脈を取り出し、計画に落とす。
実行→結果確認
システムへ操作を加え、結果を見てループする。
Freshness
04 / 16

古いほど危険

データ鮮度の正体

モデルが論理的に正しくても、在庫・口座残高・注文ステータスが古いと誤った意思決定や誤操作につながる。定期同期だけでは安全性を担保しにくい。

例（誤操作）
在庫が減った後も“ある”前提で発注する。
例：意思決定がズレる
意味（安全性）
freshness（鮮度）は品質・安全の基盤。
英語：freshness / 日本語：鮮度
Retrieval + State
05 / 16

検索が鍵

retrieval（検索）

ループが長く自律性が高いほど、必要情報へ素早く到達できるかが致命的になる。検索精度とデータへの到達速度が、行動の正しさを左右する。

速さ
低遅延で必要情報に到達。
正確さ
関連文脈を取り違えない。
更新
“いま”の状態を反映。
Burst
06 / 16

見積もり不能

バースト（急増）要求

エージェントは1リクエストあたり複数の操作（計画・検索・ツール呼び出し・読み書き・推論）を引き起こし得る。平均ではなく“ピーク”で倒れるため、計算・ストレージの伸縮が重要になる。

課題
需要の予測が難しく、ピーク停止リスクが増える。
狙い
ピーク吸収とアイドルコスト低減を両立する。
Atlas Infinite
07 / 16

分離して伸ばす

storage + compute

Atlas Infiniteは、ストレージとcomputeを独立して拡張できるデプロイ選択肢。バースト時の需要変動に合わせ、止まりにくさとコスト効率を狙う。

独立拡張
storage層とcompute層を切り分けてスケール。
効果
ピーク時の停止リスクとアイドル増を緩和。
参考：プレスリリースでは「1ドル当たり」のパフォーマンス指標として内部テストの数値も言及。
Agent Engine
08 / 16

近接統合

Atlas Agent Engine

エージェントはステートフル（状態保持）で、メモリ・検索・実行・権限/ポリシーが必要。複数コンポーネントに分散すると統合点・境界・複製が増え運用が難しくなるため、近い場所でまとめる。

Stateful（状態）
メモリ・文脈・実行結果の追跡が要る。
Governance（統制）
権限・ポリシーに沿って安全に動かす。

Risk Notes
11 / 16

ガードレール

誤った自律行動

エージェントは誤りを増幅し得るため、性能より“ガードレール”が重要。記事は方向性を示す一方、承認・サンドボックス・ロールバック・ポリシー不整合時の挙動などは追加で確認が必要。

安全
誤操作（誤更新・誤発注）を抑える設計。
運用
監視（observability）と障害時の影響範囲。
Takeaway
12 / 16

結論

データレイヤが制御プレーンへ

エージェント化で、データ基盤は“保管”から“実行の土台”へ移る。鮮度・検索・状態・統制・バースト吸収を同一の流れで設計する視点が、この記事の要点。

使う視点：freshness（鮮度） / retrieval（検索） / burst / stateful（状態保持） / governance（統制）
補完の方針：自社要件でベンチマーク、セキュリティ/監査仕様、統合パターンを確認。
