Jev-Mem / Agent Memory
02 / 16
System-One × System-Two

Jev-Mem 設計概要

長時間稼働エージェント向けに、記憶の「書き込み・検索・停止」の意思決定を軽量コントローラ（System-One）に切り出し、最終回答の統合をLLM（System-Two）に任せる構成です。

Problem Framing
03 / 16
暗黙の混在がコスト化

意思決定が読まれない

長期稼働では、(1) 書き込みの構造化、(2) 問い合わせでどこを探索しどれだけ根拠を集めるか、の判断が頻繁に発生します。

従来の課題
書き込み/検索/停止が暗黙に混ざり、遅延とコストが増える
目標
探索・停止を制御し、根拠を効率よく集める
Core Idea
04 / 16
意思決定を分離する

System-Oneで制御

Jev-Memは、記憶管理の意思決定（型付け、関係推定、ルーティング、探索予算、候補スコア、evidence評価）をSystem-Oneが担います。

System-One
探索・ルーティング・停止判断を軽量に実行
System-Two
取得した根拠の統合と最終回答をLLMが行う
Memory Model
05 / 16
evidenceを残す

原文＋来歴で保存

観測（記憶）は原文・タイムスタンプ・provenance（来歴）とともに保持し、後で重要性が判明した場合でも根拠として再利用します。

i. 原文（共有記憶 / Shared memory）を保持
ii. タイムスタンプで時間追跡
iii. 来歴（provenance）で検証可能性
iv. 重要性が後から必要でも再利用
Graph Views
06 / 16
4つの見方で接続

意味・時間・因果・主体

記憶は「意味・時間・因果・エンティティ（誰/何に関わるか）」の4観点（グラフビュー）で関連づけられます。

意味 / Meaning
事柄の類似・関連で接続
時間 / Time
いつ起きたかの順序を扱う
因果 / Causality
なぜ起きたかの関係を追う
主体 / Entity
誰（どの対象）に関係するかで絞る
Query Routing
07 / 16
探索先をルーティング

質問に応じて探索する

問い合わせが来ると、コントローラは関連するビューに探索をルーティングし、探索コスト（トラバーサル予算や検索上限）を配分します。

ルーティング
意味/時間/因果/主体のどれを掘るか選択
探索予算
上限でコストと遅延の爆発を抑える
Stopping & Evidence
08 / 16
反復して“十分”を決める

停止条件で探索を打ち切る

追加の根拠が必要かどうかを反復評価し、十分だと判断した時点で探索を停止します。

判断軸
候補のスコア・evidence評価・期待値（コスト vs 利得）
停止
十分な根拠 / 期待値低 / 上限到達で終了
Traceability
09 / 16
検証可能性を優先

型付き出力とトレース

Noul（二値命題）やChoice（カテゴリ決定）などの型付きの意思決定出力と、コードによる検証・上限適用・トレースが説明されています。

意思決定の出力が“検査可能”になる
停止理由が見える（どこで何が足りた/足りない）
再現性・デバッグがしやすい
性能改善サイクルを回しやすい

実装で効く論点

意思決定品質が鍵

性能は「ルーティング」「探索予算」「停止条件」に強く依存し、再現には評価プロトコルや探索上限などの前提を揃える必要があります。

重要：トレース/型付き出力で“どこが効いたか”を評価できる
注意：数値は条件依存（ハイパーパラメータ/スコアリング/除外など）
実用：CLI統合、ローカル実行、オフラインデモでPoC向け
スケール：長期でノード/エッジ/インデックスが肥大化しうる
