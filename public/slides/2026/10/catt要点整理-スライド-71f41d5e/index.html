CATT / 要点整理
02 / 16
契約と証拠でテストする
CATTとは
Consumer Agent Testing Tool（CATT）は、AIアシスタント（エージェント）があなたのサービスを使うときの「挙動」と「結果」を、シナリオ駆動で検証し、証拠を保存・比較する仕組みです。
Problem
03 / 16
互換性は“証明”されにくい
誤差が増える
エージェントは推論してツールを呼ぶため、テストは一度通っても回帰や差分が起きやすく、さらに「相手ホストの完全互換」をログだけで確かめにくいのが現実です。
Architecture
04 / 16
シナリオ×検証×差分
何をする
CATTは、(1) 事前に定めたシナリオで実行し、(2) サービス側の確認（oracle/結果チェック）で妥当性を判定し、(3) evidenceをsealedに保存してdiffします。

Step i

シナリオ実行（手順・許可・検証条件）

Step ii

承認と結果チェック（矛盾をfail）

Step iii

sealed evidence / replay / diff
Types
05 / 16
scripted と agent を分ける
二つの検証
CATTは「モデルなし（scripted）」と「モデルあり（agent）」を分離し、CIでは再生可能なscripted、現実性が必要な場面でagentを回す運用が想定されています。

Scripted（modelなし）

固定呼び出しを再生しやすい
→ CI向き / 回帰検知向き

Agent（modelあり）

推論込みで手順と引数を生成
→ 現実性あり / コスト・不確実性あり
Contract
06 / 16
“互換性”ではなく“契約”
Surrogate
CATTはMuse/Instinctの完全互換の保証ではなく、代替ターゲット（surrogate）として近似するホスト側で検証します。

できる

検証可能な範囲の整合性を積み上げる
契約（contract）ベース

できない

合格＝Muse/特定ホスト済みの完全互換
境界は必ず見直す
Oracle
07 / 16
承認で呼び出しを制御
Approval
承認（approval）ルールに基づき呼び出しを許可し、さらにサービス側で「確定予約の有無」「重複請求の有無」「最終回答の誤り」をチェックしてfailにします。

Allowlist

ホストが許すツール/呼び出しだけ

Result oracle

サービス側の確定状態で検証

Claim check

エージェント主張と矛盾させない
Readiness
08 / 16
readinessは“合格証明”ではない
静的チェック
readiness checksはツール一覧・ガイドライン・manifest・契約の静的レビューを行いますが、エージェントが実際の手順を踏んだときの結果までは測れません。

Readiness（準備）

“まず通る条件”を事前に確認
（例）ツール/契約の整合

実行（Run）

“実際に成立するか”を検証
（例）承認と確定結果
Workflow
09 / 16
段階運用の現実解
導入の道筋
CIではscriptedを中心に回し、モデルを使うagentは必要に応じて別段取りで実施することで、時間・課金・不確実性を管理できます。

1. 準備

readiness / manifest / 契約の確認

2. CI

scriptedで回帰検知（diff）

3. 必要時

agentで現実性の最終確認
Sealed
10 / 16
replay 可能な証拠
Evidence
sealed evidenceを保存し、replay/diffできるため、「前回は通ったが今は通らない／逆」を機械的に追跡できます。

なぜ重要

実行が変わったかを検出できる
回帰・誤差の切り分けがしやすい

どう効く

生データ再接続で別結果になる事故を低減
再現性の担保
Security
11 / 16
秘密値とガバナンス
Risk
evidenceの秘匿やsealed運用、シークレット非露出が強調されますが、サービス側のoracleや環境変数の扱いは導入者責任が残ります。

CATT側

sealed evidence / 秘匿方針
監査可能性を確保しやすい

あなた側

oracle・ZDR・データ保持ポリシー確認
“ログだけで独立検証できない”注意
Practical
12 / 16
運用で効く観点
Checklist
CATTを過信せず、サロゲート近似の境界と未確定領域を洗い出し、自社MCP仕様とシナリオ設計に反映させるのが鍵です。

評価可能性

fail/blocked理由とタイムライン

懐疑性

合格＝互換保証ではない

実務

scripted中心＋agent限定運用
Closing
13 / 16
結論：契約×検証で積み上げる
CATTの読み方
CATTは「互換性の魔法の箱」ではなく、契約と検証可能性を積み上げる工学的テスト基盤です。まずはscriptedで回帰を抑え、境界を理解したうえでagentを段階投入しましょう。
重要：surrogate / 未確定（unknown）領域を前提に、期待値と合格条件（契約ベース）を自社仕様へ最適化すること。
