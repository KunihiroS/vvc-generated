HYBRO AI
02 / 18
Hybrid Multi-Agent
HybroAI
ローカル／リモートの複数AIエージェントを、A2A（Agent2Agent）準拠で相互接続し、実行・可視化・検査まで支えるマルチエージェント基盤。
日本語 / English
オーケストレーション（Orchestration）
＝調停 / inspection（検査）
主な構成
FastAPI（バックエンド）＋Next.js（ダッシュボード）
Docker Compose + CLI（運用導線）
本レポートはREADME等の記載を要約し、導入検討で必要な観点を整理しています。
PROBLEM
03 / 18
動かした後が難しい
問題の芯
エージェントを“つなぐ”だけでなく、(i) 実行の見える化、(ii) 仕様（通信・設定）の崩れ防止、(iii) 安全な外部接続が必要になります。
通信の互換
ローカル／クラウド、実装差があっても協働させたい
運用の事故
環境変数の散在や不整合で起動失敗・挙動ブレが起きる
可観測性
誰が何をしたか（メッセージ）を追える必要がある
外部接続
MCPのような便利口は、露出すると重大リスクになりうる
METAPHOR
04 / 18
“会場”で整える
実行ルームRun Room
Hybro AIでは「実行ルーム（複数エージェントを束ねる単位）」を“会場”として、参加者（エージェント）間の会話を一つの流れにまとめます。
束ねる
実行ルーム＝エージェント群の単位（同時進行の枠）
見せる
SSE（Server-Sent Events）でメッセージをリアルタイム可視化
検査する
Agent Inspectorで協働の状態や観測点を検査
安全に
MCPは認証・隔離がないため“公開回避”が前提
ARCHITECTURE
05 / 18
三層で運ぶ
全体像Overview
FastAPI（実行・通信）とNext.js（ダッシュボード）が中核になり、エージェント間はA2Aで相互接続し、外部はMCPで接続可能にします。
Web基盤
FastAPI（バックエンド）＋Next.js（フロント）
エージェント通信
A2A（Agent2Agent）準拠：プロトコル非依存ルーティング
外部接続
MCP（Model Context Protocol）で外部クライアントから接続
運用
Docker Compose + CLI：設定を検証してコンテナへ投影
CORE
06 / 18
価値は3本柱
柱Value
Hybro AIの主要価値は「相互運用性」「可観測性（inspection）」「設定管理の堅牢性」です。
i
相互運用性：A2Aでローカル／クラウドを同じ枠組みに
ii
可観測性：SSEでメッセージ、Inspectorで検査
iii
堅牢性：JSON契約＋起動時検証＋移行
“動く”だけでなく、“確認できる／壊れにくい”体験を設計に組み込む点が特徴です。
EVIDENCE
07 / 18
A2Aが接着剤
A2A互換
READMEでは、A2A準拠によりエージェント間メッセージングを“プロトコル非依存”にルーティングできる点が中核とされています。
何が嬉しい
異なる提供形態（ローカル／クラウド）でも協働しやすい
どう効く
通信規格を揃えることで、エージェント実装の差を吸収する
結果
相互接続を“設計の前提”として成立させる
境界
A2A＝エージェント間（Agent↔Agent）を標準化する役割
DISTINCTION
08 / 18
A2AとMCPの役割
境界を分けるRole Split
READMEの文脈では、A2Aはエージェント同士、MCPは外部ツール／クライアント接続の境界として整理されています。
A2A（Agent↔Agent）
エージェント間のタスク委譲・協働メッセージを標準化
MCP（外部↔Hybro）
外部クライアントから接続し、URL/スニペット配布やTUI操作を提供
安全の前提
MCPは認証・ユーザー分離がないため公開を避ける
運用の含意
ネットワーク境界と公開可否の設計が“必須条件”になる
PROCESS
09 / 18
設定はJSON中心
~/.hybro契約
設定は環境変数ではなく、~/.hybro/config.json と ~/.hybro/auth.json に集約し、起動時にスキーマ検証される運用です。
契約
既知フィールド・型・範囲・必須組み合わせを明確化
検証
起動時に妥当性をチェックして“壊れたまま起動”を減らす
移行
config migrate 等で古い運用からの移行を支援
現場が従来の .env 運用に慣れている場合は、学習コストが発生しうる点も明示的に注意できます。
EVIDENCE
10 / 18
CLIが“検証済み投影”
起動導線CLI→Compose
READMEではCLIが、検証済みのスコープ付き設定としてComposeへ投影するため、任意のdotenvに依存しない運用ができると説明されています。
狙い
型・必須条件・範囲が崩れた設定で起動するリスクを下げる
運用の結果
日次の start/stop/logs/status/upgrade の導線が作られている
補足
Docker Compose + CLIが中心で、設定の“置き場”が一箇所に収束する
理解の要点
環境変数ではなくJSONスキーマが主役になる
DISTINCTION
11 / 18
反映タイミング
ランタイム vs ビルド切り分け
フロント側の多くの設定は再ビルドなしで反映されますが、例外として backend.api_prefix はビルド時にコンパイルされるため再ビルドが必要です。
ランタイム反映
Next.js側の多くは再ビルドなしで更新が反映
ビルド時例外
backend.api_prefix はフロント側イメージのビルド時に反映
運用の注意
チェックアウトチャネルでの再ビルドが必要になり得る
障害予防
“変えたのに効かない”を理解不足で起こしにくくする
INSPECTION
12 / 18
見えるから検査できる
SSE & Inspector可観測性
実行中のメッセージはSSEでリアルタイムストリーミングされ、Agent Inspectorで協働の状態を検査できるように設計されています。
SSE
サーバ→クライアントへ逐次通知（メッセージ可視化）
Inspector
検査（inspection）によって挙動を確認
Run Room
複数エージェントの会話を単位として追跡
“ブラックボックスにならない”ことを、監視やデバッグの導線として提供するのが狙いです。
SECURITY
13 / 18
便利でも危険
MCPの制約公開回避
READMEには「MCPには認証やユーザー分離がない」ため、公開は避け“信頼できるローカルのmock-authバックエンド”で使うべきだと明記されています。
リスクの核
認証・隔離がない＝外部露出すると情報漏えい等の誤用リスクが残る
推奨
公開せず、ローカルの信頼環境で利用する
できること
TUIでURL取得、開始停止、ログ確認が可能
導入観点
ネットワーク境界・ファイアウォール・隔離は運用設計として前提化
OPERATIONS
14 / 18
バージョン整合
Release vs Checkout違い
チェックアウト版はソースからビルド可能ですが、リリース版は既存イメージをpullして動かす前提で、--build は拒否されアップグレードは hybro upgrade で行う設計です。
チェックアウト版
ソース→イメージをビルドできる
リリース版
CLIに紐づくイメージをpull、--buildは不可
アップグレード
hybro upgrade 経由でバージョン整合を狙う
目的
バージョンのズレによる運用事故を減らす
CLOSING
15 / 18
導入前の要点
まとめTakeaway
Hybro AIは、A2A相互運用・SSE/Inspectorの可観測性・JSON契約の堅牢運用を中核にしつつ、MCPは認証・隔離がない前提で慎重運用が必要です。
必須確認
設定をJSON中心（~/.hybro）で運用できるか
可視化
SSEとInspectorでデバッグ/監査の導線が合うか
安全
MCPを公開しない前提を、ネットワーク設計に落とせるか
