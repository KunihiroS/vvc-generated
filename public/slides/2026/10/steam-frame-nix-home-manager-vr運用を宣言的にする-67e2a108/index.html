Steam Frame運用設計

SteamOS系の不変ルートと、home-managerの宣言的管理を組み合わせて、VR環境まで“普段使い”できる形に整えます。

Steam Frame（SteamOS系）／Nix（immutable対応）／home-manager（個人設定）／steamos-etc（/etc保持）／frametop（VRデスクトップ拡張）

problem
“入れて終わり”は危険

更新で崩れる

不変（immutable）なルートと、ネストされたPlasmaセッションがあるため、Nixやhome-managerを入れても運用の反映がズレやすいのが問題です。

不可逆の前提
アップデートでrootが置き換わるため、/nixや/etcをそのまま触ると再現性が崩れます。
Immutable（不変）ルート / Reproducible（再現性）
セッションのズレ
Gamescope/SteamVR側の“実セッション”と、参照先（D-Bus / XDG_RUNTIME_DIR）が噛み合わず、再読み込みがスキップされます。
session（セッション） / user systemd（ユーザーsystemd）

metaphor
残る場所へ退避

倉庫戦略

ストア（/nix相当）は更新をまたいで残る場所へ“退避”し、起動時に必要な範囲へだけ“差し込む”発想で安定させます。

退避先
/home/nix に保持（更新耐性を担保）
persistent（永続）
差し込み
systemd unitで起動時に /home/nix → /nix 相当へbind mount
bind mount（バインドマウント）

全体像（要点だけ）

四層で整える

Nixで実行環境を再現し、home-managerで個人の宣言を固定し、steamos-etcで更新由来の揺れを吸収し、VR運用をframetop側で拡張します。

Layer i
Nix（再現可能なパッケージ）／更新をまたぐ保持
Layer ii
home-manager（dotfiles・アプリ設定・systemdユーザーサービス）
Layer iii
steamos-etc（/etc/atomic-update.conf.d/へ登録して保持）
Layer iv
frametop（VRデスクトップ運用拡張）／整合性（Mesa / ドライバ）
06 / 16
process
反映がズレる理由

user systemd

home-managerのswitchが成功しても、ネストされたPlasmaセッションのせいでユーザーsystemdの再読み込みが起きないことがあります。

症状
“User systemd daemon not running. Skipping reload.” のように反映がスキップされる。
原因
XDG_RUNTIME_DIR / DBUS_SESSION_BUS_ADDRESS が“実セッション”を指さず、参照先がズレる。
対策
env上書きを付与して、実セッション向けにsystemd再読み込みを再実行する。
07 / 16
comparison
“作っても見えない”

ランチャー差

Steamの「+メニュー」は ~/.local/share/applications への依存が強く、home-manager生成のdesktopファイルが見えないことがあります。

期待
home-managerが生成したdesktopファイルがGUIランチャーに自動反映される。
XDG（XDG_DATA_DIRS等）
実際
Steamの「+メニュー」がXDG_DATA_DIRSを無視し、~/.local/share/applications前提になる。
steam menu（+メニュー）
追加の罠
NixプロフィールのPATHがSteamセッションに入らず、Execが失敗する。
PATH（実行検索パス）
解き方
desktopファイルのExecを絶対パス化＋Plasma側でsystemd.user.sessionVariables.PATHを補正。
absolute Exec（絶対Exec）
08 / 16
evidence
成功と“罠”の両方

更新耐性

steamos-etcで /etc の編集を更新に巻き戻されない形へ寄せ、さらに起動順序の問題（tmpfilesタイミング等）も吸収します。

/etc保持
/etc/atomic-update.conf.d/ に反映し、SteamOS更新でも必要ファイルが残るよう設計。
起動順序
/nixのマウントが遅いことで破綻する点を、waitForNixで避ける。
GPU参照
/run/opengl-driver をstoreリンクではなく実ファイルとして用意する（gpuDrivers）。
OpenGL（/run/opengl-driver）
サービス統合
Tailscaleのようなsystemdサービスも、home-manager側の宣言に閉じ込めつつ更新耐性を保つ。
network service（ネットワークサービス）
09 / 16
distinction
“storeリンク”の落とし穴

/run

/run/opengl-driver は、Nixのstoreリンクのままだと読み取りタイミングで失敗しやすく、実ファイル化が必要になります。

なぜ問題化する
tmpfilesのタイミングや、/nixがマウントされる前に参照されることで、ドライバが用意されない。
何をする
gpuDriversで /run/opengl-driver を「storeリンクではなく実ファイル」として用意する。
結果
NixビルドGUIやVR系の描画前提が満たされやすくなる。

architecture
VR運用の追加レイヤ

frametop

VRでの複数デスクトップ運用を広げるframetopは、Mesaやwlroots_0_20などの整合性が崩れると不具合になりやすいとされています。

連携
home-manager連携（frametop-nix）で構成を宣言的に寄せる。
要点
compositorが参照するMesaと、/run/opengl-driver由来のnixpkgsの整合性が重要。
手戻り条件
SteamVR再起動が必要になることがある（初回のswitch後など）。
実務姿勢
VRは初期化タイミングが効くため、変更後の確認を運用手順に含める。

enumeration
記事の要点（再整理）

5つの設計

この文章は「VR環境を含む日常運用」を作るために、ズレやすい箇所を設計で吸収する点が核です。

i
Nixストアは“残る場所”へ：/home/nix保持＋起動時bind mount。
ii
home-manager反映は“実セッション”基準：XDG_RUNTIME_DIR / D-Busを合わせる。
iii
ランチャー統合は“置き場＋PATH”：desktopのExec絶対化＋sessionVariablesで補正。
iv
/etc更新消失はsteamos-etc：/etc/atomic-update.conf.d/＋waitForNix。
v
frametopは整合性最優先：Mesa / wlroots_0_20 / /run/opengl-driver を揃える。
補足
VRではSteamVR再起動が必要になり得るので、運用手順に含める。

強みと限界

実践知

本稿は実運用の摩擦（起動順序・セッションズレ・/etc更新・PATH）を具体化している一方、失敗の体系化は十分とは言いにくいです。

強み
“なぜズレるか”を環境変数・参照先・保持機構まで含めて整理している。
Root cause（原因）
限界
失敗しやすい段階（権限・カーネル差・SteamOS差）や、ログ確認の最小手順が網羅的とは言えない。
Troubleshooting（切り分け）
GPU・Mesa・wlroots_0_20の互換性マトリクスがないため、将来の更新で判断材料が弱くなる可能性。

宣言を運用へ

Nixとhome-managerは“設定を書くだけ”では終わらず、immutable・セッション・起動順序・/run・/etcを運用設計として縫い合わせて初めて効きます。

最初の観点
更新をまたいで残す（/home/nix）／実セッションに寄せる（env上書き）。
次の観点
GUI統合はPATHとdesktop配置を両方直す。
仕上げ
steamos-etc・waitForNix・gpuDriversで前提を固める。
VR拡張
frametopはMesa/ドライバ整合性を最優先し、SteamVR再起動を手順化する。
