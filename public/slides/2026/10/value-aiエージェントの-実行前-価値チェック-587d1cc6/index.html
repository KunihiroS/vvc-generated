Cover
02 / 18
実行前の価値ゲート

VALUE 価値チェック

AIエージェントが「成功しても許されない」事態を防ぐために、実行境界（権限が解放される地点）へ独立した価値評価を挟む提案です。
価値体系ごとの判断を、受け手が検証できる形で渡します（検証可能性 / 可監査性）。
英：VALUE（Value-gated Execution）／日：価値ゲート実行
Problem
03 / 18
成功≠安全

目的達成と価値整合のズレ

エージェントはゴールを達成しても、やり方や結果が組織・社会の規範に反する場合があります。
特にツールや外部システムへのアクセスが可能になると、「成功したのに許されない」抜け道が起き得ます。
Risk（リスク）
意図外の手段でゴール達成
Trigger（引き金）
資格情報 / API / 長い手順の実行
キーワード：consequential action（具体的な行動）
Metaphor
04 / 18
助言では足りない

価値は「実行境界」に置く

VALUEは万能な道徳オラクルではなく、権限が実際に付与される地点に独立評価レイヤを置きます。
判断根拠（どの価値体系で、何を根拠に）を受け手が検証可能にします。
Agent（担当）
目的理解 → 行動案の提案
VALUE Broker
評価→許可/拒否（実行境界で媒介）
User / Receiver（受け手）
価値体系と根拠を検証して権限付与
設計の肝：評価を「参照モニタ」的に“越えられない形”へ。
Architecture
05 / 18
分離責任で閉じる

VALUE Broker + VAO

タスク担当エージェントは計画・実行提案を作りますが、最終的な「許可」はVALUE Brokerが独立評価して決めます。
その結果はVAO（VALUE Attestation Object）として、受け手へ検証可能に移送されます。
VALUE（評価要求）
行動案を、明示された価値体系に照らして評価
VAO（証拠パッケージ）
何の行動か／誰が／いつの文脈で／どのルールで
要点：成功通知だけではなく、評価された“行動の正規化された記述”を結び付ける。
Process
06 / 18
許可までの流れ

評価→許可（または拒否）

VALUEは「実行前」に評価を挟みます。重要なのは、助言ではなく“権限付与点”での評価バインディングです。
i. Plan（計画）
担当エージェントが行動案を作成
ii. Request（評価要求）
価値体系と共にVALUEへ送付
iii. Evaluate（評価）
評価者（エバリュエータ）が判断
iv. Attest（VAO作成）
VAOに証拠・文脈・ルールを添付
v. Authorize（許可）
受け手が検証し、権限を開放
vi. Act（実行）
許可された範囲でのみツール呼び出し
VALUEの目的は“説得”ではなく“越えられない許可プロトコル”。
Comparison
07 / 18
チャット式安全 vs 境界式安全

助言だけは回避される

「安全チャット」は参照に留まり、エージェントが直接ツールを呼んでしまう抜け道が残り得ます。
VALUEは、実行境界にVALUE Brokerを置いて評価を“無視できない”形にします。
従来（参考のみ）
助言 → エージェントが同意/不同意を選べる
VALUE（権限媒介）
評価 → 許可された場合のみ資格情報/APIを解放
ここが効果の分水嶺：権限付与点に評価を“拘束”。
Distinction
08 / 18
価値体系は一枚岩じゃない

複数の評価・合意（クオラム）

価値観は普遍ではなく、組織ごとに異なります。VALUEは単一の正解を押し付けず、複数の価値体系にも対応できるよう設計します。
Key（要点）
プロトコルの合意 × 価値の合意 を分ける
Example（例）
Model Spec / Constitution のような組織別基準
Outcome（結論）
同一行動でも別評価が成立
決定権（最終）
受け手側（銀行/クラウド/企業）がルール定義
クオラム規則：どの評価結果を満たせば許可するか。
Evidence
09 / 18
検証可能な“根拠”

VAOで追跡できる

「安全チェックを通過した」というだけでは、何が検証されたか追えません。VAOは、行動・文脈・評価者・ルール・鮮度を結び付け、受け手の検証を可能にします。
Attest（含める情報）
行動の正規化された記述（何をしたか）
Attribution（帰属）
どの評価者（エバリュエータ）が判断したか
Timing（鮮度）
いつの文脈で評価されたか（失効/更新）
Rule（ルール）
どの価値体系・バージョンで判断したか
目的：承認の再利用・すり替えのリスクを減らす。
Distinction
10 / 18
失敗モードは前提にする

評価者の誤り・操作・不足文脈

評価者が誤る／文脈が省略される／戦略的に情報を操作される可能性があります。VALUEはこれを織り込むため、拒否（abstention）・監視・人の承認・監査・失効などを必要とします。
Failure（誤り）
評価者の能力・データ不足による誤判断
Attack（操作）
評価経路のゲーム化／情報のすり替え
Gap（文脈）
意図の隠蔽や状態欠落で評価がズレる
結論：万能視せず、部分的緩和を“運用として”設計する。
Process
11 / 18
Fast / Guard / Sentinel

リスクに応じて評価の深さを調整

VALUE Fast/Guard/Sentinelは、行動のリスクに応じて評価の同期性・監視範囲・深さを変える考え方です。小さく不可逆性が低い行動は軽量評価、大きいものは深い同期レビューで扱います。
Fast（軽量）
低リスク・不可逆性が小さい行動向け
Guard（同期）
影響が大きいもの向け（追加確認）
Sentinel（監視）
複数行動の軌跡を異常監視
狙い：コストと安全性のバランス。
Evidence
12 / 18
価値観は受け手に委ねる

“道徳の正しさ”ではなく“条件下の判断事実”

VALUEは「道徳的に正しいこと」を証明する枠組みではありません。指定された条件下で、誰がどの価値体系に基づきどう判断したかという“事実”の検証を中心にします。
受け手が検証できる
価値体系（バージョン含む）／評価者／条件・鮮度
万能ではない
意図の完全理解は前提にせず、文脈不足が残る
この割り切りが、監査可能性と現実運用の境界を定める。
Risk
13 / 18
評価の信頼性がボトルネック

導入判断は“評価品質”次第

VALUEの強みは独立評価を実行境界に組み込む方向性ですが、実効性は評価者の能力・データ・文脈補完・運用設計に依存します。
署名付きVAOでも、情報が不十分なら誤許可が“検証されてしまう”危険があります。
依存点
評価精度
運用点
abstentionの質（判断保留の設計）
統制点
監査・失効・複数評価の調整コスト
結論：正しい方向性。ただしパイロットでKPI（誤許可率等）検証が必須。
Web/Standards
14 / 18
RATS / EAT の土台

検証可能性の標準枠組みと接続

VALUEのVAO（検証可能なアテステーション）という発想は、IETF RATSのリモートアテステーション枠組みと親和性があります。
関連する部品としてEAT（Entity Attestation Token）などの標準が検討されています。
IETF RATS
RATSアーキテクチャ：複数ロールやフレッシュネスを議論
EAT
Entity Attestation Token：検証結果をトークンで運ぶ想定
主張としては「AIエージェントの証拠」とアテステーションを合成する方向があり得ます。
