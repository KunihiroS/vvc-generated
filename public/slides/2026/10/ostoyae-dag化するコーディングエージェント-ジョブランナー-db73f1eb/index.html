COVER
02 / 19
Ostoyae / Coding agent orchestration

DAGで回す依存成長型ジョブランナー

コーディングエージェントが詰まった“不足要素”を、新しいノードとしてDAGに追加しながら前進する仕組みです。
Ostoyae
詰まりを「再試行」ではなく「解くべき仕事」に分解し、チェックで確定する。
対象：コーディングエージェント（例：Claude Code等）をGit上で運用するジョブ自動化
概念：DAG（有向非巡回グラフ） / Git worktree / check / judge / board.json
PROBLEM
03 / 19
“詰まる”たびに崩れる問題

失敗のまま迷子になる

エージェントが依存（前提）がない状態で止まると、何を追加すべきかが曖昧になりがちです。
Failure mode
同じ壁に当たり続ける（再試行しても改善しない）
Ops pain
依存関係を手で設計・修正し直す負担が増える
Safety
試行が汚染される（環境や成果物が混ざる）と再現性が崩れる
Quality
“それっぽい修正”が混入すると、検証基準が追えない
METAPHOR
04 / 19
壁を越える“仕事”に変換

壁→ノード

詰まり（不足要素）を見つけたら、再試行ではなく“解くべき仕事”としてDAGに追加します。
i. 起点ジョブ
ユーザーの要求（例：フレークテストを決定的に）
ii. 詰まり発生
依存が足りずチェック・前提が満たせない
iii. 壁ノード化
不足要素を表す新ジョブをDAGへ追加
iv. 先に解決
壁を解くジョブが先行し、後続ジョブが進む
DAG（Directed Acyclic Graph / 有向非巡回グラフ）だから循環せず、依存の順序が保たれます。
ARCHITECTURE
05 / 19
DAGが成長する実行ループ

実行中にグラフを更新

DAGは最初に静的に作るのではなく、実行中の発見（壁）に応じて伸びていきます。
Input
初期ジョブ：Issue/要件から始める
State
board.jsonに jobs / edges / attempts 等を集約
Edge（辺）
「依存が先、後続が従」の順序制御を表す
Growth
壁を検出 → 不足要素を新ノードとして追加
結果として、先に“必要な構造”が形成され、後続の作業が通りやすくなります。
PROCESS
06 / 19
隔離で“汚染”を断つ

worktree / ブランチで各試行を分離

各attemptは独立したGit worktreeとブランチ上で実行し、環境変数などを継承しない方針です。
Isolation
Git worktree + ブランチ
No pollution
前の試行の影響が広がらない
Env hygiene
DB URL等の環境を継承しない
再現性（reproducibility）と安全性（意図しない外部アクセスの抑制）を狙った設計です。
EVIDENCE
07 / 19
チェックが“採用条件”

check合格のみを確定

提案された変更は、checkコマンドが成功したものだけが作業としてカウントされます。
Mechanism
新しいcheckoutで check を実行
Rule
成功した変更のみ “確定” 扱い
Effect
“それっぽい修正”の混入リスクを下げる
Result
次ノードへの依存が、根拠ある成果物に寄る
再現性を担保するために、検証（verification）をフローの中心に置いています。
DISTINCTION
08 / 19
judgeで提案を裏取り

judge（検証）オプション

judgeを有効にすると、提案をそのまま採用せず別の試行で検証し、チェック結果も含めて厳密化できます。
judge OFF
check基準中心で採否が決まりやすい
judge ON
別プロンプト等で再検証して採否を絞る
Trade-off
追加の試行コストが増える
Goal
提案の妥当性と再現性の両方を高める
judgeは“品質管理のレバー”として働きます。
COMPARISON
09 / 19
再試行 vs 壁ノード化

同じ壁は再挑戦しない

同じ壁に対して再試行しても前提不足が変わらないため、壁を新規ノードとして先に解く設計です。
Naive retry
同じエラー → 同じ不足前提 → 収束しにくい
Ostoyae approach
壁＝不足要素 → 新ジョブ化 → 先行解決
Why
無駄な試行を増やさず、依存設計の負担も減る
Outcome
必要な前提が構造として用意され、後続が進む
ENUMERATION
10 / 19
並列と順序の両立

依存は順次、独立は並列

DAGにより、依存が解消したノードから並列実行し、依存関係がある部分だけ順序制御します。
i 依存あり
前提ジョブが終わってから後続へ
ii 依存なし
同時に進められる（スループット向上）
iii 大規模
複数Issueを同時に扱う運用で効果が出やすい
iv 安定化
前提が“確定成果”側に寄る
ARCHITECTURE
11 / 19
サーバ/DBレス志向

board.jsonに全状態

実行結果や提案内容などの全状態を board.json に集約し、状態を外部DBに置かない方針です。
保存
jobs / edges / attempts / proposals 等
再開
進行途中でも記録から継続しやすい
レビュー
追跡・監査しやすい（履歴がJSONで残る）
運用
viewerで可視化する前提
“状態がどこにあるか”を単純化して、運用の見失いを減らします。
COMPARISON
12 / 19
導入価値（強み）

運用可能な形へ寄せる

Ostoyaeは「エージェントの不確実性」を、DAG・検証・隔離・状態保存で扱える形に変えます。
Dependency
壁をノード化して依存を現場の反応から構造化
Quality
check/judgeで“採用基準”を明示
Reliability
worktree/ブランチ隔離で再現性・安全性を底上げ
複数Issue/複数変更が絡む開発ほど、構造化の恩恵が出やすいです。
DISTINCTION
13 / 19
注意点（不確実性）

ルール詳細が鍵

壁ノード化やjudgeの判定が、ログや例外パターンに強く依存する場合、期待通りに分解できない可能性があります。
Critical
壁発火条件がログ依存だと、誤ノード化/非ノード化が起こり得る
Risk
--launches/--invocations等のキャップで途中停止が増える懸念
Ops
上限チューニング次第で介入頻度が変わる
Collab
衝突・複雑なマージ時の最終差分品質/レビュー観点は追加情報が必要
確実性を得るには、プロジェクト側のcheck設計とjudge設定が重要になります。
PROCESS
14 / 19
実運用の“当たりどころ”

チューニング方針

成功確率は、checkコマンドの設計・judge設定・キャップ上限・壁の扱い理解で大きく変わります。
check設計
テスト/静的解析/ビルドなど“合格条件”を具体化する
judge設定
コスト増と品質向上のバランスでオン/オフを判断
キャップ
途中停止を減らす上限値を運用から調整
壁の理解
“何が不足扱いになるか”を把握して誤分解を減らす
不明点（board.jsonスキーマ詳細、壁生成ロジック、復旧の扱い）はdocs確認が必要です。
CLOSING
15 / 19
結論 / Takeaway

DAG + 検証 + 隔離

Ostoyaeは「詰まりを構造化して依存グラフを成長させる」ことで、コーディングエージェント運用を現場仕様に近づけます。
Core idea
壁をノード化して先行解決
Guardrails
check（検証）／judge（裏取り）
Operate
board.jsonで再開・可視化
DAG / 有向非巡回グラフ
worktree / 作業分離
judge / 検証エージェント
board.json / 状態集約
