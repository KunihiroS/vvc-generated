COVER
02 / 16
AIツールを安全に公開
ShareBox / 共有
AIエージェントが作った小さなWebツールを、自己ホストで「HTTPS付きの専用URL」へ導くための基盤です。
公開も共有も、ユーザーは最小の操作で完了します。/ 共有（sharing）
体験
publish（公開）→ 専用URL → Googleで共有
狙い
認証・権限・データ分離・隔離実行を“プラットフォーム側”へ集約
PROBLEM
03 / 16
本番運用の壁
公開が面倒
AIが作ったWebアプリを本番で動かすには、ホスティング、ドメイン/HTTPS、ログイン、DB、権限管理などの手間が増えがちです。
個別実装だと「安全性」も「運用」もばらつきます。
手間
HTTPS / ドメイン / セッション
難所
権限（誰が何をするか）
リスク
認証実装ミス / データ混在
CORE IDEA
04 / 16
“プラットフォームが守る”
ログインは 肩代わり
ツール側で認証を実装しなくても、プラットフォームがGoogleサインインと権限チェックを処理します。
その結果として、ツールには信頼できるユーザー情報（email/name/role等）が渡されます。 / 設計（design）
ユーザー
Googleでログイン（共有相手を指定）
ツール
“ログイン実装ほぼ不要”でユーザー情報を利用
ARCHITECTURE
05 / 16
隔離 × 分離
データは分割、実行は隔離
各ツールは独自のSQLiteデータベースを持ち、さらにgVisorベースのサンドボックスで動きます。
これにより、ツール同士やホストOSへの直接アクセスを遮断する方針です。
データ分離
ツールごとのSQLite（混ざりにくい）
実行隔離
gVisorサンドボックス（隔離実行）
EVIDENCE
06 / 16
認証の集約
権限チェックを集約
認証・認可をツール側ではなくプラットフォーム側で集中させる設計です。
セッションと権限を検査し、ブラウザから偽装されうる情報を排除して“信頼できるアイデンティティ”を注入します。 / アイデンティティ（identity）
防ぐ方向
ログイン漏れ・権限実装ミス
渡す方向
email/name/role等の信頼情報
PROCESS
07 / 16
公開・更新・共有
publishで専用URL
ツールをpublishすると、HTTPS付きの専用URLが得られます。
再公開すると同じツールの更新として反映され、データは保持されます。/ 更新（update）
共有
特定の人・特定のGoogle Workspaceドメイン・リンク
運用
権限の無効化は次のリクエストで即時反映
OPERATIONS
08 / 16
壊れても戻す
バックアップと復元
夜間バックアップと復元手順が用意されています。
（任意で）Google Driveへ暗号化コピーする運用も説明されています。
バックアップ
夜間実施
復元
手順が記載
任意
Driveへ暗号化コピー
INTEGRATION
09 / 16
AI連携→公開まで
CLI + MCP
sharebox-cliやMCPサーバにより、AIエージェント連携から自然に公開まで行ける導線が強調されています。
“公開の難所”を手作業から減らすことが狙いです。
sharebox-cli
コマンドで公開（公開者体験を短縮）
MCPサーバ
AIが生成→publishへ繋ぐ
LIMITS
10 / 16
できないことを明示
制約がある
現時点では外部API呼び出しが未対応（インターネット無し、secrets無し）とされています。
また公開はCREATOR_EMAILSに基づき制限される可能性があります。
外部API
不可（現時点）/ 将来はエグレスプロキシ等を予定
公開者
CREATOR_EMAILS登録で制限（誰でもpublishではない）
CAPACITY
11 / 16
同時稼働の目安
規模はこれから
入力データには「20〜25ツール程度が2GB RAMで同時稼働上限の目安」といった目安があります。
若いプロジェクトのため、導入前に性能・運用挙動の追加確認が必要です。
目安
20〜25ツール
条件
2GB RAM
前提
“若いプロジェクト”で要検証
ASSESSMENT
12 / 16
強みと検証ポイント
導入判断は二段階
強みは、ツール側ログイン不要・プラットフォーム集中・gVisor隔離・データ分離など「最大論点」を最初から揃えている点です。
一方で、脅威モデルや監査、復旧RTO/RPO、ログ保持粒度などの詳細は読み取りにくく追加確認が必要です。 / 監査（audit）
強み
安全性を設計で下支え（認証集約・隔離・分離）
確認したい
脅威モデル、監査ログ、暗号化方式、復旧目標、依存脆弱性管理
