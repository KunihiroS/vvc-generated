エージェント運用の“差”を握る
Agent Harnesses最重要論点
“モデルの性能競争”の外側にある、実行・制御・復旧・権限設計こそが成果を左右する、という視点を整理します。
対象
GitHub: Best of Agent Harnesses（派生含む）
焦点
Harness（ハーネス）× 実務の成功率
用語補助：agent harness＝“エージェント実行環境＋制御層＋復旧＋ガードレール”。日本語では「エージェント・ハーネス」。
Problem
03 / 16
なぜ失敗するのか
ツールと復旧が鍵
LLMが同じでも、「どのツールにアクセスできるか／何を観測できるか／失敗時にどう再開するか」で成功率は大きく変わります。
成功を左右
アクセス（権限）・文脈（入力）・観測（出力）
失敗を増幅
再試行/再開なし・状態喪失・安全柵不足
設計思想の中心：モデル単体ではなく、実行ループ（計画→実行→観測→次の行動）を“運用可能”にする層。
Metaphor
04 / 16
車に例える
エンジンではなく制御
モデルはエンジン（発想）に近い一方、ハーネスはブレーキ・配線・計器・非常停止・再起動手順です。
モデル
判断（計画）
Harness
制御（実行/権限）
運用
復旧（再開/監査/安全）
このプロジェクトは「良い車種を探す」ではなく「良い配線と手順で走らせる」知見を集めています。
Architecture
05 / 16
何が整理されているか
“ベスト集”の狙い
「最重要の競争領域」をモデル本体ではなく、エージェントの実行・制御・復旧・ガードレール（ハーネス）に置いて体系化しています。
収録
167件（テンプレ/プレイブック/MCPサーバ/機械可読データ含む）
提供形
ランキング・表・検証プロトコル・意思決定ガイド
重要な点：ハーネスを変えると同じモデルでも合格率（pass@1）が変わり得る、という主張を前面に置きます。
Evidence
06 / 16
測定可能な主張
pass@1が動く
単なる印象ではなく、SWE-bench ProやARC-AGI-3等のベンチマークを例に、ハーネス差で成果が大きく変わり得ると示します。
主張
同じ重みでも、harness差→合格率差
例
SWE-bench Pro / ARC-AGI-3 など
ただし一般化には注意：最終的には自分のタスクで検証すべき、という立場も同時に必要です。
Distinction
07 / 16
見直しの結論
モデル単独よりペア
ランキングのモデル間相関が小さく（例：-0.05程度）、モデルを変えるたびにハーネス×モデルの組み合わせを再検討すべきと述べます。
推奨方針
Harness × Modelで意思決定
理由
相関が小さく、最適が固定されない
実務の含意：フレームワークを固定すると失敗パターンや探索効率がずれて性能劣化し得ます。
Process
08 / 16
導入を“手順化”
テンプレ→検証
候補を列挙するだけでなく、導入・検証の進め方（フェアなセットアップ、複数測定、ウォークアウェイ等）を含めます。
導入材料
テンプレート
運用材料
プレイブック
検証材料
二週間トライアル
目標：自分のタスク特性（権限・ツール種類・データ品質・評価指標）に合わせて再現性を確かめること。
Architecture
09 / 16
人ではなく“エージェント”が読む
MCPで参照自動化
リストを検索し、推奨（recommend）や選定（pick_harness）などを呼び出せるように、MCPサーバとJSON/テキスト形式のデータを提供します。
提供
harnesses.json / llms.txt（機械可読）
MCP
Model Context Protocol（モデル文脈連携標準）
Bilingual: MCP（Model Context Protocol／モデル文脈プロトコル）で、ツール連携を共通の窓口にする考え方。
Distinction
10 / 16
分類の意味
headless / durable
headlessは無人実行できる設計、durableは途中停止でも状態を保持して再開できる度合いを指し、運用コストとリスクに直結します。
headless
無人（バッチ/ワークフロー向け）
durable
復旧（状態保持・再開の度合い）
同じ“強いモデル”でも、運用要件が違えば適切なハーネスは変わります。
Evidence
11 / 16
透明性の運用
Graveyard（隔離）
アーカイブ化や星操作疑いなどはGraveyardに置き、主要リスト/ランキングから除外して意思決定の信頼性を守ろうとしています。
対象例
アーカイブ／星操作疑い
意味
“本番採用は慎重に”（参考用途の余地）
ポイント：除外は自動的に無価値を意味しませんが、“ランキング根拠”の品質を守る措置です。
evidence
12 / 16
強みと注意点
鵜呑み禁止
このプロジェクトは強力ですが、ベンチマーク差と実業務のタスク特性のズレにより、改善がそのまま移植される保証はありません。
強み
ランキング＋テンプレ＋意思決定＋機械可読APIが一体
注意
二週間トライアル等で自タスク検証が必須
追加観点：各ハーネスのライセンス/保守状況（source-available/OSS混在）も要確認。
closing
13 / 16
実務の持ち帰り
選ぶのはハーネス
本質は「ツールやフレームワークの寄せ集め」ではなく、失敗・復旧・権限・観測の設計思想を再利用可能にする点です。
行動
Harness×Modelを再検討
検証
二週間トライアルで合否確認
運用
Graveyardも含め透明性を読む
入口としてのおすすめ：まず自タスクで「アクセス・観測・復旧」が満たされるハーネスを選び、その上でモデルを詰める。
