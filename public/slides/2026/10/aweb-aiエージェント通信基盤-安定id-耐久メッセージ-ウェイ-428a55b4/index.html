AIエージェントの通信基盤

aweb / 安定ID×耐久メッセージ

awebは、エージェント間のタスク受け渡しを「チャット」ではなく「サーバ状態としての配達」として設計する仕組みです。

problem
03 / 19
いま起きる困りごと

同期に縛られる

従来の会話ログ依存だと、送信側・受信側が同時にオンラインでないと成立しにくくなります。さらにランタイム（Claude Code / Pi等）が違うと連携が複雑化します。

チャット型UI：作業が完了して終わる発想になりがち
ログ型：セッション終了後に“受け渡しの保証”が弱くなる
複数マシン/複数ランタイム：統一できない問題が増える
非同期タスク：待ち合わせ（キュー/配達）を通信層で扱いたい
metaphor
04 / 19
発想の切替

“チャット”から配達へ

awebはメッセージを「ログ」ではなく「サーバ側の耐久状態（durable）」として保持します。必要なタイミングで受信側を起床（wake-up）させ、タスクを取りに行かせます。

Durable / 耐久
送信後もメッセージがサーバに残る（受信側が後で取得）
Wake-up / 起床
仕事が来た通知をイベントとして渡し、ランタイムを起動
architecture
05 / 19
awebの4つの柱

安定ID×耐久×起床×連携

awebは、(1) 安定したアイデンティティ、(2) 耐久メッセージ配達、(3) ウェイクアップ・イベント、(4) フェデレーション（複数組織・サーバ連携）を統合します。

Stable Identity / 安定ID
プロセスやマシンが変わっても同じ“相手”として扱う
Durable Messages / 耐久配達
受信側がオフラインでも後で取り出せる
Wake-up / 起床
イベントにルーティング情報を含め、取り出しを促す
Federation / フェデレーション
組織・サーバが分かれても署名付きで協調できる
evidence
06 / 19
具体例：Alice→Bob

非同期評価依頼

Alice（Claude Code、別マシン）からBob（Pi、別マシン）へ評価依頼を送ると、awebがメッセージを保存し、Bobを拡張経由で起床させます。

Alice（Claude Code） 送信 ↓（aweb） メッセージ耐久化（サーバ側） ↓ Bob（Pi）に wake-up イベント配信（拡張経由） ↓ Bobが応答 ↓（aweb） Aliceへ結果配達 Bobがオフラインなら… 応答可能になった時点で 待っていたメッセージを取得
distinction
07 / 19
要点①

メッセージはセッションではない

awebのメッセージは、会話中だけの履歴ではなく、サーバ状態として長期保持されます。これによりオンライン同時性に依存しません。

従来：ログ依存
セッションが閉じると“取り出し”が難しい
aweb：耐久保持
受信側が後からIDで取得できる（オフライン許容）
process
08 / 19
要点②

ウェイクアップ＝仕事待ち通知

配達イベントはルーティング情報を含み、受信側エージェントがイベントをトリガーにメッセージを取りに行きます。同期チャットではなく非同期ワークフローに合います。

イベント（wake-up）
「処理すべき仕事がある」ことを通知する
取得（IDで参照）
受信側はサーバに保存されたメッセージを取得
architecture

要点③

安定IDと鍵管理の分離

セッションやプロセス、マシンが変わっても“アドレスされたエージェント”として同一性を維持します。さらに秘密鍵の保管（custody選択）も運用要件に合わせて選べるとされています。

Stable identity / 身元
変化しても同じ相手として扱える
Custody / 鍵の保管
ホスト型保管か自己保管かを選択
enumeration
10 / 19
要点④

フェデレーションで連携

同一ランタイムや同一モデル提供者に束縛されず、独立運用のサーバ同士が署名付きメッセージで協調できる立て付けです。

組織やサーバが分かれても協調
署名付きのやり取りで信頼を担保
将来の拡張（連携先の増加）を見据える
ランタイム非依存：イベントを消費できれば利用可能

11 / 19
信頼チェーン：AWID

サーバが勝手に身元を定義しない

AWIDは、DNS起点の信頼チェーン（ネームスペース→チーム→メンバーシップ証明→エージェント署名）を検証できる設計を掲げています。

名前空間 / Namespace
domainから始める（DNS起点の信頼）
権限 / Authority
チームコントローラが承認→メンバー証明を署名
エージェント署名
最終的に各エージェントが自身の鍵で署名
署名検証
通信サーバが“アイデンティティを勝手に作らない”意図
comparison
12 / 19
運用形態

ホスト型 vs 自己ホスト

ホスト型（aweb.ai）と自己ホスト型は、同じCLI・同じ通信プロトコルで運用できる方針です。後から切り替えやすいのが特徴とされています。

ホスト型
aweb.ai側がネームスペース/チーム権限などを作る前提
自己ホスト型
Docker Compose等でサーバとAWIDレジストリを起動し運用
共通
同じCLIでaw initの初期化を行う流れ
ねらい
移行コストを下げ、ガバナンス要件へ対応
distinction
13 / 19
よくある疑問（要約）

チャットではない

awebの価値は見た目の会話ではなく、耐久メッセージ保持とウェイクアップで非同期のタスク受け渡しを成立させる点です。

Q：単なるチャット？
いいえ。セッションが閉じてもメッセージが残りIDで取得できる
Q：相手がオフライン？
保存→起床イベント→オンライン後に取り出し（待機が組み込まれる）
Q：別ランタイムでも？
統合チャネルはあるが、イベントストリームを消費できれば利用可能
Q：権限は？
AWIDの信頼チェーン検証で“サーバ任せ”を避ける
evidence
14 / 19
所感：強い可能性

通信層で作業キューを作れる

耐久メッセージとウェイクアップを中心に据えることで、「会話ログ」から「作業キュー/配達システム」へ発想を変えられます。複数マシン・複数ランタイムの協調に実用価値が出やすいです。

Practical / 実務
オフライン許容・非同期遂行で、運用に直結しやすい
Security / セキュリティ
AWIDで権限チェーン検証を設計可能（ただし失効・保証条件の詳細は要確認）
Operational / 運用
ホスト/自己ホストでCLI・プロトコル共通（スケール/障害は別途精査が必要）
Risk / リスク
イベント保証（少なくとも一回/ちょうど一回等）や整合性が不明だと評価が完了しない

結論と次の確認

採用前に保証条件を確認

awebは非同期エージェント連携の通信基盤として有力です。導入判断では、通信保証（配達の性質）、遅延/障害時整合性、監査ログ粒度、鍵の失効・ローテーション挙動を必ず精査してください。
