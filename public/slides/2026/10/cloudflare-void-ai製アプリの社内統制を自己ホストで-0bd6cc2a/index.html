02 / 18
AI社内アプリを、統制する器。
Cloudflare Void
Cloudflareは、AIで作られる社内アプリの「シャドーIT化」を抑えるため、オープンソース基盤「Void」を提供しました。特にPlatformは自己ホストでき、権限・ログ・運用を企業側に寄せられます。

シャドーITの 別形
非エンジニア（または経験の浅い開発者）がAIでアプリを増やすと、IT部門は「誰が何をデプロイしたか／どの社内データにアクセスするか／コスト・事故をどう防ぐか」を追いにくくなります。これが“管理できない自由”として現れます。

GOAL
04 / 18
自由は残し、責任を戻す。
“公開”を 統治へ
Voidの狙いは、AI開発を止めることではなく、成果物を“統治可能な形”に取り込むことです。従業員が作ったアプリを、権限・ログ・運用で追える状態にします。
Before / 前

After / 後
Voidで：デプロイ・利用・運用を可視化
ARCHITECTURE
05 / 18
3つの部品で回す。
SDK / CLI / Platform
Voidは、作る側（SDK）、デプロイする側（CLI）、ホスト／管理する側（Platform）の3要素に分かれます。企業は、特にPlatformを自社で自己ホストし、統制の設計自由度を確保します。
SDK（作成）
組み込み・実装
CLI（配布/実行）

06 / 18
Platformを“自己運用”へ。

Platformは自己ホスト可能に再設計されています。管理者は「誰がデプロイでき誰が利用できるか」を定め、ログ確認やトラブル時のロールバック等も運用設計に含められます。
Governance / ガバナンス
デプロイ権限・利用権限
Operations / 運用
ログ・監視・ロールバック
SECURITY
07 / 18
アクセス制御は効く。
“誰が使うか”を絞る
アイデンティティ基盤（Identity Provider）やCloudflare Accessの利用で、許可された従業員だけがアプリへアクセスできます。まずは「利用者の線引き」を確実にすることで、統制の土台を作ります。
IdP / 認証
SSO・認証連携
Access / 認可
許可ユーザのみ
Outcome / 結果
利用範囲の縮小
LIMITATION
08 / 18
万能ではない。
漏えいは“ゼロ”にできない
アクセス制御で「誰がアプリを使えるか」は制限できますが、アプリが機密情報を取得し外部へ送信する可能性をゼロにできません。Voidは監視・統制を助けますが、振る舞いの完全な封じ込めまで自動担保するわけではない点が重要です。
Control / できる
利用者・アクセス範囲
Not guaranteed / できない可能性
外部送信・機密取得の完全防止
GOVERNANCE
09 / 18
承認は“必須と断言できない”。
レビュー設計は企業側
記事の示唆では、デプロイ前の承認がVoid側で必ず強制されるわけではない可能性があります。その場合、厳格なガバナンスが必要な組織ほど、追加の運用設計・拡張で安全を担保する必要が出ます。
Default / 標準
承認フロー“必須”とは限らない
Risk / リスク
未整備だと危険
Action / 対策
権限・レビュー・監査を設計
COST
10 / 18
“無料”は表面だけ。
TCOは自己ホストで増える
自己ホストには、Workers for Platformsの費用、R2ストレージ、別途PostgreSQLが必要になり得ます。Voidのソフト自体がオープンソースでも、導入時は運用体制とTCOを前提に判断が必要です。
Potential costs / 例
Workers・R2・PostgreSQL
Decision / 判断軸
開発スピード改善 × 運用コスト

14 / 18
評価：有望、ただ誤解禁物。
結論：統治の“器”
Voidは、AI開発を無秩序に増やすのではなく、統治可能に取り込む器として有望です。一方でアクセス制御だけでは不十分になり得るため、企業は承認・検査・監査・データ保護ポリシーを別途設計すべきです。
