4年で収束：接続の確実性へ

iroh 1.0

irohは「つながること」に一点集中し、方針転換（pivot）を重ねて、安定したP2P接続コアへ到達した――その開発者視点の振り返りです。

Core stack / 中核技術
QUIC（quinn）＋BLAKE3検証ストリーミング＋TLS（rustls）

03 / 18

P2Pの本質課題はNAT

“できない”を減らす

P2Pは理屈よりも現実（NAT・ネットワーク環境・再開可能性・依存関係）で失敗しやすい。irohは最終的に「成功率の高い接続」を最上位要件に置きました。

Hard part / 難所
hole punching（穴あけ）の成否は環境依存
Design target / 狙い
エンドポイントID（公開鍵）で“ダイヤル→接続成立”
metaphor
04 / 18

互換より、試作で学ぶ

IPFS互換からの

初期irohはIPFS互換のRust実装から始まりましたが、大容量ブロブ転送の不満や依存の重さが、現実用途でボトルネックになっていきます。

Early / 初期
IPFS互換を目指す
Problem / 問題
大容量ブロブ転送の非効率
Experiment / 試作
BLAKE3で内容アドレス、krakensync等を試作
architecture
05 / 18

pivot：互換を捨て、最小コアへ

QUIC中心へ

デルタチャットのような“狭いが厳しい用途”に合わせて、IPFS互換のこだわりをやめ、QUICベース／BLAKE3検証ストリーミング／公開鍵（Ed25519）でエンドポイント認証へ収束しました。

Endpoint ID / 識別
Ed25519公開鍵（dID的な発想）
Transport / 通信基盤
QUIC（quinn）でRust上の実装と進化を加速
evidence
06 / 18

quinnが“詰まり”を解いた

開発速度×性能

当時ライブラリ統合が難しい状況でも、Rustで扱いやすいQUIC実装（quinn）を採用したことで、ネットワークデモを成立させつつ、その後の設計にも追随できる形になりました。

Why QUIC / 理由
P2Pでストリーミング・多重化を活かしやすい
Why quinn / 理由
Rust実装として統合が現実的
Outcome / 結果
実験→進化のループが回った
distinction
07 / 18

TLSは残す：標準に寄せる

Noise置換の誘惑

QUICの役割分担（RFC 9000）からTLS（rustls）を維持しつつ、raw public keyのような具体的改善で不満点を解消していきました。最終的には業界標準との整合を優先しています。

Kept / 維持
TLS（rustls）を暗号化・認証の中心に
Improved / 改善
raw public keys等で“手触り”と運用性を改善
（用語）Ed25519：楕円曲線署名、raw public key：証明書チェーンに頼らない公開鍵提示
process
08 / 18

“理想P2P”より成功率

穴あけ→失敗ならrelay

hole punchingは成功率が環境で変わるため、基本は直接接続を狙い、必要なら中継（relay）へフォールバックします。結果として、tailscaleに近い「成功率優先」の思想が入っています。

Step i / i
接続要求：hole punchingで直接へ
Step ii / ii
成功率を上げる設計（確実性重視）
Step iii / iii
不可ならrelay（企業NWでも成立）
evidence
09 / 18

検証を“ストリーミング”に

BLAKE3で再開と検証

BLAKE3を使った内容アドレスと検証ストリーミングにより、大容量転送でも「途中から再開」や「検証の自然な統合」を狙います。krakensyncのような試作が、その方向性を固めました。

Why BLAKE3 / 理由
高速で、内容ベースの識別と整合しやすい
Benefit / 効果
検証を転送の流れに組み込みやすい（再開にも寄与）
distinction

バッテリー同梱→“接続だけ”

スコープ縮小が1.0

APIが肥大化すると品質を全方位で担保しにくい。そこでirohは利用者が共通して必要とする部分――「エンドポイントIDによるダイヤル」と「確実なhole punching付き接続」へ絞り、1.0の安定化を実現しました。

Risk / リスク
API肥大化で品質保証が難化
Focus / 焦点
接続成立の最小コア
Result / 結果
ワイヤ形式＋APIの安定（1.0）
（用語）wire形式：通信メッセージの約束事（安定化対象の中心）
enumeration

納得感は強いが、数値は薄い

評価は定量も欲しい

経緯は理解しやすい一方、失敗率・ベンチマーク・依存削減量・脅威モデル比較などの定量評価が不足していると感じるポイントがあります。採用判断には、最適化された要件（成功率・再開・用途）を前提に照合が必要です。

Missing / 欠け

Also / 追加で

13 / 18

結論：接続“コア”に収束

iroh 1.0の学び

互換や汎用性より、実運用での成功確率と実装可能性を優先し続けた結果、irohは「端末間接続」を安定して提供する最小コアに絞り込みました。次は自分の用途制約に合わせて、接続方針（direct＋fallback）をどう組み立てるかを検討してください。

When to choose / 選び所
アプリに“接続”を組み込み、QUIC中心で設計したい
When not / 注意
OS/ネットワーク全体を丸ごと束ねたい（VPN的統合は不向き）
（用語）成功率/確実性：hole punching直の成立確率＋失敗時のフォールバックで総合的に最適化
