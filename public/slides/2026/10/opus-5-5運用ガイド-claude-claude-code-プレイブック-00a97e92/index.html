長い作業を“運用”で完走

Opus 5.5 プレイブック

Claude apps と Claude Code で、完了条件・停止条件・結果確認・フラグ復帰までを型化するガイドです。（長時間コード変更／移行／監査／ドキュメント精査向け）

Target: chat apps（Claude apps） / dev tool（Claude Code）
Problem
03 / 15
ゴールが曖昧

“いつ終わる？”

長いタスクは、done（完了条件）が曖昧だと終了ラインがずれます。するとモデルの走り方がぶれて、手戻りが増えます。

起きがち
「途中報告で止まる」or「終わらない」
根本
done が判定不能（Yes/Noにできない）
Bilingual: done（完了条件） / stop（停止）
Architecture
04 / 15
最重要の設計点

done を 判定 可能に

完了条件を具体化して、テスト結果や件数などで Yes/No 判断できる形にします。Opus 5.5 はゴールが見えるほど最後まで走りやすくなります。

例 1
テストが通る（all green）
例 2
旧クライアント参照：0件
例 3
移行前後で整合性が保証される
Bilingual: finish（完了） / validation（検証）
Distinction
05 / 15
余計な命令を削る

think 指示より停止ルール

「think carefully」のような思考強要文言は、品質向上より遅延を招く可能性があります。代わりに effort や CLAUDE.md の停止条件で運用を制御します。

避ける
思考を強要する文言（不要な場合）
使う
effort（effort mode）＋停止ルール設計
Bilingual: effort（努力設定） / stop rule（停止規則）
Process
06 / 15
止まり方を分ける

CLAUDE.md で 停止 を設計

長い実行は「報告だけして止まる」ことがあります。入力不要なら続行し、破壊的操作の前やユーザーなしで進めないときだけ確認する、が基本です。

続行（自律）
入力が不要ならそのまま進める
停止（確認）
削除・force-push など破壊的操作の前
停止（確認）
ユーザー判断なしで進めないとき
拡張
必要に応じてサブエージェント分割
Bilingual: destructive（破壊的） / agent（エージェント）
Evidence
07 / 15
監査は証拠で進める

検証を分割して 証拠化

監査・移行のような大規模作業は、サブエージェントで分割し、各結果の証拠を確認してから統合します。見落としや誤検出を減らせます。

分割
サブタスク（並行）
検証
各結果に証拠（evidence）を添付
統合
最終まとめをレビュー可能な表で整理
Bilingual: audit（監査） / evidence（証拠）
Comparison
08 / 15
確認順が肝

blocked → 全体 → 不確実

結果確認は、まず blocked on me 等の「ユーザー承認が必要な点」を読むのが効率的です。次に変更内容、最後に不確実点をチェックします。

i
blocked on me（承認・判断が必要）
ii
全体サマリー（何をどう変えたか）
iii
不確実点（未確定・リスク）
Bilingual: blocked（待ち） / uncertainty（不確実性）
Process
09 / 15
apps と code の使い分け

添付で精度、ファイルで把握

Claude apps では図・スクリーンショット・チャートを文章に打ち直さず添付すると精度が上がります。Claude Code では TASKS.md のようにタスクリストを保持して状況把握を効率化します。

Claude apps
画像・図を添付（文章の写経を減らす）
Bilingual: attachment（添付）
Claude Code
TASKS.md で進捗管理
Bilingual: tasks（タスク）
Bilingual: document（文書） / chart（チャート）
Distinction
10 / 15
フラグは“想定手順”へ

safeguards → フォールバック

bio/cyber safeguards でメッセージがフラグされると、別モデルへ切り替わる場合があります。切替後にどこを見て、どう戻すかを事前に決めます。

Claude apps
モデルピッカーで Opus 5.5 に戻す／新規チャット切替／自動切替を無効化
Claude Code
/model で戻す → 必要に応じて /config → 誤フラグなら /feedback
Bilingual: fallback（フォールバック） / feedback（フィードバック）
Closing
11 / 15
再現できる型

“運用設計”が勝つ

完了条件（done）を判定可能にし、無駄な思考指示を削って停止ルールで制御し、blocked を最優先で確認する—これが成功確率を上げます。

1
done（完了条件）を Yes/No で
2
CLAUDE.md で停止を設計
3
blocked → サマリー → 不確実の順
Practical note: 小さなタスクで停止/続行の境界を検証してから拡大
