Rust off Rails
02 / 18
AI時代の規約フレーム

Rustオフ・レイルズ

フレームワークが“コード資産”を配る代わりに、エージェントの判断を固定する“仕様（Markdown）”を配る仕組みです。
Problem
03 / 18
迷いが品質を壊す

生成

AIエージェントは“何を選ぶか”で実装が分岐し、同じ依頼でも成果がばらつきます。
さらに「作って終わり」になりやすく、静的解析やテストでの品質ゲートが後回しになることが起きます。
Metaphor
04 / 18
仕様がレール

Railsの移植

Rails/Phoenixの“規約・生成・運用の型”を、Rust＋エージェント向けに再解釈したのが「Rust off Rails」です。
従来
フレームワークが実装断片（コード）を提供する。
Rust off Rails
仕様（Markdown）で判断基準を固定し、生成を統一する。
Core
05 / 18
Markdownがフレーム

判断を配る

テンプレではなく、クレート選定・ファイル構成・命名・エラー方針・テスト方針まで文章化し、生成結果のばらつきを減らします。
クレート選定
命名規約
エラー方針
テスト方針
検証手順
Workflow
06 / 18
Interview→Green

流れ一貫

Interview → Plan → Generate → Greenで、生成物を“完成”として認める品質ゲートを先に設計します。
Interview
UI/認証など重要判断を面接で確定。
Plan
spec（方針）に落として永続化。
Green
fmt/clippy/テスト合格まで完了扱いしない。
DoD
07 / 18
完成条件が厳密

Green定義

“合格”の条件が明確で、SQLiteとPostgresの両方で同じテストが通ることがGreenの核になります。
fmt/clippy
静的整形・静的解析も合格条件に含める。
SQLite & Postgres
ローカルと本番DB差で破綻しないよう寄せる。
Front-end
08 / 18
UIは最初に選ぶ

モード分岐

フロントエンドは面接で選択し、生成物のルーティング/設計を後から大きく組み替えない前提です。
htmx（default）
サーバ中心で軽量に進める。
Inertia
React/Svelte等を選びやすく接続。
SPA / APIのみ
段階的開発や検証に合わせて分岐。
Back-end
09 / 18
役割ごと1クレート

統一志向

バックエンドは仕事ごとにクレートを固定し、ORMや実装の都度議論を減らす設計です。
例（スタック）
Axum / Tokio / SeaORM / Askama / Tailwind。
観測性
lettre / tracing などでデバッグ・運用を前提化。
Distinction
10 / 18
AI依存では終わらせない

生成物

エージェントに“書かせっぱなし”ではなく、生成されたコードはあなたのアプリとして所有・運用・改修できます。
また文面上は「framework codeは0 lines」とされ、実装の大量同梱ではなくspecと生成レシピ中心の発想です。
Risk
11 / 18
テストは万能じゃない

安全誤解

fmt/clippyとテスト通過は有効ですが、セキュリティや仕様外のバグは未検出で残り得ます。
未検出になりやすい
脅威モデル / 権限境界の条件 / 依存関係の脆弱性。
必要になりがち
追加検証（レビュー、権限テスト、監査ログ確認など）。
Adoption
12 / 18
導入前の確認

3つ観点

導入時は、(1)生成物の理解体制、(2)仕様外領域の追加検証、(3)例外要件への適応力を確認するのが現実的です。
理解
生成コードを追跡・説明できるか（責任の所在）。
追加検証
セキュリティ/監査/運用要件を補えるか。
適応
強い前提が、特殊要件でどこまで崩れるか。
Closing
13 / 18
結論

規約×品質ゲート

Rust off Railsは、spec（Markdown）で迷いを減らし、SQLite・Postgres両対応のGreen条件で“作って終わり”を抑える設計です。
specがSource of Truth（仕様が正）
Green=fmt/clippy+テスト（定義が先）
生成物を自前資産として運用（所有）
