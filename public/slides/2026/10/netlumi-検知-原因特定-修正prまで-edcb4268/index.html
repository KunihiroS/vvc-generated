COVER
02 / 16
一気通貫の修正支援

Netlumi

クラウド設定の継続スキャンとコード解析を組み合わせ、検知→原因特定→修正PR提案までをつなぐセキュリティ支援のコンセプトです。
PROBLEM
03 / 16
放置が増幅する

調査が重い

設定ミスは起点になり得ますが、重要資産へ到達する「攻撃経路」と、Terraformやコード上の原因を結び付ける作業がボトルネックになりがちです。
核心

警告で終わると、担当割当・原因特定・差分作成が別工程になり、是正が遅れます。

ARCHITECTURE
04 / 16
検知からPRへ

一歩先

Netlumiは、検知した問題に対してリポジトリの該当ファイル・行を対象に修正差分を用意し、ユーザーがレビューしてマージする形のFix PRを目指します。

検知（Cloud）

継続スキャンで公開設定や権限、整合性のズレを見つけます。

原因（Code）

Terraform逸脱（drift）やコミット/開発者へ紐付け、修正PRへ落とします。

METAPHOR
05 / 16
つながりを見る

Attack Path

「重大度」だけでなく、設定不備が連鎖して“重要資産へ到達できるか”を可視化し、到達可能性で優先順位を決める発想です。
例：S3の公開設定のような入口が、別の権限や設定不備と組み合わさる経路を示すことで、調査の迷子を減らします。
EVIDENCE
06 / 16
Terraformへ戻す

Drift

クラウド資源がTerraform定義と一致しなくなったタイミング（drift）を扱い、いつ・誰が・何の経路でズレたのかを追跡します。

一致しない状態

手作業変更や別経路の適用で、意図した統制から外れる。

原因の追跡

コード側の行・コミットへ接続し、再発防止につなげる。

PROCESS
07 / 16
PRで回す

Fix PR

修正は自動適用ではなく、レビュー前提のFix PRとして提示されます。ユーザーが承認してマージする設計です。

i

問題を検知

ii

原因を特定

iii

差分をPR化

この流れにより、セキュリティ→運用/開発の“調整”工数を圧縮する狙いがあります。
COMPARISON
08 / 16
従来と違う点

運用成果物

単なる通知や監査レポートではなく、レビュー可能な変更（PR）へ落とすことで、是正を“次のアクション”に変えます。

従来

警告→チケット→人が差分作成→再レビュー

Netlumi

検知→原因紐付け→修正差分（Fix PR）

EVIDENCE
09 / 16
AIも資産扱い

AI Security

Bedrock / SageMaker 等のモデル・エンドポイントの公開状態や権限、ログ無効などを検査し、クラウド設定と同じ枠組みで扱うとされています。
統合観点

クラウド（設定）＋リポジトリ（コード/呼び出し）を結び、AI利用のレビュー漏れを減らす狙いです。

DISTINCTION
10 / 16
未登録の影

Shadow AI

リポジトリにあるAI呼び出しが、AI inventory（登録台帳）に存在しない状態を「Shadow AI」として扱う考え方です。

なぜ問題

承認・把握されないまま運用に入る可能性がある。

狙い

レビューされないAI利用を可視化して是正につなげる。

DISTINCTION
11 / 16
使い方注意

監査ではない

CIS / SOC2 / ISO / PCI / HIPAA / NIST などへのマッピングは示されつつ、attestation（保証）や監査の代替ではないと明記されています。
判断軸

外部提出用途では、契約・証跡要件に対して別途の検証が必要です。

EVIDENCE
12 / 16
PoCが必要

検証ポイント

入力文だけでは、精度・カバレッジ・PR生成の網羅性・副作用リスク・プライバシー安全性の根拠が不足しています。導入検討ではPoCで確認が必要です。

精度

誤検知率/見逃し率、カバーする設定パターン

安全

変更の副作用、破壊/置換のブロック条件

運用

誤検知時の運用フロー、plan前提条件、PRレビュー工数

CLOSING
13 / 16
結論

実務の短縮

Netlumiは、攻撃経路・drift・コード/コミット紐付け・AI/Shadow AIまでを統合し、検知をPRに変えることでセキュリティ調査と是正の時間を短縮する設計思想です。
次の一手

まず自社のリソース種別とTerraform運用に合わせてPoCし、PRの適切性と運用・プライバシー要件を確かめるのが堅実です。
