重ねた2つ目のGit

git-dupe / デュープ

プロジェクトの作業ツリーはそのまま使いつつ、
自分用ファイルだけを「公開Gitからは見えない別履歴」で同期します。

日本語併記：hidden path（隠しパス） / dupe（デュープ＝重ねた2つ目）
PROBLEM
03 / 18

混入事故が起きる

“自分用”が混ざる

メモ、計画、下書きスクリプト、エージェント指示、エディタ設定などは便利ですが、うっかりPRやcommitに混ざると困ります。

起きがち
git add / commit 対象に含めてしまう
困る結果
公開履歴に“余計な情報”が残る（秘匿・ノイズ）
目標：見せない（公開から除外）＋同期する（自分の履歴は維持）
METAPHOR
04 / 18

同じ部屋に2つの台帳

二重の台帳/ dupe

プロジェクトの“部屋”は共有しつつ、あなたの“台帳”は別に持つ。公開側には見えない形で、別履歴だけを進めます。

公開側（プロジェクト）
git status / git add で除外される（hidden path）
非公開側（あなた）
.git/dupe（または worktree 配下）で通常のGitとして管理
“見えない”＝暗号ではなく、追跡から外す（暗号化しない）
ARCHITECTURE
05 / 18

場所は.gitの中

dupeは内部へ

git-dupeは、プロジェクト側の.gitディレクトリ内に自分用のGit（“デュープ”）を作り、そこにだけコミットします。

プロジェクト
通常のリポジトリ（公開履歴）
dupe
.git/dupe
worktreeあり
.git/worktrees/<name>/dupe
読み方：作業ツリーは1つ、履歴はあなた専用に分離
PROCESS
06 / 18

基本の流れ

運用ステップ

やることは「作る→隠す→あなたのリモートへ同期」。プロジェクトには混ぜません。

1) 自分用を指定
隠したいパス（メモ/指示/下書き等）を“dupe対象”に
2) 追跡から除外
プロジェクト側の hidden path（例：.git/info/exclude）で非表示化
3) あなたの履歴
git dupe commit / log / diff を普通のGitの体裁で実行
4) 同期
git dupe clone / push / pull を“自分専用リモート”へ
公開リポジトリへはpushしない前提（事故を避ける設計）
EVIDENCE
07 / 18

なぜ status に出ない

excludeが効く

git-dupeは、プロジェクト側の追跡対象からあなたの隠しパスを外します。結果として status / add / 公開commit に混ざりません。

プロジェクト側
.git/info/exclude に隠しパスを登録
観測結果
git status / git add -A / 公開コミットの対象外
ポイント：見えない＝commitできない（公開側に混入しない）
COMPARISON
08 / 18

通常Gitと対比

混ぜる/混ぜない

通常のGitは“同じ作業ツリー”に対して追跡と公開を行います。git-dupeは“公開追跡から外す場所”を前提に分離します。

通常Git（リスク）
編集したファイルが index / commit 対象になり得る
git-dupe（対策）
hidden pathでプロジェクト追跡から除外＋あなたは dupe へcommit
認知負荷の削減：普段のGit体裁に寄せつつ危険な型を拒否
DISTINCTION
09 / 18

dupeとリモート

同期先が命

あなたの履歴は“自分専用の空リポジトリ（リモート）”へ push/pull して同期します。公開リポジトリは指しません。

公開リポ
push しない（混入事故を防ぐ）
自分リモート
履歴同期の受け皿
結果
別マシンでも dupe clone で復元
“あなたのファイルは公開に出ない”が基本方針
DISTINCTION
10 / 18

暗号化はしない

秘密は別途/ non-encrypted

Nothing is encrypted。dupeでpushした内容は、通常のGitリモートにそのまま保存されます。

git-dupeの限界
暗号化（例：コミットやファイル）の自動実装はない
運用の前提
信頼できる送信先を使う／必要なら事前暗号化（例：git-crypt等）
目的は「混入事故の防止」＋「自分用履歴の同期」
EVIDENCE
11 / 18

コマンド体裁は維持

Gitっぽく使う

commit / diff / log などは“普通のGitの延長”として扱えるように設計されています。

学習負荷
普段のGitと似た体験で dupe を扱う
事故対策
stash全体化など危険な操作、リポジトリ/リモート誤指定の型は拒否
安全寄り：誤って公開側に入れる確率を下げる
PROCESS
12 / 18

detachで戻す

外すは慎重に

git dupe detach はデュープを取り除きますが、「ディスク上のファイル自体が常に消える」タイプではありません。

挙動
デュープ除去（ただしファイルは残す設計）
制約
uncommitted変更や特定状態があると --forceなしで拒否
狙い：いつでも強制的に消すより、事故を避ける
DISTINCTION
13 / 18

チーム運用の注意

上書きの可能性

同じ隠しパスを別側で先に取り込むと、上書きが起こり得ます。意思決定が必要です。

リスク
片方が先に取り込み → もう片方が上書き
必要な運用
どちらのリポジトリ（dupe側/基準）を正とするかを決める
パス衝突や隠しパス数上限など、設計上の制約も事前確認
COMPARISON
14 / 18

導入の向き不向き

強い点/限界

git-dupeは“セキュア保存”より“混ぜない・同期する”に最適化されています。機密性は運用や別暗号化で補います。

強み（実務）
エージェント運用でPR混入を大幅に抑え、サイクルを安定
限界（セキュリティ）
暗号化しないため、秘密情報は別途対策が必須
限界（運用）
パス追加の衝突・detach条件・切り分け難度に注意
相性
“エージェントキットを各リポジトリに自動反映”したい運用
結論：誤混入事故の削減と同期に価値。秘密管理は別レイヤー。
CLOSING
15 / 18

今日の要点

結論/ Takeaway

git-dupeは、プロジェクト側からは見えない隠しパス（hidden path）で公開混入を防ぎ、あなた専用のdupe履歴を同期します。

できること
自分用ファイルを別履歴でコミット/同期
できないこと
暗号化による秘密保護（Nothing is encrypted）
運用のコツ
同期先（自分リモート）と衝突ルールを決める
