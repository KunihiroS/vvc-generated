知られにくい連鎖
MCP 信頼ギャップ
エージェント間通信（MCP）を起点に、悪性の指示が「委任（delegation）」として次のエージェントへ渡り、機密漏えい・不正操作につながり得ます。
核心
LLMを騙すより「特定エージェント」を狙う
要点
信頼境界がつながるほど被害が増幅
PROBLEM
03 / 16
守りたい境界
Trust が配線される
攻撃の焦点は「モデル」ではなく、「誰が誰を信頼して、どんな情報が渡るか」という設計です。連携を増やすほど、その配線が攻撃面になり得ます。
誤解①
内部だから安全（internal trust）
誤解②
LLMガードレールだけで完結する
現実
委任チェーン（delegation chain）で拡散
METAPHOR
04 / 16
合図が伝播する
悪性指示 は「委任」で運ばれる
前段のエージェントで混入した指示が、後段では「正規の依頼」と見なされて実行される—これが連鎖のイメージです。
前段（入口）
翻訳・分析など特定役割のエージェントに悪性入力が刺さる
後段（執行）
次のエージェントへ委任タスクとして引き継がれ、検証が薄いまま動く
委任（delegation）
引き継ぎ（handoff）
信頼境界（trust boundary）
ARCHITECTURE
05 / 16
MCPの役割
Model Context Protocol （MCP）
MCPはエージェント間の文脈（context）や指示を共通手段でやり取りします。危険は、認可・検証が不足すると「渡った情報がそのまま正規扱い」になる点です。
特徴
MCPサーバがエージェントごとの認証情報を保持
設計の落とし穴
「内部同士を広く信頼」して委任連鎖を強くする
重要：LLM自体のプロンプト注入対策だけでは、役割エージェントの入出力・委任の検証が残ります。
（日本語補助：信頼ギャップ＝trust gap）
DISTINCTION
06 / 16
何が違う？
直接注入 から「間接連鎖」へ
記事の主張は、LLMに直接刺すというより「特定エージェントの役割・ガードレール・委任処理」を狙い、連携経由で増幅する点にあります。
従来（想定しがち）
LLMのプロンプトを壊す / ガードを回す
今回の焦点
特定役割のエージェントを騙して引き継がせる
増幅要因
「後段は前段を信頼」し、疑わず実行
EVIDENCE
07 / 16
複数組織に波及
protocol pivoting （踏み台移行）
最初はMCPで成立しても、エージェントが別の通信方式へ切り替えた先で能力（権限・到達先）が拡大し得ます。これが「多段階の連鎖」になります。
初期
MCP経由で侵害（混入・委任開始）
転換点
A2A（Agent-to-Agent）等へ切替して権限拡大
記事では少なくとも5組織にまたがる同種の問題が報告されたとされ、MCPが普及に比べて十分硬化される前だった点が警鐘です。
（日本語補助：硬化＝harden）
EVIDENCE
08 / 16
根は古典的
SSRF/ インジェクション等の増幅
構成要素はSSRFやプロンプトインジェクションなど古典的なバグです。しかし連携があると、攻撃が「現実の手順」として成立しやすくなります。
例
HTTPクライアント挙動（リダイレクト等）
狙い
内部端点へ誘導（到達先の回避）
要点
古い対策が「実運用で再確認」される
リダイレクト
IP検証
allowlist/blocklist
COMPARISON
09 / 16
入口より後段
検知は 連鎖全体で
危険は「入口（MCP）」だけで完結しません。後段での委任・実行・プロトコル切替まで含めて脅威モデルと監視を組む必要があります。
よくある対策
MCP入力のフィルタ、LLMガードレール
不足しがち
委任の検証、到達先検査、プロトコル横断の権限
教訓：ゼロトラスト（Zero Trust）の観点で、エージェント間の入力を「見知らぬ入力」と同等に扱う。
（日本語補助：ゼロトラスト＝Zero Trust）
PROCESS
10 / 16
点検の順序
実装を 分解して確認
記事は「危険になり得る構造」を示します。結論は一律ではないため、自組織の通信経路・権限モデル・ガードレール状況を具体に点検します。
i
エージェントごとの入出力（I/O）境界
ii
委任（handoff）時の検証と承認（approval）
iii
プロトコル横断（MCP→A2A等）の権限・到達先

11 / 16
FAQの核心
protocol pivoting と整理
protocol pivotingは「最初の突破口があるプロトコル（例：MCP）で始まり、その後別プロトコルへ切替して能力到達する」連鎖型攻撃です。
Q1
protocol pivoting＝段階的に別能力へ到達（踏み台移行）
Q2
単純なLLM注入と違い、「役割・委任・ガードレール」を狙って増幅する点が特徴
委任連鎖
検証不足
能力到達
ENUMERATION
12 / 16
優先すべき対策
ゼロトラスト を連携へ
対策は「LLM単体」ではなく、「入力を未信頼扱い」「SSRF相当の挙動を防ぐ」「プロトコル横断で承認を設計」の3点が中心になります。
i
エージェント間入力を未信頼として扱う（ゼロトラスト）
ii
IP検証・リダイレクト制御・allowlist/blocklistで到達先を堅牢化
iii
監査ログ/異常検知、プロトコル横断の権限・承認を設計
CLOSING
13 / 16
最終メッセージ
結論 連鎖は設計で止める
MCPのような連携は、正しく硬化されていないと「信頼の配線」が悪性指示を拡散します。だからこそ、境界（trust boundary）と委任（delegation）を中心に再設計し、プロトコル横断まで点検してください。
