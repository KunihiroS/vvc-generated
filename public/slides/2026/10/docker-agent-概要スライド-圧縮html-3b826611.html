01 / 13
Dockerのエージェント運用
Docker Agent
docker-agentは、YAMLでAIエージェントを定義して実行・共有できるDocker CLIプラグイン／ランタイムです。
「作る→動かす→配る」までを、Dockerの配布思想に寄せて整理しています。
Problem
02 / 13
なぜ今必要？
“動く”までが遠い
LLMは試せても、ツール実行・複数手順・データ接続・再利用が揃うまでが大変です。
docker-agentは、その“運用の壁”を宣言的な設定と拡張で埋めます。
課題
コード実装が増える／再現性が落ちる／環境がバラける
狙い
設定（YAML）＋ツール連携で、現実的なエージェントを素早く立ち上げる
Architecture
03 / 13
宣言的に定義
YAML agents
エージェントはYAMLで定義し、モデル、説明、instruction、toolsetsをまとめて扱います。
レビュー・バージョン管理・共有がしやすく、再現性を上げる設計です。
例の構造
agents: root: のように、役割と構成を階層化
運用の利点
Infrastructure as Code（IaC）的に、設定を“資産化”できる
Metaphor
04 / 13
役割分担で前進
マルチエージェント
専門化した複数エージェントが自動で委譲し、調査→計画→実行→検証のような複合タスクを進めます。
単一指示だけでは難しい段取りを、チームで分解します。
委譲
rootが方針→fixerが実装、など役割で進行
改善
失敗箇所の切り分けがしやすくなる
目的
複合タスクを段階的に解く基盤
Architecture
05 / 13
ツール接続の自由度
MCPで拡張
MCP（Model Context Protocol）サーバーをローカル／リモート／Dockerベースで追加でき、参照・実行できるツール範囲が広がります。
結果として、業務システムや社内データへ橋渡しできます。
取り込み
検索、DB操作、社内API、自動化などへつなぐ
日本語補助
MCP：モデル文脈プロトコル（ツール連携の共通言語）
Evidence
06 / 13
RAGで根拠を作る
検索×推論
RAGはBM25、埋め込み、ハイブリッド、再ランキングなど複数方式が提示されています。
さらにthink/todo/memoryのような推論補助ツールも組み込みで示されています。
RAG方式（例）
BM25 / 埋め込み / ハイブリッド / 再ランキング
日本語補助
RAG：検索拡張生成（Retrieval-Augmented Generation）
※「常に必須」とは書かれておらず、検索が効くデータ（社内文書・最新情報・根拠が必要な資料）で効果が出やすい、という読み方になります。

複数LLM対応

Process
08 / 13
作って、詰めて、配る
OCI配布
エージェントをOCIレジストリへPushし、どこでもpullして実行できます。
Dockerの強み（配布・標準化・再利用）を、エージェントにも持ち込む発想です。
流れ
Push → Pull → 実行（配布の再現性を確保）
運用効果
チーム展開・バージョン管理・ロールバック検討に寄与
※ただし、依存ツールやMCP接続の運用設計（権限・設定・互換性）は追加検討が必要になります。
Distinction
09 / 13
導入前の論点
安全×品質×コスト
README相当の情報だけでは、権限モデル・監査ログ・ツール実行の安全制約・評価手順が不足しがちです。
魅力は見えても、“使えるか”は追加資料で確認が必要です。
Security（例）
ツール権限／MCP通信／機密情報／ログ・テレメトリ
Quality（例）
自動テスト、回帰評価、失敗分類の枠組み
Operational（例）
コスト・レイテンシ、依存のバージョン管理とリカバリ
