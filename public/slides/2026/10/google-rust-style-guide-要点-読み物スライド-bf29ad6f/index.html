APIの強さ

ライブラリと アプリ

API設計のルールは、ライブラリは厳格（一般化・破壊耐性）、アプリは単純（局所最適・抽象化しすぎない）という“適用の強度”を分けます。 同じコードでも、利用者と寿命が違うから判断基準も変える、という発想です。 契約 API contract（API契約）
Library（ライブラリ）
より一般的に使われる前提で、壊れにくさ・汎用性を優先
App（アプリ）
特定用途向けに、読みやすさと直接性を優先

Option / Result / panic

エラーはOption/Result/panicのどれを使うかを“契約の意味”として選びます。 呼び出し側が期待する挙動を揃えることで、例外的な取り扱いの揺れを減らします（エラー設計）。 panic 異常停止（異常）

何が“強い”のか

ルールの目的別

重要なのは、ルールが“好み”ではなく目的（可読性・自動化・LSC耐性・契約明確化）に結び付いていることです。 そのため、状況に合わない例外が必要なら、意図に立ち返って判断できます（適用判断）。 意図 Why（なぜ）
可読性・保守性
読み追いを容易にする（import粒度、型で意味付け）
LSC・レビュー
変更の影響範囲とレビュー摩擦を減らす（glob回避等）

強みと限界

意図はある

強みは、判断の理由（LSC耐性・レビュー摩擦・契約の明確化）が相対的に説明されている点です。 一方で、Chromiumでasync/.awaitを避ける技術理由などは抜粋だけでは不足しがちで、盲目的適用は危険です（例外判断）。 注意 盲信しない（注意）
強み
“なぜ必要か”が見えやすい
限界
抜粋では背景が足りない論点がある
