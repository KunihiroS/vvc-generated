Plurnk
02 / 17
Perpetual Context
探索する
LLMクライアント
Plurnk（@plurnk/plurnk）は、モデルが“短いプログラム”を書き実行結果をジャーナルし、 必要な文脈をアドレス可能なメモリとして使い回すCLI/TUIです。
Problem
03 / 17
会話は続かない
Compaction だけでは
従来は会話履歴を圧縮して都度投入しますが、長期の調査・変更・検証では 「必要な根拠」が追いにくく文脈が途切れがちです。
起きること
重要な観測・判断が“要約の外”へ出る
困る理由
なぜそうしたか（根拠）を後から追えない
Core Idea
04 / 17
記憶を部品化
Addressable Memory
会話履歴の圧縮ではなく、観測・プログラム・推論・記録を“アドレス（参照単位）”として保持し、 必要な形で読み返し／取捨選択できます。
入力
観測（リポジトリ探索結果等）
運用
ジャーナル（実行結果の記録）
参照
必要部分だけ再利用（キュレーション）
Virtual Machine
05 / 17
毎ターン実行
短い プログラム
各ターン、モデルが短いプログラムを書き、実行側（仮想マシン）が結果をジャーナルします。 次の判断は、そのジャーナルを材料に進みます。
モデル
“次の一手”をコードとして生成
実行側
結果をジャーナル化して保存
Repo as Space
06 / 17
リポジトリ探索
アドレス空間
リポジトリ全体を“探索・編集可能なアドレス空間”として扱い、 regex／XPath／JSONPath／シンボルなど多様な検索手段を統合します。
柔軟検索
regex, XPath, JSONPath
構造理解
構文木・シンボル情報も参照
向く作業
テスト/ログ文脈整理、調査と検証
Separation
07 / 17
クライアント分離
CLI/TUI × service
Plurnkはクライアント（CLI/TUI）とサービス（plurnk-service）を分離できます。 個人利用でも、永続的な共有環境でも運用形態を変えられます。
ローカル
クライアント側で閉じた利用（プライベート起動）
共有
daemon/databaseへ保持（長期プロジェクト向き）
TUI vs CLI
08 / 17
使い分け
対話・出力
TUIはモデル選択や委譲、ツール管理を対話的に行い、CLIはパイプライン連携や構造化出力を重視します。
TUI
/models, /model でモデル選択、子モデルへの委譲、ツール管理
CLI
--jsonで構造化ドキュメント（回答・トレース・診断等）を返す
Workflow
09 / 17
循環モデル
探す→実行→学ぶ
次のループが運用の基本です：探索で得た情報をアドレスにし、短いプログラムを実行して結果をジャーナル化し、 その記録を次の判断に読み込みます。
i 探索
検索/切り取り/構造解析で関連部分を見つける
ii 実行
モデルが短いプログラムを生成し仮想マシンで動かす
iii 学ぶ
ジャーナルを読んで次の一手を更新する
Extensibility
10 / 17
後から組む
MCP / Skills
拡張はMCP（外部ツール連携）や Agent Skills（再利用可能な指示）で進められます。 単体エージェントではなく、作業環境全体を段階的に組み上げる前提です。
MCP
ツールをモジュール化し、エージェントが通信して利用
Agent Skills
手順や指示を資産化して再利用
Useful
11 / 17
--json / YOLO
運用の要点
--jsonは回答に加えて操作トレースや診断、使用情報を構造化して返し、パイプライン処理に向きます。 また PLURNK_CLIENT_YOLO=1 は自動受理の方針に関わり、レビュー方針の確認が重要です。
--json
回答 + 操作トレース + 診断 + 使用情報
YOLO
自動受理のデフォルト方針（0/?でレビュー）
鍵
APIキーはバックエンドへ（例：DEEPSEEK_API_KEY）
Security
12 / 17
境界を確認
/share 注意
/share はアンレダクテッド（未マスク）の記録を書き出す旨が強調されています。 機密情報を含みうるため、情報分類とガードレールの設計が前提になります。
危険になり得る
未マスクの共有記録（/share）
確認すべき
能力制限ポリシー、保持/廃棄ルール、脅威と対策（SECURITY等）
Takeaway
13 / 17
結論
開発エージェント基盤
Plurnkは「Perpetual Context」「Addressable Memory」「ジャーナリング」により、 長期のコード探索・編集を“根拠付き”で回しやすくします。 ただし安全運用には、SECURITYや設定カタログで境界と保持方針を確認する必要があります。
強み
文脈の参照性・追跡性
実装要点
短いプログラム + ジャーナル循環
導入前
能力制限・共有・保持の確認
