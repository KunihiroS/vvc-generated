03 / 17
単価↓でも請求↑の謎
Jevons

トークン単価が下がっても、実行回数・エージェント数・試行回数・自動化範囲が増えるため総支出が増えます。これが Jevonsのパラドックス（Jevの逆説）です。

Why（構造）
“できること”が増え、運用が拡大する
Result（結果）
単価低下の効果が相殺され、支出が跳ねる

5レバー全体像
The 5 Levers

コストは「モデル選択」だけでなく「無駄実行」「起動方式」「バッチ運用」「コンテキスト量」の合成で決まります。次の5つを組み合わせて効かせます。

i. Model / ルーティング
高価モデルを“必要な箇所だけ”に限定
ii. No-op / 実行停止
やることがない時は早期終了
iii. Trigger / 起動設計
ポーリング→トリガーへ
iv. Batch / バッチ運用
低コスト＋検証（サンプリング）前提
v. Context / 入力削減
必要十分だけを高価モデルへ
Plus / 置換
会話要約は“ツール化”も検討
ENUMERATION
06 / 17
まず“配分”を変える
i. モデル・ルーティング

すべてを最上位モデルに固定せず、抽出・分類・整形は下位モデルへ移します。判断・推論が必要な部分だけ高価モデルを使います。

Move / 移す
機械的タスク：分類 / 抽出 / 整形
Keep / 残す
判断タスク：推論 / 例外処理
品質低下を避けるため、実タスクで検証し「当日中ロールバック」できる体制にします。
ENUMERATION
07 / 17
“やらない”を課金ゼロに
ii. 無駄な実行（no-op exit）

高価な処理に入る前に「今回処理すべき仕事があるか」を確認し、なければ終了します。これが no-op exit です。

Cron の罠
定期実行で“やることなし”が課金だけ発生
Fix / 対策
役に立つ条件が揃うまでモデル呼び出しを抑止
休日・頻度・待ち時間など「問い合わせ結果の到達先」と整合しない実行も見直します。
ENUMERATION
08 / 17
待機の課金を止める
iii. ポーリング→トリガー

ポーリングは「新しい仕事ありますか？」を繰り返すたびにコストが発生します。トリガーは出来事が起きた時だけ起動し、待機中の無駄を削れます。

Polling（待つ）
一定間隔で確認：無駄が積み上がる
Trigger（起きたら）
イベント起動：必要な時だけ動く
ただしイベント源が購読できない場合などは例外で、万能策ではありません。
ENUMERATION
09 / 17
大量処理は“検証前提”
iv. バッチ運用（サンプリング）

大量の分類・清掃などは、低コストモデル＋検証（サンプリング）前提で運用します。すべてを毎回“高価に正確化”しないのがポイントです。

1) Run
まず低コストで処理
2) Sample
一部を高品質で検証
3) Gate
合格ルールで次へ
ENUMERATION
10 / 17
入力を削って失敗を減らす
v. コンテキスト削減

不要な情報を渡さず、必要十分な文脈だけを高価モデルに渡します。削りすぎは失敗の原因になるため“目的に合う削り方”が必要です。

Remove / 減らす
過去ログ全体・不要な読み取り範囲・再利用しない出力
Keep / 残す
タスク完遂に必要な根拠（十分な文脈）
「読み取り範囲を広げるほど失敗する」ような逆効果も起こり得ます。
COMPARISON
11 / 17
安いモデル一発は危険
Don’t Flip Blindly

「安いモデルに全部置換」では、判断・推論が必要な箇所で品質低下が起きます。品質比較とロールバックを前提に、タスク別に置き換えます。

Blind Swap / 置換だけ
品質が崩れる可能性（評価なしで見えない）
Routed Swap / ルーティング
機械的タスクは安く、判断は高く
変更点は小さく、検証は実タスクで、失敗時は即戻す方針が重要です。
PROCESS
12 / 17
回し続ける監視設計
月次で締めて学ぶ

効率化すると使用量が増えて再び膨らむことがあります。月次で「1回あたりコスト」「エージェントあたりコスト」「週次の増減」「無駄実行」「リトライ積み上げ」を見ます。

Watch / 観測
1回あたり・エージェントあたり・週次増減
Fix / 改善
無駄実行とリトライの積み上げを先に潰す
次に、品質評価（A/B）とロールバック体制がある前提で、レバーを段階適用します。
CLOSING
13 / 17
品質を守って削る
まとめ

コスト削減は「単価」ではなく「実行の無駄」「起動方式」「入力（コンテキスト）」「タスク別モデル」の最適化です。Jevonsの反作用を前提に、監視し続けます。
