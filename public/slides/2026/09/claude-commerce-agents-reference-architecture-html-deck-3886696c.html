Commerceの安全設計
Claude Commerce
エージェント参照設計
AnthropicのClaudeで「ショッピング／マーチャント」業務を扱うAIエージェントを、ホスト承認とゲートで安全に運用するためのリファレンスを整理します。
Shopping agent
検索・比較・カート・注文方針回答
ショッピング（探索〜準備）担当
Merchant agent
掲載・在庫・価格／販促・受注アラート
マーチャント（運用〜変更）担当
※モデルが直接「注文／決済／ライブ更新」をしない前提（ホスト最終承認）を核にします。
Problem
02 / 15
誤発注は致命傷
誤実行の 事故
をどう防ぐか
商取引AIでは、誤理解がそのまま「誤発注・誤課金・誤掲載」に直結しやすいのが最大論点です。
Risk
誤発注（実行）
誤った注文確定
Risk
誤課金（決済）
支払いの誤実行
Risk
誤掲載（変更）
在庫・価格・販促の誤反映
対策の基本は「AIは提案し、実行はホスト／人が最終承認する」構造です。
Metaphor
03 / 15
AIは企画、実行は承認者
ガードレール 前提
の設計
この参照設計は、チェックアウトや掲載／在庫変更を「ホストが最終的に確定」する流れに寄せ、ゲートを実行経路に組み込みます。
Checkout
AIは表示まで（カート完了はホスト）
checkout（表示）＝ホスト側ハンドオフ
Merchant write
ステージング＋人の承認ゲート
commit（確定）＝承認後のみ
提案（plan）と実行（commit）を分離することで、誤動作の被害範囲を小さくします。
Architecture
04 / 15
責務分離が鍵
2種の エージェント
を分ける
ショッピングとマーチャントを同一思想で構築しつつ、責務と権限の境界を分離することで、危険操作を設計上コントロールしやすくします。
Shopping
検索・比較・プランニング・カート投入
customer context（顧客の意図）を扱う
Merchant
掲載維持・在庫/価格・販促提案/作成・アラート
ops changes（業務変更）を扱う
同じ「プロンプト・スキル・ツール契約・ゲート」を共有し、権限だけを最適化します。
Architecture
05 / 15
核＝プロンプト＋契約＋ゲート
共通の 安全契約
を使い回す
実行方式（Messages API／SDK／Managed Agents）を変えても、プロンプト、スキル、ツール契約、ゲートという設計要素は共通に保ちます。
Prompt & Skills
振る舞い・判断・手順の固定
モデル出力の期待形式を揃える
Tool contract & Gates
実行前に条件・上限・検証を強制
fencing（隔離）／provenance gate（出所）など
「安全策がある」を超えて「全パスで保持される」ことが重要です。
Security
06 / 15
ゲートは“実行前検問”
Fencing / Provenance
/上限
ゲートとは、ツール呼び出し内で発火し、誤動作やコンプライアンス逸脱を抑えるための検証・制限の仕組みです。
Fencing
隔離して許可された範囲だけ実行
境界（何を触れるか）
Provenance gate
情報の出所を検証して採用
根拠（どこから来たか）
Caps & checks
上限（回数/量/金額）＋メモリ検証
暴走（過大実行）を抑制
さらに商務では「承認ゲート」が要所になります（人が最終確定）。
Evidence
07 / 15
“実注文なし”が前提
AIは 確定しない
README上の注記では、checkoutはホストが完了するための表示に留まり、決済やライブな出品変更を行いません。
Checkout
ホスト完了のための表示（表示止まり）
実行責任：ホスト側
Merchant writes
ステージング（下書き）→人の承認ゲート
確定責任：承認者
この分離が、誤発注・誤課金・誤掲載の“直接被害”を抑える設計理由です。

1. Auth / Identity

09 / 15
同じ設計、複数の動作方式
Messages / SDK / Managed
の選択
実行方式は(1) Messages API、(2) Claude Agent SDK、(3) Managed Agentsの3通りがあり、どれでも同じ安全設計要素（契約・ゲート）を核にできます。
Messages API
ホストが制御しやすい実装
messages（会話）
Claude Agent SDK
エージェント機能をSDKに寄せる
agent（実行単位）
Managed Agents
ホストされたエージェントを活用
managed（運用委任）
“移行しやすい”ことが企業採用の実務価値になります。
Comparison
10 / 15
Shopping vs Merchant
違いは 権限境界
同じ安全思想でも、Shoppingは顧客体験（提案・準備）寄り、Merchantは在庫・価格・掲載など業務変更寄りで、許可範囲を厳密に分けます。
Shopping
情報整理→方針回答→カート投入（提案）
approveが必要な“確定”はホストへ
Merchant
掲載維持・在庫/価格・販促の作成（下書き）
ステージング→承認ゲート
責務分離は「誤った権限でライブ変更が起きる」確率を下げます。
Caution
11 / 15
安全でも“ゼロ事故”ではない
安全の 頑健性を検証へ
安全設計があっても、提案品質・承認者の見落とし・ログ欠損・例外対応などで失敗モードは残り得ます。
Failure mode
誤提案→承認に間に合わない
品質×運用のズレ
Failure mode
承認疲れ（human bottleneck）
承認者負荷
Failure mode
監査ログの欠落
audit（監査）要件不足
導入判断では、docs（例：safety.md）とテスト／検証（scripts/check.py等）を確認してください。
