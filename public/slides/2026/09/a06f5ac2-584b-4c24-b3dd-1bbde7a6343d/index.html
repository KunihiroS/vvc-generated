評価は 分解 せよ

Why it’s hard
03 / 16
局所 vs 大域

同じ「分類」でも別物

研究対象は、LLM/検索・クロール向けの「ページ分類」や「サイト構造推定」など複数タスク。
しかし難しさと失敗コストは局所（ページ単位）と大域（サイト全体の意思決定）で変わる。
page classification
ページの情報タイプを判定（相対的に局所）。
crawl-root selection
URL/ナビから「最初にクロールする範囲」を決める（大域）。
実務の焦点
後工程が連鎖的に崩れるのは大域ミス。
局所タスクが強いモデルは、大域をそのまま期待すると外れる。
Insight
04 / 16
観察者と司令官

Jev は 観察者寄り

Jev はページの意味付け（観察）には強いが、サイト全体の計画（司令）には向きにくい可能性がある。
強い側（示唆）
単一ページのタグ付け：85% vs 56%。
弱い側（示唆）
crawl-root selection：27% vs 93%。
この「性格」は性能差の方向性から読み取れる。
Pipeline view
05 / 16
Context7 の工程

どこで使うかが 勝負

Context7 のような解析パイプラインでは、URL/ナビからの意思決定と、ページの意味判定を分けて扱う設計が多い。
工程A
crawl-root selection（最初にクロールする起点を決める）。
工程B
page classification（各ページのタグ/タイプを付与）。
工程C
query relevance / duplicate detection / website suitability 等（分類・妥当性）。
工程ごとに「採用するモデル」が変わるのが自然。

5つの分類タスク

勝敗は 入れ替わる

5つの分類タスクの内訳は、3つが引き分け（tie）、1つが Jev 勝ち、1つが Jev 負け。
Jev が勝ち
page classification：85% vs 56%
Jev が負け
crawl-root selection：27% vs 93%
tie i
query relevance
tie ii
duplicate detection
tie iii
website suitability
万能モデルではなく、得意領域がタスク分布で決まる。
Evidence
07 / 16
数字が示す差

精度の振れ幅が 大きい

page classification は大幅に優位。一方で crawl-root selection は大きく劣後しており、単純な一括評価は危険。
page classification（勝ち）
Jev 85% / 比較 56%（差：+29pt）
crawl-root selection（負け）
Jev 27% / 比較 93%（差：-66pt）
含意：失敗コストが大きい大域工程ほど、Jev の配置には注意が必要。
数値は提示された実験要約に基づく。
Efficiency
08 / 16
速い・安い

性能だけじゃない コスト

実効面では Jev が 10〜170倍高速、3〜20倍安価という主張がある。これは導入判断の大きな根拠になり得る。
高速（latency）
10〜170倍 faster（条件依存の可能性あり）
安価（cost）
3〜20倍 cheaper（バッチ/入力長/手順で変化）
運用の見方
一部タスクで精度が劣っても、全体コスト最適で採用価値が残る。
検証の必要
再現性（同条件での測定）と、総工程でのコスト見積りが必要。
「条件依存」を前提に、導入環境で測るのが安全。
What ties mean
09 / 16
tie は重要

万能ではない 証拠

query relevance、duplicate detection、website suitability は引き分け。Jev が全分類を一気に置き換えるタイプではない。
query relevance（tie）
検索意図との関連性。
duplicate detection（tie）
重複ページの検出。
website suitability（tie）
サイトとしての適合性（技術ドキュメント価値など）。
運用：主要KPI（どの失敗が致命か）に対して、改善が出る工程を選ぶ。
tie が多いほど「導入効果の上限」を疑って設計する。
How to decide
10 / 16
工程割り当て

Jev を置く 場所を決める

page classification が強いならラベリング工程で活用し、crawl-root selection が弱いなら初期クロール意思決定は別手法と併用する。
採用推奨（例）
ページごとのタグ付け / 情報タイプ推定（Jev を主担当に）。
併用推奨（例）
crawl-root selection はルールベース/別モデル/ハイブリッドで補完。
失敗防止
大域工程での誤りは連鎖するため、Jev に「低い工程」ほど置かない。
評価設計
部分導入（ラベルのみ等）→主要KPIで効果検証。
「一括置換」ではなく「工程分業」が合理的。
Skepticism
11 / 16
再現性の壁

条件が読めないと 決められない

提示情報だけでは、データ分布・サンプリング・再現性・チューニング有無・計測定義が十分に読み取れない。
精度差の理由
crawl-root selection の失敗がデータ要因かモデル要因かが不明。
一般化の不安
5タスクだけの比較では網羅性が不足する可能性。
速度/安さ
「10〜170倍」「3〜20倍」は比較条件（入力長・推論手順等）で変わり得る。
次の検証
失敗の一般性（どんなサイトで壊れるか）を追加評価。
数字を意思決定に使うなら、条件の確認が必須。
Governance
12 / 16
技術の外側

TOS は 後から効く

コメント欄では「利用規約（TOS）に触れる可能性」が指摘されている。性能比較とは別に、クローリングやデータ利用の適法性が導入可否を左右する。
リスク
契約・法令・保存/再配布方針の不整合で、技術的に正しくても実装が止まる。
必要作業
規約・法務順守前提の監査可能なデータ取得・評価手順を整備。
結論：性能だけで採用すると失敗する可能性がある。
合法性は「オプション」ではなく意思決定条件。
Takeaway
13 / 16
最終判断

Jev は 分業で活きる

Jev は page classification で大きく勝つが、crawl-root selection では大きく負ける。運用は「得意工程に配置」「大域工程は別で補完」が合理的。
採用戦略（要点）
ラベリング中心に使い、初期クロール計画は別手法とハイブリッド。
意思決定の条件
速度/安さは条件依存。再現性とTOS監査を先に固める。
