Slack 起点の自動化デモ
Crab Bot
と OpenAPPA
Slackのバグ報告から、隔離環境で調査・修正し、レビューを経てPR作成まで進める仕組みと、情報漏えいを抑える実行時ガードレールを整理します。
Bilingual / バイリンガル：Slack → Agent → PR（自動化）/ Guardrails（安全制御）
Problem
03 / 16
便利さの裏にある穴
漏えい リスク
内部データを“読める”だけでなく、“出せる”経路があり、さらに無人実行になっていると、プロンプト禁止だけでは情報漏えいを十分に抑止できません。
危険要素 i
内部データの閲覧権（Slack / クラスタ / ログなど）
危険要素 ii
公開先へ出力できる（例：公開GitHub issue / 外部通信）
危険要素 iii
無人で実行（LLMがツール呼び出しまで進める）
結論
“モデルの従順”ではなく“実行時の政策”が必要
Architecture
04 / 16
閉じたループ
Slack 起点
Slackの投稿をコントローラが取り込み、隔離された開発環境で情報取得→修正→デモ生成→PR提示までを一連の流れとして回します。
i. Ingest
Slackスレッドを取り込み（指示・ログ・文脈）
ii. Execute
隔離VMで環境構築（リポ取得 / Tilt / headless Chromium）
iii. Ship
PRを作成し、レビューを経てマージ手前まで
人の操作は「バグ記述」「動画を見る」「Ship it」「Promote」へ圧縮（in the loop / 二段階）
Evidence
05 / 16
UI不具合を修正
デモ 例
コンテキスト圧縮中に入力できないというUI不具合を、エージェントが動作確認デモ付きで修正し、PRとして提示しました。
入力
Slackのバグ報告（何が起きるか）
出力
修正PR + 動作確認デモ動画（再現性の補助）
価値
調査コストを「チケット作成・環境構築」から切り離す
適用範囲
“少しのバグ”で自己完結しているほど向く
Distinction
06 / 16
読む vs 出す
分離 が鍵
内部データを読むこと自体は必要ですが、理解した内容を外部へ“持ち出す”ルートを制度として塞ぐ必要があります。
安全寄り
読む（調査・修正に必要な材料を得る）
危険寄り
出す（公開先や外部通信に直接出力する）
実装思想
プロンプトより「実行前にブロック」が効く
狙い
“内部化→公開”の連鎖を断つ
Architecture
07 / 16
実行時政策エンジン
OpenAPPA
OpenAPPAは、内部ツールから何を読んだかを追跡し、その“理解の状態”に応じて公開先へのツール呼び出しを事前ブロックします。
i. Track
内部ツールの読取・内部化を追跡
ii. Decide
公開先へ出すべきか判定（政策適用）
iii. Block
公開系ツール呼び出しを直接止める
Process
08 / 16
抜け道を“塞ぐ手順”
多層 検知
MCPゲートウェイ／MCPツール／CLI／クラスタ参照／クラウドAPI判定／LLM分類など多層で検知し、検知回避への耐性を狙います。
対象
MCPツールとCLIツールをカバー
判定軸
参照先（クラウド/ローカル）、読取に該当するか
補助
手動注釈のない呼び出しをLLM分類で補助（二段階防御）
狙い
公開へ“勝手に転載”するルートを制度的に遮断
Comparison
09 / 16
プロンプト依存の限界
政策 依存
“禁止しろ”はモデルの気分や挙動に依存しがちです。そこで、ツール呼び出しレベルで実行時に政策を適用します。
プロンプト
期待：従うだろう / しかし挙動は揺れる
実行時政策
実際：出力先のツール呼び出しを事前にブロック
効果
内部化→公開の“現実的ルート”を塞ぐ
要点
安全は仕様（policy）で担保する
Fit
10 / 16
向き・不向き
適用 条件
定型で自己完結しやすい“少しのバグ修正”は自動化向き。一方で難問は無人ではなく人のループ前提に寄せます。
向いている
文脈が揃う / 既存範囲で修正可能 / 再現・検証しやすい
向いていない
味・アーキテクチャ判断 / 高度な推論が必要
方針
“in the loop”を維持（独立実行を広げない）
ガバナンス
private mirror / Promote は人が判断
Opinion
11 / 16
説得力の核心
実装 で語る
強みは“夢の自動化”ではなく、実務で問題になる情報漏えいを、実装レベルの制御（OpenAPPA）として扱っている点です。
良い点
読み取った事実→出力先を実行時に遮断する設計
良い点
依頼者ごとのアクセス範囲や、公開は二段階フローで統制
良い点
小さなバグは費用対効果が高いという適用戦略が明確
含意
安全は“運用と政策”で回す（policy engine 依存）
Limits
12 / 16
過信は禁物
検証 が要る
OpenAPPAが完全に抜け道を塞げるかは別問題で、判定網羅性・誤判定・検知回避への評価指標やテスト範囲が読み手には不足しています。
未提示の論点
攻撃シナリオ、第三者評価、再現可能なセキュリティ検証
懸念
CLI/LLM分類の誤判定、ルールの外側を突く可能性
別経路
ログ、動画/スクリーンショットのメタデータ、PR本文以外
結論
“方向性の良さ”を評価しつつ、評価・監視で補う
Closing
13 / 16
持ち帰る要点
安全 自動化
小さなバグ修正は自動化しやすい。だが内部データを扱うほど、出力先を実行時に政策で制御するガードレールが不可欠です。
Key idea
読取（Track）→ 公開ブロック（Block）を“制度として”つなぐ
Operational
private mirror + Promote 人承認で無人暴走を抑える
Next check
評価（どれだけの脅威に、どれだけの精度で対処）と監視手順
