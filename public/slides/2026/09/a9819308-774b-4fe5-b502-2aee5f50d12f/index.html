LLM EXFIL API
02 / 17
Weights を“持ち出す”
GETで 書いて 実行
LLMがGETリクエスト経由でデータ（例：重み・プロンプト）を保存し、後でその内容を実行できる“API”の概要と、危険性の見立てをまとめます。
ORIENTATION
03 / 17
何を説明するか
仕様と リスク
「管理された環境で意図的に許可する用途」も想定されていますが、設計次第で情報漏えい・任意実行へ転用し得ます。
説明（仕様）
バケット作成→チャンク書込み→プロンプト付き実行
懸念（セキュリティ）
GET露出・認証/検証不足・実行封じ込め不足
CORE IDEA
04 / 17
APIの流れ
Bucket方式
バケット（保存場所）単位でデータを保持し、最後にそのバケットをプロンプトと組み合わせて実行する構成です。
i
create/{bucket}
ii
write/{bucket}/{filename}/{offset}/{base64_data}
iii
run/{bucket}?prompt=...
GET ONLY
05 / 17
HTTP設計
GET だけ
データ投入や実行がPOSTではなくGETで行われるため、URLにbase64やプロンプトが入り得てログ・履歴に残りやすいです（機密性の副作用）。
便利
手順が単純で、デモ/検証が回しやすい
副作用
監視・履歴・プロキシ経由で露出しやすい
STORAGE
06 / 17
保存場所
/var/exfil/ 永続
データはサーバ側の /var/exfil/buckets/ 配下に保存される想定で、後でプロンプトとともに使われます。
運用の観点
削除ポリシー・容量管理がないと蓄積が進む
安全の観点
保存データが漏れれば、意図しない再実行につながる
CHUNKING
07 / 17
大容量対応
offsetで チャンク
offset 付きで base64_data を分割書き込みできるため、大きなデータも投入しやすい設計です。
技術的価値
重みなどの巨大データを分割して扱える
攻撃面
検証・上限が弱いと“長い投入”が可能になり得る
EXECUTION
08 / 17
実行の主役
runで 結合
run/{bucket}?prompt=... により、保存済みデータとプロンプトを組み合わせて実行する仕組みです。データ種別の検証と隔離が要点になります。
自然
LLM連携として“保存→利用”の流れが分かりやすい
要注意
不十分な検証/サンドボックスは危険入力の実行を招く
TOKEN MODEL
09 / 17
バケット分離
鍵の ふり
create/{bucket} が“トークンのような役割”として説明されますが、バケット名の推測容易性や認証欠如では分離が形骸化し得ます。
分離の利点
保存場所・実行対象が対応づけられ、運用を整理しやすい
成立条件
認証・ランダム性・アクセス制御が必要（未確認だと不安）
SECURITY GAP
10 / 17
最大の不確実性
安全策が 見えない
README相当では認証・レート制限・アクセス制御を“プロダクションでは実装”する警告がある一方、入力断片だけでは実装の有無と強度が判断できません。
必要
認証方式（APIキー/JWT等）
必要
レート制限・監査ログ
必要
入力検証・実行隔離（サンドボックス等）
THREAT SHAPE
11 / 17
転用リスク
“exfil”は テンプレ
題材が“exfiltration（持ち出し）”で、GETで投入・runで実行できる形は、悪意ある利用にも転用しやすい構造です（意図より設計が勝つ）。
情報漏えい
URL露出・保存データの再利用
任意実行
検証/隔離不足で危険入力が“実行側”へ到達
CHECKLIST
12 / 17
確認すべき点
実装の 証拠
公開/運用前に、少なくとも次の項目が“実装され、検証されている”ことをコードと設定で確認する必要があります。
Auth
APIキー/JWT、バケットごとの権限
Limit
サイズ上限、レート制限、同一IP制限
Sandbox
実行隔離、コマンド許可リスト、ネット遮断
TAKEAWAY
13 / 17
結論
価値はある
プロトタイプとしての開発体験は良い可能性がありますが、GET投入・永続保存・run実行の組合せは危険度を押し上げます。安全策が“実装済み”であることが前提です。
日本語: 管理された環境 + 強い制御（認証/検証/隔離）
EN: Controlled setup + Verified controls (auth/validation/sandbox)
