02 / 17
意思決定を“考えて”強くする
Jeeves / Jev-like + thinking
Jev風の「確率・スコア」を出すモデルに、決める前の thinking フェーズを学習で組み込み、精度と校正を両立しようとする取り組みです。
土台
Qwen3.5-9B（Gated DeltaNet系）
出力
choice / noul / score（Jev互換API）
鍵
拡散ドラフタ（speculative decoding）で高速化
thinkingは遅くなり得るため、max_think / nothink_thresholdで運用調整する前提です。
Problem
03 / 17
確率は欲しいが精度は揺れる
Jev-likeの弱点
Jev-likeは校正された確率・スコアを扱える一方、単純な精度が常に高いとは限りません。その結果、「推論モデルへのフォールバック」などの工夫が現場では必要になります。
できること
選択肢ごとの確率・スコア（校正の学習）
課題
低精度領域が残り得る（確率だけでは救えない）
Core
04 / 17
決める前に“考える”
Jeevesの方針
意思決定直前だけでなく、先に推論チェーンを生成し、その後に各選択肢を評価して確率を計算します。これにより「確率モデルが苦手なケース」を推論で補う狙いです。
  • i
    thinkingチェーン生成（決定根拠を事前に形成）
  • ii
    pointer headで choice / noul / score をスコア化
  • iii
    temperature scaling等で校正された確率へ
Architecture
05 / 17
モデル構造：学習された意思決定
pointer head と確率計算
Qwen3.5-9Bに LoRA と pointer head を追加し、推論チェーンを作った後に選択肢ごとのスコア（確率の根）を計算する構造を採用しています。
学習の追加要素
LoRA / pointer head（Jev-like出力のための頭部）
推論の流れ
thinking生成 → 選択肢評価 → 確率（score）化
“思考→採点”の二段階で、意思決定要件（確率・校正）を維持しつつ改善を狙います。
API
06 / 17
互換API：1リクエストで複数形式
choice / noul / score
Jev互換APIとして、同一の状態 state と複数の質問（例：department: choice、escalate: noul、frustration: score等）を同じリクエストで処理します。運用差し替えを意識した設計です。
choice
選択肢から1つ＋確率
noul
Yes/No判定（例：urgent）に近い形式
score
段階カテゴリ/数値へのスコア・確率
同じ推論基盤で扱えるため、アプリ実装を一本化しやすいのがポイントです。
Learning
07 / 17
学習レシピ：SFT→CISPO→校正
“決める前に考える”を獲得
SFT（教師あり微調整）と CISPO（推論付き強化学習に近い学習方式）で、thinkingを含む挙動を学習します。さらに temperature scaling 等で校正をフィットし、確率出力の質を狙います。
学習フェーズ
SFT → CISPO → temperature fitting
安定化
過学習でヘッドが過度にシャープ化しないよう停止点を工夫
意思決定モデルでは「確率が使い物になるか」が評価の中心です。
Efficiency
08 / 17
thinkingの遅さを削る
拡散ドラフタ（block-4）
通常、thinkingありはレイテンシが増えます。Jeevesは凍結した drafter を別途用意し、block-4 の diffusion drafter で speculative decoding を高速化します。
狙い
“思考あり”でも運用可能な速度へ
根拠（提示情報）
H100で思考あり中央値が数秒レベル、チェーン短縮でさらに短縮
Trade-off
09 / 17
常にthinkingする必要はない
max_think / nothink_threshold
同一チェックポイントでも thinkingなしで一定の精度は得られるため、運用では max_think や nothink_threshold のようなパラメータでレイテンシと精度のトレードオフを調整できます。
thinkingあり
精度向上（ただし遅い可能性）
thinkingなし
速い・一定精度
制御
max_think / nothink_threshold
必要なときだけ“考える”ことで、SLA設計に寄せる思想です。
Evidence
10 / 17
評価：JevBench hardで差
Jeevesは何が良い？
提示情報では、Jeevesは Kev-9B や Jev を上回るスコアを示し、とくに JevBench public の hard ティアで大きな改善が見られるとされています（条件付きの比較）。
改善の方向
thinking前置で意思決定精度が向上
注目ポイント
JevBench hardで相対的に差が大きい
“確率出力のモデルが苦手なケースを推論で補える”可能性が示唆されています。
Distinction
11 / 17
分類器ではない：校正のための学習
Jev-likeの“意味”
Jev-likeの最大の違いは、正解クラスを出すだけでなく、選択肢ごとの確率（やスコア）を校正された形で扱えるよう学習する点です。JevBenchでは精度だけでなく ECE などの校正指標も評価対象になります。
ただの分類
当たり/外れ中心（確率の品質が別問題になりがち）
Jev-like
確率・スコアの校正品質（例：ECE）まで設計
thinkingは精度・校正の両立を狙う“補助輪”として位置付けられます。
Risks
12 / 17
万能ではない：条件差と制約
導入前の注意
比較には条件制約があり（public tiersのみ等）、評価セット差が性能差に影響し得ます。さらに言語整合性リワードが含まれないため、thinkingチェーンの解釈可能性には限界があります。
評価セット
item一致範囲などの制約あり
解釈性
言語整合性リワードなしの可能性
適合性
知識問題ではJevに劣る結果
“意思決定・構造推論で強い”と理解し、知識依存タスクは別設計と組み合わせるのが無難です。
Takeaway
13 / 17
採用判断：どこに効く？
私の結論（運用視点）
Jeevesの強みは、Jev-likeの要件（確率・校正・互換API）を維持しつつ、推論で弱点領域を補う設計にあります。採用するなら「規則構造・対比ポリシー・held-outルール」中心に適用するのが妥当です。
強い点
JevBench hard改善＋拡散ドラフタでレイテンシ現実化＋max_thinkで制御
慎重点
評価条件差／thinkingの解釈性限界／知識問題での劣後
