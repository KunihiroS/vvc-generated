自然言語 × SQL（確率判定）
pg-jev
PostgreSQLに「行ごとの確率評価」を追加し、WHERE / ORDER BY / GROUP BY に“AIの判断”を自然に統合します。 （言語で条件を書くのに、返り値は確率0〜1）
PROBLEM
03 / 16
曖昧さをSQLへ
Why probability?
自然言語の条件は「完全一致」ではなく、どれくらい当てはまるかの曖昧さがあります。 pg-jevはそれをboolean生成ではなく、calibratedな確率としてSQLに返します。
従来（典型）
一致/キーワード
ルール化しづらい条件は性能が頭打ち。
pg-jev（狙い）
行ごとに確率
閾値・ランキング・分類へ接続。
METAPHOR
04 / 16
AI審査員（row judge）
行が 審査 される
SQLが対象の“各行”をAPIへ送り、AIがその行に対する確率（0〜1）や候補を推定します。 その結果がSQLの条件・順位付けに使えます。
入力（SQL）
row + condition（自然言語）
推定（AI API）
prob / choice / score
出力（SQL）
WHERE / ORDER / GROUP
ARCHITECTURE
05 / 16
SQL関数で“判定器”
jev() 系関数
pg-jevは `jev()` / `jev_prob()` / `jev_choice()` / `jev_score()` などで、確率と意思決定をSQL内に配置できます。 生成（テキスト生成）ではなく“確率付き評価”が核です。
判定（二値）
jev(row, condition [, threshold])
WHEREで直接使える（boolean相当）。
確率（0〜1）
jev_prob(row, condition)
閾値でtrue/false、ランキングにも利用。
ENUMERATION
06 / 16
確率で何ができる？
SQL への3つ接続
確率（calibrated）を受けることで、曖昧さを閾値・順位・分類として制御できます。 ※“自然言語条件”はrowごとに評価されます。
i. フィルタ
WHERE / threshold
例：0.5以上を採用（閾値設定）。
ii. ランキング
ORDER BY prob
上位N件を“当たり度”で並べる。
iii. 分類
choice / score
選択肢（カテゴリ）推定でGROUPへ。
EVIDENCE
07 / 16
全スキャンになり得る
Tradeoff: cost
pg-jevは設計上、基本的に“全スキャン”になり得ます。 ただし拒否された行は `jev()` 実行前にスキップでき、WHERE句の書き方でAPIコストを抑えられます。
注意点
API呼び出しが増える
データ量が増えるほど遅延/費用が伸びやすい。
工夫
安価な述語を先に
WHEREで先に落としてから判定する。
PROCESS
08 / 16
バッチ＆並列
20行ずつ評価
1リクエストで行を `jev.batch_size=20` 単位にまとめ、さらに最大 `jev.concurrency` で並列化します。 これにより1行ごとの待ち時間やオーバーヘッドを抑えます。
バッチ
jev.batch_size = 20
トークン/リクエスト効率を改善。
並列
jev.concurrency
API呼び出しの同時処理を制御。

“検索”ではなく“評価”
Index不要・埋め込み不要
pg-jevはインデックス、embeddings、ベクトル列を前提にしません。 その代わり、行をAI APIへ送り“その場で確率評価”します。
不要
検索用インデックス
ベクトルDB/近傍探索の前提がない。
方式
APIで確率
`jev()`呼び出しが評価トリガー。
EVIDENCE
10 / 16
キャッシュはセッション内
2回目が速い
キャッシュはセッション単位で保持され、同一セッション内で再評価が減る設計です。 READMEでは2回目が約50msといった測定が示されています。
初回
APIコスト発生
最初は遅くなるが計算・通信が走る。
2回目
セッション内キャッシュ
同条件・同一行の再計算を回避。
DISTINCTION
11 / 16
LIMITは効くことがある
“必ず速い”ではない
`LIMIT`を付けると早期停止により問い合わせ対象を減らせますが、必ず速くなるわけではありません。 READMEでは読み取りの事前読み取りが止まり得ると説明されています。
期待
上位Nだけ評価
ランキング用途では相性が良い。
不確実性
先に評価される述語
高コスト述語だと効果が薄い可能性。

12 / 16
導入の制約（重要）
Security / Ops
pg-jevは `plpython3u` を用い、untrusted言語として拡張作成はスーパーユーザに限定されます。 また外部APIへ行データを送るため、共有可否（個人情報・機密）を慎重に判断します。
実行環境
plpython3u
ホスティングによっては不可。
権限
untrusted
拡張作成はスーパーユーザ限定。
データ
外部API送信
マスキング/契約確認が必要。
CLOSING
13 / 16
まとめ：確率でSQLを拡張
SQLにAI判断を
pg-jevは、自然言語条件をrowごとに“calibrated確率”へ変換し、フィルタ・ランキング・分類をSQLで完結させます。 一方で全スキャン傾向・APIコスト・データ送信と権限制約があるため、WHERE設計とガバナンスが成否を分けます。
使いどころ
曖昧条件 + 閾値運用
例：0.5近傍の評価を見てチューニング。
導入前チェック
コスト/レイテンシ/安全性
batch・concurrency・キャッシュ・送信データの適合。
