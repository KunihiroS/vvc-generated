“書き込み”を渡す安全設計

MCP 書き込みの安全

LLMにタスク更新などの“書き込みツール”を使わせるときは、LLMの賢さに頼らず、 ツール側で失敗の形を制御する設計が要点です。 （Model Context Protocol / MCP）

PROBLEM
03 / 14

失敗は起きる

“更新”は事故りやすい

読み取り→更新の間に状態が変わる、幻覚で存在しないフィールドを送る、失敗後に同じ呼び出しを繰り返す。 これらは“読み取り専用”では目立たず、“書き込み”で顕在化します。

典型1（更新事故）
lost update：古い状態前提で上書き
典型2（幻覚）
未知フィールド混入で「指定したのに反映されない」
対策は「LLMが守る」ではなく「入口で破綻させない」。
METAPHOR
04 / 14

安全は契約で作る

ツールは契約書

MCPサーバの「schema・instructions・description・検証」を契約として設計し、 失敗したら次の行動が分かる“分類”と“戻り方”を用意します。

schema
型・必須・許容範囲を検証（入口）
instructions
手順/整合（ツール間の順序）
description
副作用や更新の意味を明示
ARCHITECTURE
05 / 14

核：競合制御

expectedUpdatedAt必須

更新ツールの引数に expectedUpdatedAt を必須化し、 読み取り→更新の間の変化があれば“不一致”として失敗させます。HTTPの ETag/If-Match と同型です。

設計方針
古い状態前提の更新を入口で弾く（事故確率を低下）
効果
失敗→取得し直しへ導ける（誤更新を回避）
ENUMERATION
06 / 14

契約の分離

instructions と description

schemaだけでは順序や整合が表現できないため、ツール単位で“運用仕様”を契約として分離します。 これが、LLMがUIを見ない前提でのズレを減らします。

instructions（例）
外部状態との一致・更新手順・ツール間の順序を明文化
description（例）
副作用を明示：配列は全置換、空配列は全解除、blockedは理由必須
（用語）契約=contract / 日本語：契約
EVIDENCE
07 / 14

幻覚を“黙殺しない”

Zod の .strict()

Zod の .strict() で未知フィールドを拒否し、 「指定したのに反映されない」事故を検知可能にします（エラーで止める）。

狙い
幻覚で混ざった値が無視される状況を防ぐ
結果
失敗を分類でき、再実行や修正の余地が生まれる
（用語）幻覚=hallucination / 日本語：幻覚
DISTINCTION
08 / 14

意味の整合

整合性は superRefine()

状態間の整合性は .superRefine() で検査し、 変更項目がない更新（実質 no-op）を .refine() で禁止します。

superRefine
複数フィールド間の整合性
refine
変更は1つ以上（no-op防止）
実務効果
“見かけの成功”を減らす
PROCESS
09 / 14

更新の曖昧さを消す

テンプレ更新は全置換

部分更新を避け、テンプレート更新は全定義必須の“全置換”に寄せます。 省略の意味（維持/クリア）を契約から排除して事故を減らします。

避ける
省略＝維持、null＝クリア…の解釈違い
取得→丸ごと再送で“何が変わるか”を明確化
（用語）全置換=replace all / 日本語：全置換
DISTINCTION
10 / 14

再試行の暴走を抑える

エラーは分類＋次手に直結

エラー応答は、エージェントが読み続ける前提で「原因の分類」と「次に取るべき行動」に結びつく形にします。 ただし retryable を誤って解釈させない設計が必要です。

望ましい
conflictは取得し直し、バリデーションは入力修正へ誘導
注意点
粒度が粗いと原因が混ざり、“同じ呼び出し繰り返し”の原因に
ARCHITECTURE
11 / 14

道具を減らす

危険操作は非公開

依存関係の解除のように突破を促しやすい操作はツールとして公開せず、 相談・提案へ倒して人間側の意思決定に寄せます。

公開しない例
戻せない操作、権限変更、依存解除などの“詰まり突破”系
狙い
誤操作ではなく確認・承認へ誘導（攻撃面を縮小）
（用語）承認=approval / 日本語：承認
COMPARISON
12 / 14

“守る”ではなく“塞ぐ”

サーバ検証が要点

description / instructions は契約として誘導になるが、必ず守られる保証ではありません。 最終的な安全性は schema 検証（例： .strict() ）と整合性チェックで担保します。

LLMへの期待
読んで意図を合わせる（でも保証はしない）
安全の担保
入口で検証し、整合しない入力を失敗させる
（用語）保証=guarantee / 日本語：保証
CLOSING
13 / 14

再現できるチェック

要点：失敗設計

書き込みMCPは「データの作法」ではなく「失敗の設計」です。 expectedUpdatedAt を必須にし、.strict() と整合性検証、全置換、エラー分類で事故を減らします。

競合
lost update を expectedUpdatedAt で入口拒否
幻覚
.strict() で未知フィールドを検知可能に
曖昧さ
全置換＋エラー分類で次手を一意に寄せる
限界もある：未徹底のツール、エラー粒度、クライアント依存は棚卸し対象。
