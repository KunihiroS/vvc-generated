Cover
02 / 16
権限境界を“合成”で設計する
Permission Outcomes
AIエージェントの「ツール許可」だけでは、意図しない業務決定（取引の成立）が通ることがあります。
取引（transaction）単位で承認し、執行時に再検証して失効させる—という考え方を整理します。
Problem
03 / 16
予算は“境界”じゃない
上限
予算上限は「量（いくらまで）」を抑えるだけで、「目的（何の意思決定として）」は制御しません。結果、上限内でも未承認の意思決定（調達切替など）が成立しえます。
Budget（上限）
支出の暴走を抑える
量の制約（amount cap）
Permission（境界）
目的と取引の成立を制御する
意思決定の制約（outcome bound）
Metaphor
04 / 16
緑ボタンの罠
合成
各操作が許可されていても、エージェントがそれらを組み合わせると「誰も承認していない結果」だけが成立します。これが合成による権限逸脱（composed authority）です。
Step 1
苦境を検知（調査）
Observations（観測）
Step 2
代替ベンダーを提案
Planning（計画）
Step 3
資金を移して切替
Execution（執行）
Architecture
05 / 16
境界を“取引”へ
Transaction
境界（permission）は「ツール」ではなく、「成立するビジネス決定」に紐づけます。承認対象は、ベンダー変更＋資金移動のような“取引全体（全体の束）”です。
Bad：操作境界
ベンダー変更OK + 資金移動OK
→ 結果が未承認でも通る
Good：取引境界
「調達切替」というアウトカムに承認
→ 結果単位で安全性を担保
Evidence
06 / 16
分割承認の破綻
意図の断線
ベンダー変更の承認と、予算（資金移動）の承認を別々に出すと、エージェントはそれらを“つなげて”未承認の調達変更を成立させる可能性があります。
承認A
vendor変更：承認済
（同意した範囲が限定的）
承認B
fund移動：承認済（上限内）
（量の妥当性だけ見ている）
→ 合成されたアウトカム（切替取引）が、元の承認意図から外れていても検出しきれない。
Distinction
07 / 16
整合性≠安全性
Hash
署名やハッシュは「改変されていないか（整合性）」には効きますが、「承認対象が適切だったか（安全性）」は別問題です。さらに執行時再検証がないと、部分実行や状態競合で事故ります。
Integrity（整合性）
承認後に改変されていない
tamper-evidence（改ざん検知）
Safety（安全性）
その“取引束”が正しかった
correctness-of-approval（承認妥当性）
Process
08 / 16
承認→執行→再検証
失効
承認を固定情報（vendor・金額・資金源・期限・アウトカム等）に結び、変更があれば承認を失効させます。執行時にも再チェックし、合成されたアウトカムが変わったなら無効化します。
i
承認：取引束を特定
approval binds fields（結合）
ii
執行：実体化を観測
runtime evidence（証跡）
iii
再検証：同一性を確認
invalidate on drift（失効）
Architecture
09 / 16
承認キーの設計
Fields
無効化の粒度は「どのフィールドが取引束の同一性を作るか」で決めます。例：vendor・金額・資金源・期限・アウトカム（意図）などが変われば承認を落とす。
承認に含める
vendor / amount / fund source
期限 / アウトカム / 依存関係
無効化の条件
変更で“同一の意思決定束”が崩れる
single outcome identity（単一性）
Distinction
10 / 16
UIが“飾り印”になる
Human
承認UIがまとめた情報しか人間に見せないと、合成された最終アウトカムが理解できず、承認が形式化します。失効条件（何が変われば無効か）も追随しないと危険です。
見せる情報
“合成されたアウトカム”単位
approval target clarity（対象の明確性）
追随するもの
失効条件（同一性の崩れ）
expiry ≠ drift。（期限≠変化）
Comparison
11 / 16
単純化の落とし穴
Trade-off
取引全体にバインドすると安全性は上がりやすい一方で、承認面が大きくなり遅延や負荷が増えます。実装では失効粒度・再検証頻度・UI設計・補償（ロールバック）まで設計が必要です。
安全側
アウトカム単位で承認・無効化
risk↓ / clarity↑
コスト側
遅延・承認負荷・運用例外
latency↑ / ops難化
Governance
12 / 16
境界は“責任設計”
Agreement
「どこに境界を引くか」は組織的合意で決まります。技術設定だけでなく、誰が（承認者／ポリシーエンジン／独立実行者）定義と拒否を持つかが安全性を左右します。
Risk
操作が緑でも合成で事故
Ops
失効条件の誤りは止まる/抜ける
Audit
承認がボタン記録で終わると説明不能
Closing
13 / 16
結論：アウトカム境界
要件
権限境界は「予算上限」や「単操作許可」ではなく、合成されたアウトカム（取引全体）に結びます。さらに執行時再検証と失効で、ズレた意思決定を無効化します。
Must
承認単位＝取引アウトカム（vendor/amount/fund/期限/意図）
binding + runtime recheck（結合＋再検証）
Next
無効化・補償（ロールバック）・監査（誰がどの粒度で）を一体設計
governance を明確に（責任の所在）
Keywords: composed authority（合成による権限逸脱）, transaction-bound approval（取引束への承認）, invalidate on drift（ズレで失効）
