02 / 16

Actor-first Identity / 認証観

SoulAuth 人間とAIを同じ主体へ

SoulAuthは、AIアクター（ボット・エージェント・サービス等）も「同等の主体」として認証する、Actor中心の認証・アイデンティティ基盤です。
このデッキでは、認証と権限の分離、OIDC/Tokens、SoulAuthの境界設計と運用上の安全策を、読みやすく圧縮して整理します。
PROBLEM
03 / 16

主体が増える / Who is real?

AIを“誰”として認証する

従来は「ユーザー＝人間」前提で、AIは付属物として扱われがちでした。
新しい前提
AIが継続的に判断・行動する“長寿命の主体”になる
重要な論点
「いま認証されているのは誰（何）か」/「誰が責任を持つのか」
METAPHOR
04 / 16

Passport と Permission / 分ける

認証は本人性、権限は別

SoulAuthは「本人（Authentication）」の事実を確立し、行動の可否（Authority）は上位側が判断する線引きを中核にします。
Authentication / 認証
“誰（何）か”の確立（claims・監査に使う事実）
Authority / 権限
“行動できる理由”やガバナンス判断（消費側の責務）
ARCHITECTURE
05 / 16

Lifecycle分離 / 契約で守る

分離で安全性を作る

SoulAuthは Identity（誰か）/ Credential（証明方法）/ AuthSession（継続性）/ Token・Federation（外部提示）を分けてライフサイクル境界を設計します。
Identity
Actorの“ルートとなる誰か”
Credential
署名・鍵など“どう証明するか”
AuthSession
継続性（sidやセッション結び付け）
Token
外部への提示単位（claims含む）
Federation
外部連携のための提示/交換
境界
鍵・監査・セッションを前提化
ENUMERATION
06 / 16

安全策セット / Fail closed

設計で事故を抑える

SoulAuthは“認証であること”を保証するために、鍵・セッション・失効・監査耐性の前提を実装に織り込みます。
sidが前提
sidなしIDトークンを発行しない（できないなら署名しない）
Fail closed
参照解決できない場合は“発行しない”で取り違えを防ぐ
再利用検知
トークン再利用を漏洩シグナルとして扱い失効側に倒す
監査耐性
監査の改ざん耐性を意識した設計（追跡可能性）
補足：リプレイ拒否（step watermark）、ロックアウト（ユーザー/ IP両面）、MFAなども安全策として言及されています。
EVIDENCE
07 / 16

OIDC準拠 / 統合しやすく

OIDCとして“壊さない”

SoulAuthは、一般的なOIDCプロバイダとして動く前提を持ち、エラー応答などをOIDCクライアント互換に寄せます。
コンセプト
/token等のエラーはOIDCライブラリ互換を優先
理由
仕様ラップを避け、統合時のデバッグ時間を減らす
この方針は「SoulAuthが分かる」ではなく「既存OIDCで扱える」に寄せる実務価値です。
DISTINCTION
08 / 16

概念の混同を防ぐ

ActorとAccountは別物

SoulAuthでは、Actor Identityは“アイデンティティの根”、Accountは運用上の概念として位置づけられ、相互に置き換えないとされています。
Actor Identity / アクター
認証のルートとなる“誰（何）か”
Account / アカウント
運用・管理のための概念（アイデンティティと混ぜない）
混同すると、監査・無効化・権限推論が難しくなり、境界設計が崩れます。
PROCESS
09 / 16

クライアント側の責務 / Verify

BFFやOIDCクライアントが見るもの

消費側はIDトークンを検証し、iss/aud/expや署名（JWKS）に加え、sidをキーとしてセッション理解する必要があります。
必須
iss / aud / exp・署名検証（JWKS）
重要
sidをセッション結び付けの前提として扱う
場合により
token交換をしない構成ならクライアントシークレット不要のことも
例
BFFがauthorization code flowを担うならシークレットが必要になり得る
DISTINCTION
10 / 16

sidなしの危険 / Fake valid

sidは無効化の前提

sidがないと、取り消し可能なセッションと結び付かないため“有効に見える”トークンが生まれ、無効化や監査が成立しにくくなります。
目的
トークン↔セッションを結び、取消可能性を成立させる
SoulAuthの対応
参照解決できない場合は署名しない（Fail closed）
結論：sidは“オプション”ではなく、統合設計の要所です。
EVIDENCE
11 / 16

運用の現実 / クォータや鍵

運用で安全性を維持する

起動時ゲーティング（鍵/設定不足なら拒否）、レート制限DBの共有、TLS終端の外部委譲など、マルチレプリカ運用と攻撃耐性を意識した記述があります。
起動ゲーティング
本番鍵や設定が欠ければ処理を拒否
レート制限
再起動でクォータをリセットしない/共有DBで整合を取る
TLS終端
リバースプロキシに委譲（外部境界で整理）
狙い
事故や攻撃の“ズレ”を減らし、事故対応も設計しやすくする
COMPARISON
12 / 16

既知の制約 / 先に知る

失効は“常に即時”ではない

ドキュメント上の既知の制限として、RFC7662 token introspectionがない、失効反映が即時でない可能性がある等が挙げられています。
token introspection
RFC7662がないため、消費側は有効期限までの挙動に依存しがち
OIDC token失効
即時ではなく、有効期限到来で反映されるケースがある
フロントエンド
No front-end（APIとして提供）
前提
導入時はキャッシュ戦略・期限設計・インシデント手順を別途組む必要
CLOSING
13 / 16

導入レビュー観点 / Checklist

結論Actor中心 + 境界分離

SoulAuthは、Actor Identityを根に据え、AuthenticationとAuthorityを切り分けることで「AIアクターの認証と監査」を成立させやすくします。
確認すべき点
claimsとsidをauthorizationにどう使うか（消費側設計）
失効と反映
失効が即時でない可能性を織り込む（キャッシュ/期限）
運用
マルチレプリカと再起動時挙動、レート制限DB共有を想定
上位ガバナンス
SoulseedOS/SoulseedAGIとの境界実装を統合仕様で確認
追加で不明点があれば、DEPLOYMENT.md / SECURITY.md / 統合ドキュメント（例：Mind/データフローや鍵ローテーション）を必ず参照してください。
