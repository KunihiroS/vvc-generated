02 / 16
Nix × GitHubレビュー

trynix-preview実用化

PRのNix成果物（/nix/store）を、サーバーやDockerなしでブラウザから“起動”できる流れを整理します。
PROBLEM
03 / 16
いまのレビューは重い

CIは結果中心

従来はテスト結果がログとして返るだけで、成果物を実行するには別途準備（ダウンロード、環境構築）が必要になりがちです。
つまり「動くか確認」はレビュー後半の手作業になりやすい、という課題があります。
ARCHITECTURE
04 / 16
責務分離が鍵

Actionは“リンク係”

trynix-preview（例：fzakaria/trynix@v1）はビルドやキャッシュ提供をせず、既にあるNixストアパスへの参照情報をPRへコメントします。
前提
成果物がキャッシュ（例：Cachix等）に存在
役割
Nix評価/解決結果 → ブラウザ参照リンクを提示
METAPHOR
05 / 16
“起動”だけ渡す

クリックで検証

レビュー担当者はPRをチェックアウトせず、リンクを開くだけでブラウザ上の仮想的な実行へ到達します。
入力
PR /nix/store（例：.#default）
中身
キャッシュURL・公開鍵等（参照情報）
体験
起動 → 動作確認
PROCESS
06 / 16
実運用の流れ

GitHubで回す

ポイントは「ビルドの生成」は別工程で終わっておき、Actionは“参照リンクだけ”をPRに残す点です。
i. 事前
Nixで成果物を生成しキャッシュへ
ii. Action
trynix-previewがストアパスを解決
iii. PR
解決結果（リンク）をコメント
iv. レビュー
クリックしてブラウザ実行
EVIDENCE
07 / 16
成功条件が明確

キャッシュ必須

Actionはキャッシュを作らないため、リンクを出しても参照先が無いと起動できません。
成立
Cachix等に成果物が既に存在
崩れる
成果物が未投入 → ブラウザ起動失敗
運用設計として「いつ・どこに・何をキャッシュするか」が本体になります。
DISTINCTION
08 / 16
従来CIとの違い

“ログ”→“実行”

この仕組みはテストを置き換えるというより、レビューの検証ポイントを実行に寄せます。
従来
CIログ中心、実行は別途準備
trynix-preview
PRへ起動リンク、ブラウザで確認
COMPARISON
09 / 16
性能で範囲が決まる

大きいほど遅い

大きなバイナリでは起動に1〜2分かかる場合があるため、常設の高速フィードバックには不向きになり得ます。
向く
小〜中規模バイナリ、レビュー段階の軽い検証
厳しい
巨大成果物の本格的な代替CI
DISTINCTION
10 / 16
フォークPRは注意

allow-unsafeが必要

フォーク由来PRを扱うために、actions/checkout の allow-unsafe-pr-checkout: true のような設定が必要になる場合があります。
これはワークフロー実行のセキュリティ制約に関係します。
PROCESS
11 / 16
キャッシュ分離推奨

混線を防ぐ

PRビルド用キャッシュを分離し、フォークがメインキャッシュへ書き込むリスクを避ける設計が推奨されます。
目的
参照の意図しなさを減らす
設計
PR用とメインを分ける（名前空間/権限）
効果
利便性とリスクのバランス
EVIDENCE
12 / 16
この方式の価値

レビュー短縮

「CIログを読む」から「PRを直接起動して確かめる」へ、フィードバックループを短縮できます。
技術的整合
/nix/storeの再現性が参照リンクに向く
実用性
Nix/Cachix戦略と責務分離で接続しやすい
CLOSING
13 / 16
導入判断の要点

万能ではない

小〜中バイナリのレビュー検証を強化する補助線として有効ですが、性能・セキュリティ・キャッシュ運用の追加確認が必要です。
性能
起動1〜2分の可能性
安全
フォークPRと分離設計（権限/削除ポリシー等）
不足情報
サンドボックス強度、定量基準、失敗時挙動
