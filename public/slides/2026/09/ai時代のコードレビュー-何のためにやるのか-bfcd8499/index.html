question
02 / 16
AIで崩れる前提
すべてレビュー？
AIで生成されるコード量が増えると、「人間が全件PRレビューする」運用はボトルネック化します。 では、コードレビューは本当に“完成物のチェック”のためにあるのでしょうか。
日本語訳の要点（英語 + 日本語）：Shift the judgment left（判断を前倒し） / Review by exception（例外でレビュー）
problem
03 / 16
レビューの多目的
目的が混ざる
従来のコードレビューは、バグ検出だけでなく「学習・知識共有・設計整合・共同所有」など多様な価値を担ってきました。 しかし運用は“同じ重さで全件レビュー”に寄りすぎた、という問題提起です。
役割（目的）
学習 / 知識共有 / アーキテクチャ整合 / collective ownership（共同所有）
運用（形）
完成コードを見て判断する“最後のゲート”化
stance
04 / 16
AIへの反論
「壊した」は違う
ThoughtworksのCTOレイチェル・レイクックは、「AIがコードレビューを壊した」のではなく 「そもそもコードレビューに“間違った問題”を解かせてきた」と反論します。
前提の誤り
レビュー工程が、必要な“判断”のタイミングを抱え込みすぎた
本質
価値の源泉を、レビュー以外へ移し替える必要がある
idea
05 / 16
判断の置き場所
Shift Left
重要な代替案探索や知識移転は、完成コードの後ではなく実装前・推論中に行うべきです。 これによりレビューが“検討の場”になり続ける構造を弱められます。
前倒し
設計セッション（白板/合意）
共同
ペア / モブで推論プロセスを共有
結果
レビュー待ちが“最後の難所”に集中しにくい
architecture
06 / 16
自動化で代替
決定可能品質
フォーマット、既知のセキュリティパターン、決定的にテストできる条件などは機械化で担保します。 人間は“判断が必要な変更”へ集中する前提が必要です。
機械に任せる
CI / 静的解析 / テスト / セキュリティスキャン
人間が見る
設計の選択・重要境界・影響の大きさ
exception
07 / 16
全件→例外
Review by exception
「コードを一切レビューしない」ではありません。レビューすべき対象を例外に絞ることで、スケールします。
例外 i
根幹アーキテクチャ変更（core architecture）
例外 ii
センシティブなセキュリティ境界を跨ぐ変更
例外 iii
影響範囲が大きい / 未経験領域 / 当事者が自信なし
risk
08 / 16
待ち行列の罠
儀式の自動化
AIで実装量が増えても、人間の判断コストが同じならレビュー待ちが詰まり続けます。 つまり「AIに人間の儀式をなぞらせる」だけでは、組織の10倍能力につながりません。
起きること
PRが増える → 最後のゲートに滞留
なぜダメ
“なぜその儀式が必要だったか”の設計見直しにならない
evidence
09 / 16
価値は前倒しへ
学習と合意
レビューで得ていた価値（代替案探索、知識移転、育成、所有形成）は、より協調的な場に移すべきだと主張します。
代替案
実装前に設計で比較・選択
育成
推論プロセスを一緒に進める
共同所有
運用責任と境界をチームで持つ
distinction
10 / 16
認知負債の扱い
万能ではない
懸念される「cognitive/intend debt（認知/意図負債）」は重要です。 ただしPR形式だけでは、それを十分に防げるわけでもないと述べます。
懸念
なぜ動くかの意図を理解する人が減る
対策の方向
協調設計 / ペア / 境界管理 / 実行可能アーキテクチャ
myview
11 / 16
同意できる点
価値の再配分
強みは、コードレビューを“バグ探し”に矮小化せず、学習・合意・所有の制度として捉え直している点です。 判断を前倒しに移す方向性は合理的だと考えます。
特に効く
ペア / モブ / 設計セッションで理解の希薄化に間接対応
要点
“速度”ではなく“設計の置き場所”を問い直す
caution
12 / 16
不足している情報
検証が必要
ただし、前倒しで置き換えられるという因果が、具体的な実証データとしては提示されていません。 また、協調活動への移行はコスト増になり得て、相殺される保証も必要です。
課題 i
置換の因果が定量的に不明
課題 ii
ペア/設計のコストと調整負荷
課題 iii
例外の基準が曖昧だと解釈が割れる
closing
13 / 16
導入の測り方
Next Step
導入するなら、(1) 自動化で置換する品質・判断、(2) 例外レビューの対象基準、(3) 学習指標や運用障害率の改善を段階的に測定します。 そうして“レビューの儀式”ではなく“理解を保つ設計”へ寄せます。
「全件レビュー」ではなく、「判断の置き場所」を変える。
Bilingual: 例外運用 / Review by exception
