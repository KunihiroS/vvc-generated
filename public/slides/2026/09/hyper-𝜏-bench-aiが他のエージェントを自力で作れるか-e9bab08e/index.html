Hyper-𝜏-bench
Hyper-𝜏-bench（ハイパー・タウ・ベンチ）は、AIエージェントが別の顧客サービス用エージェントを自力で構築し、未知会話に正しく対応できるかを評価する長期ベンチマークです。 （測る：agent→agent の自動開発）
PROBLEM
03 / 16
できるなら革命
鍵は要件探索
企業のエージェント開発は、人間が規約・手続き・データ構造を整理し、設計し、テストして品質を作ります。 もし developer agent がほぼ一人で別エージェントを作れるなら、工数とスケールが大きく変わります。
ARCHITECTURE

Construction
Sierraが2026年9月にオープンソース化した本ベンチは、developer agent に資料（ドキュメント、会話ログ、API、コードベース等）を渡し、コストやモデル制約の下で顧客サービス用エージェントを作らせます。
入力（資料）
ドキュメント／会話ログ／API／コードベース
評価（合否）
未見の顧客会話へ正答＋基盤システム変更の正確さ

FAILURE MODES
07 / 16
典型的な“開発の弱点”
人間っぽい失敗
失敗は「機械的なミス」ではなく、人間開発者が直面する典型課題に酷似していました（情報収集・質問・設計選択・探索の不足など）。
情報収集
早すぎて不足、または拾い切れない
要件獲得
質問が少なく、必要要件を取りに行かない
判断
計算資源（推論コスト等）の選び方が弱い
探索
設計・技術の反復探索が少なく、動くものを最初に出す

DOMAIN
09 / 16
銀行で崩れる
要件量の壁
銀行領域では特に成績が悪化しやすいとされています。政策ファクトが多く、参照し得る条件が散在するため、すべてを拾い切るのが難しいのが理由です。
銀行の特徴
政策ファクト大量／条件が多層
AIの難所
要件の取りこぼし・反映漏れ
DISTINCTION
10 / 16
実装力≠運用到達
別問題
Hyper-𝜏-benchは「AIがコードを書いて動く」だけでなく、「業務要件を正しく発見し、期待品質で運用まで到達する」難しさを浮き彫りにしています。
よくある誤解
会話が上手い＝要件達成できる
観察された現実
要件探索・検証設計がボトルネック
PROCESS
11 / 16
どう解釈するか
条件付き結論
Human + AI reference の 82.2% は oracle reference の可能性があり、比較は条件付きです。したがって「自律は無理」ではなく「現時点で研究・要件探索・検証設計がボトルネック」と段階的に読むのが安全です。
言えること
差分が出る：要件探索の弱点が可視化
注意点
oracle寄り：人間優位を即断しない
次に必要
代表性・制約・再現性の追加検証
TAKEAWAY
12 / 16
実務での打ち手
質問×探索
自律開発を「研究・レビュー工程の代替」より先に「草案生成や補助」と位置づけるのが合理的です。成功率を伸ばすレバーは、質問方針（追加情報獲得）と設計探索の増強にあります。
設計の焦点
質問ポリシー（Q）／検証サイクル
戦略
探索（設計・技術反復）を増やし、出荷を遅らせる
Risk：最初に動いた案を出荷 → ガードレール必須
Bank：要件量多 → 追加テストと監査ログが重要
