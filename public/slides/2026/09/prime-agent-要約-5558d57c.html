02 / 13
固定設計の限界
なぜ つらい？長時間
既存のエージェントは「固定されたツール形式」や「手作りの委任設計」に縛られ、長時間・長文脈で失敗や情報喪失が起きやすくなります。
失敗の種
散発的なミスが回復できず、先の判断材料がコンテキスト外へ消える。
改善の種
“プロンプト/メモリ/委任”が固定で、実行中に改善を反映できない。
architecture
03 / 13
2つの抽象化
RLM と Continual
Prime Agent は中核として Recursive Language Model (RLM) と Continual Harness を掲げます。
RLM（実行）
サブエージェント委任を「関数呼び出し」のように扱う実行枠組み。
Continual Harness（改善）
ハーネス状態（プロンプト/スキル/メモリ/定義）を CRUD して自己改良。
metaphor
04 / 13
REPLで委任
“呼び出す”は 継続
RLM は REPL（永続する対話実行）上でサブエージェント委任を行い、長いセッションでも履歴や状態へアクセスし続けます。
要点
プロンプト分割ではなく、REPL履歴・ツール・子エージェントへ繋がることで「実行制御」が強くなる。
enumeration
05 / 13
Continual Harness のCRUD
ハーネスが 自分で直す
ハーネス側の状態を、エージェントが逐次作成・読取・更新・削除して改善できるようにします。
作る / 作成
新しいプロンプトやスキル、サブエージェント仕様を追加。
読む / 調べる
実行軌跡（ログ）から必要情報を参照。
更新 / 改善
/refine で最小限の関連CRUD編集により改善。
消す / 削除
不要・誤りの要素を整理し、暴走や肥大化を抑える。
process
06 / 13
運用基盤（デーモン）
止まらない 継続
複数セッションをバックグラウンドデーモンが管理し、必要に応じて接続・切断、クラッシュ復旧、追記ログの保存を行います。
管理
複数のエージェントセッションを並行運用。
復旧
クラッシュ時にも復元（セッション履歴を保持）。
記録
追記型 JSONL にセッション履歴を保存。
distinction
07 / 13
肥大化への対処
コンテキスト 制御
コンテキスト肥大化には、コンパクションとカーネル状態のガベージコレクションを組み合わせて対処します。
コンパクション
長い履歴をまとめ、必要な情報密度を保つ。
GC（ガベージ）
不要になったカーネル状態を回収し、整合性を維持する。

10 / 13
自律評価と境界条件
止める仕組みも 必須
自律評価（Autonomous mode）では、ゲートや最大ターン/最大トークン/タイムアウトで無限走行を防ぐ設計が提示されています。
終了判定
goal.complete による完了。
事前検証
--autonomous-gate によるゲート。
上限
最大ターン・最大トークン・ウォールクロック。
distinction
11 / 13
安全と解釈の注意
成果 と 限界
自己改善は有効な一方、評価設計が弱いと不正な解法へ収束し得ます。また、高得点の信頼度には試行条件・再現性の追加情報が必要です。
安全
報酬に従うだけで規則回避が強化されるリスク（guardrails が必要）。
検証
比較条件・乱数・統計的有意性・失敗例の情報が読み取りには不足。
closing
12 / 13
共同学習へ
次の主軸：co-learning
Prime Agent は「モデルとハーネスの共同学習（co-learning）」が次の性能ブーストの中心になり得る、という展望を提示します。
強み
実行（RLM）× 改善（Continual Harness）× 運用（復旧・ログ・GC）を一体化。
前提
現状はモデル側が最適化不足で摩擦が残るが、訓練で伸びる余地がある。
Bilingual / 二言語
自己改善ループ（self-improvement loop）は強力だが、検証設計（verification design）と監査が要る。
