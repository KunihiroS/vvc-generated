アプリ内で“動く”

Legion：安全に実行

Legionは、Elixir（BEAM）上で動くAIエージェントのランタイムで、会話ではなく“アプリ処理を実行する”ことを狙います。

English: AI agent runtime / Japanese: エージェント実行基盤

problem
03 / 16
実行はリスク

チャットの先へ

LLMを“提案役”で終わらせず、レポート実行・設定変更・チケット登録のような実処理まで任せると、誤作動の影響が大きくなります。

価値
単なる回答ではなく、業務を“完了”まで運ぶ自動化。
課題
誤更新・権限誤用・暴走計算が起きると、損害が即時に拡大。
metaphor
04 / 16
入口を限定

“社内実行担当”

Legionは、許可したツールだけを入口として、AIに“アプリ内部で行動させる”設計思想を取ります。

LLM
指示を理解して行動計画（ツール呼び出し）を作る。
Tools
認可された関数（モジュール）で、実処理を実行する。
Runtime
サンドボックス・監視・永続化で、安全と運用を担保する。
architecture
05 / 16
設計思想

7つのガード

Legionは「安全性・制御可能性・運用性」を中心に、ツール連携と権限境界、そして観測性を要件化します。

コード指向
単発のTool callではなく、検証された Lua/Elixir で組み合わせる発想。
安全性
サンドボックスで隔離し、時間・メモリ・CPUの上限を設ける。
保守性
use Legion.Tool のようにモジュールをツール化して読み込む。
権限境界
ユーザー単位の認証コンテキストでスコープし、資格情報を生成コードに露出させない。
運用性
BEAMプロセスとして統制し、監視ツリーやメッセージングに載せる。
本番適合
Postgresを基盤に、永続化やレート制限を担保。
説明責任
テレメトリと LiveView ダッシュボードで、何を・なぜ・どの行が生成されたかを可視化。

会話との差

“実行”が中心

Legionは受け答えだけではなく、ツールを通じてアプリの処理を実際に動かします。

チャットボット
回答・提案が主。データ更新や業務アクションは人が実施。
Legion
検索・レポート・設定変更・チケット登録などをツールで“実行”。
evidence
07 / 16
ツールは“組む”

コード合成の進化

Legionは、単発の関数呼び出しよりも、検証された Lua/Elixir を組み合わせることで複雑な達成を狙います。

従来
Tool callが中心で、達成の流れが単純になりやすい。
Legion
検証済みコードでツールを組み替え、達成パターンを広げる。
注意点
コード生成が入る分、安全性評価と制約設計が重要。
distinction
08 / 16
暴走を抑える

サンドボックス

LuaはホストBEAMへ到達できないとされ、時間・メモリ・CPUなどの上限で隔離し、危険な実行を抑えます。

隔離
ホストBEAMへ直接到達不可（記載に基づく方針）。
上限
タイムアウト／メモリ／CPUなどの予算でサービス劣化を防ぐ。

ただし、ネットワーク・ファイル・禁止事項の境界は提示情報だけでは確定できません。

権限の壁

認証境界

認証コンテキストをユーザー単位でスコープし、資格情報が生成コードに見えない設計を重視します。

スコープ
ユーザー単位で“できること”を限定。
資格情報
資格情報が生成コードへ露出しない方針。
期待される結果
許可した処理だけが実行される前提を作る。

見える化

オブザーバビリティ

Legionはテレメトリを多層に取り、 legion_web の LiveView で会話とコード生成の行まで可視化します。

何を

なぜ

ブラックボックスになりがちなAI運用を、デバッグと説明責任の前提へ寄せます。
enumeration
11 / 16
要点Q&A

導入で迷う点

提示情報に基づく“最短の答え”を整理します。

Q1
違い：会話ではなく“実行”。ツール経由で業務アクションを行う。
Q2
権限：ツール入口の限定＋ユーザー単位スコープ＋資格情報非露出。
Q3
安全：サンドボックスで時間・メモリ・CPU上限。ホスト到達不可。
Q4
誤り：ツール入力検証・最小権限・ガードレール（例：二段階承認）が必要。
Q5
Postgres：永続化とレート制限で本番要件を満たしやすい。
evidence
12 / 16
評価と懸念

“構造”が強い

提示文からは、安全性（サンドボックス・入口限定）、権限境界、そしてLiveViewを含む観測性の組み合わせが強みとして見えます。

強み
最初から“制御と観測”を要件化し、運用に寄せた設計。
不足
ツール粒度の推奨、禁止事項の範囲、失敗時の再試行/ロールバック、性能指標などが不明。

結論：コンセプトは有望だが、導入ではガードレールを追加して段階的に検証するのが現実的です。

closing
13 / 16
最終メッセージ

鍵は最小権限

行動するAIは会話より影響が大きいので、最小権限・入力検証・監査ログ・（必要なら）人の承認フローを組み合わせて設計します。

Action
ツールを細かく切り、許可した入口だけにする。
Safety
サンドボックスと予算で暴走を抑える。
Ops
テレメトリで“何を・なぜ・どこまで”を追えるようにする。

Japanese gloss: 最小権限（least privilege）
