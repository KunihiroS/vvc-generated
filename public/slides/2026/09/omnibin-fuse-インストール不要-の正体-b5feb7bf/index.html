COVER
02 / 16
読み替える、パッケージ体験
omnibin （遅延参照）
Nixpkgsの“過去バージョンのバイナリ”を、インストールせずにFUSEで見せます。必要になった瞬間だけ、キャッシュからNARを取り出して展開します。
用語補助：遅延取得（lazy fetch）／FUSE（ファイルシステムをユーザ空間で実装）
PROBLEM
03 / 16
入れる前提が重い
“選んで、入れて”
通常のパッケージ管理は、必要なものを事前に選び、ビルド/展開してから使います。結果として「入れる作業」と「保存（ディスク消費）」が先に発生します。
omnibinはその順序を逆転させます。
通常
事前に選ぶ → 展開する → 使う
omnibin
見える → 必要時に展開 → 使う
METAPHOR
04 / 16
“全部ある”は嘘じゃない
夢の倉庫 …ではなく
“全部あるように見える”の正体は、索引で場所を案内し、実体はアクセス時に遅延取得することです。問い合わせ（ls/which）にはすぐ答え、展開は必要時だけ行います。
i索引
Hydraの`.ls`メタデータ（内容JSON）で事前把握
ii見せ方
FUSEがファイル操作を捕捉し、見える名前を提供
iii本体
NAR（アーカイブ）をcache.nixos.orgから取得→unpack
iv結果
初回だけコスト、2回目以降は高速
JP補助：NAR＝（Nixの）アーカイブ実体／unpack＝展開
ARCHITECTURE
05 / 16
“ls”は即応、“実体”は遅延
構成要素
omnibinは、索引・名前解決・遅延取得・FUSE展開の4点セットで成立します。
索引
Hydra `.ls`
名前解決
nixpkgs-multiverse
取得
cache.nixos.org（NAR）
実体生成
FUSEでunpack
応答
ls/whichに即応
UX
“必要な時だけ”
ポイント：パッケージ“配置”ではなく参照“解決”中心
PROCESS
06 / 16
アクセスの流れ
遅延取得の動作
ファイルに触れるまでは“存在を見せるだけ”。アクセスが来た瞬間にだけ、NAR取得→展開へ進みます。
i列挙
/omnibin/bin が“最新提供版だけ”を名前表示
ii解決
python3@3.6.2のような要求は内部で対応ストアへ紐付け
iii取得
cacheからNARを取り出す（初回のみ遅延）
iv展開
unpackして必要ファイルを/として提供、以降は再利用
FUSE＝“ユーザ空間でファイル操作を実装する”仕組み
EVIDENCE
07 / 16
例：昔のPythonも“触れる”
python3@3.6.2
`python3@3.6.2`のような特定バージョンでも、初回アクセス時に限って遅延取得・展開が発生します。二回目以降は即時利用できます。
1回目（初回）
2.7秒程度の初期コスト
2回目（以後）
高速（ウォーム済み）
これは“0コスト魔法”ではなく、コストの発生点を「インストール時→利用時」に移した設計です。
JP補助：ウォームアップ＝必要なストアパスが溜まって高速化
ENUMERATION
08 / 16
“全部ある”の内訳
何が先に揃う？
omnibinが事前に用意するのは「実体そのもの」ではありません。先に揃うのは“参照できるための情報”です。
i情報
`.ls`メタデータで、どのファイルがどこにあるかを索引化
ii対応
multiverseで“属性名↔バージョン”をストアパスへ解決
iii名前
/omnibin/binは最新名だけを表示し、探索負荷を抑制
iv実体
NAR取得→展開は、アクセスが来たときだけ実行
DISTINCTION
09 / 16
Docker/OCIと何が違う？
“詰める”ではなく “取りに行く”
Docker/OCIは多くの場合、イメージに素材を詰める方向です。omnibinは必要になった部品だけを後から取りに行き、しかもNixpkgsの過去成果物まで参照対象に含めます。
Docker/OCI
事前にイメージへ同梱（基本は“詰める”）
omnibin
参照時に遅延取得（基本は“取りに行く”）
本文は比較のニュアンス中心で、性能・安全性の厳密比較は不足
COMPARISON
10 / 16
探索のボトルネック回避
lsが巨大でも
Nixpkgsには約881,933本級のバイナリが存在し得ます。エージェントが毎回stat/探索すると破滅的に遅くなるため、/omnibin/binは“最新名だけ”を列挙します。
問題
巨大ツリーをそのまま列挙すると探索が重い
対策
最新だけ表示／バージョン付きは内部解決へ
これにより自動化エージェントの“探索し過ぎ”を抑えます。
DISTINCTION
11 / 16
python3 と python3@3.6.2
意味の違い
`python3`は「その時点の最新Python3」を指します。`python3@3.6.2`は「特定バージョン（2017年の系譜）」を指します。
python3
最新バージョン参照（latest）
python3@3.6.2
指定バージョン参照（pinned）
両方とも同じFUSE上で解決されるが、“指定の度合い”が違う
PROBLEM
12 / 16
万能ではない：初回遅延
制約を理解する
omnibinの落とし穴は、初回アクセス時の遅延取得・展開コストが確実に存在することです。短命な環境や毎回まったく別のバイナリに触れるワークロードでは不利になり得ます。
i初回コスト
触れた分だけNAR取得→unpack（遅延が発生）
iiウォーム依存
長寿命マシンでは利用が進み負担が小さくなり得る
iii説明不足
オフライン時の挙動・欠損時のエラー・監査/ログは追加確認が必要
ivセキュリティ
ネットワークキャッシュとFUSEの運用前提（整合性検証など）が重要
判定の軸：利用頻度（ウォーム率）と要求パターン
CLOSING
13 / 16
結論：インストールではなく参照
参照体験を再設計
omnibinは「パッケージ管理を、選ぶ作業から参照する作業へ再定義」し、Nixの“バージョン共存”を過去まで拡張します。夢ではなく、Hydra索引＋nixpkgs-multiverse＋FUSE遅延展開の工学的組み合わせです。
強い点
過去バージョンまでシームレスに辿れる（検証/再現に強い）
注意点
初回アクセスの遅延と、運用前提（ネット/整合性/監査）を詰める
