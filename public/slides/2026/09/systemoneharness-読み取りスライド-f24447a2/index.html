02 / 16

有限アクションで安全に回す

SystemOneHarness 意思決定ループ

System One を「観察→意思決定→実行→記録」のエージェントループとして動かすためのハーネスで、自由文生成ではなく 環境定義の有限アクションを1ステップずつ選びます。

英: finite actions / confidence gate / complete trace（有限アクション・確信ゲート・完全トレース）を中核に置きます。

PROBLEM
03 / 16

誤操作と再現不能が課題

Why Harness?

意思決定モデルをそのまま環境に接続すると、危険な操作が混ざりやすく、さらに「なぜそう判断したか」が追えない問題が起きます。

Safety / 安全
破壊的操作（destructive）を、モデルの“それっぽさ”だけで実行しない設計が必要。
Repro / 再現
自由形式の指示だと、同条件で結果が揃わず監査・デバッグが難しい。
ARCHITECTURE
04 / 16

観察→決定→実行→記録

1ステップ 1モデル呼び出し

コントローラが状態を観察し、利用可能な行動を“型付きの質問”にコンパイルして、モデルに1回リクエストするだけで次の行動を決めます。

Step input / 入力
状態（環境）→ 質問（アクション候補＋パラメータ）
Step output / 出力
行動・パラメータ・ゴール判定＋確率分布（confidence）
METAPHOR
05 / 16

自由文ではなく選択

有限アクションのゲーム盤

モデルは自由に“書く”のではなく、環境が列挙した有限の駒（actions）から1つを選び、必要ならパラメータも選びます（自由作文なし）。

Example / 例
ship, pack, choose_carrier
Param / パラメータ
carrier の候補から選択
Promise / 約束
レビュー・再現・安全に寄与（何が起きうるかが限定される）
PROCESS
06 / 16

confidence gateで実行制御

確率で 通過／拒否

read/write/destructive それぞれに対して最小確率しきい値を設定し、モデルの提案が足りない場合は未決として扱い、危険な実行を抑制します。

read
閾値を比較（例: 0.5 目安）
write
より高い確信を要求（例: 0.7 目安）
destructive
最も厳しく遮断（例: 0.9 目安）
EVIDENCE
07 / 16

完全トレースで監査可能

状態と分布を 保存

各ステップで、入力・質問・確率分布・判定・実行結果・停止理由に加えレイテンシ／コストまで逐次トレースとして記録します。

Trace / トレース
「どの状態で」「どんな質問に対して」「どの分布で」「なぜ停止したか」
Handoff / 引き継ぎ
別の推論ハーネスや人間へ渡すための構造化情報として使える
DISTINCTION
08 / 16

1ステップの設計が効く

再現性・安全性・レビュー

「1ステップにつき1モデル呼び出し」かつ「生成アクションなし（環境が定義した選択のみ）」が、挙動の予測可能性を上げます。

Consistency
条件が揃えば、同じ“選択肢”の上で意思決定する
Review
危険な操作の候補が限定され、承認フローを組みやすい
Ops
停止理由と分布でデバッグしやすい
ARCHITECTURE
09 / 16

環境プラグ可能性が強み

Python / MCP / Browser / UHP

同一コントローラで、プロセス実行、MCPサーバ、ブラウザDOM制御（有限アクション化）、さらにUHPを介した配信まで扱えます。

Browser / ブラウザ
DOMの可変性を、モデルが選べる有限アクションへ落とす
UHP / 通信
実行アクションと拒否／終了を、分布とゲート判定と結びつけて対応
PROCESS
10 / 16

realtime は履歴を抑える

realtime: true の考え方

環境が動き続ける場合、拒否や繰り返しの意思決定を“時間の進行（clock tick）”として扱い、履歴を短く保ちつつ最後に有効だった行動を維持します。

Clock tick
時間が進む単位ごとに意思決定を整理
Keep last valid
最後に有効だった行動を運用上の方針として維持
COMPARISON
11 / 16

読み取れる強みと限界

保証の範囲を 明確化

ベンチマークは「小さく決定的なタスクで完了できる」点を支持しますが、曖昧状態・算術・日付・長い無関係コンテキストへの一般化は主張しません。

Supported / 支持
成功率、応答時間、コスト（複数回のライブ実行で提示）
Not guaranteed / 保証外
曖昧さ、計算、日付、長文コンテキスト
Design dependency
環境のアクション定義・危険度分類・DOM安定化が品質を左右
EVIDENCE
12 / 16

批判的に見る：confidenceと環境

何が不明？ 何が効く？

提示情報だけでは、confidence をどう定め／校正し／しきい値をどう調整するかの厳密さは読み取りにくいです。加えて、有限アクション化の“環境側のモデリング品質”がボトルネックになります。

Risk / リスク
しきい値が不適切だと、誤実行だけでなく未決増加（no_confident_action）にも偏る
Assumption / 前提
環境が十分なアクション列挙を提供できないと、そもそも表現できない
CLOSING
13 / 16

運用志向の制御層

Takeaway 3点

SystemOneHarnessは、モデル単体より「安全に動かす制御層」を中心に据える設計です。

i / i
有限アクションで再現性（自由文を避ける）
ii / ii
confidence gateで安全性（read/write/destructive を区別）
iii / iii
完全トレースで監査性（停止理由・分布・コストまで）

導入の鍵は「アクション定義と危険度分類をどれだけ良く作れるか」。そこが揃うほど、設計思想の価値が出ます。
