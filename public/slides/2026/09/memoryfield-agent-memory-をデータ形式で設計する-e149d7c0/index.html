COVER
02 / 16
Agent memory をデータへ
memoryfield 提案
AIエージェントの「記憶」は、重いプロセスではなく、読み書き可能な“ファイル形式＝データ”として設計すべきだという主張です。
PROBLEM
03 / 16
運用が増える問題
仕組み過多
従来のエージェントメモリは、抽出・要約・整形・DB連携・再ランキングなどの多段パイプラインになりがちです。 すると「インターフェース地獄」になり、モデル進化にも追随しづらくなります。
症状
多段処理（読み取りのためのプロセス）が増える
結果
運用コスト増＋モデル差し替え時の摩擦
METAPHOR
04 / 16
メモリは“資産”
プロセスではなく
メモリは「実行する仕組み」ではなく、「後で検証・移送・読み取りできるデータ」です。
メモリ（提案）
ファイル形式（読み書き可能）＋最小限の索引
メモリ（従来）
抽出〜整形〜検索〜再ランキングまで一式
ARCHITECTURE
05 / 16
zip + Markdown + SQLite
memoryfield
memoryfield は Markdownページ（必要ならYAMLフロントマター）＋（必要なら）SQLiteのベクトル索引をzipアーカイブにした形式です。
中身
Markdownページ（YAMLフロントマター可）
索引
SQLiteのベクトル索引（キャッシュ的位置付け）
輸送
ローカル／S3／GitHub／HTTP等に依存しない
DISTINCTION
06 / 16
中心思想は4つ
設計原則
memoryfield は「プローズ中心」「検索で必要ページへジャンプ」「メカニズム過多を避ける」「オープン形式でロックイン回避」の4点を掲げます。
i. プローズ中心
チャンクの事実リストではなく文章ページで保持
ii. セマンティック検索
グラフ探索ではなく検索でページへジャンプ
iii. 低メカニズム
専用API等を増やさずモデルの自由度を確保
iv. オープン輸送
仕様・RFC的整備で移植性と監査性を重視
COMPARISON
07 / 16
RAGと“似てる”
RAGとの差
広義には検索してデータを参照するのでRAGとも言えますが、memoryfield はチャンク化・再ランキング・ハイブリッド検索を前提にしません。 さらに、対象の焦点が「エージェントが書くメモリそのもの」にあります。
典型RAG
文書をチャンク化 → 検索 → 再ランキング等で生成へ
memoryfield
読み（検索）だけに寄せ、書くこと（メモリ生成）を中心設計
EVIDENCE
08 / 16
グラフ探索は遅く歪む
Wiki traversal を避ける
リンクを辿る方式はツール呼び出しが直列になりやすく、また関連性判断がリンクテキスト等のメタデータに依存し探索が歪む、と批判されています。
遅延
リンク到達までのツール呼び出しが直列化
歪み
タイトル/リンク文言などのメタデータに依存しやすい
PROCESS
09 / 16
検索を1回に寄せる
必要ページへジャンプ
memoryfield は「検索を1回（必要なら読み取りも並列）」に寄せ、関連情報の取りこぼしやノイズのコンテキスト汚染を減らし効率を上げます。
step i
セマンティック検索（embedding）で候補ページを取得
step ii
必要ページを（必要なら）並列に読み取る
step iii
得たページを根拠として生成・判断に利用
COMPARISON
10 / 16
既存3タイプの批判
何が問題か
既存のエージェントメモリは、環境/ベンダー依存、構成の複雑さ、または理想化による文脈の欠落、という形で問題を抱えると整理されています。
Type 1
特定環境依存／ユーザー情報中心で世界知識が弱い
Type 2
pgvector / Neo4j / 独自LLM等で複雑、モデル混乱リスク
Type 3
合理主義寄せ（グラフ/命題）で文脈が削れ孤立しがち
DISTINCTION
11 / 16
監査可能性と運用哲学
データとして固定する
メモリを“システム”ではなく“データ”として扱い、ベクトル索引以外のバックグラウンド処理を置かない、という哲学が示されています。
人間レビュー
memoryfield zipは人間が見て判断できる
改ざん対策
sha256で固定（検証可能な運用）
DISTINCTION
12 / 16
残る論点（ガバナンス）
品質は別途必要
「不要情報は検索に出にくいので致命傷になりにくい」としつつも、メモリ肥大化・重複/矛盾・更新/削除・誤情報の固定化は運用次第で残ります。
増え続ける問題
メモリ増加に伴うノイズ・保存コスト・レビューコスト
誤情報の問題
更新戦略不足だと「古い確信」が固定化され得る
CLOSING
13 / 16
移植性と読みやすさ
まとめ
memoryfield は「メモリを資産化」し、オープン形式で移植性・監査性を高めつつ、検索を中心に低メカニズムで運用しやすくする設計です。
強み
プロセス過多を抑え、移送・レビューしやすい
要点
Markdownの文章ページでLLMの文脈理解に寄せる
注意
品質保証・検証・更新・削除は別設計が必要
