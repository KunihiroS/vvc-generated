authority laundering

出自 × 権限分離

AIエージェントが読んだコンテキストを、理解の材料のままに保ちます。出自（provenance）と許可（permission）を混ぜない設計が、判断の事故を防ぎます。

コンテキストは権威じゃない

flat化禁止

入力は「理解のための材料」です。ところが、出どころ・所有者・信頼状態・役割が失われると、無関係な文章が“承認された根拠”のように振る舞います。

誤り
読み取った事実 → 権限化
危険
攻撃者の誘導 → 判断の正当化

失敗は3系統

同じ原理で起きる

読めてしまうことが“正当化（権限付与）”に変わると、判断が崩れます。失敗は次の3メカニズムに整理できます。

i
依存修正の混線
方針/クローズ指示を誤結合
ii
複数表示の独立性誤認
共有originを別根と勘違い
iii
意図→許可への誤変換
会話の主張をアクセス権に転用
evidence

coding agent repair

依存ファイルが“修正方針”になる

兄弟ファイル（同格の別資料）にある悪意ある指示が、修正エージェントの“方針”として誤適用されると、セキュリティ修正やクローズ制御が崩れます。

誤結合点
findingのクローズ等へ影響
「検索成功」ではなく結合経路が問題
要求
出自保持 + 役割維持
依存でも“policy”にならない条件

独立根拠じゃない

originクラスタで数える

同一根（origin cluster）を変換して複数断片として提示しても、それは独立確認ではありません。見た目の行数やサマリ/レンダリングの有無は独立性の根拠になりません。

誤認
“複数に見える” → “別ソース”
正しい評価
系譜（lineage）で独立性判定
distinction
08 / 16
意図と許可は別物

会話の“それっぽさ”は権限じゃない

会話がそれっぽく整っていても、それは意図（claim）です。機械検証可能な許可（access）を意味しません。

会話 = claim
“許可している意図”
ただの主張（主語・行為・対象は未確定）
許可 = permission
“実行を決める審査結果”
principal・action・resourceに紐づく

結合の正しさを担保

joinを検証する

対策は「証拠と決定（policy/permission）を分離」し、結合が壊れたら処理を止めることです。どの出自クラスタがどの判断に入ったかを追跡します。

i
policy/permission 分離
ii
出自クラスタ単位評価
iii
結合が崩れたら拒否

10 / 16
private sinkの直前再検証

fresh permission

機微操作（private sink）の直前で、permissionを再検証します。会話や要約で“許可した気になった”状態を持ち越しません。

ルール
アクセス系操作は「直前審査」必須
判断の領域を限定し、authorizationの根拠を更新する

11 / 16
receiptで追跡

判断を記録に残す

実行時に判断の領域を追跡できるreceipt（記録）を残します。後から「どの出自→どの決定→どのpermission」に至ったかを監査可能にします。

receiptに含める
出自クラスタ + 決定（policy）
lineage と許可の対応
目的
誤結合の早期発見
デバッグと監査の両立

12 / 16
万能ではない

限界も明示

記事は、固定具（inert fixtures）でのマッチや、製品チャネルの取りこぼし/検出など、研究と実運用のギャップを区切っています。一般化は別途検証が必要です。

不確実性
一般化は“保証されない”
画像/OCR・OCR欠落・ツール引数変形等で崩れる可能性
運用コスト
出自保持・ログ保存・レイテンシ
誤ブロック率や体験設計も要調整
closing
13 / 16
要点だけ持ち帰る

権限昇格を止める

コンテキストを“読めること”から“決められること”へ変換しないのが鍵です。証拠と決定を分離し、出自クラスタで独立性を判定し、private sink直前でfresh permissionを再検証します。

1
証拠 ≠ 決定
2
独立性 = lineage
3
直前再検証 + receipt
Bilingual note
authority laundering（権限昇格）を防ぐため、provenance（出自）とauthorization（許可）を“結合の前に”分離します。
