only-cli / oc

Web→AI閲覧CLI

ocは、Webページを“コンパクトな番号付きビュー”に変換し、LLMが少トークンで段階的に読めるようにするCLIツールです。

日本語併記：英語用語は括弧内に短い日本語（必要箇所のみ）。
PROBLEM
03 / 16
トークン爆増問題

生HTMLは重い

HTMLをそのまま渡すとトークン数が膨れ、コストと処理時間が増えます。さらに、クローラ対策・ログイン制限・JavaScript依存で「単純取得では読めない」ことが起きます。

入力の重さ
数万トークンに膨張し得る
取得の難しさ
ブロック / 認証 / JS依存で失敗が増える
目的：読めること + 読ませる量（token）を抑えること。
ARCHITECTURE
04 / 16
番号で段階取得

oc open

oc open <url>はページを取得し、LLM向けの番号付きコンパクトビューとして返します。必要ならoc doやoc readで対象部分だけ追加取得します。

閲覧単位
番号（例：[1]）で選択
コスト設計
“数百トークン級”を狙う（圧縮）
段階進行
do/readで必要分だけ
ポイント：要約だけでなく、番号アクションで“参照対象”を増減できる。
METAPHOR
05 / 16
読むのは命令じゃない

データビュー

READMEは、ページ内にコマンドのように見えるテキストが埋め込まれている可能性を前提にします。ocは、出力を“命令”ではなく“読取対象（データ）”として扱う設計思想を取ります。

リスク
プロンプトインジェクション的な誤誘導
対策の方向
表示形式 + 運用ルールで誤解を減らす
“見えるテキスト”が本当に意図した操作かを分離する発想。
PROCESS
06 / 16
番号付きアクション

do / read / next

ocの表示にはリンクやテキスト領域が番号付きで並びます。oc do <n>は番号がリンクなら辿り、テキストなら読取対象として扱います。

oc do
番号→リンク遷移 or テキスト読取
必要時だけ
URL操作を増やさずに進める
next
段階的に次へ（構造化された流れ）
重要：エージェントは“指示文”ではなく“データ参照（番号）”で進む。
EVIDENCE
07 / 16
認証はCookie注入

oc login

ログインが必要なページはoc loginでCookieを注入し、oc open --session <name>で閲覧します。Cookieジャー（Cookie storage）は分離保存され、外部への混入回避を重視します。

運用
OC_HOME配下に保存（ディレクトリ指定）
安全
権限（例：0600）や--json混入回避
ログインページが返る場合は“失敗”として明示し、誤解釈を減らす。
DISTINCTION
08 / 16
--jsonと秘匿性

秘密は混ぜない

--json出力にCookieなどの秘匿情報が入らない設計方針が述べられています。あわせて、--cookieで渡す場合はプロセスやシェル履歴に残り得る点への注意があります。

--json
Cookieジャーを混入しない
--cookie
シェル履歴等に残る恐れ → 慎重利用
目的：LLMパイプラインに載せるデータと、秘匿情報を分離。
COMPARISON
09 / 16
比較は2軸

閲覧 + 実行

ocのベンチマークは、トークン削減だけでなく、Claude CodeやCodexのような“ツール実行まで含む”費用でも比較しています。評価はWikipedia/言語ドキュメント等で示され、トークン数で最大数十倍削減が報告されています。

比較対象
生HTML / Jina Reader / Playwright系など
評価観点
閲覧コスト + エージェント実行コスト
“読めた感”ではなく、実際の回答・コストまで見に行く。
EVIDENCE
10 / 16
失敗の判別

終了コード2

読み取れるテキストが得られない場合、stderrで判定が出て終了コード2になります。さらに--jsonでも同様の扱いとして設計されており、“読めなかった”と“空である”を切り分けやすくします。

失敗条件
読み取れるテキストがない
終了コード
2で判別
--json
空フィールド等で一貫
エージェント運用では“失敗をデータとして扱う”ことが重要。
DISTINCTION
11 / 16
できないことも明記

万能ではない

JavaScriptレンダリング未対応のため、外形上JavaScriptのみで表示されるページは読めない（失敗の可能性）があります。加えて、ハードなbotチャレンジにより拒否されることがあり得ます。

制約
JavaScriptレンダリング未対応
残余リスク
botチャレンジで拒否の可能性
導入前に「自社タスクで読めるか」を確認すべき、という前提が立つ。
PROCESS
12 / 16
導入時の確認3点

期待値調整

ocを使う前に、(1)典型タスクのページが読めるか、(2)ログインが必要な場合にCookie注入が現実的か、(3)JavaScript必須のケースを別手段でどう組むか、を確認するのが要点です。

i可用性
静的中心か、必要な情報が“取得できる形”か
ii認証
Cookieジャー運用（更新/期限/失敗時挙動）
iii代替
JS必須はブラウザ自動化等との併用を設計
評価
ベンチ結果は前提条件に依存 → 自前検証
ocは“万能ブラウザ”ではなく、トークン効率と可用性のバランス型の読み取り基盤。
CLOSING
13 / 16
要点まとめ

少トークン閲覧基盤

ocは、Webを“AIエージェント用の番号付きデータ”に変換し、段階取得・命令注入対策の思想・Cookie認証・終了コードで運用事故を減らします。ベンチは閲覧と実行の両コストで優位性を示す一方、JavaScript未対応とbot拒否の残余リスクは前提として扱います。

核
番号付きコンパクトビュー（token削減）
運用
Cookieジャー + --json非混入
限界
JS未対応 / botチャレンジ耐性に差
