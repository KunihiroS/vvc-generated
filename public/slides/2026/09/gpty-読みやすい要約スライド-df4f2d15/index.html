Godot × Rust × PTY

gpty 読みやすい要約

gptyは、ターミナル（PTY）を“AIが扱える作業空間”として再構成し、JSON-RPC / MCPで「生成・注入・観測」できる基盤です。
Problem
03 / 16
難しい理由

AI操作が不安定

AI/自動化は「出力を観測して次の行動を決める」一方で、誤操作や事故のリスクがつきまといます。
現場課題
複数ターミナル状態を“見える形”で管理しにくい
自動化課題
観測と制御の境界（入力注入/出力観測）が曖昧になりがち
Architecture
04 / 16
核となる設計

Multi-PTY + IPC

gptyは、複数PTYをタイル状のペインとして並べ、外部からはJSON-RPC IPCやMCPで制御できるように設計されています。
PTY
疑似端末（セッション）を複数同時に扱う
GUI
タイル状グリッドで“状態”を視覚化
IPC
JSON-RPC / MCPでエージェント連携
Metaphor
05 / 16
Concept Engine

見て振り分ける

Concept EngineはPTY出力を正規表現（Re/Trigger）で捉え、隣接ペインへ“表示”として流す概念エンジンです。
やること
出力を捕捉して、対応するペインへ振り分けて表示
重要な前提
概念エンジンは“シェルへ入力しない”
Core
06 / 16
ペインの種類

Tiles と多様な表示

ターミナルだけでなく、コードビューやファイルツリー等もペインとして独立に扱え、リサイズ可能なグリッドで管理します。
Terminal
PTYの対話/状態を可視化
Code
コード内容を別ペインで閲覧
Files
ファイルツリーで探索
Process
07 / 16
AIの流れ

観測→注入→結果

エージェントは、JSON-RPC/MCPでペインを作り・（必要なら）注入し・出力を観測して次の行動を決めます。
i
ペイン生成（new / layout）
ii
テキスト注入（inject）
iii
出力観測（inspect）
iv
必要ならkill/再構成
Comparison
08 / 16
制御の2経路

JSON-RPC vs MCP

GUIを使う場面ではJSON-RPCで制御し、GUI不要の場面ではMCPサーバとして標準入出力経由で提供します。
JSON-RPC IPC
GUIを動かしつつCLIがRPCで制御
MCP Server
標準入出力でツール提供（GUIなし運用）
例：gpty schema --format mcp（ツールマニフェスト出力）／gpty mcp（標準入力から起動）

Security
10 / 16
攻撃面への配慮

抑える設計

Concept EngineのReDoS対策、PTY環境のサニタイズ、IPC hardening、OSC 52制限などが挙げられています。
ReDoS
正規表現処理の悪用を抑制
IPC hardening
JSON-RPC/MCPの境界を安全寄りに設計
PTY sanitize
端末環境の取り扱いを前提化
OSC 52
制限で情報注入の余地を縮小
Risk
11 / 16
保証ではない

署名なし & LLM由来

コード署名は実施されていないと明記され、また大部分がLLM生成で非慣用パターンやバグが入り得ます。
コード署名
バイナリはコード署名されない
LLM生成比率
実装品質の不確実性が残る可能性
対応：ネットワーク分離、権限最小化、入力制限、テスト/監査を運用ガードレールとして用意するのが現実的です。
