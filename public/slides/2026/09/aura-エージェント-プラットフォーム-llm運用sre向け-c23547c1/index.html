AURA
02 / 16
SREに“安全実装”
Agent Platform
AURAは、AI（LLM）を運用・保守（SRE/DevOps）に組み込むための“プロダクション前提”エージェント基盤です。
運用者が定義した境界の中で、ログ・トレース・メトリクス・Kubernetes履歴を相関し、障害調査と復旧確認を支援します。
PROBLEM
03 / 16
チャットの限界
事故が怖い
LLMをそのまま“本番運用”に使うと、誤操作・説明不能・監査性不足でリスクが上がります。
誤操作（安全性）
AIが勝手に実行すると、復旧より先に被害が拡大します。
監査（説明性）
なぜその判断になったか追えないと、後から検証できません。
観測（運用性）
判断やツール実行が“ログ/トレースに残らない”と運用に組み込めません。
統制（ガードレール）
実行範囲・承認ポリシーがコード化されていないと統制できません。
CORE
04 / 16
中核の発想
相関で仮説
AURAは“単発の助言”ではなく、複数ソースを突き合わせて原因仮説の優先順位を上げます。
入力（例）
Mezmoトレース/ログ、Prometheusメトリクス、Kubernetes変更履歴。
出力（例）
回帰（例: N+1）特定→ロールバック推奨→復旧チェック提示。
専門エージェントが分担し、必要に応じて“次のアクション”まで落とし込みます。
SAFETY
05 / 16
安全境界
ガードレール
AIがセンシティブな操作を実行する前に、承認や境界によって“安全側”へ倒す設計が中核です（fail-closed）。
承認（人）
センシティブなツール呼び出しは、WebHookまたは会話内承認を要求して実行を止めます。
fail-closed
拒否・タイムアウト・輸送失敗などで“実行しない方向”に倒します。
※承認失敗時の“部分実行”などの細部は、入力データだけでは確定できないため事前検証が必要です。
OBSERVABILITY
06 / 16
運用で必要
OpenTelemetry
AURAは、LLMの判断やツール実行をトレースとして追跡可能にし、監査と改善に使える観測性を提供します。
追跡対象 i
LLMのターン・意思決定。
追跡対象 ii
ツール呼び出し（何を実行したか）。
追跡対象 iii
多エージェントのオーケストレーション。
チャットボットとの差は、「なぜそう判断したか」を後から検証できる点です。
INTEGRATION
07 / 16
外部へ接続
MCP
MCP（Model Context Protocol）などの連携規格により、AURAは外部ツールへ接続して運用タスクを拡張できます。
狙い（EN）
Standardized tool access（ツール接続の標準化）
対応（例）
AWS/Azure、Confluence、Datadog、Docker、GCP、GitHub/GitLab、Jira、Kafka、Kubernetes、Mezmo、New Relic、Notion、PagerDuty、Prometheus 等。
“現場の基盤”に合わせて組み込みやすいのがポイントです。
ARCH
08 / 16
構成を統制
TOMLでレビュー
専門エージェント、プロンプト、ツール、承認ポリシー、ガードレールをTOMLでまとめ、レビュー可能に管理する方針が示されています。
管理単位
“誰が・何を・どの境界で許可したか”を設定として残す。
運用効果
監査性・説明可能性・変更管理（バージョン管理）を強めます。
config: agents / tools / approvals / guardrails（概念）
EVIDENCE
09 / 16
デモの流れ
決済障害
決済失敗の調査デモでは、トレース/ログ・メトリクス・Kubernetes変更履歴を突合して回帰を特定し、復旧の手順まで提示します。
i: 相関
Mezmoトレース/ログ＋Prometheusレイテンシ＋Kubernetesデプロイ履歴を同時に見る。
ii: 特定
productcatalogservice 1.13.2 で導入されたN+1回帰を特定。
iii: 復旧
ロールバック推奨→復旧チェック→エンジニアリングのフォローアップ提示。
iv: 決断支援
“次に何を確認し、どう動くか”まで落とし込みます。
SECURITY
10 / 16
配備の現実
air-gapped対応
セキュリティ境界の中で稼働でき、空中遮断（air-gapped）環境を含む運用形態にも適応することが強調されています。
モデル切替
OpenAI / Anthropic / AWS Bedrock / Gemini / Ollama などを設定変更で切り替え可能。
権限制御
センシティブなツール実行は人の承認を挟む方針。
“基盤ごとの制約”を前提に設計している点が、導入障壁を下げます。
COMPARISON
11 / 16
チャットとの差
運用部品付き
AURAは“質問するだけ”ではなく、状態管理・ストリーミング・失敗処理・観測性・承認など、運用に必要な部品を同梱します。
LLMチャット
判断と実行が追跡されず、統制・監査が難しくなりがち。
AURA
境界内で実行し、OpenTelemetryでトレースし、承認とfail-closedで安全側に倒す。
運用チームが“受け入れられる形”に整理されているのが差別化点です。
GAP
12 / 16
未確定ポイント
検証が要る
README中心の入力では、性能指標や“承認失敗/部分失敗時の具体挙動”の定量データが読み取れません。
不足 i
誤判断率、承認フローの遅延許容などの定量。
不足 ii
承認タイムアウト時の確実性、ツール呼び出しのフォールバック。
不足 iii
ツール権限のベストプラクティス、典型的な運用手順。
必要
セキュリティ/データ取扱いモデルの精読＋限定環境での運用試験。
CLOSING
13 / 16
導入の結論
次の一歩
AURAは、障害調査の相関・安全境界・OpenTelemetry観測性・TOML統制を“運用前提の形”で提供します。
強み
承認を挟むfail-closed、相関調査、監査可能なトレース、MCPでツール拡張。
前提
セキュリティ設計レビューと限定環境での運用テストを必ず行う。
（EN）Validate first. Deploy safely.（日本語）安全に検証してから導入。
