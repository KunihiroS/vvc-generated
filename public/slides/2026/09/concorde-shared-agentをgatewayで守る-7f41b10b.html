Shared agentを“支配不能”に

Concorde 共有AI

複数の当事者が同じAIエージェントを使うとき、誰か一人が直接操作できる設計は不公平や秘密の介入を生みます。

核心（Core）

Gateway（ゲートウェイ）で入出力を一本化し、当事者の“直接到達”を遮断します。

対象（Audience）

一般向けに言うと「同じ相談相手」を、裏切りが起きにくい形で共同利用するための骨格です。
problem / 根本
02 / 13

“誰が触れられるか”

公平性 支配

shared agentでは、ある当事者がエージェント本体へ直接到達できると、指示の書き換えやメモリの改変で他者を害せます。

改変（Tamper）

指示を書き換える／メモリを読み替える

秘匿（Hidden）

他者に見えない情報で誘導する

結果（Impact）

不公平・権利侵害・合意の崩壊
metaphor / 比喩
03 / 13

窓口が“唯一”

Gateway 窓口

Gatewayは、当事者それぞれの経路を一本化する“検問所”です。ここを通らないと、誰もエージェントへ直接手を伸ばせません。

入（Input）

当事者 → Gateway → 共通の実行経路

出（Output）

実行結果 → Gateway → 当事者全員が同じ記録に近づく
※README要約では、改ざん耐性は運用・DB管理・権限設定に依存するとされています（保証の範囲は別途要設計）。
architecture / 全体
04 / 13

部品で選べる

構成要素 コンポーネント

ConcordeのGateway配下には、コアとなる部品（PostgreSQL / Signal Worker / Agent server / Public server）が含まれる前提があります。

保存（DB）

PostgreSQL（共有記録の土台）

実行（Worker）

Signal Worker（処理の段取り）

提供（Server）

Agent server / Public server（受け口と配布）
加えて、必要に応じて Users / Messenger / Signatures and Decisions / Scheduler などをデプロイで選びます。
architecture / デプロイ
05 / 13

単一エントリポイント

Runtime+Gateway 開始口

デプロイは「単一のエントリポイント」で Runtime と Gateway を作り、extendで必要なコンポーネントを組み上げます。

extend（拡張）

必要な部品だけを返す設計で、構成管理を容易にします。

ルーティング

routesを公開サーバ／エージェント側へ追加でき、責務分離を促します。
また、フレームワークは“ブロック境界（Gateway外）”にあるべき、DDL（スキーマ変更）はデプロイ移行で行う方針が示されています。
enumeration / 安全境界
06 / 13

安全を肩代わりしない

期待値 制約

Concordeは、機密性・プロンプトインジェクション耐性・エージェント隔離（confinement）・レート制限などを“意図的に提供しない”としています。

提供しない

機密性（Confidentiality）／プロンプトINJ耐性（Prompt Injection）

提供しない

隔離（Confinement）／レート制限（Rate limit）
結論：運用側で認証・入力検証・暗号化・隔離環境・監査ログ・DoS対策等を追加設計する前提になります。
evidence / 署名
07 / 13

合意を“検証可能”に

Signatures & Decisions 署名/決定

shared agentでは“誰が何を根拠に決めたか”が争点になり得ます。そこで、第三者が検証できる形でコミットする狙いがあります。

目的（Why）

検証可能性（Verifiability）を持たせ、後から監査できる状態にする

効果（So what）

“改ざんされた結果”を争点にしやすい土台を作る（運用とセット）
process / 振る舞い
08 / 13

共同利用の流れ

同一経路 Shared IO

shared agentの要点は「同じAIエージェントの実行結果を、複数当事者が利用する」ことです。

i / 入力

当事者ごとの要求を Gateway に集約

ii / 実行

コア部品が処理し、共有実行経路で結果を生成

iii / 共有

当事者が同じ記録・同じ出力（に近い形）へアクセス
distinction / 差別化
09 / 13

“チャット”ではない

sharedの定義 支配不能

Concordeのsharedは「会話が同じ」ではなく、「誰も直接支配できない構造」を指します。これが単なる会話AIフレームワークとの差です。

従来（がち）

各当事者が直接触る → 指示や状態が非対称になりがち

Concorde（狙い）

Gatewayで遮断 → 入出力と記録の経路を揃える
だから重要なのは“AIの賢さ”より、共同運用の権限・経路・検証の仕組みです。
distinction / 期待値調整
10 / 13

安全は利用者設計

リスク前提 要脅威モデル

README要約にある「提供しない安全領域」を踏まえると、最終的なリスク低減は利用者側の設計・検証に依存します。

追加で必要

認証強度／入力サニタイズ／隔離環境／ログ監査／DoS対策

確認ポイント

脅威モデル・ログ/DB権限・検証手順・運用ポリシーの揃い具合
process / 進化

APIは未確定

0.1.0以降 変更

0.1.0で破壊的変更があり、公開APIは未確定です。マイナーアップでエントリポイント修正が必要になる可能性があります。

導入方針

共同利用の安全は“技術仕様＋運用”で決まるため、更新管理はセキュリティ管理の一部になります。
closing / まとめ
12 / 13

結論（takeaway）

骨格 Securityは別途

Concordeは“共有エージェント”をGatewayで守る思想を、署名・決定・スケジューラ等の部品と共に提示します。

強み

支配不能な構造で、共同利用の公平性を作る

注意

機密性・INJ耐性・隔離・レート制限は提供しない
