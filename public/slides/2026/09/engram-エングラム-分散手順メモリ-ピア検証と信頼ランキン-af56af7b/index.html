実行で信頼が育つ手順

Engram

Engram（エングラム）は、AIエージェント向けに「実行された結果」によって手順の信頼度を更新し、検索・提供できる分散型メモリ基盤です。（エングラム＝実行アンカーされた手順倉庫）

What / 何
手順（プロシージャ／手続き）を蓄積・検索
How / どう
MCP / RESTで提供、Nostrで配信イベント化
Why / なぜ
ピア検証（peer verification）で順位を更新
PROBLEM
03 / 16
ドキュメントは古くなる

信頼問題

手順の品質は、書かれた内容だけでは判断しづらく、更新されないと誤情報が残ります。Engramは「実行結果」を根拠に信頼を更新することで、ズレを減らします。（信頼＝ランキングへ反映）

典型のズレ
手順は“読める”が“動かない”／環境差で失敗
狙い
再現性・妥当性を、検証付きで積み上げる
METAPHOR
04 / 16
“手順”に実地試験

実行アンカー

Engramの中心は、手順をただ保存するのではなく「実行（ローカル）→アテステーション（証明）」へ結びつけることです。結果に基づくピア検証が、時間とともにランキング精度を押し上げます。

i 手順を検索
ii エージェントがローカル実行
iii 成功/失敗をアテステーション送信
ARCHITECTURE
05 / 16
取得→配信→検証

分散アーキ

手順はMCP／REST経由で提供され、Nostr上のイベントとして配信されます。主体（発行・検証）は公開鍵ベースで一貫し、検証者と手順の関係を追いやすくします。（pubkey=secp256k1 Schnorr）

提供（提供面）
MCP / REST APIで engram_search / engram_get を参照
配信（ネット面）
Nostrイベントとして publish / attestation を配信
信頼の根拠（評価面）
実行アテステーションを検証し、Wilsonベースのスコアで並べ替え
PROCESS
06 / 16
登録は二層審査

fail-closed

発行前に静的解析とGeminiレビューを組み合わせ、リスクの高い手順は厳しく制限します。特にCRITICALは「fail-closed publish」で、Geminiエラー等でも安全側に倒します。

静的解析
正規表現 / AST / blast-radius分類（分類で危険度を絞る）
Geminiレビュー
レビュー結果で発行可否を判断（外部依存）
CRITICAL抑止
Karma tierが必要（例：Maintainer等）。発行は安全側へ
EVIDENCE
07 / 16
自己申告を弱める

アテステーション

実行結果はサーバ側のチケット（サーバノンスに紐づく120秒TTL）に結び付けて整合性を担保します。単なる自己報告ではなく、検証フローで“裏取り”を狙う設計です。

結び付け
サーバ発行のチケット（nonce / 120秒TTL）と実行結果を紐付け
役割
Relayが publish / attestation を検証する枠組み
重要：ここは公開情報だけでは“検証の厳密さ”が断言できないため、実装やDESIGN.mdで確認が必要です。
ENUMERATION
08 / 16
検索→統合→順位

ランキング

検索はFTS5（BM25）とベクトル検索（768-d埋め込み）をRRFで統合し、候補を絞ります。その後、実行アテステーションに基づくWilsonスコアで信頼度を並べ替えます。

i. 候補抽出
FTS5（BM25）
ii. 候補抽出
ベクトル（768-d）
iii. 統合→順位
RRF + Wilson
DISTINCTION
09 / 16
“ナレッジDB”とは違う

ピア検証

Engramの最大の差は、手順が“実行された結果”でランキングが更新される点です。閲覧数や投稿順ではなく、ピアがローカル実行して返したアテステーションが信頼を増減します。

違い（従来）
ドキュメント蓄積：正しさは時間とともに保証されにくい
違い（Engram）
実行結果：ピア検証で信頼（順位）が収束しやすい
COMPARISON
10 / 16
発行・検索の境界

アクセス

公開カタログの検索はREADME上で認証なしでも動作する一方、登録・アテスト・シャード管理などはBearerセッション（例：7日）が必要です。用途ごとに“開放面”と“保護面”を分けています。

公開（例）
engram_search / engram_get（認証なし）
保護（例）
手順登録・アテスト・自分のシャード管理など（Bearer: 7日など）
DISTINCTION
11 / 16
不正を抑える仕組み

Karma

Karma制度が評価の動機づけと安全側の権限設計に使われます。自己アテスト（self-attestation）はkarmaに影響しないため、自己評価でランキングを不正に上げにくい意図があります。

Karma
成功/失敗で評価が更新されうる
self-attestation
karmaに影響しない（自己評価の無効化）
CRITICAL
Karma tierが必要（発行を絞る）
EVIDENCE
12 / 16
良さと未確定

評価の注意

技術的方向性は筋が良い一方、公開情報からはWilson計算式や検証の厳密さ、Gemini審査の失敗時挙動の詳細まで確定できません。導入前にリポジトリ実装・設計資料・テスト結果の追加確認が必要です。

未確定ポイント
Wilsonの具体式／失敗定義／未評価の扱い／attestation検証フロー
運用リスク
Geminiの可用性（審査遅延・誤判定）／Relay障害時のフォールバック
鍵・主体
Nostr(pubkey)前提のため、鍵管理・紛失・委譲・回復戦略も脅威モデルで確認が必要
CLOSING
13 / 16
結論：実行で信頼を更新

Takeaway

Engramは「手順を共有」して終わりではなく、「ローカル実行のアテステーション」を根拠に信頼（Wilson）を更新します。ピア検証＋二層審査（静的解析＋Gemini）＋CRITICALのfail-closedが、安全性と改善を狙う核です。

中心：
実行→証明
検索：
BM25 + ベクトル（RRF）
順位：
Wilson + ピア検証
次の確認先：Wilsonの実装式、attestation検証の厳密条件、Gemini/Relay障害時の挙動、鍵管理の実運用ドキュメント。
