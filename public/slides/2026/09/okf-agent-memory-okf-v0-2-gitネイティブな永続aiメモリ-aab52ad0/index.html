OKF Agent Memory
02 / 16
Persistent memory for agents

Gitネイティブ永続メモリ

AIエージェントの“会話が閉じて知見が消える”問題に対し、OKF v0.2準拠で永続的に残し、レビュー可能にするための仕組みです（Progressive Disclosure付き）。
Key terms: 永続メモリ / Gitネイティブ / BM25（語彙検索）/ Progressive Disclosure（段階的開示） / MCP（統合）
Problem
03 / 16
Context windowの期限切れ

知見が消える

会話のコンテキストウィンドウが閉じると、重要な判断材料や設計知見が失われがちです。 そのため“再利用できる永続メモリ”が必要になります（永続 / persistent memory：日本語）。

よくある症状

判断理由が次回に引き継がれない / 再学習・再設計が発生

求める性質

残る・探せる・直せる・監査できる（audit：監査）

Metaphor
04 / 16
DBではなく“開発物”

メモリをリポジトリへ

知識をベクタDBのようなブラックボックスに預けず、リポジトリ内の `knowledge/` 配下にプレーンMarkdownとして保存し、Gitの履歴で監査できるようにします。 （Git-native：Gitでネイティブに運用） 
knowledge/
  ├─ index.md
  ├─ concepts/
  └─ pages/
（例）YAML frontmatter + Markdown本文で出所・信頼度・ライフサイクルを扱う
Architecture
05 / 16
検索→必要分だけ投入

ローカル検索＋段階開示

検索はローカルでBM25（語彙ベース）を使い、埋め込みAPIのコストやネットワーク往復を抑えます。 さらにProgressive Disclosureで、必要な概念だけを読み込んでtoken肥大を回避します。

Search

BM25 / 語彙検索

Control

index.md / 階層

Load

必要部分のみ（リンク）

Comparison
06 / 16
ベクタDB vs OKF

ブラックボックス回避

重要な狙いは、ベクタDBのような外部ブラックボックスへ依存しないことです。 Git上の差分と監査性を優先しつつ、BM25で高速検索を行います。

ベクタDB中心

埋め込み・外部管理 / 監査が難しくなりがち

OKF Agent Memory

Markdown（YAML frontmatter付き）/ Git履歴で追跡

Core moves
07 / 16
5つの運用原則

品質を守る設計

新規作成では重複や発散を抑え、知識の寿命と整合性を保つためのルールが提示されています（Search-Before-Write等）。

i Gitネイティブ

knowledge/へ保存し、レビュー・差分で監査

ii ローカルBM25

埋め込みAPI不要 / 高速・低コスト指向

iii Progressive Disclosure

index.md＋リンクで必要分だけ読み込み

iv Search-Before-Write

既存検索後に追記し、分裂を抑制

v MCP統合

Claude Code / Cursor等とstdioで連携

狙い

速度・監査性・運用コストを両立

Evidence
08 / 16
主張される性能

コストを削る

入力では、ローカルBM25による概念検索の高速性や、1,000クエリあたり$0のようなコスト指標が強調されています。 これにより、エージェントの高頻度ツール呼び出しでもレイテンシと費用の悪化を抑えやすい、という含意があります。

速度指標

<300µs（概念検索）という主張

コスト指標

埋め込みAPIを介さないため、クエリ費用を抑制

注意：BM25は語彙一致に強く、意味的類似は弱くなり得ます。用途によりメタデータ設計や補助戦略が必要です。
Distinction
09 / 16
token bloat対策

必要分だけ読む

知識が増えるほど、毎回全文を投入するとtokenが膨張します。 index.mdの階層構造とリンクグラフにより、エージェントが必要な概念だけをロードする方針です（Progressive Disclosure）。

問題

全文投入 → token肥大 / 応答遅延

解決

階層インデックス＋リンクで絞り込み

Workflow
10 / 16
CLIとMCPで回す

運用を自動化

`okf` CLIは validate/search/show/create/update/bootstrap を備え、リポジトリ整合性と検索・参照を日常作業へ落とし込みます。 さらにMCPサーバ内蔵により、エージェント基盤へ統合しやすくします。

CLI（例）

validate / search / show / create / update / bootstrap

MCP（統合）

Claude Code / Cursor等とstdioで連携

Limits
11 / 16
導入判断の落とし穴

検証が必要

入力には、検索精度の評価条件・ベンチマークの再現条件・失敗ケース分析などの詳細が不足しています。 そのため導入時は、自分たちのクエリで期待通りに動くかを実データで検証するのが推奨です。

検索品質

BM25の意味的弱さ → タグ/命名/メタデータが効く

運用設計

stale_after等のライフサイクル運用ルールの具体性が要確認

性能の頭打ち

大規模データでの性能上限は追加情報が必要

ガバナンス

PII/機密の混入防止は、入力チェックとアクセス制御が鍵

Closing
12 / 16
結論

監査できる永続メモリ

OKF Agent Memoryは、AIメモリをGit上のプレーンテキストへ寄せ、監査性・運用しやすさ・コスト最適化（BM25＋Progressive Disclosure）を狙う設計です。 採用するなら、提示ベンチマークに加えて自分たちの実クエリで“当たるか”を必ず検証してください。

強み

Git差分でレビュー / ローカルBM25 / token肥大の抑制

次の一手

小さく始め、検索精度と運用ルールを固める
