COVER
02 / 16
Slowave™
AIエージェントの“セッション途切れ”を埋める、ローカル型の適応メモリレイヤー（生きた記憶 / adaptive memory）。
Key idea
記憶を蓄えるだけでなく、使われた結果で重要度を育てる。
Local first
SQLiteにローカル保存（ホスト送信なし）。LLM APIキー不要として設計。
PROBLEM
03 / 16
セッションが切れる

同じ判断の再入力

チャットやコーディングは終了すると文脈が消え、同じ制約・好み・失敗パターンを毎回言い直す負担が残ります。
Pain
制約 / constraints を毎回説明
Pain
過去の判断 / decisions を再提示
Pain
同じ失敗を繰り返す
METAPHOR
04 / 16
静的RAGではない

記憶は“倉庫”でない

Slowaveは、検索（retrieval）や要約（summarization）で終わらず、フィードバックで記憶の優先度を調整する“適応システム”を目指します。
Static
RAG: 関連文書を返して終わり（適応は薄い）
Slowave
Feedback: 役に立った記憶を強め、無関係/古いものを抑制する
ARCHITECTURE
05 / 16
育つためのループ

remember→recall→use

基本フローは「remember→recall→use→feedback→reinforce/ weaken→decay」。参照の有用性を評価して記憶を更新します。
i. remember
事実/決定/選好/指示を保存
ii. recall & use
必要な記憶を呼び出し、タスクで使用
iii. feedback
役に立ったかを渡し、強化/弱化/減衰
ENUMERATION
06 / 16
何を“覚える”か

保存対象

公式説明では、rememberで「事実、決定、選好、指示」を保存し、成果や再利用可能な手順（procedures）も保存しうるとされています。
Static memory
事実 / facts、決定 / decisions、選好 / preferences、指示 / instructions
Procedures
commitで、成果に基づく再利用手順（procedures）も蓄積され得る
EVIDENCE
07 / 16
判断はエージェント側

真偽を自動で保証しない

Slowaveは「主張の真偽」や「重要かどうか」を自分で判断しません。接続したエージェントが判定し、結果をフィードバックします。
No truth-judge
真か誤りかを自律評価しない
No importance-judge
重要度も自分で確定しない
Agent does
役に立った/無関係/古い等をFeedbackで渡す
DISTINCTION
08 / 16
強化・弱化・減衰

“使われた履歴”で重み変更

フィードバックを根拠に、役に立つ記憶は強化し、無関係な記憶は弱化。時間とともに古い情報は減衰（decay）させます。
Reinforce（強化）
参照が有効 → 優先度↑
Weaken / Decay（弱化・減衰）
無関係/古い → 優先度↓、抑制・減少
ポイント: 記憶は“静的なファイル”ではなく、利用結果で形が変わる（適応 / adaptation）。
PROCESS
09 / 16
運用の見える化

ローカルダッシュボード

保存された記憶、手順（procedures）、どの記憶が返されたか（retrievals）、フィードバック、システム稼働状況などを確認できます。
Memory
保存された記憶
Procedures
手順（再利用単位）
Retrievals
返された記憶履歴 + Feedback
ブラックボックス化を避け、改善・原因究明をしやすくする設計意図です。
EVIDENCE
10 / 16
ローカル優先の前提

SQLite・APIキー不要・透明性

ローカルSQLite保存（ホスト送信なし）と、LLM APIキーを不要にする方針が強調されています。透明性はダッシュボードで補われます。
Local storage
SQLiteで保存（ホスト型メモリサービスへ送信しない）
API key
LLM APIキー不要（とされる）
※内部実装の詳細は提示文だけでは不足。design資料の確認が必要です。
DISTINCTION
11 / 16
境界（Boundaries）

できないことを前提化

Slowaveは推論エンジンではなく、記録されていない情報は想起できません。品質や性能はクライアントとフィードバック運用に依存します。
No inference
記録なし = 想起なし
Client dependent
クライアントのFeedback品質が鍵
Beta risk
公開βのためAPI/スキーマ変更・移行保証なしの可能性
COMPARISON
12 / 16
導入時の注意

品質・安全・運用の期待値

フィードバックが弱いと記憶が汚染されうる一方、SQLite平文保存は端末保護（権限/暗号化など）を前提にします。βなので移行手順も必要です。
Quality
Feedback依存 → 初期に改善が小さい可能性
Safety & Ops
平文SQLite（暗号化/権限管理） + バックアップ/復旧 + 移行互換性
ベンチマークは予備的で、エンドツーエンド精度の強い主張ではないとされています。
CLOSING
13 / 16
結論

“再入力”を減らすが要観測

Slowaveの主価値は、セッション途切れで発生する繰り返し作業を減らし、利用結果で記憶を適応させる点です。導入後はダッシュボードでretrieval/記憶更新を継続観測しましょう。
Pros
実務的：制約・判断の再利用を促進
Transparency
retrieval/feedbackを検査可能
Watch
不要記憶の蓄積・フィードバック品質・β変更を管理
Next: design.md/architecture.md と benchmarks.md（方法論・限界）で実装詳細を確認するのが妥当です。
