ターミナル実務型
FuXi 整理
FuXi（fuxicodex）が「何か」「どう動くか（Think→Act→Verify）」「安全・評価・導入/運用」を、README等の記載をもとに読みやすく再構成します。
対象：一般（技術用語は必要最小限にして、英語＋日本語の補助語を付けます）。
READING DECK
PROBLEM
03 / 16
質問で終わる？
作業が続かない
多くのAIは「提案」や「コード生成」で止まりがちですが、開発は“編集→実行→検証”まで一気通貫で進めたい領域です。
Output / 出力 だけ
回答は出るが、変更が正しいかは人が確認する。
Loop / 反復 が必要
失敗→修正→再実行→検証までが本体。
FuXiは、この“反復ループ”をエージェントの中核として設計すると説明されています。
Think • Act • Verify
METAPHOR
04 / 16
車と運転手
モデルは車
READMEの見立てでは、LLMは「エンジン」、FuXiは「運転手（ワーカー）」であり、推論だけでなくコード編集と実行と検証を回します。
Think 考える
状況を読み、次の手を計画する。
Act 実行
ファイル操作・コマンド実行・ツール呼び出し。
Verify 検証
結果を確認し、失敗ならループ継続。
要点：成果物を“出力”として終えず、“検証可能な状態”へ寄せる思想。
Agent Loop
ARCHITECTURE
05 / 16
プロバイダ非依存
選べるLLM
FuXiはOpenAPI互換モデルなどを前提に、複数のLLM提供元をルーティングしつつ、失敗時はフォールバックで継続を狙います。
OpenAPI Compatible 互換
“何でも可”ではなく、想定する接続方式に合う必要がある。
Routing + Fallback 切替
コストや応答品質、失敗継続を意識して運用する設計。
注意：設定条件の詳細は抜粋だけでは断定できないため、ログと挙動確認が重要になります。
Cost-aware
CORE
06 / 16
実務の要点
“端末で”回す
FuXiの価値は、エージェントがターミナル内でコードを読み・編集し・コマンドを実行し、ツールを使い分けるところにあります。
Read 読む
既存コードベースを理解する。
Edit 編集
変更を入れ、差分として管理する。
Run + Verify 実行/検証
コマンドで確かめ、必要なら再度ループ。
解釈の核：出力品質より“作業完了までのループ性能”を測りたい姿勢。
TUI / Terminal
PROCESS
07 / 16
失敗前提で設計
安全な自律
自律実行は最重要リスクなので、シェル命令をASTベースで事前検査し、権限モードと監査ログで制御すると説明されています。
AST Safety Classifier 事前分類
シェル命令を解析して、実行前に安全性を判定。
Permissions + Audit Log 統制
権限モード（例：default/plan/bypassPermissions）とログで追跡。
限界：万能な安全保証ではないため、段階的許可とログ確認を前提に運用するのが現実的です。
Not perfect, but designed
EVALUATION
08 / 16
スコアより再現
公開ベンチ少なめ
README上ではSWE-bench等の“第三者ヘッドライン数字”を全面に出しておらず、再実行可能な自前タスクと検証手順を重視すると読めます。
Third-party Headline 未掲載
「普遍的に強い」比較の直感は作りにくい。
Self-check / Replay 自前検証
手順を追えば、ユーザー側で確認できる。
注意喚起：小規模タスクでは“モデル性能”というより“エージェントループ”を測る点に注意。
Measure the loop
DISTINCTION
09 / 16
何を期待すべき？
強みの場所
FuXiは“一般的なベンチ比較での勝利”より、“実作業を回し、検証まで到達する設計”が中心にあります。
Good fit 向く条件
端末での編集/実行/検証が絡む開発業務。
Caution 注意
比較スコアだけで性能保証を判断しない。
あなたのプロジェクトで再現検証することが、判断の精度を上げます。
Reproduce locally
OPS
10 / 16
導入は段階的に
doctor / verify
導入・運用は、自己診断（fuxi doctor）や接続検証（fuxi verify）で環境を確かめ、更新はチェックサムと原子的置換でリスクを下げるとされています。
fuxi doctor 診断
環境・設定の問題を洗い出す。
fuxi verify 検証
接続や動作の確認をする。
Atomic update 更新
SHA-256確認＋原子的な置換。
補足：どの範囲が原子的か、ロールバック挙動などは追加確認が必要です。
Operational safety
DATA
11 / 16
履歴とメモリ
保存は要確認
トランスクリプトの永続化、チェックポイント、トークン節約、アイドル時の“dreaming”でメモリ統合が述べられていますが、保存先や期間は本文抜粋だけでは確定できません。
Persistence 永続化
/history などの設定・保存方式を確認する。
Token & Memory 節約/統合
保持量・統合条件が運用コストに直結。
運用上は、削除手段・保持期間・共有範囲を把握しておくと安心です。
Privacy posture
TAKEAWAYS
12 / 16
判断の型
導入は前提付き
FuXiは“編集→実行→検証”を回す実務型エージェントで、プロバイダ切替・フォールバック・安全分類器・doctor/verifyの明文化が強みです。
Strengths 強み
Think→Act→Verify、費用意識ルーティング、AST安全分類、監査ログ、自己診断。
Limits 限界
第三者スコアは限定的、分類精度や失敗モードの保証は別途確認が必要。
おすすめ運用：権限モードを段階的に引き上げる／/statusや/usageで観察する／自分のプロジェクトで再現検証する。
Pragmatic rollout
