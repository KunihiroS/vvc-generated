KEY IDEA
02 / 18
receiptで“権限の起点”を固定する

Capability receipt

署名検証がスキップされる、または自己承認のように“承認されたように見える”状態は同じ脆弱性です。
それを防ぐ鍵は、監査用の receipt（証跡）を設計し、生成主体と検証境界を外部化することです。
英: capability / receipt / signature verification（署名検証）
日本語：権限 / 証跡 / 検証
PROBLEM
03 / 18
“署名なし”が通る恐れ

検証の欠落

2015年に知られた「alg=noneで未署名トークンが受理される」型は、権限詐称の最短経路になります。
重要なのは“署名がある/ない”ではなく、署名検証が行われないことです。
失敗の形
検証器が見落とす → 未署名トークンが「有効」扱い
本質の原因
“権限の起点”が偽造できる（検証されない起点）
同じ根：承認根拠が検証されない
英: unverified trust
METAPHOR
04 / 18
“鍵”に見える紙切れ

起点を偽る

capability（権限）が“鍵”だとしても、付与者の署名・承認根拠が検証不能なら、攻撃者は鍵の見た目だけ作れます。
receipt（証跡）と外部検証境界は、その“偽の鍵”が通らない壁です。
capability
実行可能な権限の単位（英: capability）
receipt
承認の証跡（英: grant receipt）
witness
目撃者/外部参照（偽造を難しくする境界）
自己申告は“鍵束”になり得る
日本語：権限の自己主張
ARCHITECTURE
05 / 18
capability_grant_receipt

receiptスキーマ

提案は capability_grant_receipt を監査用に明確化し、付与・検証の根拠を構造化して曖昧さを減らします。
receiptが「証拠である」ために、フィールドを“必要な問い”に合わせます。
監査できる中身
granted_by=nullの誠実な扱い／grant_recordの所在／detected_by／reviewer／disposition（取消・限定・未解決）
狙い
「誰がいつ何を承認し、どの状態にしたか」を形式化（監査の属人性を低減）
receipt = “後から納得”ではなく“入口”
英: auditability at decision-time
EVIDENCE
06 / 18
露出した“設定の危険”

プレーンテキスト秘密

実運用では、MCP configのような実行時設定から資格情報や許可を読み込むケースが増え、そこに自己申告の承認が混ざると同種の失敗が起きます。
例として GitGuardian は「公開GitHub上のMCP設定で2,117件の“verified-valid secrets”」を報告しています。
なぜ危ない
設定が未レビューのまま“意図せず有効”になる（境界の不在）
何が同型化する
「署名が検証されない起点」と「自己が承認する起点」が同根
机上の議論ではない
2,117件という具体
DISTINCTION
07 / 18
ログ≠証拠（receipt）

“体裁”は脆弱性

receiptを「単なるログの枠」で扱うと危険です。
“誰も生成できないはずなのに生成された体裁”があるなら、それは単なる記録ではなく、防御設計の不備（脆弱性）になります。
ログの弱点
後追い記録だけでは、付与の正当性（誰が検証したか）を担保できない
receiptの役割
検証の入口を作り、必要情報（所在・reviewer・disposition）を要求する
英: evidence vs. trace
日本語：証拠と痕跡
COMPARISON
08 / 18
二つの現象は同じ

同一の失敗

投稿は「署名がないのに署名検証を通す」ことと、「誰も割り当てていないのに自己が承認権限を持つ」ことを同一の失敗として捉えます。
どちらも“検証されない起点”が権限を有効にしてしまうからです。
2015型（例）
alg=none → 未署名トークンが受理
自己承認型
自己が“付与された”ように宣言 → 承認の根拠が欠落
共通原因：起点が未検証
英: unverified trust anchor
BOUNDARY
09 / 18
内部生成は無効

receiptの置き場所

receiptが「内部者（攻撃者が自由に書ける領域）」に置かれ、更新権限が奪えるなら、receiptは証拠ではなく偽物を量産できます。
したがってreceiptには、不変の外部目撃（witness）や外部参照が必要です。
危険
攻撃者が書ける receipt → “検証された体裁”だけ増える
必要
外部の目撃・不変参照（英: witness / immutable reference）
結果
改ざんできない“真実の参照”で権限の起点を固定
receiptは“媒体”であり“境界”でもある
日本語：配置設計が本体
PROCESS
10 / 18
submission前に結合する

pre-submit lock

receiptは「許可の枠」だけで終わらせず、意図（intended action）に事前結合し、submission前にロックするべきです。
さらに履歴（行為の連鎖）まで監査できると、すり替えの余地が減ります。
結合する対象
campaign_snapshot_hash / recipient / amount / asset / policy_version / evidence_summary_hash
追加の要件
オンチェーン確定状態との照合（例：BaseScan等）へ参照を持つ
“何かが許可された”を“この行為が許可された”に変える
英: bind to intended action
RISKS
11 / 18
receiptの落とし穴

再帰と誤判定

receipt設計だけでは勝てません。エージェント自身が自己の証跡を作れるなら、自己検証＝自己署名のループになり得ます。
さらに verified の定義・検出閾値は誤検知/見逃しという運用ボトルネックを生みます。
再帰問題
i 内部で検証 → 自己が証跡注入可能
ii audit_scopeの境界を誤ると無力化
verifiedの難所
閾値設計（例：埋め込み類似度）で止めすぎ/見逃しが発生
→ receipt以外の意思決定ロジックも必要
receiptは万病薬ではない
英: system-level policy required
POLICY
12 / 18
granted_by=nullの扱い

null ≠ 有効

granted_by=nullは「付与者が不明」という誠実さを表しますが、それでも権限が実行される設計なら危険です。
原則として null のまま有効化しない（または安全な制限付きへ落とす）方針が必要です。
提案の意図
誠実に不明を表現する（falseの承認を作らない）
必要な挙動方針
最終的に実行されるまでに null を許容しない
英: unknown grantor should block by default
日本語：既定で拒否
TRUST
13 / 18
外部検証境界が要点

誰が検証するか

成功条件はスキーマ自体ではなく、receiptの生成主体と保管主体を厳密に分離し、外部検証境界を設けられるかにあります。
ここが曖昧だと、攻撃者は“それらしい receipt”を作れてしまいます。
生成主体
誰が receipt を作れるか（英: issuer）
保管主体
誰が不変参照として保持するか（immutable storage）
検証主体
外部境界で検証できるか（英: external verifier）
receiptの“正しさ”は運用設計で決まる
日本語：分離が鍵
TAKEAWAY
14 / 18
防御設計の焦点

脆弱性は“証跡”に出る

receiptを“誰も生成できないはずなのに生成された”なら、それはログではなく脆弱性です。
勝ち筋は、receiptの形式化に加えて、receiptが改ざん不能な外部事実になるようにシステムを組み替えることです。
設計の要点
i capability_grant_receiptを監査可能に
ii witness/外部検証境界を必須化
iii intended actionへ事前結合
運用の要点
verifiedの定義・閾値・停止/通過方針を別途設計
（receiptだけでは誤判定は消えない）
英: evidence-first security
日本語：証拠起点の安全設計
