研究の作業机を統合
Panel 概観
チャットだけでなく、ファイル・PDF・ノートブック等を同一ドック内の複数Panesに統合し、研究者とエージェントが同じ作業フローを進められる統合ワークスペースです。 （日本語 gloss: 統合UI=“統合された画面での作業空間”）
目的
コンテキスト切替を減らし、研究成果物を同じ画面で扱う
主機構
Panes / Modules（型付き） / DAL（データ抽象）
読み手前提：ファイル種別の切替が多く、進捗の透明性が重要 （README要約ベース）
PROBLEM
03 / 18
研究の“切替地獄”
Panes が効く理由
研究は画像・データ・コード・PDF・ノートブックなどを行き来するため、画面の行き来が認知的コストになります。 PanelはそれをPanes（表示枠）で同一空間に統合します。
問題
資料種別ごとの切替が頻発
設計
同一ドックにPanesとして統合
効果
“同じ作業机”で読み書き・参照
カスタムPanesも追加可能（拡張前提） （Japanese: 表示枠=表示ユニット）

研究ワークスペース
Panelはチャットに加え、ファイル・PDF・Markdown・Jupyterノートブック等を同一画面で扱います。 エージェントは必要に応じて読み書きし、Panesへ成果物を出します。

05 / 18
透明性を設計で担保
Modules Protocol
Modules Protocolは、入力・出力だけでなく途中経過（Intermediates）を型付きで定義し、検証や進捗表示につなげる方針です。 長時間処理や複雑ワークフローの信頼性を狙います。
Input
型付きで“何を渡すか”を固定
Intermediates
途中生成物を観測可能に
Output
型付きで“何を出すか”を固定
読み取れる狙い
Chain-of-Thoughtやスクラッチパッド“相当”の観測要素を設計対象にする意図
ただし表示/非表示の運用はREADMEだけでは不明 （Japanese: 観測可能=見える化）
DISTINCTION
06 / 18
UIだけじゃない拡張点
Panes vs Modules
Panesは“表示枠”で、Modulesは“実行の部品”です。 Panelはこの2つを分け、研究者が成果物を見ながら、エージェントの処理が進む構造を目指しています。
Panes
読み書き対象（成果物）を同一画面に配置
Modules
入力/出力/途中経過を型で定義し実行する拡張
結論
見える場所（Panes）と、考える/作る手続き（Modules）を接続することで“研究机”を再現
カスタムModules + 可視化Panes も想定 （Japanese: 可視化=視覚で追跡）
ARCHITECTURE
07 / 18
保存先の面倒を隠す
DAL（Data Abstraction Layer）
DALはURI（参照）を、メモリ上とローカルファイル上のどこに割り当てるかを吸収します。 Modules側の実装負担を下げる意図が示されています。
対象
URI / 実体（メモリ or ファイル）
役割
割当の判断を吸収して隠蔽
効果
モジュール実装の負担を軽減
読み替え
“参照の書き方”を統一し、保管場所の違いを後段で吸収する設計
（Japanese: 抽象化=具体を隠す層） 拡張性の土台

起動できない時
dev:doctor と確認
サーバ到達不可のときは `pnpm start` を実行しているか確認しRetryを押します。 ポート競合や読み込み不能は `pnpm dev:doctor` で競合相手と解消方法を確認します。
ケースA
サーバに到達できない
i `pnpm start` 実行確認
ii Retry
ケースB
ポート競合 / 読み込み不能
i `pnpm dev:doctor` 実行
ii 競合相手を解消
（Japanese: doctor=診断/補助） FAQベース

13 / 18
要点4分類で整理
強み/リスク
Panes統合とModules設計は実務適合と拡張性に寄与します。一方で早期ビルドゆえの誤操作・不安定挙動、セキュリティ/透明性の運用不足がリスクになります。
Practical（実務性）
同時にチャット/ファイル/ノートブックを扱うUI
Strategic（戦略/拡張性）
型付きInput/Output/Intermediates + DALで土台固め
Risk（リスク）
テスター段階：安定性/ガードレール/復旧が読み取りにくい
Transparency（透明性）
Intermediates可視化を狙うが、露出範囲の実装は不明
（Japanese: Transparency=見通し） Securityも同様に要追加検証

14 / 18
追加で確認したいこと
判断のための論点
README情報だけでは、ファイル操作の確認粒度、ノートブック競合解決、変更履歴/バックアップ/ロールバック、セキュリティ方針、Modules作成時のガードレールが十分に分かりません。
運用（安全性）
① ファイル操作の“確認範囲”
② ノートブック競合の挙動
③ 変更履歴/バックアップ/ロールバック
ガバナンス（情報/保護）
④ セキュリティとプライバシー方針
⑤ Modulesの作成例とガードレール
⑥ ログ保持と取り消し可能性
結論（慎重姿勢）
個人データや重要成果物への適用は“テスター前提”としてバックアップ込みで検討すべき
（Japanese: ガードレール=誤操作防止） 追加情報が意思決定を支える

研究ワークフロー再設計
結論一言要約
Panelは、研究者が“同じ作業机”でエージェントと共同作業できるよう、統合UI（Panes）と型付き拡張（Modules）とデータ抽象（DAL）を組み合わせた実験的ワークスペースです。 テスター段階ゆえ、安定性・安全性・透明性の運用確認を前提に導入するのが妥当です。
核
Panes統合で切替負担を削減
設計思想
Input/Output/Intermediatesを型で定義
前提
早期ビルド → ガードと検証が必須
次の一歩
重要データは避け、まずは小さなワークフローで：ファイル操作確認/ノートブック競合/ロールバック/ログ/セキュリティを検証する
