静的解析・LLMなし

推定の前提

PromptSonarはスキャン中にLLM呼び出しをせず、ローカルファーストで実行します。推定結果に root cause と Confidence を添えて提示します。

No LLM during scan
“それっぽい生成”を避ける
Evidence-first
finding.workflow.path と root cause
静的解析のため、推定は「攻撃が成立することの保証」ではなく、危険の可能性が高い経路を示します。

06 / 16

何を出すか（発見物）

3つの核

PromptSonarは、信頼境界越えの“経路”を、Confidenceと合わせて提示し、MCPの攻撃面をスコア化し、運用できる形で出力します。

i. Path
workflow.path：trust-state/taintを伴う到達
ii. Confidence
0–100で“推定の確度”を可視化
iii. MCP Risk
autoExecute／permissions／承認等を総合評価

07 / 16

高確度の経路例

Root Cause

入力データの例では、autoExecute=true と permissions="*" が、最終的にMCP実行に繋がる疑いを強めます（例：Root Cause: MCP Tool Poisoning）。

設定ミスの典型
permissions="*"：特権的シンクへ広がる
実行到達の形
autoExecute=true：承認前に実行機会が増える
発見は「なぜ危険か」をルールと根本原因へ分解して説明する、という姿勢が強調されています。

11 / 16

fail-onの改善

fail-open回避

--fail-on が認識されない場合、以前は0で静かに終了する（fail-open）挙動だったものをやめ、未認識ならエラーに変更したとされています。CIゲートの信頼性を上げる変更です。

以前
未認識 → 0で終了（見逃し）
改善後
未認識 → エラー（検知の沈黙を防ぐ）
COMPARISON
12 / 16

強みと限界

静的推定の現実

強みは「特権シンク到達」「承認ゲート」「ワイルドカード権限」「資格情報伝播」など、成立条件に近い論点へ焦点を当てることです。一方、静的解析ゆえ誤検知や過信には注意が必要です。

Strength
経路ベースで優先順位を付けられる（Confidence付き）
Caution
推定＝攻撃成立の保証ではない（人手レビュー＋実行時ガード）
CLOSING
13 / 16

最終判断は運用次第

使いどころ

PromptSonarは「危険の可能性が高い実行経路を早期に発見し、経路を切る判断材料を提供する」価値が大きいです。静的推定の制約を前提に、mcp_risk_threshold・waiver（許可/免除）・レビュー体制を慎重に設計してください。

1
Confidenceとroot causeを確認
2
SARIF/CIで差分監視
3
実行時のガードで最終担保
