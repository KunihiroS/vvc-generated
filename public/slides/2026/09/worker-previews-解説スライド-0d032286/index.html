COVER
02 / 20
ブランチ検証を“隔離”で速く
Worker Previews
Gitブランチごとに本番同等に近いプレビュー環境を用意し、テスト→観測→修正のループを安全に回せる仕組みです。
対象: エージェント開発ライフサイクル（ADLC） / state isolation（状態分離）/ reproducibility（再現性）
PROBLEM
03 / 20
stagingのズレが罠
なぜ
サーバレス/エッジ開発では「stagingでは動いたのに本番で違う」が起こりやすく、原因が設定・シークレット・バインディング・URL・ログ/計測・永続状態に分散します。
差分が生むもの
再現できない挙動 / 調査時間の増加 / 修正の見当違い
特に危険
Durable Objects・Containersのような“状態”の共有
結果: 検証ループが長くなり、エージェントが根拠（観測）を揃えにくい
METAPHOR
04 / 20
検証用“隔離スイート”
本番の型
Worker Previewsは、ブランチごとに“本番同等に近い隔離環境”と“テスト用URL”を自動作成し、変更ごとに問題を閉じ込めます（ブランチ検証のスイートルーム）。
each branch
独立URL（テスト窓口）
same product-ish
設定/観測/状態まで分離
safer iteration
観測→修正→再検証を短縮
bilingual: 隔離（kakuri）/ 再現性（saisei-sei）
ARCHITECTURE
05 / 20
ブランチがURLを持つ
仕組み
Worker PreviewsはGitブランチごとにプレビュー環境を構成し、URL・変数/シークレット・バインディング・観測・永続状態をブランチ単位で切り分けます。
実行単位
ブランチ（branch）ごとに独立
切り分け範囲
URL / vars / secrets / bindings / observability / state
目的
互いのテスト干渉を減らす
運用効果
原因探索の探索空間を縮小
補足: previews blockでベース設定→上書き制御が前提
COMPARISON
06 / 20
“バージョンURL”との違い
比較
従来のバージョンURLは特定のアップロード済みバージョンへ到達する参照点で、ブランチごとの隔離（設定・状態・観測の完全切り分け）を保証しません。
バージョンURL
参照（uploaded version）中心 / ブランチ隔離は一貫しない
Worker Previews
ブランチ別に独立URL・設定・状態・観測を構成
核: “テストが相互干渉しにくい”こと
ENUMERATION
07 / 20
重要ポイント五つ
要点
Worker Previewsが“検証の質”を上げる核は、隔離・状態分離・設定規律・認証連携・観測追跡です。
i 隔離
本番同等に近い環境（URL/設定/観測/状態）
ii 状態
Durable Objects/Containersをブランチ専用に分離
iii 運用
previews blockでベース定義＋上書き差分
iv 認証
カスタムドメイン＋Cloudflare Accessで本番同様に検証
v 観測
ログ/エラー/メトリクス/トレースがプレビュー単位で追跡可能
効果
ADLCの実効性（原因→修正→再検証）を高める
bilingual: 隔離（kakuri）/ 観測（kansoku）/ 認証（ninshou）
EVIDENCE
08 / 20
観測が“証拠”になる
トレース
変更ごとに計測が分離されると、原因究明の探索空間が小さくなり、エージェントがトレース等の“根拠”を使って修正ループを回しやすくなります。
何が分かれる
ログ / エラー / メトリクス / トレース
なぜ効く
失敗状況と挙動をブランチに結び付けられる
ADLCの前提: “実行結果”＋“観測情報”が揃うこと
DISTINCTION
09 / 20
Durable Objectsは“同一ID固定”
核心
Durable Objectsは「同一オブジェクトIDは同一インスタンスが担当」するため、本番と同じ名前空間を共有するとテストがライブの状態を変えてしまう恐れがあります。
性質
同一ID → 同一インスタンス
リスク
本番状態の破壊 / 想定外の相互作用
対策
プレビュー作成時に新しい名前空間/Containersを自動生成
結果: 失敗の波及を抑え、同時並行検証が可能になる
PROCESS
10 / 20
検証ループ（ADLC）
回し方
エージェントはプレビューURLを開き、観測（トレース等）と挙動を根拠に修正し、再デプロイして再検証します。
Step i
ブランチのプレビューURLへアクセス
Step ii
Workers Observabilityのトレース等を確認
Step iii
失敗原因を修正→再デプロイ→確認
必要に応じてヘッドレスでログイン/UIフローも検証
ENUMERATION
11 / 20
設定は“雛形＋上書き”
previews block
すべてを毎回手作業すると破綻するため、Wrangler設定の previews blockでベース（共通）を定義し、差分だけを制御します。
ベース設定
共通のvars/secrets/bindings/観測方針
上書き差分
例: 別DB / テスト用APIキー
メリット: ブランチ増に対して運用負荷がスケールしやすい
EVIDENCE
12 / 20
認証連携まで再現する
カスタムドメイン
OAuthやCookie、CORSは条件がシビアなため、カスタムドメイン＋Cloudflare Accessで本番同様に認証/連携検証できます。
外形
カスタムドメインで体験を近づける
制御
Accessでサインイン必須にできる
検証
Cookie / CORS / OAuthリダイレクトを確認
単なる機能確認ではなく“実運用に近い動作検証”へ
DISTINCTION
13 / 20
“本番同等”の前提
限界
本記事の強調は「URL・観測・永続状態まで分離して差を減らす」ことですが、外部依存（DB/外部API等）の揃え方によっては差分が残ります。
残り得る差分
ネットワーク条件 / 外部サービスの接続先差
確認すべき点
外部依存先をどう切り替えているか
結論: “隔離で再現性を上げる”が、完全一致はチーム実装に依存
PROCESS
14 / 20
導入前の設計チェック
要点
導入するなら、ベース/上書き規律、永続状態のポリシー、外部依存の切り分け、失敗時のリカバリ手順を事前設計します。
(1) 設定規律
ベース設定＋上書き差分のルール統一
(2) 状態ポリシー
消去/保持の方針（どこまで残すか）
(3) 外部依存
DB/決済/メール/認証プロバイダの接続先分離
(4) リカバリ
隔離によって“守られる変更/守られない変更”を明確化
心理/品質面: 「stagingと本番のすれ違い」コストを減らす
COMPARISON
15 / 20
利点と懸念
まとめ
利点は再現性と安全性、観測可能性の同時向上。懸念はコスト/運用負荷と、外部依存の切り分け責務が残り得る点です。
利点
検証可能性（reproducibility）↑ / 状態分離（state isolation）↑ / 原因究明コスト↓
懸念
大量ブランチ時の消費 / トレース量 / 環境ライフサイクル / 外部依存の差
戦略: 短寿命/保持の線引きを設計するほど効果が出る
