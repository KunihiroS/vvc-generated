RSIの“芽”を実装から見る

GLM 推論 進化

巨大言語モデルの推論インフラ（GPU運用・メモリ・並列化・通信・監視）を、AIエージェントが実験と検証で改善していく初期事例を要約します。

Concept / 概念
Recursive Self-Improvement（RSI）／再帰的自己改善
核心 / Core
dense feedback（原因帰属可能な高密度フィードバック）
PROBLEM
03 / 16
ログだけでは次へ進めない

原因 が見えない

エンドツーエンドの指標だけ（TTFT・スループット等）だと、どの層（カーネル実装、並列戦略、通信、メモリ、オーケストレーション）が原因か特定できません。

E2E
改善/悪化は見えるが、原因が混ざる
Local
局所検証がないと仮説が更新できない
Agent
次の実験に進む“根拠”が不足
METAPHOR
04 / 16
地図がない探索は迷子

dense feedback

量の多さではなく、「安価・迅速・局所・客観検証」で、観測が“どの変更の効果か”結び付く設計が鍵です。

Local性
カーネル／経路（例：CP）単位で検証できる
検証性
数値誤差・イベント・トレースにより因果を写像できる
安価・迅速
仮説→変更→局所検証を短い周期で回せる
客観
ログ増量でなく、判断を支える観測の整理
ARCHITECTURE
05 / 16
Infra Agentの検証ループ

段階検証 連結

カーネル単体テスト→マイクロベンチ→実行トレース/ランタイムイベント→エンドツーエンド負荷試験を段階的に組み、必要に応じて本番確認へ接続します。

i
Kernel tests / カーネル単体
ii
Microbench / マイクロベンチ
iii
Trace-Event / トレース・イベント
iv
End-to-End / 負荷試験
v
Production / 本番確認（必要時）
Loop
仮説→変更→局所検証→必要なら本番
EVIDENCE
06 / 16
事例1：数値誤差は“経路対応”で潰す

CPで 誤る

CP（Context Parallelism）経路の数値誤差は、並列構成→実行されるカーネル経路→入力分割→精度設定（TF32/FP32等）まで対応付けて原因を特定しました。

観測
CP経路でモデル出力が一致しない（数値誤差）
写像
並列構成→経路→入力分割→精度（TF32入力でも精度選択が不適切）
KDAの例
Context Parallelism（CP）経路のバグ：tl.dot が TF32 入力にも関わらず精度選択が適切でない
EVIDENCE
07 / 16
事例2：並行性の穴は“境界条件”にある

KV転送 だけ遅い

KV転送が想定より大幅に遅いとき、タイムラインから「GPU計算とオーバーラップできていない」と判断し、Python/C++境界でのGIL解放不足が原因だと結び付けました。

症状
KV転送性能が想定を下回る
検証
実行タイムラインでオーバーラップ欠如
原因
Python/C++境界のGIL解放不足
教訓
上位レイヤがロック保持していれば、非同期機構があっても“期待並行性”は成立しない
PROCESS
08 / 16
事例3：カーネル成功を目的関数へ繋ぐ

速さは 全体 で

カーネル単体を速くしても、パイプライン全体では遅くなることがあります。そこで「最適化スケルトン（適用条件・制約・根拠）」を抽出し、層状の検証でエンドツーエンド効果を確認しました。

抽出
既存カーネル知見を再利用可能な形へ（適用条件/制約/検証根拠）
検証
アブレーションやプロファイルで“全体指標”へ接続
例
ReplaySSM／Replay後の計算削減などを短いサイクルで適用
COMPARISON
09 / 16
3観点を同時に守る

Correct / System / Perf

推論最適化は「速い」だけでなく、正確性（Correctness）、安定性（Performanceの安定）、本番で出るエンドツーエンド効果の同時達成が必要です。

Correctness
並列経路（CP等）での数値誤差を潰す
System Behavior
トレースで動作崩れ（並行性、境界制約）を特定
Performance
微小ベンチの成功をエンドツーエンドへ写像

短期で本番準備まで到達

2週間未満 投入

GLM-5.3-Flashの本番推論サービスを約10万台規模の中国製AIアクセラレータ上で新規構築し、段階最適化とフィードバックループで生産準備に到達しました。

スケール
約100,000台（AIアクセラレータ）
期間
2週間未満で本番投入の準備
改善
エンドツーエンドスループット：約3倍
示唆
次の学習・設計へ影響し得る点でRSIの“芽”
DISTINCTION
11 / 16
ただし“完全自律”ではない

人間の境界が 必要

目的設定・境界設定・リスク評価は人間が担うべきで、この記事の範囲では無制限な自己改善が自動的に到達するわけではないと明確に述べています。

到達点
インフラ最適化の高速ループ
未解決
目的・安全・リスクの自律最適化
責任
人間がガードレールを維持
COMPARISON
12 / 16
評価：説得力と不足点

次へ 考える

dense feedbackの強みは「局所で早く誤りを排除し、トレースで並行性を特定し、最後にエンドツーエンドで受け入れる」分界の明確さです。一方で、一般化・コスト・因果分解・安全メカニズムの詳細が読み取りにくい点が課題です。

強み
段階検証＋原因帰属可能性（判断できる観測）
不足
dense feedback環境のコスト・再現性・統計的扱いが不十分
追加で欲しい情報
構築コスト、成功/失敗率、主要な失敗モード、権限・安全制御（trusted access program）、他ハード/他モデルへの転用
CLOSING
13 / 16
要点まとめ

dense feedback が道具になる

RSIへ向かう初期実装として、重要なのは「改善」を魔法にせず、原因帰属可能な観測設計と段階検証で次の手を選べる状態にすることです。

i
E2Eだけでなく局所テストで仮説更新
ii
並列経路・境界条件に対応付けて原因特定
iii
カーネル最適化を全体目的関数へ写像
