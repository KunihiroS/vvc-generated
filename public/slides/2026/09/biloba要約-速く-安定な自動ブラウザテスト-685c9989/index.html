BILOBA / BROWSER TEST
02 / 14
速い・安定・デバッグ容易
Biloba要約
Biloba は「自動ブラウザテストが遅い・不安定（flaky）」問題に対し、待ち（polling）と入力の忠実性（fast/realistic）を設計で制御します。
狙い / Goal
非同期性を吸収して、テストの 手調整 を減らす。
体験 / Experience
Ginkgo/Gomega のような簡潔さ + 失敗情報の厚さ。
（日本語：Biloba / polling / fast/realistic は本文の用語として保持）
PROBLEM
03 / 14
flakyの原因
待ち不足
ブラウザ操作テストは非同期性（反映待ち・遅延）や画面遷移でタイミングずれが起き、遅い/不安定になりがちです。
遅い
手動の待機時間・再試行の増加。
不安定
成立前にクリック/入力して失敗。
原因特定が遅い
失敗時情報が薄く、推測が増える。
Biloba は「待つ」をライブラリ責務に寄せ、テスト記述側の負担を減らす設計です。
CORE IDEA
04 / 14
Eventuallyの実装
“成立まで待つ”
Biloba は基本的に、操作や状態確認を「成立するまで polling して」成功を確かめます（timeout までに成功しなければ失敗）。
polling / ポーリング
クリックや setValue が成立するかを見て、ダメなら一定間隔で再試行。
Eventually / いつか成立
明示的に matcher（Eventually/Consistently）で制御することも可能。
結論：タイミング依存の失敗を「テスト側の待機調整」から切り離します。
INPUT STRATEGY
05 / 14
fast/realistic
速度×忠実性
入力を二層に分け、通常は fast（軽量）で進め、必要な場面だけ realistic（CDP 経由でより本物）へ切り替えます。
fast track
JavaScript シミュレーションで高速化。
例：多くのクリック/入力はシミュレーションで再現可能。
realistic track
hover / occlusion など精度が必要なケースで使用。
例：realistic は CDP（Chrome DevTools Protocol）経由の入力。
Same API（例：Realistic()）で切替できる方針が、移行負担を下げます。
3 PILLARS

設計原則
Performance / Stability / Conciseness
Biloba は「速さ」「安定性」「簡潔なテスト記述」を同時に満たす方向で設計されています。
i / Performance
並列化 + fast 入力で高速化。
ii / Stability
デフォルト polling が非同期性を吸収。
iii / Conciseness
Ginkgo/Gomega 体験のように書きやすく。
ワンメッセージ：速くして、落とさず、書く量を減らす。

“見える化”

Screenshot

画像差分

VITEST SCALING
09 / 14
並列の作り方
Chrome共有
Vitest では「1つの Chrome を起動し、並列ワーカーごとにタブとデーモンを分ける」モデルでスケールさせる説明があります。
削減
Chrome 起動コストを 1回に圧縮。
確保
並列ワーカーが干渉しない構成（タブ/デーモン分離）。
結論：並列化による速度向上を、現実的な構成で実現します。
HOW IT FEELS
10 / 14
運用フロー
迷いを減らす
書き手が待機時間を微調整しなくても良いように、デフォルト polling が「成立まで試す」責務を担います。
i / 記述
クリック/入力/確認を意図で書く。
ii / 実行
成立判定 → 成立しないなら再試行。
iii / 失敗時
スクショ/console/DOM outline + 差分の言語化。
結果：タイミング依存の失敗を減らしつつ、原因特定を前に進めます。
DISTINCTIONS
11 / 14
fastでは足りない
realisticの出番
fast で基本を固めつつ、hover や occlusion、入力忠実性が必要な箇所だけ realistic に寄せるのが合理的です。
fastが得意
多くのクリック/値設定はシミュレーションで成立。
高速・軽量が効く領域。
realisticが得意
hover / CSS挙動 / 本物入力の精度が効く領域。
CDP 入力で正確性を上げる。
ワンメッセージ：正確さは“必要な所だけ”買う。
RISKS
12 / 14
導入時の注意
前提差とAPI変化
READMEの主張（速度比較・flakiness）は条件依存で断定できません。また v1 前で API が変わり得る点も明記されています。
ベンチ条件
CPU/ブラウザ/テスト構成/ネットワーク/並列度/CI性能で結果が変わる。
互換性
メソッド名・オプション・デフォルト挙動・pollingや比較ロジックが変わる可能性。
運用の結論：タイムアウト/間隔、realistic適用条件、回帰ベースラインを先に設計する。
CLOSING
13 / 14
今日のまとめ
鍵は polling と入力制御
Biloba はデフォルト polling で非同期性の失敗を吸収し、fast/realistic で速度と忠実性を切り分けます。さらに失敗時情報の厚さで、CIやエージェントでもデバッグを進めやすくします。
No.1
デフォルト polling（成立まで）で flake を減らす。
No.2
fast/realistic（二層入力）で速度と精度を最適化。
No.3
スクショ/console/DOM outline + 差分言語化で原因特定を早める。

補足：Ginkgo/Vitest、CDP（Chrome DevTools Protocol）、Eventually/polling の理解があると読み進めが速くなります。
