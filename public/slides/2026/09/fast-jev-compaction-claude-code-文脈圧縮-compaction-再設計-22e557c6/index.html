Overview
02 / 11
要約しない圧縮
fast-jev-compaction
Claude Codeの“コンテキスト圧縮”を、従来の要約ではなく意思決定（Jev）で最小限の情報喪失に寄せる設計です。(情報損失を抑えるための compaction)

Target 対象

tool_use / tool_result のみ（ユーザ/アシスタント文章は原文維持）

Core 発想

「残すべきか」と「結果本文を残すべきか」を分けて評価し、不要だけ削除/短縮

Problem
03 / 11
要約の落とし穴
“後で効く情報”が消える
通常のコンテキスト圧縮では、古い発話を要約するためファイルパス、エラー文言の正確さ、制約、コマンドなどが薄まる/消えるリスクがあります。

典型的に失われる

エラーの正確な行・文言／パス／制約／再現に必要なコマンド

Why 困る

テスト失敗の根因確認や、次のツール実行で参照すべき具体が欠落する

Metaphor
04 / 11
要約ではなく判定
“必要な事実だけ”
文章をまとめるのではなく、ツール呼び出しと結果をその時点で作られた事実として扱い、残す/消すを分岐させます。 (fact retention / 事実保持)

Step i

tool_use 自体を残すかを評価

Step ii

tool_result 本文をそのまま残すかを評価

Step iii

不要だけを削除/短縮し、トークン上限に収める

Architecture
05 / 11
二段階の意思決定
Jevで二つの問い
各非固定（pinnedでない）ツールに対し、Jevが(a) 呼び出しは残すか、(b) 結果本文はそのまま残すかを別々に判断します。

(a) Keep tool_use

「そのツールが実行された」という事実（呼び出しの存在）を維持

(b) Keep tool_result

「結果の中身を原文のまま残す必要」を判断し、不要なら短縮/削除

さらに、pinned（例：preserveRecentMessages の新しめ範囲）は決して触らない（保持）扱いで、直近文脈の損失を抑えます。 (固定/保持: pinned)
Mechanics
06 / 11
段階的 fit + 失敗時フォールバック
上限へ収める工夫
最大トークン上限（maxStateTokens / maxRequestTokens）に収めるため、fitを段階的に行い、入らなければ compaction throw してフォールバックへ委譲します。

Fitの手段

tool inputの制限、長文の頭末 abridgement、古い非固定メッセージの折りたたみ、古い tool call の1行化

Keepの確率

keepThreshold で“残す確率”を扱い、しきい値を下回れば削除され得る（安全性の証明ではない）

限界は「Jevの確率判断＝再実行できるから安全」ではなく、最終的に失敗時はClaude Code標準要約へフォールバックする設計で運用リスクを管理します。 (fallback / フォールバック)
Takeaway
07 / 11
採用の判断軸
結論：損失を制御する
fast-jev-compactionは「要約」から「意思決定（スコアリング）」へ圧縮の中心を移し、ツール関連で“後で効く情報”の喪失を抑える狙いです。同時に、誤判定・推定誤差・設定依存はゼロにできません。

Strength 強み

テキスト要約を避け、tool_use/tool_resultを粒度別に保持・削除。鍵情報（パス/エラー/制約）を残しやすい

Limitation 限界

keepThresholdの確率判断／トークン推定（文字数ベース）誤差／throw時フォールバックの挙動が依存点

導入は、短いセッションだけでなく「ツール結果が後で根因確認に効く」ケースで、preserveRecentMessagesやkeepThresholdの妥当性を検証するのが現実的です。 (verification / 検証)
