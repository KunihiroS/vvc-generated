main再設計

スマホでの mainline Linux を「動く」から「長く壊れにくい」へ近づけるために、Nura が main カテゴリをどう定義し直したか。

対象
スマホ端末ポート（移植）
鍵
Hardware CI（実機検証）
目的
長期安定運用 & セキュリティ追従
Problem
02 / 15
動く→崩れる

課題の中心

移植（ポート）が「起動して動く」状態でも、カーネル更新や変更の回帰で壊れ直すことがある。だから “main” は品質の期待指標として再設計が必要になる。

従来のズレ
機能数の多さが “本質” になりやすい
本質
長期維持の確実性（運用で守れるか）
Mainの再定義
03 / 15
main = 信頼

main意味が変わる

main カテゴリは「機能が多い端末」ではなく、「Hardware CIでよく検証され、強いメンテ体制で長期維持が見込める端末ポート」を指す。

再設計のタイミング
v24.12 で一度 main を空にし、PMCR-0009 を経て再設計
期待される効果
他ディストリでも扱いやすく、カーネルセキュリティ追従を容易化
要件
04 / 15
ほぼ完全 mainline

技術要件（移植）

main 入りには、UEFI起動・厳格で最小限のパッチ・フォークされたデバイス固有パッケージへの依存禁止・汎用デバイスパッケージ利用などが求められる。

Boot
UEFI 経由（UEFI boot）
Patch
最小限・厳格（回帰を抑える設計）
Dependency
フォーク/独自パッケージ依存を禁止
Reuse
アーキ向け “汎用デバイスパッケージ” を利用
Hardware CI
05 / 15
回帰を潰す

Hardware CIの役割

実機で継続的に動作確認する Hardware CI が、main が “壊れにくい” という期待を支える。コードだけでなく運用の信頼性を作る。

目的
カーネル更新時の回帰（regression）検出
結果
長期維持の見込みを数える（再発防止へ）

結論だけ

“main” の合意

main は「動作の成功」ではなく「長期維持できる設計と体制」。UEFI・最小パッチ・フォーク依存回避・汎用パッケージと、Hardware CIが品質の前提になる。

Meaning
長期維持の確実性（品質指標）
Tech
本流互換を高める最小パッチ戦略
Policy
フォーク依存禁止 / 汎用パッケージ利用
Ops
Hardware CI + メンテ体制で回帰対応
