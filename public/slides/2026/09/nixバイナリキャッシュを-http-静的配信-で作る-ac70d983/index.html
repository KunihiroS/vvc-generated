Nix Remote Cache
02 / 18
“Nix以外”も代理できる

発見転用

Nixのバイナリキャッシュは、Nix専用サーバである必要がありません。
必要なのは最小IFと、検証（署名・ハッシュ）です。
Problem
03 / 18
“場所”は要らない

前提非依存

Nixは、配布サーバの“住所”や“プロトコル”を信用しません。
だからこそ、別のHTTP配信や静的配信が同じ仕事をできます。
Nixが信用しない
通信経路 / ホスト / URL / 圧縮形式
Nixが検証する
Sig（署名） + NarHash（ハッシュ一致）
Core
04 / 18
最小IFは3要求

結論三つ

Nixバイナリキャッシュを提供するIFは3つの要求だけです。
これが満たされれば、サブストレータは“既存配信基盤”になり得ます。
①
nix-cache-info
StoreDirを得る
②
<hash>.narinfo
メタデータ取得
③
nar.xz（URLの圧縮本体）
アーカイブ取得
Security
05 / 18
検証が主役

鍵NarHash

Sigは特定フィールドをカバーし、URLや圧縮方式自体は署名対象外です。
それでも取得後にNarHashが一致すれば、内容は確定します。
Sigが守る範囲
StorePath / NarHash / NarSize / References など
最終合否
取得したアーカイブの NarHash 一致で受理

注意名前空間

何でもできる一方で、配信側の“仕様差”に合わせる必要があります。
特にGitHub Releasesはフラットな名前空間で、通常のパス構造とズレやすいです。
問題の例
通常想定（例：nar/接頭辞）と一致しない

npmで配る

提案配布網

さらにnpmを“バイナリキャッシュ兼チャネル”として使う例が詳述されています。
nix copyで作ったディレクトリをnpm publishすると、Nix成果物の依存込みパッケージとして配れます。
再現できること

Limitations
12 / 18
差分配信が弱い

弱点重複

npmは差分的なインクリメンタル配信が基本的に弱いです。
そのため同一ライブラリ（例：glibc）を含む複数版で重複アップロードが起きやすくなります。
具体例
glibcのような共有ライブラリが版ごとに再アップ
影響
帯域・ストレージが膨らむ（長期運用ほど効く）
Risk
13 / 18
セキュリティ以外もある

現場可用性

成功の背景にはCORSや静的配信ヘッダなど“周辺環境依存”があります。
また、URL先が壊れる・期限切れで落ちると、ハッシュ検証以前に取得できません。
依存
CORS / キャッシュ制御 / 配信ヘッダ
壊れた時
取得失敗（署名/ハッシュがあっても届かない）
期限
pastebinのGCのような削除リスク
Takeaway
14 / 18
できる→設計する

要点設計手順

“転用可能”の本質は、Nixの検証ロジックが経路の信用を不要にする点です。
実運用では、配信側の制約（ヘッダ/構造）と可用性運用（GC・ミラー）を別途評価します。
最初に確認
3要求：nix-cache-info / <hash>.narinfo / nar本体
次に設計
Sig運用 + NarHash一致 + URL/GC/保持期間を計画
