02 / 16
プロジェクト別の部屋
hop Session Manager

Sway workspace と Kitty を土台に、プロジェクト単位で作業空間を“集約”するセッション管理ツール。

前提 / Assumption
Sway（Wayland）＋ Kitty（端末）
核 / Core idea
セッション ≠ ウィンドウ管理（分離）
PROBLEM / 問題
03 / 16
tmux的な結びつき
なぜ 分ける？

tmux 等は「セッション（何を動かすか）」と「ウィンドウ（画面）」が強く結びつきやすい。

従来の圧 / Friction
端末内の操作が増え、GUIも散らばる
狙い / Goal
プロジェクト移動を素早くし、Swayの操作をそのまま使う
ARCHITECTURE / 全体像
04 / 16
セッションは“部屋”
Sway workspace が中心

hop はプロジェクトごとに専用の Sway workspace を用意し、エディタ・ターミナル・ブラウザ等を同じ空間にまとめる。

workspace
プロジェクトの作業空間
editor / terminal / web
GUIも含めて“集約”
移動
Vicinae で選ぶ→瞬時に移動
workspace名例：s:<session>
DISTINCTION / 差分
05 / 16
tmuxと何が違う？
二重のキーを 外す

hopは「端末多重化」よりも「プロジェクト作業空間の統合」に重点を置き、ウィンドウ管理をOS側（Sway）に委ねる。

tmuxの傾向
セッション管理と画面（ペイン/ウィンドウ）が密結合
hopの姿勢
セッションを分け、ウィンドウ管理はSwayショートカットに統一
結果として、GUIアプリを同一 workspace に入れやすい。
PROCESS / ライフサイクル
06 / 16
prepare / teardown
自動で 立ち上げ

hopはセッションに紐づくライフサイクル（prepare / teardown）を面倒みる。

prepare（準備）
環境準備・必要プロセス起動・初期化
teardown（後片付け）
終了処理・クリーンアップ
失敗時は debug_log / popupログで確認できる設計。
ARCHITECTURE / backend
07 / 16
環境差を隠す
backendで 抽象化

ローカル実行だけでなく、DockerコンテナやSSH先などへセッションを展開するための backend を導入する。

host（ホスト）
そのままローカル実行
container（コンテナ）
同じプロジェクトを隔離して実行
remote（リモート）
SSH先で同様に起動
URL/アドレスのズレは次の変換で吸収する。
EVIDENCE / URL変換
08 / 16
port_translate / host_translate
クリックが 迷子 にならない

port_translate / host_translate が localhost 等を“ホストから辿れる”アドレスへ書き換える。

問題 / Risk
ブラウザ起点のアクセス先が backend 側のアドレスと不一致
対策 / Mechanism
port_translate / host_translate による変換
特にブラウザが常にホスト側の場合、この変換が体験の要になる。
METAPHOR / 体験
09 / 16
出力から“開く”
Kittyが 配線 になる

Kitty のプラグイン（kitten / hints 等）で、端末出力からファイルパスやURLを抽出し、エディタやブラウザへルーティングする。

エディタへ
ファイルパスを開く指示に変換
ブラウザへ
URLを送って閲覧へ誘導
png / pdf 等のバイナリは分岐して開く（後述）。
DISTINCTION / 制約
10 / 16
信頼とブラウザ常駐
“便利”の 条件

.hop.toml は shell コマンドを含められるため、hop trust を前提に実行される（信頼していない設定は実行されない）。

hop trust（信頼）
設定が実行コードになりうる
ブラウザの所在
README上「常にホストGUIアプリ」
ローカル/コンテナ/リモートの“隔離”をUIまで完全に求めるとズレる可能性。
PROCESS / 開発者連携
11 / 16
hop run / hop wait
外部統合の 契約

外部統合のために hop run / hop wait というコマンド契約を用意し、テスト実行結果を集めやすい設計になっている。

run（実行）
セッション内でジョブを走らせる
wait（待機）
完了・結果回収の導線を作る
日常運用と自動化を“同じ操作体系”へ寄せる狙い。
COMPARISON / 持ち味
12 / 16
導入判断の軸
強みと 注意点

強みは「tmux的閉鎖空間から抜けて、Sway workspaceでプロジェクトを統合」できること。

強み / Strength
セッションとウィンドウの分離、GUIも同空間、環境差をbackendで吸収
注意 / Watch
trust運用・ブラウザ常駐・前提（Sway/Kitty/Vicinae）・バックエンドの失敗時挙動
導入前に初期設定の信頼フローと debug ログ確認手順を検証するのが現実的。
CLOSING / まとめ
13 / 16
読むべき結論
hop を一言で

hopは「プロジェクト単位のworkspace」を軸に、セッション準備と環境差、Kitty出力のルーティング、URL変換まで統合しようとする設計。

要点 i
セッション/ウィンドウ分離（Swayに寄せる）
要点 ii
backend + port_translate / host_translate
要点 iii
hop trust とホスト常駐ブラウザ
bilingual補助：workspace（作業空間）/ セッション（session）/ 環境差（environment differences）。
