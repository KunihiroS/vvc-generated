02 / 16
Typed Decisions in One Pass
GLM-5.3-Flash/Jev流
LLMの「文章生成」ではなく「次トークン確率」を利用して、Jevのように選択肢ごとの確信度つき意思決定を単一フォワードパスで作る方法。
対象：オフ・ザ・シェルフLLM（GLM-5.3-Flash）を、候補（options）の集合と順序が既知なtyped decisionシステムへ変換するアプローチ。
problem
03 / 16
自信度は作業が重い
LLMの壁
通常のLLMは逐次トークン生成なので、毎回JSON全体を書いたり長い推論を入れたりすると、速度・コスト・定量的confidenceの扱いが難しくなる。
従来（生成）
文章やJSONを出すため、オーバーヘッドが増える。
必要（決定）
選択肢ごとの確率（confidence）を、低コストで返したい。
目標：選択肢集合が既知なら、確率分布を「生成」ではなく「確率切り出し」で得る。
metaphor
04 / 16
文字を作らない
確率だけ復元
LLMに「choice_index（選択肢番号）だけ」を出させ、その時点の語彙確率から各選択肢の確率分布を正規化して返す。
プロンプト設計
choice_index: に続けて「番号のみ」指定。
確率復元
次トークン位置の確率をallowed_token_idsで切り出し、オプションごとに正規化。
生成文は不要：Typed decisions = “同一出力位置の確率分布”の切り出し。
architecture
05 / 16
Jev型の出力形式
State × Options
Jevのように、state（状態）とoptions（候補）から最終選択だけでなく、各候補の確率（confidence）も返す構造をLLM運用に落とし込む。
入力
state（テキスト/画像）
候補
options（集合・順序が事前に固定）
出力
chosen option + 各confidence（確率分布）
本方式の鍵：optionsが既知であるため「番号→確率→正規化」を一発で成立させられる。
process
06 / 16
1回のフォワードパス
Single ForwardPass
「各候補を個別評価」せず、出力位置の語彙確率からallowed_token_idsに対応する部分だけを抜き出して、オプション確率分布を得る。
ステップ i
choice_index の次トークン位置を固定して問い合わせ。
ステップ ii
allowed_token_idsの確率を抽出し、総和で正規化してconfidenceにする。
期待される価値：JSON生成や長文推論のためのトークン消費を削減。
architecture
07 / 16
実装の要所
logprobが鍵
取得できるlogprob/logitsとトークナイザ挙動に依存するため、allowed_token_idsやlogprob_token_idsの扱いが設計の中心になる。
allowed_token_ids
選択肢インデックスに対応する“許可済み語彙”だけを対象にする。
logprob_token_ids
その語彙の確率（logprob）を取得して、オプション別に割り当てる。
単純に「top_logprobsだけ」では不十分になり得るため、指定tokenの整合を優先する。
evidence
08 / 16
公開29セット評価
精度は概ね同等
GLM-5.3-FlashをPrivatemode上で、公開データ29セットのベンチマークによりJevと比較した結果、テキスト系タスクでは意思決定精度・正確性が概ね同等と報告されている。
良い傾向
分類/意図ルーティング/法文/文書で、差が小さいケースが多い。
弱点
Layaは多くのデータセットで劣り、統計的に有意差が出たとされる。
「同等」は条件付き：候補数やラベルの揺れが結果に影響する。
comparison
09 / 16
Jev/Layaとの差
Typedの戦い方
この方式の差別化は「確率付き選択を1出力位置で作ること」で、さらにGLMのvision対応により画像付きtyped decisionsを狙える。
共通点
候補から選択 + confidence を返す。
違い
LLM確率の切り出しで“1回推論”に寄せる。
追加価値
画像入力：スキャン文書の分類など。
画像は可能だが、トークン/コストが増えるため経済性は別途見積もりが必要。
distinction
10 / 16
速い・安いは一律でない
コスト変動
入力トークン数、options数、サーバ側logprob取得の上限、ネットワーク要因でレイテンシ/費用が変わるため、単純比較は危険になる。
optionsが多い
精度が下がりやすく、実装上も問い合わせが増え得る。
logprob上限
logprob_token_idsの制約で複数回レスポンス統合が必要な場合がある。
例：地域（PrivatemodeがEU、JevがUS）でレイテンシが逆転することもある。
distinction
11 / 16
Confidenceは“復元された相対値”
校正の確認が必要
出力確率を正規化して得るため相対的な確信度としては有用だが、確率の校正（calibration）まで保証されるとは限らない。
有用性
相対順位・閾値運用の判断材料として活きる。
注意点
高リスク領域はconfidence閾値だけで自動化せず、キャリブレーション/人手介入が要る。
追加で知りたい：ECE/Brier等の指標、失敗パターン、失敗時の回避策、監査ログ設計。
process
12 / 16
導入チェックリスト
運用設計
精度・費用・安全性は条件依存なので、導入前に「options分布」「遅延SLA」「費用試算」「失敗時のガードレール」を固める必要がある。
評価
候補数分布とラベル揺れで天井を測る。
安全
校正・監査・人手介入条件を定義。
費用
テキスト/画像比率とSLAでROIを試算。
セキュリティ面はPrivatemodeで障壁を下げるが、脅威モデルや監査範囲は別途確認が必要。
closing
13 / 16
意思決定を“製品仕様”へ
答えは確率
LLMの生成コストを避け、次トークン確率を切り出して“Jev型のtyped decisions”を作る。導入の成否は、options数・logprob制約・確率の校正と運用設計で決まる。
強み
Single forward passで確率付き選択（confidence）を返せる。
留意
候補数/校正/費用/失敗運用を要検証。
参考：optionsが既知であることが、この方式の前提（Typedへの変換が成立する条件）。
