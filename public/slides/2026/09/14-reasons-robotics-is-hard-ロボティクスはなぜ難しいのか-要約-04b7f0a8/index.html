02 / 16
デモだけでは測れない
14 Reasons Robotics Hard
「ロボットがすぐ来る」という期待にブレーキをかけ、現実の現場で“何が難しいのか”を整理する視点です。
Key idea / 要点
デモ動画の“成功”が、現実の安定稼働（安定運用）を隠す。
Demo gap / 実現ギャップ
読みのコツ / How to read
技術だけでなく、安全・信頼・運用・制度まで含めて“システム”で見る。
Problem
03 / 16
見える進歩の偏り
データセンター偏重
私たちが目にしやすいのは、文章生成やコード作成のような“知的作業”の進歩です。
一方で、調理・介護・清掃・工具作業のような“身体性を伴う仕事”は、失敗や条件差がデモでは見えにくい。
デモの性質
成功場面を編集しやすい（cut/カメラワーク）。
観客の問題
試行回数・失敗率・環境揺らぎが分かりにくい。
結論
進捗指標として“デモ成功”を誤用しがち。
Metaphor
04 / 16
測定の失敗
一回の成功
デモは“たまたまうまくいった一瞬”を切り取れるため、汎用性（未知環境での再現性）を過大評価しやすいです。
起こりうる偏り
i 何十回に一度の成功
ii 状況を事前に最適化
iii 編集で速度・安定性を誇張
本来欲しい指標
安定稼働率、失敗の頻度、エッジケースでの挙動、環境変動への頑健性。
Architecture
05 / 16
ロボットは統合問題
“手”が最後
手先の性能（指・センサー）だけでなく、制御と総合性能が要求されます。
触覚の耐久、対象選定、運動計画、柔らかい物への瞬時補正まで“束”で難しい。
手（Manipulation / 操作）
握る対象の見極め → 路線計画 → 触れて補正 → 破損回避まで同時に必要。
総合（System / システム）
部品性能×制御×環境適応×信頼性が合成されて初めて“使える”。
Enumeration
06 / 16
乗り越える壁
14領域
汎用ロボットに必要な課題は技術だけでなく広範で、どれか一つでは済みません。
i 入力理解
視覚理解（Vision / 視覚）
文脈理解（Context / 文脈）
ii 意思決定
計画と反応（Plan+React）
協調（Collaboration / 協働）
iii 実行制約
速度・強度（Speed/Strength）
移動性・安全（Mobility/Safety）
iv 運用条件
稼働時間・信頼性（Uptime/Reliability）
過熱（Thermal）
v 現実の揺らぎ
エッジケース（Edge cases）
環境変動への頑健性
vi スケール
計算資源とスケーリング（Compute/Scaling）
量産・保守・供給網
Evidence
07 / 16
視覚だけではない
見る→掴む→避ける
混雑した現場では、対象を見分けるだけでなく「どこを掴むか」「転倒や接触をどう避けるか」まで同時に要ります。
認識の限界 / Recognition limit
精度向上だけでは足りず、行動として成立させる必要。
全体設計 / Whole behavior
予期せぬ出来事に応じて再計画（re-planning）し、連続的に安全を保つ。
Distinction
08 / 16
知識労働と身体労働
LLM≠現場の安全
LLMのような推論は強力でも、ロボットは“行動の連続性”と“危険が分散する領域”を抱えます。
そのため、同じ安全設計・検証の手順が単純には通用しにくい。
LLM / 知識
回答の品質（推論・言語）を中心に改善。
ロボット / 行動
動き続ける（常時運用）ことでリスクが積み上がる。
結果
安全と信頼性の工学が主戦場になる。
Process
09 / 16
暗黙知がボトルネック
文脈を要する
物の置き場所、個人の好み、介護者の補助レベル、異常の見分けなどが“常識”として働きます。
文脈（Context）
「何を」「どのように」するかの判断が状況依存で変わる。
暗黙知（Tacit）
広さと深さの事前データを準備しにくく、オン・ザ・ジョブ学習（随時学習）の設計が難しい。
Constraints
10 / 16
同時に厳しい条件
安全×速度×強度
速く動くほど安全確認の余裕が減り、強くて重いほど危険も増えます。さらに稼働中の過熱や故障頻度も、信頼性を下げます。
速度（Speed）
安全余裕が縮む。
強度（Strength）
事故の影響が大きくなる。
信頼性（Reliability）
可動部の多さ・過熱・故障頻度が効く。
Comparison
11 / 16
技術以外も壁
導入の障壁
ロボットは現場に入る瞬間から、政治・規制・組織・文化、サイバーセキュリティ、監視・プライバシー、責任の所在、コストの問題が立ち上がります。
制度・組織（Policy/Org）
規制、責任、導入義務、監督体制。
運用リスク（Cyber/Privacy）
サイバー攻撃への耐性、監視とプライバシーの設計。
Risks
12 / 16
“悪い事態”設計
前提は安全側
人身事故、誤動作、凍結（挙動停止/固まり）、サイバー悪用のような“悪い事態”を想定し、設計・検証しない限り現場投入は進みにくいです。
身体リスク
接触・転倒・衝突の連続制御。
状態リスク
過熱・故障・停止などの“現場状態”。
情報リスク
悪用・侵入・データ流出（privacy）への備え。
Closing
13 / 16
結論：過度な早期期待は危険
“すぐ来る”を疑う
工場のような制御環境を出て、家庭・介護・物流で「常に役に立つ」には、知識作業以上の壁があります。
だからこそ、デモに引っ張られた期待を前倒ししすぎないことが重要です。
実務への含意
成功率・稼働率・失敗パターン・安全検証を“指標”として要求する。
読後の注意
課題は広く列挙されるが、優先順位や定量比較は十分に示されない。
