Bounded choices + 確信度
Structured reads
vLLM の DiffusionGemma を使い、固定選択肢（はい/いいえ、カテゴリ、スケール等）から“確率付き”に選ぶ仕組みを、 PRとして整理します。さらに、entropy / logprobs で不確実性まで返す方向性を示します（Jev-like 思想）。
用語メモ：structured reads（構造化された読み取り）／bounded choices（事前固定の選択肢）
Problem
03 / 16
自由文だと困る
なぜ 選択 が必要か
通常のLLMは自由記述になりがちで、クライアントが確信度（確率）を使って意思決定するのが難しくなります。 そこで「固定選択肢から選ぶ」形式にし、さらに logprobs / entropy を返して判断を制御します（確率付き判定器）。
従来

自由文出力 → 構造化の解釈が不安定（確率も扱いにくい）

このPR

bounded choices（事前固定）→ 1つ（または複数）を選び、確信度も返す

bilingual：確信度（confidence）／不確実性（uncertainty）
Metaphor
04 / 16
canvas＝座標
判定器を 配置 する
DiffusionGemmaの内部にある canvas（復元対象の枠）上の“位置”を、リクエスト側で seed して固定します。 すると、選択肢が同じスロットに対応し、指定位置の logprobs を解釈しやすくなります（構造の安定化）。
canvas

枠（復元対象の位置）を固定

seed

選択肢の“座標”を同期

logprobs

座標に対応する確率を採取

Jev-like（Jev表現互換というより思想）：選択肢＋確信度で制御する
Architecture
05 / 16
単一トークン縛り
選択肢は 1トークン
構造化の成立条件は「選択肢が canvas 上の同一スロットに対応する」ことです。 そのためラベルを“単一トークン”として扱う制約を置き、位置ズレによる不整合を抑えます（クライアント側の設計が重要）。
狙い

canvas位置 ↔ ラベル の対応を固定

副作用

多トークンラベルはクライアント側で単一トークンへ写像が必要

schema design（スキーマ設計）が性能を支配する、という実証がある
Process
06 / 16
read-only＝収束で採取
diffusion_read_only
通常は commit が進むと状態が更新されますが、diffusion_read_only では read-only として、 収束（converging）ステップで canvas の出力を読み取り、温度1に近い確率情報（logprobs）を採取します。
ignore_eos

終端による停止を抑制

max_tokens

ステップの上限を制御

commit forward

スキップして“読み取り”に徹する

結果：entropyベースで確信度評価 → 運用ループへ接続可能
Evidence
07 / 16
確率で意思決定
再読（re-reads）運用
最初の read で entropy が閾値を超えたら追加サンプリング（re-reads）して agreement を確認できます。 例では「H1 entropyの比較→必要なら再読」という運用が示されています。
判断

entropy（不確実性）が低い → そのまま確定

救済

entropy が高い → 追加 read で一致性（agreement）を取る

これは単なる整形ではなく、“確率付き判定器”としての価値
Distinction
08 / 16
top-kではない
logprob_token_ids
top-k ではなく、指定した token ids について“正確な logprobs”を返すために logprob_token_ids が用意されます。 これにより、ラベル集合に対する確率分布（少なくとも指定ラベル群）をより正しく推定し、entropyなどの判断に使えます。
top-k

候補を切り詰めがち（ラベル集合全体の確率を直接は扱いにくい）

token ids指定

ラベルに対応する確率を直接採取 → 不確実性評価が安定

bilingual：確率分布（probability distribution）／不確実性（uncertainty）

傾向

まとめ：強みと条件
原理は強い、条件付き
強みは、DiffusionGemmaの canvas を seed し、read-only の収束ステップで logprobs を採取して、entropyに基づく“calibratedな意思決定”へ落とし込める点です。 一方で本番投入には、API正規化、回帰テスト増強、安全策（矛盾の検証や上限管理、透明性）など追加整備が必要です。
強み

確率付きの判定器（選択＋不確実性）／re-reads運用まで見通し

必要な追加

API設計の正規化、並列回帰、運用上限・整合性チェック、透明な検証

結論：方向性は非常に有望だが、プロダクション品質には未完が残る
