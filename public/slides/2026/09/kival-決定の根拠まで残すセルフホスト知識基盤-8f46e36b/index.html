02 / 18
決定の根拠を保存する

Kival × 組織知

Kivalは、単なるファイル置き場ではなく、議論・履歴・関係・プロヴナンス（出所/根拠）までを“文脈付きの共有知”として管理するセルフホスト型システムです。

このデッキは、提示README内容を根拠に「狙い／運用含意／注意点」を整理します（性能・監査・権限粒度などは不明点として明示）。

PROBLEM
03 / 18
理由が消える

なぜ決めた？失踪

時間とともに、意思決定の経緯（なぜそうしたか）が失われ、結論だけが残って説明が途切れます。

Symptoms / 症状
決定だけ残る / 根拠が追えない 根拠のトレーサビリティ不足
Why it matters / 影響
属人化・監査対応の負荷・説明コスト増 運用が重くなる
METAPHOR
04 / 18
結論ではなく物語

Knowledge = story

Kivalの焦点は「知識＝情報」ではなく、「知識＝関係と履歴を含む物語」を保つことです。

Decision / 決定
結論 Decision
Rationale / 根拠
なぜそうしたか Rationale
Provenance / 出所
誰が・何を根に Provenance
ARCHITECTURE
05 / 18
文脈付き共有知

Shared + Continuity

Kivalの価値は、同じ知識空間での協働（Shared knowledge）と、更新されても経緯を追える連続性（Continuity）を両立する点にあります。

Shared knowledge / 共有
人とエージェントが同じ基盤へアクセス 共同作業の前提
Continuity / 連続
履歴・関係・根拠を追跡 後から辿れる
ARCHITECTURE
06 / 18
Durable context

壊れない文脈

環境やツールが変わっても理解可能な“持続する文脈”（Durable context）を目指し、知識とその根拠を切り離しません。

Deliberate authorship / 著者性
組織作業に“責任ある作り方”を付与 編集と統治を明確化
Durable context / 文脈
更新後も経緯を辿れる設計志向 理由が消えない
PROCESS
07 / 18
セルフホスト導線

PostgreSQL → serve

READMEの初期導線は、PostgreSQL準備 → kivald serve起動 → admin bootstrapでpasskey登録、という流れです。

Setup / セットアップ
i) PostgreSQL 永続化を前提
ii) kivald serve 起動
iii) admin bootstrap 最初の管理者
Access / アクセス
i) WebでAPIキー作成 認証の入口
ii) CLI/SDKで同モデル利用 運用の統一

不明点：DATABASE_URL等の具体手順、権限スコープ、デフォルト設定の範囲。

“読む”からつなぐ

追跡→学習→再構成

Decision tracking / 決定
意思決定の経緯を辿る Trace
Synthesis / 要約
要約→新しい知識を作る Summarize
Incident → Follow-up
運用履歴を学習へ転換 Feedback loop

人×エージェント

CLI / API / SDK

CLI、APIキー、SDK（Rust/TypeScript）で同じアクセスモデルに基づき操作できることが強調されています。

Rust / TypeScript SDK
外部自動化や連携を実装しやすい Automation-friendly
API keys / passkey
認証導線が明示される Authentication model

不明点：レート制限、監査ログの項目、エージェントの安全策（誤リンク/誤作成対策）。

PROCESS
13 / 18
導入前の検証

小さく試す必須

価値を最大化するには、データ移行・権限テスト・エージェント安全性・バックアップ/復旧・監査要件の適合を小規模で検証すべきです。

Access / 権限
i) ロールとスコープ確認 誰が何を作れるか
ii) 監査可能性の確認 いつ/何が起きたか
Ops / 運用
i) バックアップ/復旧 停止・障害を想定
ii) アップグレード戦略 運用コストの見積り
DISTINCTION
14 / 18
価値と落とし穴

期待できる強み

Kivalの強みは、意思決定トレーサビリティと“運用知の循環（インシデント→学習→次の判断）”にあります。

Strategic / 戦略
ナレッジを“資産”へ引き上げる 次判断に接続
Risk / リスク
権限・運用ルール不備で価値毀損 文脈が守れない

不明点が残る領域（権限粒度、監査、性能、連携成熟度）を先に潰すほど成功確率が上がります。

CLOSING
15 / 18
結論

結論＋根拠を残す

Kivalは「文脈付きの共有知」として、意思決定の経緯を追える基盤をセルフホストで提供しようとしています。

Do / やる
小規模検証 移行・権限・安全策
Don’t / やらない
ACMEデモを本番転用 前提を崩さない
Next / 次
公式仕様で監査/権限/連携を確認 導入判断の確度を上げる

あなたの想定運用（部門規模、既存ツール、AIエージェントの使い方、監査要件）が分かれば、確認チェックリストに落とし込みます。
