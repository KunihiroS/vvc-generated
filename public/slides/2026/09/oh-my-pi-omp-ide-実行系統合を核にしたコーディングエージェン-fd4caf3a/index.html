COVER
02 / 14
IDE×実行統合
oh-my-pi（OMP）
LLMの“チャット”ではなく、IDE/LSP/DAPや編集エンジンを同じワークフローに接続し、実装→検証→デバッグを回すコーディングエージェント。
対象: README抜粋ベースの要点整理 Language: EN概念 + JP要約
PROBLEM
03 / 14
つながらない問題
“生成”だけでは足りない
従来のコード補完は、整合性・検証・デバッグを“実行手段”まで引き取れないため、開発工程が分断されやすい。
欠落になりがち
rename整合性 / ブレークポイント追跡 / 安全な編集手順
結果
手作業の再確認が増え、ワークツリー破壊のリスクも残る
英: coding agent（実行可能手段で進める） 和: 生成→実行→検証の連結が鍵
METAPHOR
04 / 14
同一ワークスペース
“編集と検証”を一つに
OMPは、ファイル操作・AST編集・grep/glob・LSP・デバッガ接続（DAP）を、同じエージェント空間の道具として扱う。
Edit
read/write/ast_edit / preview
Sense
検索: grep / glob
Debug
LSP renaming / DAP breakpoints
英: tool-calling（道具の呼び出し） 和: 実務の工程に寄せる
ARCHITECTURE
05 / 14
二層の実装
Rust core × TS SDK
RustコアとTypeScript SDKの組み合わせで、in-process方針を強調し、編集・検索などのホットパスを安定に回す狙いが見える。
Core（基盤）
実行系ツール統合 / in-process寄せ
SDK（接続）
providers切替 / host組み込み（ACP/RPC）
副作用: 速度だけでなく安定性・デバッグ容易性も 英: provider（LLM提供元）
EVIDENCE
06 / 14
壊れにくい編集
hash anchor と原子性
content-hash anchor（ハッシュアンカー）や「ステージ→Acceptカードで適用」の考え方で、古い対象への誤編集や破壊的変更を抑える。
古い編集の拒否
編集対象の古さ（アンカー不一致）で拒否
適用の節目
Accept（受諾）まで適用しない＝リスクを隔離
英: hashline（ハッシュで対象を縛る）/ stage（準備） 和: “それっぽいパッチ”を避ける
DISTINCTION
07 / 14
一発勝負を避ける
subagents で品質確保
単一モデルで終わらせず、サブエージェント（副エージェント）やレビュー専用モデルでタスクを監督し、見落としを減らす発想が示される。
Fan-out
並列タスク（役割分担）
Advisor
全ターンを監視
Rules
時間をまたぐ制御（中断/再試行）
英: review model / advisor（監視役） 和: 正しさの多段検査
PROCESS
08 / 14
“実行系”を内側へ
fork/exec を減らす
grep/find/sed/jqなどを統合し、ホットパスでfork/execを減らす方針が強調される。Windowsでも同一OMPバイナリ運用を志向。
高速化の筋
コマンド実行のオーバーヘッドを圧縮
導入の筋
WSLブリッジなしで動かす方針（記述ベース）
注意: 互換性は環境差の影響を受け得る 英: Windows support（方針の記載）
ARCHITECTURE
09 / 14
運用を選べる
providers とフォールバック
provider統合とフォールバック、モデル切替により、429/クォータ制限等で役割別モデルへ切替える設計が言及される。
切替の例
default / smol / slow / plan など役割別にモデルを運用
組み込み
ACP / RPC / SDK でホストに載せる選択肢
英: /model（切替操作の説明がある旨） 和: 最終挙動は設定次第
DISTINCTION
10 / 14
魅力の裏面
安全と監査は未確定
提示文は安全機構を示す一方、README抜粋のため、脅威モデル・失敗時のロールバック保証・権限境界・監査ログ粒度は読み切れない。
未提示の可能性
セキュリティモデル / 確率的失敗条件
性能評価
ベンチ手法・条件・再現性が不足
運用依存
権限・承認フロー・dry-run等で安全性が変わる
結論: 便利さより先に安全な運用を固める必要 英: governance（ガバナンス）
CLOSING
11 / 14
導入の指針
段階的に“安全”へ
OMPの強みは、IDE/実行系ツール統合と編集安全策（hash anchor・原子性）により、開発工程を壊しにくく繋げる点。導入は read-only / 承認厳格 / ログ保存から開始。
Step 1
read-only＋編集承認（Accept）を厳格化
Step 2
テスト環境で挙動確認→ providers と権限境界を検証
