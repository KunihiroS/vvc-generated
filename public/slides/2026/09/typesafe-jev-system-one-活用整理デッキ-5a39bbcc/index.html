判断を返すAI

Jev
活用整理レポート

Jev（System Oneモデル）は「文章生成」ではなく「選択肢・確率・点数」といった判断結果を返すAIです。本記事の要点を、業務導入の視点で圧縮して整理します。

Choice / Noul / Score 自動化・分岐に直結 確信度ゲート運用
Problem
03 / 16

生成AIの壁

要件

LLMで文章を作ると、後段でパース・解釈・例外処理が増え、業務システムに接続しづらくなります。

発生しやすい負担

「自由文」→「判定ロジック」への変換コストが高い

例：文字列から分類/数値抽出/判定を再実装

求められる形

分岐に使える固定フォーマット（選択肢・確率・点数）

判断AIとして「そのままif文へ」
Architecture
04 / 16

役割分担

分業

投稿の核は「計算はコード」「意味判断はJev」という分業です。コードが候補を作り、Jevは“意味”だけを選びます。

コードがやる
候補抽出・並べ替え・予約日時計算など
Jevがやる
操作種別・部屋名の意味判断・選択/採点
Choice/Noul/Score
結果を分岐条件へ直結（固定型）
運用ゲート
確信度が低い/割れる→人確認へ回す
Metaphor
05 / 16

選別の目

審査

Jevは“文章を作る脳”ではなく、“審査員”として選択肢から最も適切な判断を返すイメージです。

Choice（選択）

順序なし・正解が1つに決まる

例：問い合わせ種別を1つ選ぶ

Noul（はい/いいえ）

二値で決められる

例：同意が“書かれているか”

Score（段階）

段階評価（順序あり）

例：改善提案を観点別に点数化

確信度（確率）

自動/人確認の分岐に使う

例：割れたら再確認フローへ

07 / 16

聞き方が命

金額

同じタスクでも、指示の“距離感”で結果が変わります。遠回しだと「該当なし」寄りになり、直接的だと正解に近づきました。

悪い指示

「まだ払う必要がある金額」

結果：該当なしを選びやすい

良い指示

「この請求メールの請求金額」

結果：55,000円に近づく
Process
08 / 16

設計手順

型

精度を上げるには、(i)候補抽出をコード側で用意し、(ii)Jevには意味判断だけをさせ、(iii)曖昧さは安全側の選択肢で受け止めます。

i. 候補を作る
正規表現/ルールで数値や要素を抽出
ii. 判断させる
Choice/Noul/Scoreで“最も近い意味”を選択
iii. 安全側へ
「該当なし/書かれていない」を選択肢に入れる
iv. ゲートする
確信度が低い/割れる→人確認
Distinction
09 / 16

得意/不得意

線引き

投稿の整合的な方針は「計算・日付推論はコード」「意味判断はJev」です。Jevの弱点領域を避けるほど安定します。

Jevが強い

分類・選別・採点・整合性チェック（意味判断）

例：操作種別/根拠整合性/観点別スコア

Jevが弱い

計算・日付などの推論、曖昧表現の扱い

例：予約の日時計算はコードへ分離

誤判定対策

ガード

安全設計は「該当なし/書かれていない」選択肢と「確信度ゲート」を組み合わせて成立します。誤って断定しないことが鍵です。

安全側の選択肢

「書かれていない」を入れ、確認漏れを抽出

例：コンプライアンス一次チェック

運用ゲート

確信度が低い/割れたら人確認へ回す

自動化100%ではなく段階導入

Closing
13 / 16

結論

要点

Jevは“文章生成AI”ではなく“判断AI”。候補はコードで作り、Jevは意味判断（Choice/Noul/Score）に限定し、確信度で人確認を設計するのが最短ルートです。

核心

生成ではなく判断結果を返す → 業務分岐へ直結

成功条件

選択肢設計（該当なし/書かれていない）と指示の距離感

運用条件

確信度ゲート＋PoCで実測（誤判定率/再現率）

注意

日本語の安定性や法的責任分界は別途検討が必要
