ctx / ctx pro

03 / 16

ログは“孤立”しがち

根拠追跡の断絶

コードは残っても、「なぜそう判断したか／何が前提だったか」は、ログ形式がバラバラだと追えません。

現象
JSONL/SQLite/断片ログに散らばり、必要箇所へジャンプできない。
損失
要約（エージェントメモリ）の圧縮で、前提・制約が失われる。

git
「いつ／どのコミットで」
ctx pro
「どのセッションで」
復元
「何を見て／どう判断したか」

ctx：検索基盤の統一

ローカル・インデックス化

ctxは、セッション履歴（メッセージ／イベント／ツール呼び出し／リポジトリ活動）を統一フォーマットで取り込み、必要箇所へ直接ジャンプできるようにします。

取り込み
過去ログを統一ローカルレコードへ。
高速検索
raw transcript検索より実運用で効率的。
ARCHITECTURE
06 / 16

Tantivyで“速い検索”

ローカルで最適化

ctxはRustで高速化し、インデックス基盤としてTantivyを用いることで、SQLite等の別取り込み手順を省きつつ検索性を確保します。

速度ローカル・インデックスで検索→該当レコードへ復帰。
効率トークン消費面でもrawログ検索より有利になり得る。
方式デフォルトはBM25、semantic検索も併用可能。

07 / 16

要約劣化を抑える

原本トランスクリプト

エージェントメモリが圧縮してしまう前提・制約を、ctx proは該当コードの生成元セッションへ戻して確認できます。

よくある落とし穴
“結論だけ”が残り、制約が消える→誤解の温床。
ctx proの狙い
行単位／ファイル／コミット／PRからセッションへ復元。
PROCESS
08 / 16

“行→セッション”手順

根拠追跡の流れ

コードの該当箇所から出発し、その行を生んだエージェントセッション（トランスクリプトとツール呼び出し）へ辿ります。

i（入力）
コード行／ファイル／コミット／PRを指定。
ii（結び付け）
“過去のエージェントセッション記録”に紐付け。
iii（参照）
要約ではなく原本に近い形で復元。
iv（活用）
再調査のやり直しを減らし、品質を上げる。
DISTINCTION
09 / 16

ctx pro vs エージェントメモリ

圧縮の有無

メモリは要約として残りやすい一方、ctx proは“その瞬間のセッションログ”へ戻すことで前提の劣化を抑えます。

エージェントメモリ
会話から抽出した事実・要約を保存。
ctx pro
該当生成元セッションへ直接参照（トランスクリプト＋ツール呼び出し）。
日本語（用語）: 帰属=「その行を生んだセッションは何か」。

親セッション

DISTINCTION
11 / 16

証明の限界

“ログがある場合のみ”

ctx proの帰属（この行を生成したのは誰のセッションか）は、該当ログがあなたのローカルに存在する場合に限り、根拠として提示できます。

可能
生成元セッションの記録（トランスクリプト＋ツール呼び出し）が手元にある。
難しい
チーム由来などでログがローカルにないと、完全な帰属ができない。
COMPARISON
12 / 16

導入の論点

効果と条件

再調査コストと監査性を同時に下げられる一方、効果は「ログ整備・運用ガバナンス」に強く依存します。

Practical
デバッグ／仕様監査が速くなる（行・PR・コミット→セッション）。
Safety
ローカル完結でも、トランスクリプトの秘匿運用が必要。
Operational
初回インデックス時間・容量・取り込み範囲は事前見積り推奨。
CLOSING
13 / 16

結論

“次の迷路”を減らす

ctx / ctx proは、過去のエージェント作業をローカルで検索し、git blame相当で原本の根拠へ戻すことで、同じ調査のやり直しを減らします。

得られるもの
高速検索（ctx）＋根拠復元（ctx pro：セッション起点のblame）。
成立条件
帰属には“ログがローカルに存在”が前提。運用設計が鍵。
