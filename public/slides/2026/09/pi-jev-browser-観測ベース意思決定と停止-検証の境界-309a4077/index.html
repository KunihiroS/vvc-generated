Observations → Decisions → Safer Stop

pi-jev-browser 境界設計

pi（TypeSafe System One）のブラウザ/デスクトップ操作エージェントは、「DOM等の構造化観測で意思決定し、停止と検証の境界で暴走を抑える」ことを中核に作られています。

意思決定
DOM観測ベース（可視テキスト＋操作ターゲット）
停止
review gate / blocked / 進捗なし 等
検証
最終的なスクリーンショット等で照合
PROBLEM
03 / 16
Screenshots Aren’t a Decision Engine

なぜ 観測 が要るのか

ステップごとにスクリーンショットへ依存すると、遅延・不確実性・入力の揺れが意思決定に混ざります。pi-jev-browserは、DOM等の観測情報を構造化して行動選択します。

“判断入力”を安定化：可視テキスト＋操作可能ターゲット
“行動空間”を制御：選択肢ベース（CLICK/TYPE_TEXT/…）
画像は“結果検証”へ：意思決定では使わない方針
速度以前に安全：不確実な推論経路を減らす
METAPHOR
04 / 16
Driver with Guardrails

自律ではなく 運転

pi-jev-browserは“完全自動”ではなく、観測→判断→実行のループに、停止・承認・検証のガードレールを埋め込みます。事故は「暴走」ではなく「境界が欠ける」ことで起きる、という前提です。

Loopの核
Observation（状態）→ Choice（選択肢）→ Action（tool）→ Verification（検証）
Human-in-the-loop
safety上の review / confirmation が必要なら制御を人へ戻す
ARCHITECTURE
05 / 16
What the agent can “see”

観測→選択肢 決定

意思決定はTypeSafeへの「選択肢質問」で行い、スクリーンショットを推論入力にしない設計です。次のアクションは固定の行動カテゴリから選びます。

観測（Observation）
DOM等：可視テキスト＋操作可能ターゲット
意思決定（Choice）
CLICK / TYPE_TEXT / SELECT / SCROLL / WAIT
停止（Stop）
BLOCKED / REVIEW / DONE

目標に対して“何を入力するか”も制約され、TYPE_TEXTはゴール文から候補抽出が基本です（必要時のみ補完）。

PROCESS
06 / 16
Stop Reason Map

止める理由を 分類

進捗なし、状態の陳腐化（stale observations）、繰り返し、検証が必要などをstopReasonとして整理し、暴走しにくくします。REVIEWとBLOCKEDは役割が異なります。

BLOCKED（停止）
選んだ行動が進行不能（支持アクションがない等）
REVIEW（停止）
次がセンシティブ or CAPTCHA等で人の判断・操作が必要
verification gate
ループ自体が検証ゲートを検知し、人へ返すタイプ
“安全な中断”
CAPTCHA等で越えられない場合は、その場で止めて解決を待つ
ARCHITECTURE
07 / 16
Browser vs Desktop Scope

実行範囲は 別設計

ブラウザ操作とmacOSデスクトップ操作では前提が違います。ブラウザは隔離環境で比較的閉じ、デスクトップはデフォルト無効で強いゲートが必要です。

ブラウザ
Playwright Chromium の隔離環境で操作（観測と検証を内製化）
デスクトップ
アクセシビリティツリー経由（デフォルト無効）
allowedBundleIds
許可リストで対象アプリを限定
requireConfirmation
trueなら毎回ユーザー確認（危険操作を抑制）
COMPARISON
08 / 16
Input Safety: TYPE_TEXT

自由文生成を 抑える

TYPE_TEXTは任意に文章を作るのではなく、原則としてゴール文から候補を抽出して選びます。候補がない場合のみpiモデルで補完し、形式不一致は入力されません。

基本方針
ゴール文 → 候補化 → 選択（勝手な自由入力を減らす）
例外とガード
必要時のみ補完（text_helper_invalid_output等で不許可）

ただし機微情報が“完全にマスクされる”とは限らず、運用ではログ/送信範囲にも注意が必要です。

ENUMERATION
10 / 16
Tool Loop Boundaries

基本用語で 把握

理解の入口は「ツール実行」「状態観測→意思決定→実行→検証」「人間の承認（review/verification gate）」です。これが“いつ止まるか”を決めます。

ツール実行
jev_run / jev_actions 等
観測→判断
DOM等を読み取り、選択肢ベースで行動を決める
実行→検証
結果をスクリーンショット等で照合
承認ゲート
review/verification gateで人へ制御を戻す
DISTINCTION
11 / 16
Captcha & Access Limits

越えないものは 越えない

CAPTCHAやGoogle等の自動アクセス制限には対応しません。必要な場合は初回観測時点で停止し、ユーザーが解決してから続行する流れです。

停止の扱い
REVIEW/blocked系で止まり、状況確認と人の判断を促す
設計意図
安全バリア（検証）を“突破”しない。ユーザーの介入前提

その場でブラウザを開いた状態になるため、解決を待つ運用が想定されています。

DISTINCTION
12 / 16
Strengths vs Watch-outs

強みと 注意点

pi-jev-browserは「停止・検証の境界」を最初から前提化しており堅い一方、性能（速度/失敗率の分布）や情報取り扱い運用には追加確認が必要です。

強み
境界設計（観測と実行の整合、stale対策、human-in-the-loop）
注意点
ライブ速度/失敗率の統計が見えにくい。reviewは“決定的セキュリティ境界”ではない
情報リスク
機微情報が自動マスクされない可能性（パスワード/ファイル除外以外）
運用リスク
CAPTCHA等は止まるため、継続には人が必要。ログ/送信範囲の監査が要る
CLOSING
13 / 16
Takeaway

結論：自律のための 停止と検証

pi-jev-browserの本質は「観測ベースで意思決定する」ことと同じくらい、「いつ・なぜ止めるか」と「何で検証するか」を設計の中心に置く点です。導入はベンチマークの範囲と運用ルールを確認して進めるのが安全です。

意思決定
DOM観測＋選択肢質問（スクリーンショットは推論に使わない）
停止
blocked / review / verification gate / 進捗なし で境界化
検証
結果をスクリーンショット等で照合し、“やったこと”を測る

（必要なら次に：benchmarks/README.md の表と失敗要因を精査して、あなたの運用条件に当てはめてください。）
