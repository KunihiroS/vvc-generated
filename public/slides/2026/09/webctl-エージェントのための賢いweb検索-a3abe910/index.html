LLMのための最適化

webctl

エージェントがWebを調べるとき、読む量（トークン）を減らして必要情報だけを集めるためのCLIツールです（relatedness scoring / チャンク最適化）。 日本語補足: “関連性スコアリング（関連度判定）” と “チャンク分割（分割読み）” が核です。
PROBLEM
03 / 16
文量が支配する

入力制約

LLMは入力（コンテキスト）に上限があり、長いWebページをそのまま読むとコストと速度が悪化します。 さらに検索結果にはノイズが多く、無駄な文脈が混ざりやすいのが課題です。
症状
長文投入 → トークン増 → コスト↑ / 速度↓
追加の障害
スニペット/URL中心 → 関連性の誤差が出る
METAPHOR
04 / 16
選別してから読む

フィルタ器

webctlは「見つける」だけでなく、関連性でふるいにかけてから、必要なときだけ本文を読みます（検索→評価→必要ならスクレイプ→要約/重複排除）。
目的は明確です：LLMに渡す情報量を最小化しつつ、品質を崩しにくくすること。
(関連性スコア: Jev / Jevで絞り込む)
ARCHITECTURE
05 / 16
パイプライン設計

四段ろ過

webctlの基本フローは「検索→Jevでフィルタ→スクレイピング/チャンク評価→（必要なら）要約・重複排除」です。
段階何をする
i 検索 複数プロバイダの結果を集約（例: 約25件の候補を受ける想定）
ii 関連性評価 各結果をJevで0〜10点評価し、閾値（デフォルト6）で残す
iii スクレイプ 必要なら本文取得し、全投下せず「チャンク単位」でJev判定
iv 仕上げ 重複排除（完全一致→ニア一致）と要約（--summarize）をオプションで実行
COMPARISON
06 / 16
生URLを投げない

節約

そのまま“生URL/スニペット”をLLMに渡す代わりに、webctlはJevで上位候補だけを残します。 これによりトークン削減がそのままコストと速度に効きます。
ナイーブ
検索結果を多めに投入 → ノイズ混入 → 読む量が増える
webctl
Jev(0〜10)で0〜閾値6前後をカット → 必要な候補だけ保持
ENUMERATION
07 / 16
チャンクで最小化

--filter-chunks

スクレイピング後もページ全体ではなく、本文をチャンクに分割してJevで絞ります（--scrape --filter-chunks）。
既定
チャンク2000文字
重なり
オーバーラップ20%
残す量
関連性の高い3〜6チャンク
長文（PDF/掲示板/Wikipedia等）でも「必要部分だけ」を渡す設計です。
日本語: チャンク単位で“読むべき箇所”を選別。
DISTINCTION
08 / 16
重複は段階的に

完全一致＋ニア一致

重複排除は一発勝負ではなく、完全一致とニア一致を分けて段階的に行います。 誤判定は最終的にJevで補います。
完全一致
正規化URL/タイトルで統合
ニア一致
MinHash LSHで候補ペア抽出 → Jevで「同一か」を確認
EVIDENCE
09 / 16
安定稼働の工夫

クールダウン

HTTP 429（レート制限）や402（クオータ消費）が起きたプロバイダは、一定時間スキップするクールダウン機構があります。 単発失敗で止まりにくく、運用の安定性を上げます。
トリガ
429（レート制限）
トリガ
402（クオータ消費）
挙動
15分→72時間へ延長（共有クールダウン）
「機械的な失敗」を吸収し、バッチ実行や複数プロセスでも効きます。
日本語: 同一マシン上でクールダウンを共有。
PROCESS
10 / 16
要約は任意の圧縮

--summarize

--summarizeは、スクレイピングした各ページを小型モデルで目標指向の短い要約に圧縮するオプションです。 必要に応じて、さらにトークン削減を狙えます。
位置づけ
Claude WebFetchのような動作に近い“圧縮層”
注意
圧縮でニュアンスが失われる可能性（ファクト精度は設定と目的次第）
RISK
11 / 16
落とし穴もある

Jev依存

webctlは効率が強みですが、Jevの評価基準・モデル選定・目標（--goal）の書き方に品質が左右されます。 閾値やチャンク設定が合わないと、必要情報を落とすリスクがあります。
誤除外
閾値（例: デフォルト6）ミス → 必要情報をカット
取得差
サイト構造（動的/JSON/ナビ）で本文が変わる
要約の副作用
--summarizeでニュアンス損失 → 検証精度に影響
FAQ
12 / 16
使い分けの要点

判断軸

「--no-filter」「スクレイピング」「重複排除」は目的により使い分けます。 代表的な考え方を短く整理します（関連性で読む量を制御）。
--no-filter
Jevでのスコアリングをスキップ（キー不要のケースも）→ ノイズ増の可能性
スクレイプ
必要時のみ本文取得し、--filter-chunksで関連箇所だけ残す
重複排除
完全一致→MinHash LSH候補→Jevで同一性確認
上限
--max-outputで出力上限（ページ欠損/切れの可能性は残る）
CLOSING
13 / 16
要点まとめ

結論

webctlは、検索結果をJevで絞り込み、必要時だけスクレイピングとチャンク評価で読む量を削減し、 さらに重複排除と（任意の）要約でコンテキスト負荷を下げる設計です。
狙い
トークン削減 → コスト/速度改善
核
Jev関連性スコアリング（関連度判定 / 関連性評価）
注意
閾値・チャンク・スクレイプ精度・要約で品質が変動
次に見るなら：Jevの閾値と--goal、そして長文ページのチャンク設定を確認してください。
