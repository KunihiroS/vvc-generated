HarnessTax
02 / 16
コーディングは“道具”で変わる
HarnessTax
コーディングエージェントの性能は、モデルだけでなく harness（ハーネス） 設計でも大きく変わり得ます。
「成功率」より「運用コスト」に効く—その示唆を、ベンチマーク結果から整理します。
対象：SWE-bench Lite / Terminal-Bench 2.0、モデル7種×harness3種（計21ペア）
Problem
03 / 16
モデル偏重の罠
本当に“モデル”だけ？
従来は「どのLLMを使うか」が注目されがちでしたが、同じモデルでも harness が違えば結果とコストが変わる可能性があります。
問い
同一モデル条件で、成功率とコストはどれほど動く？
重要点
タスク成功だけでなく、呼び出し回数/入力長が運用コストに直結
Bilingual（用語補助）：harness＝ハーネス（道具・手順・コンテキスト管理の層）
Concept
04 / 16
Harnessの役割
実行の“層”
LLM（モデル） が推論するのに対し、harness は「ツールの使い方」「指示の与え方」「実行ループ」を管理します。
Tools
read/write/edit/bash 等
Context
指示文・ツール仕様・環境情報
Loop
何をいつ呼ぶか（反復）
同じ推論器でも、入力の長さと呼び出し設計は harness が決める
Key Result
05 / 16
成功率は鈍く、コストは鋭い
“Harness Tax”
Harness選択は成功率よりもコストに大きく影響し得る—これが主要結論です。
成功率
同一モデル内で大きくは変わらない（±数%程度の収まり）
コスト
最大で約5倍程度の差（運用上の“見落とし”）
Harness Tax＝harness由来の上乗せ運用コスト（成功率だけ見ても見えにくい）
Setup
06 / 16
何を比べたか
21ペア
7種類のモデル × 3種類のharnessを組み合わせ、2つの公開ベンチマークで評価しました。
ベンチマーク
SWE-bench Lite / Terminal-Bench 2.0
Harness例
Claude Code / Codex CLI / Pi（最小構成）
評価観点：成功率だけでなく、LLM呼び出し回数・入力長に紐づくコストも同時に比較
Insight
07 / 16
最小でも強い
Piが前線
最小構成のオープンソースharnessである Pi は、成功率とコストの両面でパレート境界に到達するケースが報告されています。
設計
read/write/edit/bash へ機能を絞る
示唆
リッチ＝常に最適ではない。必要十分な足場がある
Bilingual補助：パレート境界（Pareto frontier）＝「成功率×コスト」で両方を同時に改善しにくい境界
Distinction
08 / 16
推奨＝正解ではない
Provider最適化神話
Anthropic / OpenAI のような“プロバイダ最適化”でも、別harnessを組み合わせた方が成功率が高くなる比較が多数あります。
i
成功率が同等でも、コストは harness で変わる
ii
「推奨スタックだから大丈夫」は成り立たない
iii
結論：組み合わせ実験（A/B）が運用で必要
Evidence
09 / 16
コストの起点
最初の入力
コスト差は「最初のモデル呼び出しのコンテキスト」によって生まれ得ます。具体的に Claude Code は初回入力が Pi より非常に長いと示されています。
観測
Claude Code：初回の指示・ツール仕様が平均で“10倍超”の長さ
解釈
指示/スキーマの冗長さが、直接コスト増に繋がり得る
モデル×harnessで、入力トークン量と呼び出し回数がコストを左右する
Process
10 / 16
実務判断の手順
比較で決める
ユーザは「成功率が同程度ならコストが低い組み合わせ」を選び、デフォルトを鵜呑みにせず比較するべきです。
i
候補スタック列挙（モデル×harness）
ii
同一評価設計で成功率とコストを測定
iii
パレート境界から運用最適を選定
Caution
11 / 16
外挿は慎重に
2ベンチ依存
結論は2つのベンチマークに限定されます。また学習時に同種ベンチマーク知識が混入している可能性も指摘されています。
制約
SWE-bench Lite / Terminal-Bench 2.0のみ
未分解の可能性
キャッシュ、並列、再試行、失敗時リカバリ、ツール実装効率など
他の現場ワークロードで同様の相関が成立するかは追加検証が必要
Takeaway
12 / 16
私はこう評価する
意思決定向き
この研究の強みは、成功率だけでなく“同一モデル条件でコストも比較”し、Harness Tax を意思決定に落とし込める形で可視化した点です。
実務（Practical）
デフォルト採用の危険性を具体化
財務（Cost）
成功率が近くても最大5倍のコスト差
Closing
13 / 16
結論
“Model＋Harness”
最適は「モデル」だけでは決まりません。成功率—コストを同時に見て、最適な モデル×harness を自社で検証してください。
i
成功率差は小さくても、コストは大きく動く
ii
Piのような最小構成が最前線に来ることがある
iii
プロバイダ推奨を鵜呑みにせず、組み合わせ実験で選ぶ
