Source of truth shift
意図を閉じ込める/src/md
エージェント的コーディングでは、生成されたコードが“いまの真実”になりやすい。だからこそ、Markdownをコード近傍に置き、意図をリポジトリの中心へ寄せる。

02 / 12
Ground truthの歪み
コードが答えになる
LLMコードは現時点での最も近いground truthになりがちだが、プロンプト履歴は消えやすい。結果として「なぜそうするのか」を後から追えない。
起きること
生成物（code）が“事実”扱いに
失われること
プロンプトや試行の意図が追跡不能

遠い
理由が別サイト
distance / 距離
近い
同じリポジトリ
locality / 局所性
狙い
人もLLMも同じ文脈
shared context / 共通文脈

意図→派生

Markdownをコードと同じ場所に置く（提案：/src/md）。コードとテストを“Markdownから派生させる”方向へ寄せる。
置くもの
アーキテクチャ判断 / データ設計 / ソース設計の意図
繋ぐもの

PROCESS / 手順
05 / 12
更新の流れを整理
分業の設計
Markdownは“仕様（ish）”にし、テストは自動検証に寄せる。対話的に意図を扱う役割をMarkdownに寄せると混乱が減る。
i Intent
何をする/しないかを文章で固定
intent / 意図
ii Spec-ish
Markdownで制約・根拠を言語化
spec-ish / 仕様っぽい
iii Tests
自動検証としてCIで回す
verification / 検証

06 / 12
どこまで書くか
中間レイヤに置く
Markdownは形式仕様と高レベル設計書の間に位置する。テスト（検証）より“対話・説明”に向き、設計の因果を見せやすい。
形式仕様寄り
決めごとを明示し、差分レビュー可能
設計書寄り
理由・制約・意図を自然言語で伝達
EVIDENCE / 根拠
07 / 12
LLM運用との相性
Markdownが強い理由
Markdownは人間にもLLMにも読み書きしやすく、差分管理とレビューにも向く。結果として、意図を“残せる形”で維持しやすい。
差分
変更点がレビューで見える
読みやすさ
自然言語で根拠を保持
再利用
コード生成の参照材料になる
DISTINCTION / 制約
08 / 12
人のキュレーション
LLMに任せすぎない
/src/mdをソース化するほど、品質管理が重要になる。著者は“LLMに大量生成させるべきではない”と明言し、人がレビュー・キュレーションし続ける前提を置く。
やる
人が作り、正確性を維持する
避ける
誤り・曖昧さを含む文書を大量に固定する
COMPARISON / 比較
09 / 12
テキスト真実の罠
同期ルールが鍵
Markdownがソースになると、コードとの乖離が問題になる。どちらを優先し、どう同期・検知するかの運用がないと混乱しやすい。
リスク
誤った意図が“永続化”される
対策の方向
同期ルール / 乖離検知 / 承認・責任分界
EVIDENCE / 実務観点
10 / 12
導入で効く点
現実的な価値
コード生成が安価になるほど価値は実装細部から“意図（何をし、何をしないか）”へ移る。Markdownをコード近傍に置くと、PR運用の観点でも参照性が上がる。
Strategic
ソース優先順位を再設計
戦略
Practical
差分レビュー可能で運用に乗る
実務
Governance
承認/更新/裁定（乖離時）を決める
ガバナンス
PROCESS / 注意
11 / 12
Complexity budget
書きすぎは破綻する
Markdownをソースとして扱うと、ドキュメントも肥大化する。抽象度・粒度・責務分割を誤ると、コードと同様にメンテ不能になる。
失敗パターン
責務の重複 / 更新漏れ / 粒度の不統一
守る設計
どのレベルまで書くか、どの単位で分けるか
CLOSING / 結論
12 / 12
結論：運用設計までセット
導入するなら先に固める
発想は有効だが、成功は“運用設計”次第。Markdownとコードの同期ルール、乖離検知、責任者/更新頻度を先に決めれば、意図の散逸を抑えられる。
1
同期メカニズム（自動/手動の境界）
2
乖離検知（レビュー観点 / CIチェック）
3
責任者と更新頻度（ガバナンス）
