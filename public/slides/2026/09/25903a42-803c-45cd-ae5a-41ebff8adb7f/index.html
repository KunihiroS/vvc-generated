PROBLEM
03 / 14
ハーネスの穴
OSと意図の分離
従来のエージェント実行ハーネスは隔離や権限分離があっても、監査（誰が何を承認し、何が改変されたか） や取り消しの「取引性」が弱くなりがちです。
失敗モード
自動修正が気づかれず進む / 説明できない変更が残る / 取り消しが困難
必要な層
トランザクション性・スコープ制御・プロベナンス＋監査（provenance / 来歴）
min privilege + audit + rollback の不足
METAPHOR
04 / 14
差分は預り金
コミットが確定
OVERLORDは、エージェントに「ディレクトリを完全書き込み可能に渡す」一方で、実世界のディスク変更は コミットまで反映しません。
1) 実行
隔離環境（jail / pivot_root 等）内で変更を作る
2) 差分
ハッシュ化マニフェストでレビュー可能にする
3) 確定
人が承認して初めて実世界へ反映（取消/部分確定も可能）
transactional execution / 取引実行
ARCHITECTURE
05 / 14
三つの柱
信頼の設計
信頼カーネルとして、OVERLORDは「トランザクション性」「能力ベースのスコープ制御」「プロベナンスと監査ログ」を OSプリミティブ近くに寄せて実装します。
Transaction
実世界反映をコミット時まで遅延 / rollback・部分確定
Capability
identityではなく path / budget / network / time window を制約として付与
Provenance
変更前後ハッシュ＋原因（caused_by）を生成時から結び付ける
Audit
MAC署名・検証・witness（オフボックス検証）で改ざん耐性
transaction + scope + provenance/audit

READMEの主張は、エージェントの変更を直接反映せず、ハッシュ化マニフェストとして提示してレビュー可能にすることです。
Manifest

reviewable diffs / レビュー可能差分

能力で線を引く
Capability /cap制約
エージェントに「ユーザ権限」を渡すのではなく、カーネル制約として path・予算・ネットワーク・タイムアウト等を付与します。 （capability / 能力）
Scope

Isolation
jail（pivot_root等）や net=none、または記録・allowlist付きプロキシ
intent vs privilege の混同を減らす

来歴は「後付け」しない
Provenance /出どころ
provenance.jsonlのように、変更前後のハッシュと「どのセーブポイント・ツール呼び出し・原因（caused_by）で起きたか」を保持します。
Before/After

Cause Chain

DISTINCTION
09 / 14
監査は“署名付き”
署名と witness
監査ログはMAC署名で改ざん検知し、witness（オフボックス）により引っ込め困難な検証点を外部に保持できます。
MAC
署名付きログで改ざん耐性を上げる
Witness
オフボックス検証で「破壊して隠す」可能性を下げる
Limit
万能防御ではない前提を明示（鍵管理が要）
signature + off-box verification
COMPARISON
10 / 14
隔離だけではない
コンテナと何が違う?
OVERLORDは隔離（jailやネット制限）を行いますが、中心は「差分を取引として扱い、承認・取り消し・監査を同時に成立させる」点です。
Container運用の例
実行は隔離できても、変更の確定・来歴・承認チェーンが別体系になりやすい
OVERLORDの特徴
保存点/rewind/resumeとcommit-by-cause、provenance＋監査を一貫化
isolation ≠ transactional governance

外部作用も連鎖へ
MCPコネクタの取引
MCPコネクタ（メール送信など）は取引の外側で起きがちですが、connector.call / decision / result を監査チェーンに結びます。
外部はロールバック不能
現実の制約を踏まえ、承認を入力フィンガープリントに結び付ける
二人ルールの強化
countersignature（相互署名）で差分とレビュー対象を別主体に担保させる
connector audit + fingerprint binding

CLOSING
13 / 14
強みと限界
導入判断の軸
OVERLORDは「取引性・能力制約・プロベナンス監査」を一貫させることで、説明できない変更や承認なき改変のリスクを下げます。
強み
commitまで反映しない / caused_by連鎖 / MAC＋witness / MCP承認も追跡
限界（前提）
カーネル・プロファイル依存 / 鍵管理が要 / 複雑性増で運用設計が必須
not universal security / 段階的統制
