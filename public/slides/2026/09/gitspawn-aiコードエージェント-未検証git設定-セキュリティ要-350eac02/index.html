02 / 16

GitSpawn / 脆弱性クラス

Gitを起点に侵害

AIコード作成・編集エージェントが、作業前にGitでリポジトリ状態を取りに行く過程で、未検証のGit設定により任意コード実行へ至り得る、という報告。

PROBLEM
03 / 16

「入力前」でも発火

早すぎる実行

エージェントは起動直後やユーザー入力前、場合によっては認証前でも、git status や差分取得のためにGitコマンドをバックグラウンド実行することがある。

失敗モード
承認・確認の前に実行が走る
攻撃者側の得
検知や判断のタイミングを前倒しで突破
METAPHOR
04 / 16

設定が“指令書”

Git設定がレバー

問題の中心はモデルやプロンプトではなく、Gitがリポジトリ内設定（.git/config など）を参照し、その結果として外部プログラム起動のような挙動が誘発され得る点。

根因
Git設定のサニタイズ不足（安全化しない）
結果
利用者権限で任意コード実行の余地
ARCHITECTURE
05 / 16

コンテキスト収集の連鎖

ツール連鎖（subprocess）

エージェントがホスト上でGitを呼び、そのサブプロセスが権限を継承するため、危険な設定が引き金になるとホスト侵害へ繋がる。

Step i
リポジトリ状況把握（例：status / diff）
Step ii
Gitがリポジトリ設定を参照
Step iii
外部起動が誘発される → 任意コード実行
EVIDENCE
06 / 16

観測された“広さ”

単発ミスでない

特定ベンダーの個別不備ではなく、複数のエージェントに共通する「コンテキスト収集のためのGit呼び出し」という設計上の類似パターンが、影響の広がりを示唆する。

強い示唆
共通設計が根にある可能性
運用上の状況
未修正が残る案件／重複報告で調整が必要
DISTINCTION
07 / 16

clone不要でも成立

“受領フォルダ”が危険

攻撃はGitのネットワーク操作（clone/fetch/pull）に限られず、.gitディレクトリ込みで配布・同期されたフォルダ（zip/USB/共有）を移動するだけで成立し得る。

成立しにくい
単純なネットワーク取得だけの場合
成立しやすい
ローカルに設定が“持ち込まれる”場合
COMPARISON
08 / 16

何が“攻撃面”か

モデル vs Git

この問題は「プロンプト注入」の話ではなく、エージェントがホスト上でGitを実行し、その際に危険なGit設定を無効化できていないことが主戦場。

注目点A（誤解されがち）
モデルの脆弱性 / 文章の誘導
注目点B（本質）
ツール実行の“裏側”で設定が適用される
DISTINCTION
09 / 16

被害の射程

権限付きの情報奪取

任意コード実行になれば、SSHキーや環境中のクラウド資格情報、シェル設定中のトークン、ディスク上の他リポジトリなどへアクセスし得る。

機密
SSHキー / クラウド資格情報 / トークン
足場
他リポジトリ参照・バックドア的侵入の拡大
PROCESS
10 / 16

攻撃が成立する流れ

設定→実行

危険なリポジトリ設定がエージェントのGit呼び出しに“そのまま”影響し、結果としてホスト上の実行へ繋がる。

i. 入手
zip/同期で .git/config を含む形で受領
ii. 開始
起動直後にGitで状態取得（status / diff等）
iii. 反映
危険設定が適用 → 任意コード実行
PROCESS
11 / 16

対策の二本立て

ユーザー×提供者

ユーザーは受領前提で点検し、提供者はGit実行時に危険設定を明示的に無効化する設計へ寄せる。

ユーザー側
開く前に .git/config を確認（外部実行指定の有無）
提供者側
コンテキスト収集のGitに -c 等で危険を無効化（例：git -c core.fsmonitor=false status）
※実装は「リポジトリ設定を信頼しない」方向（サニタイズ）を徹底する。
EVIDENCE
12 / 16

検知の難しさ

“見慣れた実行”

EDRやゲートウェイは、正規の開発ツール挙動（Gitコマンド）として処理してしまい、「どの入力（リポジトリ設定）で実行が決まったか」を追えない可能性がある。

ギャップ
実行“内容”だけでなく、決定要因を追えない
示唆
ログ監査は“設定適用”まで視野に入れる
CLOSING
13 / 16

横展開できる教訓

脅威モデルを拡張

この報告の強みは「プロンプト注入」から「ツール連鎖（サブプロセス）＋未検証設定」へ視点を拡張した点。現場は自社前提（Gitコマンド/タイミング/バージョン/サニタイズ有無）を点検し、安心しないことが重要。

最小アクション
①受領プロジェクトの .git/config 点検
②エージェント更新確認（サニタイズ有無）
調査観点（懐疑）
環境差（Gitバージョン/ディレクトリ形態/実行タイミング）を再現で確認
