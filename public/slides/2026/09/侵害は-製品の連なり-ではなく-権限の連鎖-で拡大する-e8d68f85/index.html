権限の連鎖を読む

SSO×Agent

侵害は「どの製品が壊れたか」より、境界を越えた結果として権限がどう変換・増幅されたかで拡大する。
キーワード：境界 / 権限変換 / step-up認証 / セッション分離 / Connected Account
03 / 16
PROBLEM
点ではなく矢印

侵害の増幅

低信頼領域（例：フォーラム）で侵害が起きても、すぐ全社コード奪取に直結するとは限らない。だが、境界を越える「矢印（ログイン→操作主体→書き込み権限）」が成立すると被害は連鎖する。

入口（低信頼）

フォーラム等の不具合で「主体（人/セッション）」が侵害される

増幅（高信頼）

SSO/連携で「主体」が高権限操作へ変換される（増幅）

本稿の焦点：コンポーネント名の列挙ではなく「権限の変換」を追うこと。
04 / 16
METAPHOR
鎖で決まる

権限の鎖

脆弱性修正は重要だが、被害は「鎖の次の段」がつながったときに拡大する。狙うべきは“壊れた場所”だけではなく“次に何へ変身できるか”だ。

i. 証明

SSOは「本人（認証された事実）」を示す

ii. 運搬

その事実が「安全な経路/保証レベル」として扱われるかは別問題

iii. 増幅

step-upなしで高権限へ渡ると被害が連鎖する

Bilingual：権限（privilege）鎖（chain）＝侵害後の次の到達点。
05 / 16
ARCHITECTURE
境界をまたぐ設計

SSOの役割分離

SSOは「本人性（誰か）」を統合する仕組みだが、「安全な通信経路」や「保証レベル（どの条件で認めるか）」までは自動担保しない。

SSOが担う

複数サービスで同じ“本人”として認証（認証された事実）

SSOが担わない

その認証の前提（どこ経由/端末/異常有無）を高権限の根拠にできるか

対応の方向：高権限へ移る局面で再評価（step-up/再認証/セッション分離）。
06 / 16
ENUMERATION
高権限の再検証

Step-up設計

高権限領域へ移すときは、直前の認証要素と端末状態を再評価し、必要ならstep-up認証や再認証で保証レベルを上げる。

確認する要素

前回認証の条件 / 端末・セッション状態 / 特権アカウントか / 書き込み・実行が絡むか

入れる対策

step-up / 再認証 / セッション分離（読みと書き）で高リスク操作を隔離

狙い：低保証のセッションが“根拠”として運搬されないこと。
07 / 16
COMPARISON
人間より速い

Agentの加速

AI AgentやConnected Accountがあると、侵害された主体が人間より速く連続操作できる。結果として“到達権限”と“操作の連続性”が被害を左右する。

脅威の違い

人間：確認・待機が入る
Agent：同じ権限で連続利用が可能

評価すべき粒度

Organization/Repository単位 / read-write / merge権限分離 / クライアント制限

Bilingual：連続操作（continuous actions）＝権限が“次へ渡る速度”。
08 / 16
EVIDENCE
公開情報の示唆

連鎖の可能性

公開情報ベースでは、フォーラム側の画像処理経由でRCE入口が成立し、その後SSO関連の問題と組み合わさって、複数従業員のChatGPT/Codexへ到達し得る可能性が示唆されている。

段階 1

フォーラム画像処理→RCE入口（侵害）

段階 2

SSO/認証の組合せで主体が高機能側へ

段階 3

Connected GitHub操作→内部PR作成へ（到達）

注意：著者は攻撃手順の再現には踏み込まず、確認できる範囲を整理している。
09 / 16
DISTINCTION
入口修正の限界

十分条件ではない

Discourse（例）のCVE修正版適用は最優先でも、入口が別プラグインや依存ライブラリへ“すり替わる”可能性がある。したがって、パッチは必要条件であって十分条件ではない。

パッチで減るもの

同種の入口（当該脆弱性経由の侵害パス）

残るもの

侵害後の権限変換（次段へ渡る条件）

結論：継続的に「侵害後に何ができるか」を脅威モデルへ含める。
10 / 16
PROCESS
脅威モデルの作り方

権限グラフ追跡

脅威モデルではコンポーネント名ではなく、侵害された主体が次に“変換”される先を追跡する。境界ごとに保証レベルがどう落ちる（上がる）のかを可視化する。

i. 境界

サービス間の接続点（SSO/連携/Agentツール）

ii. 変換

認証事実→操作主体→書き込み/実行権限

iii. 失効

異常時にトークン/連携が連鎖的に失効するか

指標化の方向：どこで保証レベルが崩れるかを測れる形にする。
11 / 16
ENUMERATION
対策の最短ルート

設計原則

現場で落とし込みやすい整理として、入口隔離、サービス別セッション、再認証、リポジトリ操作の最小化が“次段”を切る。

基本

最小権限 / セッション分離（読みと書き） / step-up/再認証

Connected Account

粒度評価（Org/Repo・read/write・merge）/ 失効伝播 / クライアント制限

目的：侵害後に“高信頼権限へ変換されない”設計にする。
12 / 16
COMPARISON
SSOをやめない理由

守るのはSSO運用

SSOを“やめる”だけでは解決になりにくい。SSOは退職・権限変更の集中管理など利点があり、問題は低保証のセッションが高保証操作へ持ち込まれる点にある。

SSOの価値

本人性の一元化 / 運用統制（権限変更の集中管理）

必要な追加

高リスク操作で保証レベル再評価（step-up/再認証）

Bilingual：保証レベル（assurance level）＝“条件が満たされたか”の評価。
13 / 16
CLOSING
要点の復唱

結論

侵害の拡大は“製品の連なり”ではなく、“権限の連鎖”で決まる。入口パッチに加えて、侵害後に権限がどう変換・増幅されるかを脅威モデルに含め、step-up・セッション分離・最小権限・失効伝播で次段を切る。

あなたの次の一手

自社の権限フローを可視化し、境界ごとに保証レベルを再評価する

目標状態

低信頼の侵害が高信頼権限へ変換されない（到達を抑止）
