PI AUTORESEARCH
02 / 18
自律で“測って直す”
最適化ループ
pi-autoresearch は、pi に「実験 → 実行 → 計測 → 採否 → 反復」を持ち込む拡張です（※コード生成ではなく、改善探索が中心）。
一文で言うと
やること / Doing
性能・品質・学習効率などの指標を対象に、改善を継続探索。
成果 / Output
記録・可視化・レビュー可能な“整理済みブランチ”へ変換。
PROBLEM
03 / 18
探索が面倒
検証コスト
単発の改善は当たり外れが大きく、反復検証と計測が増えるほど作業が重くなります。そこで必要なのは“試して測る”ループを自動化することです。
抱えがちな失敗
i
改善が効いたのか、たまたまのばらつき（ノイズ）か判断しにくい。
ii
試行履歴が散らばり、再起動やcontext圧縮で復元できない。
iii
変更が絡み合い、レビュー（PR差分確認）が困難になる。
iv
安全性・正しさの担保（テスト/型/Lint）が自動化から抜けがち。
CORE IDEA
04 / 18
Edit → Run → Decide
自律実験
/autoresearch モードでは、まずベースラインを走らせ、その後「編集→コミット→実行(run_experiment)→ログ(log_experiment)→採否(keep/revert)」を回します。
ループの骨格
(1) 変更
編集・コミット。
(2) 計測
run_experiment で実行。
(3) 採否
結果に基づき keep / revert。
決め手
metric（指標）と direction（上が良い/下が良い）で比較可能にする。
PERSISTENCE
05 / 18
途切れない真実
永続ログ
反復前提のため、記録を残すのが肝です。pi-autoresearch は .auto/log.jsonl と .auto/prompt.md を“真実のソース”として追記・保存します。
2つの中核ファイル
.auto/log.jsonl
各実験結果を jsonl 形式で追記。
.auto/prompt.md
セッション情報（目的/既試行/スコープ）を保存。
効果 / Impact
再起動やcontext compaction を挟んでも文脈を復元し、探索を継続できる。
CONFIDENCE
06 / 18
ノイズを見積もる
信頼度スコア
3回以上の実験があると MAD（Median Absolute Deviation）でノイズ推定し、best improvement と MAD から“信頼度スコア”を算出します。
狙い
見分けたいもの
改善が本物か、ベンチマークの揺らぎか。
実務上の意味
ML学習やLighthouseのように不安定でも判断の指針にできる。
留意
信頼度は“自動破棄”ではなくアドバイザリ（助言）として扱われる。
FINALIZE
07 / 18
レビュー可能へ整理
finalize
/skill:autoresearch-finalize は、採用された改善を“論理的変更セット”としてまとめ、レビューしやすい独立ブランチ群を生成します。
なぜ必要
i
自律ループは試行が増えるほど変更が絡みやすい。
ii
人がPRレビューしやすい“切り分け”が必要。
入力
.auto/log.jsonl を読み取り。
出力
マージベースから分岐する独立ブランチ。
QUALITY GUARDRAILS
08 / 18
壊さないための検査
checks & Hooks
最適化が正しさを壊す可能性があるため、.auto/checks.sh による任意のバックプレッシャーチェックや、before/after hook による外部処理を組み込めます。
選べるガード
.auto/checks.sh
テスト・型・Lint などを実行し、結果を失敗扱い等で扱う。
.auto/hooks/before.sh / after.sh
反復前後で情報収集・学習ログ・通知などを挿し込む。
設計意図
“計測自動化”を“運用できる自動化”へ寄せる。
CONFIG
09 / 18
コストを閉じる
maxIterations
ループが無限に回ると困るため、APIキー上限と .auto/config.json の maxIterations が停止・セグメント再初期化の制御として提示されています。
停止策
APIキー側
予算（上限）でコストを制御。
.auto/config.json
maxIterations で一定回数後に自動停止。
運用イメージ
一定期間ごとに区切って、新しいセグメントとして再初期化。
METRICS
10 / 18
何を測るか
metric設計
計測の成否は metric の設計に依存します。目標（例：テスト実行時間、バンドルサイズ、学習損失など）と計測方法（metric、実行コマンド）を明確にします。
例（入力データ）
時間
テスト実行時間 / テスト duration。
サイズ
バンドルサイズ / bundle size。
学習
学習損失 / training loss。
実務ポイント
評価指標が“比較可能”であるほど、自律ループは賢く探索できる。
FAQ1
11 / 18
スコアは捨てない
Q1 信頼度
信頼度スコアは自動で採用/不採用を決めるものではなく、入力データ上はアドバイザリ（助言）です。破棄（auto-discard）はしません。
要点
i
自動破棄（auto-discard）ではない。
ii
エージェントは再実験を検討する方向づけを得る。
iii
最終判断は keep / revert ロジックに依存。
FAQ2
12 / 18
前提フォルダ
Q2 .auto/
.auto/ フォルダは必須の前提です。反復で生まれる中間ファイルやセッション状態を、revert しても壊さないために保持します。
設計意図
なぜ必要
中間成果物と状態を“失わない”。
運用上の効果
セッションの整合性を保ち、継続探索が可能。
前提
説明では .auto/ を単一サブフォルダにまとめ、revert しても保持されるよう設計。
SAFETY OPERATION
13 / 18
見落とし注意
副作用 & 制約
pi-autoresearch はコマンド反復実行を行うため、副作用（外部API、生成物の肥大化、データ破壊など）リスクは常に残ります。checks.sh と作業設計でガードする必要があります。
不透明になりやすい点
失敗時の挙動
どの例外でどう回復するか、詰まり条件など。
安全性の設計
外部通信・未知コマンド実行のガードがどこまでか。
レビュー分割の限界
“共有ファイルなし”制約のため、複合改修が自然に分解できないケースはあり得る。
VERDICT
14 / 18
測る探索の実装
採用しやすい
pi-autoresearch の強みは、“測ることを中心に据えた探索”を開発ワークフローに実装している点です。さらに .auto/log.jsonl と .auto/prompt.md を single source of truth として扱うのが実務的です。
実務目線の勘所
i
最適化指標（測定可能性・副作用の少なさ）を先に決める。
ii
checks.sh で正しさを担保し、失敗モードを可視化する。
iii
可能なら作業ディレクトリ分離と成果物クリーンアップで副作用を抑える。
iv
finalize で“変更セット”を PR レビューに接続する。
