MCP on Workers
02 / 16
避けたい“成功の罠”
5つの落とし穴
Cloudflare Workers 上で MCP（Model Context Protocol）サーバを動かし、Claude/MCP Inspector などの外部クライアントからツール呼び出しする際に遭遇しがちな実装・運用トラブルを、作者の実例として整理します。
日本語の用語は短く併記：MCP（モデル文脈プロトコル）/ JSON-RPC（JSON遠隔手続呼び出し）/ TLS（通信の暗号化層）
Problem
03 / 16
“通った”は別物
buildでは安心できない
ビルドや --dry-run が通っても、本番の実行経路・TLS・クライアント引数パースまでは保証されません。
安心材料
型チェック/ビルド/ dry-run
未保証
Workers起動/ export形/ DNS/TLS/ Inspector引数
Architecture
04 / 16
全体像（最小）
MCP → ツール実行
MCPサーバ側は「ツール名」「入力スキーマ」「実行ロジック」を登録し、外部クライアントがツール呼び出しを行う設計です。
1. 登録
tool name / inputSchema
2. 実行
実行ロジック（Workers上）
3. 呼び出し
Claude / MCP Inspector（検証）
Workersの制約：Node.jsバージョン適合・起動/エントリポイント仕様が影響。
Distinction
05 / 16
見えない前提
テンプレートの 黙ってた仕事
公式テンプレートを使わず手で組むと、テンプレートが黙って面倒を見ていた“見えない場所”を自力で踏むことになります。
テンプレートあり
暗黙のexport/起動/スキーマ整形
手組み
小さな違いが型/実行/疎通で露呈
Pitfall
06 / 16
型が壊れる
inputSchema：空は危険
引数なしツールで inputSchema: {} を書くと、型とオーバーロード解決が破綻し、エラー位置が“戻り値側”に見えることがあります。
誤解
入力がない→空スキーマでOK？
教訓
inputSchema自体を省略するのが安全
Pitfall
07 / 16
dry-run安心は幻
Workers起動で クラッシュ
createMcpHandler が関数を返す実装で、default export にそのまま置くと Workers 起動時にクラッシュします。
例：default export の “export形（形そのもの）” が Workersの起動仕様と合わないと実行時に落ちる。
dry-runはアップロードや形式的確認で止まることがあり、ランタイム起動経路までは保証しない。
Pitfall
08 / 16
切り分け迷子
ローカルポートは 揺れる
ローカルの待ち受けポートがテンプレート設定に依存し、ドキュメント通りとは限りません。その結果「サーバ破損か、ポート不一致か」を迷います。
迷う原因
Readyログの読み違い/ポート差分
対処
Ready on ... を見て切り分け
Pitfall
09 / 16
Successの落とし穴
TLS反映が 間に合わない
workers.dev のサブドメイン未登録でも deploy は Success になり得ますが、実アクセスでは TLS 失敗が起きます。
見えるもの
ダッシュボード上の “Success”
実態
DNS到達後に証明書初期化で失敗
Subdomain登録＋反映待ち（著者は約75秒観測）→実測で再確認。
Pitfall
10 / 16
クライアントが誤解
--tool-arg改行で 分割
MCP Inspector CLI の --tool-arg に改行を含む値を渡すと、改行で分割されて誤解釈されます。
よくある例
CSVを複数行で渡す
起きること
キー=値が途切れ、rows=0 など
Distinction
11 / 16
疑う順番
サーバ不具合と 決めない
Inspector側の引数パースが原因のことがあり、「サーバが悪い」と疑う前に、Inspector側の解釈も確認して切り分けます。
1
--tool-arg に改行/多行があるか
2
CSV等が “最後まで” 渡っているか
3
UI/InspectorでなくJSON-RPC直叩きも検証
Process
12 / 16
デバッグ層を分ける
保証の層を 分解
「ビルド」「dry-run」「Workers起動」「実アクセス（TLS）」「Inspector検証」を分けて考えると、原因が散らばりません。
開発時
型/ export形/ ローカルポート
運用時
Subdomain/TLS反映/ 実アクセス確認
最後の“検証結果”は Inspectorの引数パースにも左右される。
Evidence
13 / 16
5つを一枚で
Checklist（落とし穴集）
#1
inputSchema: {} は危険 → 省略推奨
#2
--dry-run成功 ≠ 起動成功 → export形注意
#3
ローカルポートはテンプレ依存 → Readyログで確認
#4
deploy SuccessでもTLS失敗 → Subdomain/TLS反映待ち
#5
--tool-argの改行で分割 → Inspector解釈も疑う
結論
“見えてる成功”の意味を確かめる
Closing
14 / 16
手組みの価値
理解は 罠から生まれる
著者は当初「非推奨のMcpAgentを使うからテンプレ回避」と考えたが、実際はテンプレ移行済みでした。それでも手で組んだ経験が、次回以降の理解とデバッグ効率に繋がったと結論づけています。
次回予告：CSVをそのまま引数で渡すとトークン枯渇に限界 → “データ本体ではなく置き場所ID” を渡す方向へ。
