待ち時間を前倒しで削る
Speculative
sPTC（Speculative Programmatic Tool Calling）は、LLMエージェントのREPLで ツール呼び出しを“生成途中”から前倒し実行し、待ち時間を重ねて短縮する設計思想です。 （投機実行 / shadow REPL）（影の実行）
PROBLEM
03 / 16
ボトルネックはツール
Tool Latency
通常のREPL型ハーネスは「コード生成完了 → ツール実行 → 結果待ち → 続行」で直列になりがちです。 高遅延のサブLLM・サブエージェント・検索が、推論時間の大部分を占めやすいのが課題です。
直列（通常）
生成完了待ち
→ ツール実行待ち
狙い
生成とツールを重ねる（overlap）
→ 待ちを減らす

04 / 16
JITの発想で前倒し
Overlap
CPUの投機的実行やLLMのspeculative decodingに似ていますが、目的は“デコード短縮”ではありません。 ツール呼び出しの高遅延を、コード生成と同時進行で消すことです。
生成中
予測できるツールを検知
→ 先に起動
shadow
影のREPLで promise を作成
→ キャッシュ化
本番
同じ呼び出しなら即返
→ 後段の待ちを削減
ARCH
05 / 16
sPTCの動き（概略）
REPL + Promise
LLMがストリーミング出力中に「この先起きそうなツール呼び出し」を読み取り、ツールを非同期に立ち上げます。 結果は promise（将来値）として保存し、本番が同じ呼び出しに到達したらキャッシュから返します。
speculate（予測）
部分コードから
tool call候補を抽出
real（本番）
生成完了後に実行
→ キャッシュ即返
FLOW
06 / 16
どのタイミングで？
Streaming
sPTCは「コードを出し切るまで待たない」ため、ツール生成直前の遅延を隠せます。 ただし、推定できる入力条件が揃うときほど有効です。
i. 検知
ストリーミング途中で
ツール呼び出しを特定
ii. 非同期起動
shadow REPLでpromise生成
→ ツールを走らせる
iii. 即返
本番REPLで同一呼び出し
→ キャッシュから応答
iv. 不一致
推定が外れた場合は通常実行へ
（待ちが残る可能性）
EVIDENCE
07 / 16
速度はどれくらい？
1–1.2x
RLM（再帰的言語モデル）での実験では、速度向上は概ね 1〜1.2x と報告されています。 大きな倍率というより、設計どおりに重ね合わせが効くことを示す位置づけです。
効きやすさ
ツール待ちが多い構造
→ overlapの余地が大きい
依存性
ツール遅延 / 生成量 / 同時実行負荷
/ speculationの強度に左右される
DESIGN
08 / 16
重要な設計判断
What to Speculate
sPTCの効果を決めるのは、何をspeculateするかと、その入力が確実に推定できるかです。 高コストなサブRLMは見送り、推定可能性の高いものを優先する方針が述べられています。
優先候補
サブLLM / 検索など
遅延が大きいもの
慎重候補
推定コストが高い
（例：サブRLM）
条件
引数がリテラル等で確定
依存関係が安全（純粋）
SAFETY
09 / 16
推定できない領域は止める
Unsafe Block
条件分岐やループの結果は実行しないと分からないため、speculationは危険になります。 そこでshadow REPL（deepcopy）を使い、副作用を持つ外部I/Oをunsafeとして遮断します。
speculateしない
依存が安全に扱えない
（“実行しないと不明”な箇所）
shadowで隔離
deepcopyで状態を複製
→ 外部I/Oは遮断

10 / 16
非決定性ツールの難しさ
Same Call?
非決定的ツールでは、同じ入力でも結果が変わり得ます。 そのため「identical tool callsをいつ同一視するか」を区別する必要があります。
キー設計
入力＋出現（occurrence）で追跡
または決定性がないなら別インスタンス化
目的
誤キャッシュで意味を変えない
→ 整合性を守る

誤差より整合性を優先
Shadow REPL
speculationは“速さ”だけでなく、“誤動作しないこと”が要件です。 shadow REPLで安全に実行し、unsafe遮断で外部影響を防ぎます。
deepcopy
状態を分離して
副作用の漏れを抑制
unsafe I/O

TAKEAWAY
12 / 16
まとめ
Design Pattern
sPTCは、REPL型ハーネスにJIT的な発想を持ち込み、ツール遅延を生成と重ねて短縮します。 効果は1〜1.2x程度が目安で、導入前は「ツールレイテンシ分布」「条件・ループ頻度」「同時実行負荷」「speculate選定」を測るのが現実的です。
