秘密をAIに渡さない

envault 暗号化シークレット

ローカルで APIキー・トークン・パスワードを暗号化保管し、必要なときだけ実行プロセスへ注入します。英語：runtime injection／日本語：実行時注入。
狙い
チャット文脈・ログへの平文混入を減らす
核の設計
AIには「実値」ではなく「名前／暗号文」だけ
前提：envaultは「ランタイム隔離（サンドボックス）」ではなく、秘密を扱う経路を制御する仕組みです。
problem
03 / 18

よくある事故

AI×キー漏えい

AI連携では、APIキーをプロンプトに貼ったり、ログや .env に残してしまう事故が起きがちです。結果として、秘密が「AIの文脈（チャット履歴）」へ流れてしまいます。
経路 i
プロンプト貼り付け
経路 ii
チャット履歴に残る
経路 iii
.env / ログへ混入
envaultは「事故が起きる場所（入力・文脈・出力）」を設計で避けます。
metaphor
04 / 18

暗号の倉庫

見せない金庫

金庫（暗号化保管庫）に鍵をしまい、AIには札（暗号文）だけを渡します。実値は、必要なときにだけ扉の前で出します。
AI側
名前：key name（日本語：鍵名）／暗号文：ciphertext（日本語：暗号文）
実行側
envaultが実値を環境変数へ注入（英語：process env）
この分離で「平文がチャット文脈に出る」確率を下げます。
architecture
05 / 18

3つの境界

保管→注入→隠す

envaultの流れは「保管（暗号化）」→「注入（環境変数）」→「出力マスク（漏えい抑制）」です。ポイントはAIが平文を“見る”設計になっていないことです。
i 保存
秘密をローカル暗号化で保持
ii 注入
必要時のみ実行プロセスへ環境変数注入
iii 出力
実値はマスクして返す
この3点セットで、チャット・履歴・.env混入の主要ルートを抑えます。
evidence
06 / 18

AIに渡すもの

名前と暗号文

エージェントが参照するのは主に「キー名」と「age（年齢）」で暗号化された“暗号文”です。実値はenvaultが起動するプロセス環境変数に注入されます。
見える情報
key name（鍵名）／age（年齢）／暗号文（ciphertext）
見せない情報
APIキー・パスワードの平文（plaintext）
少なくともREADME上は「平文をAI文脈に渡さない」方針が明確です。
process

入力の事故を防ぐ

一度だけ確認

未登録の鍵が必要な場合、エージェントがチャットに貼り付けるのではなく、ユーザー確認用のウィンドウで一度だけ入力（または拒否）させる流れです。
悪い例
チャットへ貼って履歴に残る
envault流
確認ウィンドウで入力し、拒否も可能
“貼ってしまった結果が残る”運用リスクを下げる設計です。
enumeration
08 / 18

運用の制御点

編集をゲート

鍵の編集・ローテーション・設定変更は Touch ID / Windows Hello でゲートされます。これにより、エージェントが勝手に安全性を下げる行為を抑えます。
Touch ID
指紋認証（生体）で承認
Windows Hello
生体認証で承認
効果
ローテーション等をユーザー主導へ
TUI（ダッシュボード）で秘密を追加・編集し、重要変更は承認が必要という構図です。
distinction
09 / 18

正直な境界

サンドボックスではない

envaultは隔離技術ではなく、秘密を扱う経路を制御します。そのため「ランタイム完全隔離（サンドボックス）」は保証されません。
あり得る制約
悪意あるプロセスが稀に秘密を利用
脅威依存
侵害されたマシンでは監査ログ停止の懸念
危険度の高い環境ではOSレベルの隔離が別途必要になります。
comparison

従来運用 vs envault

“貼る”をやめる

従来はキーをプロンプトや .env に渡しがちですが、envaultは平文をAI文脈に置かないルートへ移します。
従来
プロンプトにキーを含める／ログや履歴に残る可能性
envault
AIには暗号文・鍵名だけ／実値は実行時に注入／出力をマスク
結論：AI連携の“事故ポイント”を設計的に迂回します。

注入とマスク

必要時のみ露出

envaultは必要なときだけ秘密を環境変数へ注入し、同時に出力はマスクします。これにより「見える時間」と「見える場所」を短くします。
注入（注：実値）
envault起動プロセスの環境変数へ格納
マスク（注：表示）
実行コマンド出力に含まれる平文を隠す
狙いは「AIの文脈・履歴に平文が残らない」状態を作ることです。

14 / 18

まとめ

価値と条件

envaultは「AIに秘密を渡す問題」を、設計（平文を渡さない）と運用（確認・マスキング・生体ゲート）の両面で現実的に改善します。
強み
事故率を下げる具体策が揃っている（平文非提示／注入／マスク／承認）
条件
“サンドボックスではない”ため、脅威モデルに応じたOS隔離・運用が必須
結論：日常的な漏えい事故を減らしたい開発者に向くが、万能の安全装置ではない。
