02 / 16
実用の差は“設定”で決まる
Qwen 3.8 27B
ローカルで動くビジョン対応LLMは“能力”が高くても、推論設定と提供形態が合わないと無駄やズレが増える。今回の実験ログは、その勘所を示している。
モデル
Qwen 3.8 27B（Apache 2.0）
量子化で約17GB級
観測点
reasoning_effort / context length
さらにサービング最適化（MTP）
出典：Simon Willisonの実験ログ要約（本デッキは提示文に基づく圧縮整理）
PROBLEM
03 / 16
賢いのに“過剰に作る”
デフォルト罠
推論努力（reasoning_effort）がデフォルトで xhigh だと、ユーザーの要求を超えて凝り始めることがある。結果として待ち時間も推論トークン消費も増える。
症状
“先回り”で作り込み
必要以上の背景・凝った構図
コスト
生成時間が伸びる
内部の推論トークン増
影響
指示忠実性が下がる
“丁寧すぎる”がズレの原因に
例：ペリカンSVG、円を描くSVGなどで“要求以上”の出力傾向が観測
CORE IDEA
04 / 16
速度と品質はトレードオフ
比率が鍵
体感速度・結果の一致度は、「推論トークン（内部思考）」と「出力トークン（ユーザーに返る結果）」の比率で変わる。reasoningを上げるほど“良くなりうる”が、“余計”にもなりうる。
reasoning を上げる
精度/出来栄え ↑
ただし無駄思考・待ち時間 ↑
reasoning を下げる
速度 ↑ / 指示忠実性 ↑
ただしタスクによっては精度↓の恐れ
運用の要点：まず低/オフで整合を取り、必要な時だけ段階的に上げる
EVIDENCE
05 / 16
能力は“幅広い”
何でもできる
Qwen 3.8 27Bは、画像認識・境界ボックス（bounding boxes）・ツール連携・コード生成などで「かなり使える」ことが確認された。17GB級の量子化でも成立している。
ビジョン
認識 + bounding boxes
画像→位置推定
出力形式
JSONで座標
後続処理に接続可能
実装
HTML可視化/ツール生成
周辺アプリ運用へ
根拠：ペリカン画像でbounding boxesがレンダリング結果と良好に一致したとの記述
EVIDENCE
06 / 16
“値が出る”≠“後で動く”
ツール接続
bounding boxesが正確でも、後続処理（座標スケーリング、実装）が一発で合うとは限らない。ログでは推論オフ版で「ほぼ動くが位置がズレる」例が挙げられている。
モデル出力
座標（JSON）
正確に推定されることも多い
実運用リスク
ズレは別レイヤ
座標変換/スケールで破綻し得る
示唆：評価は「生成結果」だけでなく「後続処理の成功率」まで含める
PROBLEM
07 / 16
コンテキストが足りないと崩れる
長さ制限
LM Studioのデフォルトコンテキスト上限（8,192 tokens）では、思考が枯渇して問題が起き得た。最大262,144まで確保すると改善したとされる。
デフォルト
8,192 tokens
思考で使い切り→挙動が破綻し得る
対策
262,144 tokensまで
長い推論が必要な設定で整合性を確保
要点：“モデルが大きい”だけではなく“提供側の上限と挙動”が一致する必要がある
PROCESS
08 / 16
最初のセッティング手順
段階運用
まず reasoning を低（low）またはオフで動かし、指示忠実性と動作を確認する。次に必要なタスクだけ推論を上げる。
i
reasoning 低/オフ
無駄思考を抑え、ズレを検出
ii
context を十分に
デフォルト8,192に固めない
iii
必要時だけ xhigh
精度が効く場面でだけ増やす
設計思想：速度・コスト・忠実性の“バランス”を先に取る
DISTINCTION
09 / 16
能力 vs 運用設計
両輪
Qwenの能力は高いが、実用感は「推論設定（reasoning_effort）」「コンテキスト長（context）」そして「サービング方式」で決まる。デフォルト値だけでは最適にならない。
モデル能力
ビジョン + ツール
指示に沿って動ける
設定
reasoning / context
無駄思考・枯渇を左右
提供形態
MTPなど最適化
体感速度を変え得る
この切り分けが、追試と改善の近道になる
COMPARISON
10 / 16
APIに置き換えは未完
速度が壁
15〜30 tokens/秒は悪くないが、日常的な“常時相棒”としては遅さが残る。すぐにAPI相当へ置き換える判断には至っていない。
現状
15–30 tok/s
常用の待ち時間に影響
方向性
サービング改善
MTP（Multi-Token Prediction）で短縮の余地
言い換え：ハード都合もあるが、ソフト側の改善で体験は伸びる
EVIDENCE / RISKS
11 / 16
“良かった”の一般化に注意
限界もある
速度や精度の比較が、完全に同条件とは限らない（LM Studio/llama.cpp、量子化、推論設定、端末差）。さらに、再現性（失敗率・安定性）や長期運用データが十分でない可能性がある。
比較
環境差が大きい
厳密な同条件ベンチではない
主観
“面白さ”が混ざる
ビジネスではコスト/忠実性が支配的
再現性
タスク別の安定性
ツール呼び出し失敗頻度など未詳
結論：追試できる部分（設定差）は強いが、普遍保証はしない
TAKEAWAY / 教訓
12 / 16
運用設計が勝つ
三つの指針
Qwen 3.8 27Bを“ローカルで使える状態”にする鍵は、デフォルト疑い、段階的推論、そして最適化の見極め。モデル評価というより運用設計の教科書になる。
i
デフォルト（xhigh）を疑う
過剰思考→無駄/ズレの温床
ii
low/オフから開始
指示忠実性とコストを先に合わせる
iii
MTP等で体験を詰める
速度ボトルネックの改善余地
まとめ（EN / 日本語）: Tune reasoning + context + serving（推論・コンテキスト・提供方式を調整して“実用化”する）
次の実験は、同一タスクで reasoning と context を動かして比較するのが最短
