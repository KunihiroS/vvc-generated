MCP/CLIの本質
eager vs lazy

「MCPかCLIか」より重要なのは、設計がeagerかlazyかで、LLMのコンテキスト（トークン）消費が決まる点です。

Problem
03 / 19
トークンは有限
Context Cost

LLMには有限なコンテキスト窓があり、ツール説明やスキーマにトークンを使うほど、推論とコード生成の余裕が減ります。

Core idea
説明/スキーマの早出し＝先に埋まる
Impact
タスク継続や出力品質に影響
Architecture
04 / 19
何を渡す？
Tool Interfaces

MCPはツールの入出力スキーマを提示し、CLIはコマンド体系に従って呼びます。

MCP
モデルへ：ツール定義（入力/出力）を提示
CLI
モデルへ：コマンド（例：gh issue create）を実行
Metaphor
05 / 19
説明を先に配る
Eager / Lazy

eager（先出し）は必要前に情報を載せ、lazy（後出し）は要求に応じて必要最小だけ開示します。

Eager
初期化でスキーマ大量投入
Lazy
必要時に詳細を要求・開示
Result
トークン効率が設計で変わる
Evidence
06 / 19
Blocksの計測
Count Tokens

Blocks.aiはClaude Sonnetの count_tokens で、CLI/MCP/Skill file/サードパーティMCPの「初期時の増分」を比較しました。

Method
初期化時のコンテキスト増分を差分計測
Why it matters
感想ではなく“コストの位置”を見える化
Evidence
07 / 19
MCPは増えがち
Schema Bloat

Blocksの例では、Blocks MCPサーバの初期時スキーマトークンが約3,185。一方Blocks CLIはスキーマ追加が0でした。

Blocks MCP
初期化スキーマ：~3,185 tokens
Blocks CLI
スキーマ追加：0 tokens
Evidence
08 / 19
26,644の例
GitHub MCP

GitHub MCPの例では、ツールセットを有効化すると初期時に約26,644 tokensを消費するケースが示されました。

Observation
ユーザ要求の前に情報が埋まる
Concern
推論・継続・出力に影響し得る
Distinction
09 / 19
原因はプロトコル？
Not Protocol, Design

「MCPは高コスト」というより、数値の大部分は不適切なサーバ設計（eager設計）が生む可能性が高い、と記事は譲歩します。

Likely cause
ツール詳細を常に全部開示
Fix direction
階層化・オンデマンド開示
Takeaway
MCPでも削減余地あり
Comparison
10 / 19
CLIは軽くしやすい
Inner Loop

CLIは「ヘルプ確認＋本実行」で数百トークン程度に収まりやすい、という方向性が示されます。モデルが既に理解しているコマンド体系とも整合します。

Strength
追加説明を載せる必要が薄い
Best fit
内側の開発ループ（inner loop）
Comparison
11 / 19
安全運用の軸
Credential Custody

MCPはcredential custody（認証情報の管理）で有利になりやすい一方、合成（composability）では弱くなり得る、と記事は整理します。

MCP：できること
モデルが持たないキーは漏れにくい
CLI：起きやすいこと
Unix的な連鎖で合成しやすい（ただし鍵の扱い注意）
Process
12 / 19
外側と内側
Outer / Inner Loop

CLIは開発者の内側のループに向き、MCPはエージェント間で境界をまたいで統制する外側のループで有用になりやすい、と述べられます。

CLI
inner loop：実行・反復が速い
MCP
outer loop：エージェント統制・連携が得意
Distinction
13 / 19
Lazy設計が鍵
Design Controls

MCPでもコストを抑えるには、ツールを階層化し、詳細をオンデマンドで要求するなど、lazyな開示設計を取るのが有効です。

1) Hierarchy
知識層/行動層を分離（粒度を調整）
2) On-demand
必要なツール詳細だけ追加提示
3) Separation
サーバの責務を明確化
Comparison
14 / 19
併用の結論
Use Both

固定の二択にせず、用途で分けて併用するのが合理的です（例：構築・公開はCLI、他者のエージェント呼びはMCP）。

Build & Publish
CLI（素早い反復）
Call Others
MCP（外側の統制）
Rules / Skill
Skill file（行動規約を教育）
Closing
15 / 19
最終チェック
Evaluate Requirements

「トークンが少ない＝常に正解」ではありません。認証統制、合成可能性、ツールカバレッジ、運用コストまで含めて選びましょう。

Risk to watch
ツールカバレッジ不足 / 合成の弱さ
Practical stance
初期コストだけでなく総コスト・成功率も評価
