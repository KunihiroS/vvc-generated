COVER
02 / 16
プロセスを縛る

Sandyサンディ

Sandyは、AIコーディングエージェントをローカル実行するときに、実行プロセスの権限を事前に確定し、実行中に増やせない形で制限するツールです。コンテナ/VMではなく“フォアグラウンドコマンド”として動きます。
担うもの / Scope
プロセスのアクセス制限（ファイル・環境・権限・プロファイル）
担わないもの / Boundaries
承認・監査ログ・振る舞い監視は別コンポーネント前提
PROBLEM
03 / 16
誤動作の連鎖

被害拡大を抑える

AIエージェントが誤って広い権限で動くと、ファイル改変や情報流出などの被害が連鎖しやすくなります。サンドボックスは、アクセスできる範囲を狭めることで“被害が広がりにくい”状態を作ります。
考えるべき制限
ファイル / ネットワーク / 環境（PATH等） / 実行権限
Sandyの焦点
特に「プロセスの権限」を、実行前に詰めて固定する
METAPHOR
04 / 16
実行前ロック

扉を先に閉める

Sandyは「走り出してから鍵を増やす」ことをさせません。実行前にコマンド・パス・プロファイル・環境・権限を解決し、サンドボックス適用を検証できなければ実行を拒否します。
i 解決
コマンド / パス / プロファイル / 環境 / 権限
ii 検証
サンドボックス適用が可能かを確認
iii 運用判断
不可なら“無制限フォールバック”しない（失敗時安全）
ARCHITECTURE
05 / 16
プロセス境界

プロセス・サンドボックス

SandyはコンテナやVMのようなカーネル/メモリ/ユーザー境界を提供しません。できるのは、OS上の“そのプロセス”に対するアクセス制限を強制することです。
特徴
コンテナ/VM不要 / 通常のフォアグラウンドコマンドとして動作
限界（脅威モデル）
カーネル/ユーザー/メモリの隔離は前提に含めない
ENUMERATION
06 / 16
何を指定する

権限を“最小化”

Sandyは既知のエージェントをコマンド名などから認識し、組み込みプロファイルで必要最小限のアクセスを提供します。ユーザーは読み書きやネットワーク遮断を追加指定できます。
ディレクトリ制御
--read / --read-write（例：許可する範囲の指定）
ネットワーク制御
--block-net（通信を遮断するオプション）
エージェント認識
コマンド名など → 組み込みプロファイル適用
運用の肝
“許可する範囲”と“遮断する範囲”を明示してレビュー
EVIDENCE
07 / 16
失敗時安全

フォールバック禁止

Sandyは、検証・適用できない場合に“無制限にフォールバック”しません。つまり、サンドボックス適用が不可能なら実行拒否（fail-safe）で倒す設計です。
安全側に倒れる
「部分的に動くことで誤認」ではなく「動かない」を選ぶ
運用影響
環境によっては実行できないことが起き得る → 事前テストが必要
DISTINCTION
08 / 16
ネットは標準許可

デフォルト許可に注意

Sandyのネットワークはデフォルトで許可されます。外部送信や情報流出のリスクを下げたい場合は、方針として--block-netを検討します。
デフォルト
ネットワーク通信が許可される（危険になり得る）
対策
--block-netで遮断（互換性目的の例外もあり得る）
※「互換性のため特定ディレクトリアクセスを許可する」など、要件に応じた判断が必要です。
PROCESS
09 / 16
dry-runで事前確認

実行前にJSON監査

--dry-runは、起動せずにサンドボックス解決後の内容をJSON（バージョン付き）で出力します。公開スキーマのバージョンと、解決されたruntime_controlsが分かります。
出力に含まれるもの
dry_run_schema_version / runtime_controls
効く場面
監査・レビュー／組織運用で「何が許可されるか」を確認
INTEGRATIONS
10 / 16
統合は別管理

Kontext / Numbat

KontextやNumbatのような周辺統合（in integrations）は、明示的にセットアップした場合に限って安全に維持・適用するモデルです。セットアップはサンドボックス“外”でホスト設定に変更が入り得ます。
重要ポイント
ホスト側の永続的変更 / trust boundary（境界）の理解が必須
注意の方向性
統合が弱いと、サンドボックスの効果以上にホスト側影響が出る
LIMITS
11 / 16
HTTP配信は不可

Numbatフックの制約

NumbatフックはHTTPによるDirect deliveryがサポートされず、ファイル出力を使うよう案内されています。これは境界（trust boundary）を越えた通信を安易に許さないための制約として理解できます。
不可
Direct HTTP delivery（HTTP直配信）はサポートなし
代替
ファイル出力でフック（境界を意識した設計）
COMPARISON
12 / 16
コンテナ/VMと別物

隔離強度は違う

Sandyは“プロセス・サンドボックス”であり、コンテナやVMと同じレベルの安全性は期待できません。OS全体の隔離が必要な場合は、別の層（OS設定・別マシン運用など）も検討が必要です。
Sandy
プロセス権限の制限に集中（カーネル境界は提供しない）
コンテナ/VM
隔離の強度がより高い（ただし別コスト/運用）
CLOSING
13 / 16
導入の勘所

多層防御で使う

Sandyは「実行前に権限を確定し、適用できなければ実行しない」ことで安全性を上げますが、0.1.xは実験的で独立監査が未完了、さらにmacOSでは非公開/非推奨のSeatbeltインターフェースを利用する点に注意が必要です。safe-by-designを周辺（dry-runレビュー、ネット方針、統合の差分管理）で支えるのが現実的です。
推奨（最低限）
i dry-runでruntime_controls確認（監査・レビュー）
ii --block-net方針を明確化（必要に応じて）
iii 統合（Kontext/Numbat）のセットアップ差分管理
前提
承認/監視/監査ログは別ツール前提。Sandy単体で“万能のセキュリティ”にはならない。
日本語補足: 多層防御（たそうぼうぎょ / defense in depth）が鍵。
