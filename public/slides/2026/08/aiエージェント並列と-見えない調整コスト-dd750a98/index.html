02 / 16
Topic
並列は“速さ”ではなく“責任”
AIエージェント並列
実行ランタイムでは、リトライ・タイマー・ツール呼び出し・キャンセルが同じ状態や外部資源を巡って競合し、因果が壊れます。
結論：無制限並列は性能より先に整合性を傷つける。そこで「complexity budget（複雑性予算）」で並列を抑えます。
03 / 16
Problem
緑でも壊れる
スループット罠
ダッシュボードの処理量（スループット）が上がっても、失敗が「矛盾する結果」として後から蓄積することがあります。
見える指標
完了件数・平均レイテンシ・再試行率
見えない破壊
レースによる副作用競合 / 古い結果の再投入 / 因果崩壊
04 / 16
Core
同じ“瓶”を共有
競合
リトライ・タイマー・ツール呼び出し・キャンセルは別物に見えても、実態は同じ状態（state）や同じ外部資源を巡る相互作用です。
Retry
失敗時の再実行（再試行の増幅）
Timer
一定時間後の停止/切替
Tool / Cancel
外部副作用＋無効化/停止の責務
05 / 16
Key idea
並列は“能力”ではなく
complexity budget
各エージェント実行レーンに「失敗回復の責任」を含む固定の complexity budget を与え、満たせないなら並列を増やしません。
目的
並列増加で生まれる“調整コスト”を封じる
運用
予算を超えるなら待たせる（レーン追加を拒否）
06 / 16
Mechanism
増やすほど壊れる
オーナー権限
並列レーンを足すと、キャンセル経路・タイムアウト時の状態所有権・回復コストまで“自分で担保”する必要が増えます。
Owner
誰が次の状態遷移の正当性を持つか
Failure recovery
副作用競合後の整合性回復責任
07 / 16
Risk
distributed corruption
整合性破壊
状態の所有権が曖昧だと、無制限並列は「配布された汚染（distributed corruption）」になり、取り消しが形だけになります。
Race
古い試行が勝って書く / 新しい試行が上書き
Timeout
待ちをやめるだけで正当性を定義しない
Cancel
“無効化の対象”が共有されず遅延結果が混入
08 / 16
Tools
フェンシングで守る
権限剥奪
キャンセルは丁寧に止めるだけでなく、lease（権限）を剥奪して遅延結果（zombie callback）を無効化します。
Fencing token
古い試行の書き込みを拒否
Epoch / Token検証
ツール呼び出し境界で“書ける正当性”を確認
09 / 16
Design
Idempotencyが要る
冪等
外部副作用があるなら、冪等性（idempotency）とコミット境界設計が必要です。取り消しに頼れないからです。
Idempotent
同じ試行（or 同等キー）が複数回あっても一度と同等
Commit boundary
いつ外部に“確定”し、その後の無効化は何を意味するか
英：idempotency / 日：冪等性
10 / 16
Complexity
スレッドじゃない
副作用増幅
並列化コストの中心はスレッドではなく、副作用（外部連携・DBロック・キャッシュ更新）とリトライ増幅（amplification）の組み合わせです。
External limits
サービス制限・レート制限が先に破綻
Locks / Cache
競合で待ちが増え、順序も崩れやすい
Retry amplification
失敗→再試行→さらに負荷→さらに失敗
11 / 16
Consequences
並列は“調整経路”を増やす
矛盾の同時生成
並列化はエージェント能力を増やすというより、矛盾する世界（相互に成立しない状態遷移）を同時に作ることになり得ます。
隠れたコスト
キャンセル・タイムアウト・回復の責務がレーンごとに増える
方針
サーキットブレーカー / アドミッション制御 / リトライ予算
12 / 16
Limitations
原理は良いが
測定が要る
提案の強みは失敗設計としての再定義ですが、導入には「予算の数値化」と「境界（所有権・コミット・ツール・外部副作用）の担保」が別途必要です。
必要な検証
どの指標（キュー滞在、リトライ率、ツール待ち、因果不整合率等）を優先するか
注意
サービスによって“キャンセル＝無効化”が成立しない領域がある
13 / 16
Closing
並列は正しく設計して
制御する並列
支持点は「無制限並列は最悪になり得る」という視点。結局は、並列を憎むのではなく“条件つきの資産化”が要点です。
やること
complexity budget / owner / fencing / idempotency / retry予算
最後に
対象システムごとに境界と閾値を決め、整合性を測り続ける
