COVER
02 / 16
Tailscale 拡張（ベータ）
Mullvad exit nodes
Tailscale の出口ノードとして Mullvad VPN サーバーを使うために必要な条件、DNSの注意点、運用の制約を一望します。
対象
Tailscale テールネット（tailnet）でのインターネット経路制御
焦点
導入要件／制限・DNS／プライバシー／ガバナンス／ライセンス運用
PROBLEM
03 / 16
“出口”は簡単そうで難しい
落とし穴
Mullvad exit nodes は機能拡張ですが、DNS設定の失敗や既存構成（DERP、ACL、管理方式）との不整合が致命傷になり得ます。
DNS ローカルDNS挙動がバージョン依存で、設定ミスで DNS 喪失 → 実質的なインターネット途切れ
運用 管理コンソールとテールネットポリシーファイルの併用不可（統制が崩れるとズレる）
制限 すべての機能が “通常exit node同等” ではなく制限がある
枠 Mullvad add-on とライセンス枠（プール・先着割当）が可用性に直結
METAPHOR
04 / 16
暗号トンネルの“先”
出口は
第三者
Tailscale の WireGuard トンネル先にある“出口”を Mullvad 側に置き換えるイメージです（出口先があなたの機器ではなく Mullvad）。
Tailscale
tailnet 内で暗号化して経路を制御（DNS/経路も設計対象）
Mullvad exit
VPN サーバー経由でインターネットへ（ログ把握の可能性あり）
ARCHITECTURE
05 / 16
何を満たせば動く？
導入要件
Mullvad add-on（アドオン）を購入し、管理方式と署名/割当の流れを満たすことで利用できます。
必須
Mullvad VPN add-on（ベータ）購入
管理
管理コンソール or ポリシーファイル（どちらか一方が正）
割当
ライセンス枠が必要（プールは先着で割当）
運用
有効化/無効化/削除/移行/署名の手順を前提化
ENUMERATION
06 / 16
制限：全部同じではない
利用できない
通常の exit node に近い動作でも、構成によって “動かない/効かない” があり、事前整合性確認が必要です。
DERP カスタム DERP サーバーは非対応（制限）
ACL Google-synced groups の ACL が動かない（制限）
端末UI Windows でリスト表示が不完全な場合がある
挙動 提案された/必須（mandatory）exit node は概ね対応（ただし制限あり）
EVIDENCE
07 / 16
DNSが主戦場
DNS注意
特定バージョン（例：1.48.1/1.48.2）でローカルDNSの使い方が変わり、誤ると DNS が失われます。
失敗の症状
DNS喪失 → 名前解決不能 → インターネット利用が困難（実質的に停止）
上書きの影響
Tailscale接続中は全クライアントのDNSクエリが指定DNSへ向かう（経路変化はexitの有無に関係し得る）
PROCESS
08 / 16
設計チェックの要点
DNS設計
“ローカルネットワークアクセス”と“グローバル名解決”を同時に成立させる必要があります（DNSリーク対策を含む）。
原則
exit node 利用有無に関わらず、DNS経路/上書きの影響を確認する
対策
ローカルネットワークアクセス許可、必要ならグローバルDNSの上書き設計
検証
設定変更前に “名前解決” と “外部到達” をテスト（復旧手順も用意）
前提
Tailscaleバージョン差を織り込む（特にローカルDNS挙動）
DISTINCTION
09 / 16
統治（Governance）
二択運用
Mullvad access を管理コンソールとテールネットポリシーファイルで併用できず、どちらかを正に固定します。
選択肢 i
管理コンソールを正（UI運用を徹底）
選択肢 ii
ポリシーファイルを正（例：GitOpsで管理）
禁止
両方で同時に設定・編集（意図しないズレの温床）
推奨
正系を決め、変更フロー（誰が何をいつ）を明文化
COMPARISON
10 / 16
匿名性：完全ではない
プライバシー
Tailscale はトラフィック内容を復号できませんが、“どのユーザーがどの Mullvad サーバーへ接続したか” の対応がログとして把握され得ます。
Tailscale 側
ユーザーと Mullvad アカウントの紐づき、WireGuardトンネル単位の接続先の把握があり得る
Mullvad 側
ユーザーの身元情報（渡る前提の情報）は受け取らない（利点）
結論
匿名性は“設計次第で強化できるがゼロではない”
読み方
脅威モデル（誰が何を見得るか）を前提に評価する
EVIDENCE
11 / 16
ライセンス：枠が可用性を決める
枠と割当
Mullvad exit nodes はライセンス枠が必要で、アドオンにはベースで5ライセンス分が含まれ、追加購入で拡張できます。
ベース枠
Mullvad add-on：5ライセンス分を含む
拡張
追加購入でライセンス枠を増やせる
プール共有
枠を共有すると “先着順” で接続時に割当
注意
余剰端末があると、想定外の割当が起こり得る（結果として利用可否が変わる）
PROCESS
12 / 16
安全に進める段取り
導入の順序
最短で失敗しないために、(1)前提確認 → (2)DNS検証 → (3)管理方式固定 → (4)枠と制限の確認 の順で進めます。
i 前提 DERP/ACL/OS差など “制限” をリスト化して合否を先に判断
ii DNS 1.48.1/1.48.2 等を含めバージョン別に名前解決をテスト
iii 統治 管理コンソール or ポリシーファイルのどちらかを正に固定
iv 枠 必要端末数と同時接続を見積もり、枠が埋まる状況も想定
CLOSING
13 / 16
結論
成功条件は
DNS×統制
Mullvad exit nodes は強力ですが、DNS設計と管理方式の統制を誤らなければ、運用事故を大きく減らせます。
最優先
DNS（ローカル/上書き/リーク）を先に固めて検証
次点
制限（DERP/ACL/OS差）と枠（先着割当）を計画に組み込む
参考：用語ミニ（例）：exit node（出口ノード）/ tailnet（テールネット）/ WireGuard（暗号トンネル）/ DERP（中継）/ nodeAttrs（ポリシー）。
