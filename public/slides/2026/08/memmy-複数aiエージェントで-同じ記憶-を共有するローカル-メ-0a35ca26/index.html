02 / 16
Memmyで“同じ記憶”へ

Memmy—長期メモリ基盤

複数AIエージェントが、同じ“個人の記憶（長期メモリ）”と“永続的な文脈”を参照できるようにする、ローカル寄りのメモリサービス＋ゲートウェイ＋CLI/TUI。

開発方針の要点：(1) 外部記憶参照、(2) ローカル常駐運用、(3) BYOKで依存調整
PROBLEM
03 / 16
乗り換えが“文脈断絶”に

問題は 記憶の分散

エージェントを切り替えるたびに、作業状況や背景知識が継続しにくくなります。長期的な流れを保つには、会話履歴ではなく“参照可能な記憶”が必要です。

i現状
エージェントごとに文脈が分かれ、タスクが途切れる。
ii狙い
“同じ記憶”を共有してタスク継続を作る。
METAPHOR
04 / 16
脳の“外部メモリ”

Memmyは 長期脳

エージェントは“作業する手”で、Memmyは“覚えておく場所”です。保存された知識は、次のエージェント利用時にも参照される前提で設計されています。

Input
知識・作業状況を memmy-memory へ追加
Store
長期メモリとして永続化し、参照可能に
Reuse
別エージェントが同じ文脈を引き継ぐ
ARCHITECTURE
05 / 16
ローカル常駐の部品構成

構成：memory＋gateway

Memmyは主に「メモリサービス（memmy-memory）」「ゲートウェイ」「CLI/TUI」で構成され、systemdユーザーサービスとしてローカルに常駐運用できます。

memmy-memory
追加・検索・取得（例：memmy-memory add/search/get）
memmy-gateway + API
OpenAI互換として提供（例：:18990）
PROCESS
06 / 16
導入の流れ：運用を前提に

起動と反映を systemdで

CLI/TUIは初回起動時にモデル設定ウィザードを開き、systemdユーザーサービスはTUI/ターミナル終了後も継続稼働する想定です。設定変更は環境変数が反映されるよう再起動されます。

初回
モデル設定ウィザードで構成（BYOK含む）
常駐
memmy-memory.service / memmy-gateway.service を即時有効化
反映
~/.memmy/systemd/gateway.env（0600）を更新→再起動
接続
localhost バインドで、エージェントから参照
ENUMERATION
07 / 16
利用形態は3ルート

選べる 運用モード

Memmyは、(a) デスクトップアプリ、(b) LinuxのCLI/TUI（systemd運用）、(c) メモリサービス単体CLI（memmy-memory）という3形態で提供されます。

iDesktop
推奨。トライアル→BYOKへ切替の道筋あり
iiCLI/TUI
初回ウィザード＋ローカルAPI（:18990）で接続
iiiMemory-only
memmy-memory のみ操作（検索/追加/取得）
DISTINCTION
08 / 16
“保存”と“連携”を分ける

Hook導入は 段階的

README抜粋では、Memory SkillとHook/pluginはインストール段階と有効化段階が分離される可能性があります。明示的に memmy-memory init --agent <agent> のような運用が示されています。

インストール
Memory Skill / Hook を導入しても、既存エージェント挙動は“変更しない”趣旨
有効化
必要なときに init --agent で明示的に連携
EVIDENCE
09 / 16
検証しやすい手動操作

memmy-memoryで 中身を確認

長期メモリはブラックボックス化しがちですが、CLIで検索・追加・取得できる構造が示されています。人手で“何が入っているか”を確かめられます。

search
保存内容を検索して見つける（例：memmy-memory search）
add / get
追加と取得で、保存と参照を往復（例：add / get）
重要：全会話自動保存の有無は抜粋だけでは断定不可。保存ポリシー確認が必要。
DISTINCTION
10 / 16
BYOKで外部依存を調整

データ運用を 自分で握る

BYOKモード（ユーザー自身のモデルAPI利用）への切り替えが可能です。最小構成として ~/.memmy/config.yaml の例が提供されています。

切替
トライアルからBYOKへ、構成変更で運用を維持
最小構成
~/.memmy/config.yaml に provider 設定（例：OpenAIキー参照）
利点
ベンダ依存を弱め、運用ポリシーに合わせやすい
関連
memmy-memory / gateway が接続に必要な設定（URL/Token/Config等）を扱う前提
COMPARISON
11 / 16
Q&Aから見える“確度”

確認すべき 不明点

抜粋から言えることは強い一方、長期記憶は個人情報に直結するため、保存ポリシーやセキュリティ実装は追加確認が必要です。

保存
“全会話を自動保存”かは不明。memmy-memory addで保存可能は示唆。
systemd
TUI終了後も利用可能。ただし linger有効化の有無などは環境依存の可能性。
連携
既存エージェントの挙動は“変更しない”趣旨。だが有効化段階は要確認。
セキュリティ
0600権限など配慮はあるが、暗号化・保管・転送・監査は抜粋だけでは不十分。
EVIDENCE
12 / 16
良い点／未完点（意見）

“便利”を 運用で支える

意見として、Memmyは「同じ記憶」を理念で終わらせず、ローカル常駐・OpenAI互換API・systemd・CLI/TUIで運用導線を用意している点が強みです。一方で、保存粒度・保持期間・削除・監査・誤保存対策などの情報不足がリスクになります。

強み
ローカル運用＋再起動設計＋手動検証（search/add/get）でブラックボックスを抑える方向。
リスク
誤保存・過剰保存・秘匿情報混入。データセキュリティ／ガバナンスの未確認部分が残る。
倫理面：同意・透明性・データ最小化を、ユーザー側でコントロールできるか要確認。
CLOSING
13 / 16
導入判断の結論

まずは ポリシー確認

Memmyはエージェント横断のタスク継続に向く可能性が高い一方、長期記憶は個人情報リスクも増えます。導入前に、保存ポリシー・削除/エクスポート・アクセス制御・暗号化/通信保護・監査ログを確認するのが安全です。

チェックリスト
自動保存条件／保持期間／削除・エクスポート／アクセス制御／暗号化／監査
期待できる効果
複数AIの乗り換えでも同じ文脈を引き継ぎ、作業の中断を減らす
Terms：BYOK（Bring Your Own Key/モデルAPI）＝自分のモデル提供元を使う選択
