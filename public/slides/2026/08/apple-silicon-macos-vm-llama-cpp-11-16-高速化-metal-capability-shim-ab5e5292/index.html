VM×推論の壁
11–16×高速化
Apple Silicon の macOS VM で、llama.cpp の推論速度が「GPU能力の見え方」を変える Metal shim により大きく改善される。
軸（要点）
Virtualization.framework がゲストに提示する Metal capability が保守的
手段
対象プロセスだけ capability 回答を上書き（互換レイヤ / shim）
読み物向け圧縮まとめ（数値は提示されたテスト事例ベース）
PROBLEM
03 / 16
ボトルネックの誤解
“パススルー不足”
VM で遅い原因を「GPUの直付け（passthrough）がないから」と片付けがちだが、分岐条件を決める capability のズレでも性能は大きく落ち得る。
実際の経路
macOS VM は Virtualization.framework により Metal を仮想GPU経由で実行
効く要因
ゲストが問い合わせた能力情報が低めだと、アプリが高速カーネルを選べない
METAPHOR
04 / 16
分岐を止める数字
能力表の 誤読
アプリは起動・初期化時に GPU 能力テーブルを参照し、使うカーネルやコードパスを選ぶ。答えが保守的だと、本来通れる高速ルートへ行けない。
ゲスト
capability を問い合わせ
アプリ
返答に基づき分岐（高速/低速）
結果
高速カーネルが選ばれず遅くなる
ARCHITECTURE
05 / 16
shimの入れどころ
プロセス単位
互換レイヤは「特定プロセス」だけに capability 応答を差し替える。VM全体を変えず、推論ワーカー側の最適化に寄せる設計。
設計
Metal capability の問い合わせ応答を shim が上書き
範囲
対象プロセス以外へ波及させない（意図的に局所化）
Bilingual（要約）: shim = 互換レイヤ / 置換層（Japanese gloss: かんぞくそう）
PROCESS
06 / 16
何を返す？
回答の調整
shim は主に「GPU family の回答値」と「最大 threadgroup memory」を引き上げ、llama.cpp がより新しい Metal 経路（例：SIMD-group reduction / matrix / bfloat16）へ寄れるようにする。
主な差し替え
Apple GPU family の capability 回答
追加の調整
max threadgroup memory を増やして分岐を誘導

COMPARISON
11 / 16
VFIOじゃない
“回答”を差し替える
この手法は GPU パススルーではなく、Virtualization.framework のパラバーチャライズドGPU経路は維持したまま、Metal capability 問い合わせへの“返答”だけをプロセス単位で調整する。
いい意味での差
ホストGPU直付けではなく capability 回答の矛盾 を解消
本質
アプリの高速分岐（カーネル選択）を起動側へ寄せる
DISTINCTION
12 / 16
限界と注意
更新耐性
私的・バージョン依存のゲスト Metal 実装に依存するため、OS更新や環境差で動かなくなる可能性がある。さらに注入手法（例：環境変数やライブラリ注入）にはセキュリティ運用上のリスクがある。
主な制約
OS / ゲスト / ホスト組み合わせと、対象 API・分岐の範囲に依存
運用リスク
DYLD_INSERT_LIBRARIES 等の注入は拒否され得る（サンドボックス/監査など）
結論: “自分の環境で再現性確認”が前提（常時・万能の最適化ではない）。
CLOSING
13 / 16
持ち帰り
再現性重視
VMでの遅さは GPU “能力の提示”の保守性が原因になり得る。shim はプロセス単位でその返答を調整し、llama.cpp の高速カーネル選択を引き出して 11–16× を狙う。
コア理解
capability の矛盾 → 分岐条件が変わらない → 高速経路に到達できない
実務の勘所
対象プロセス限定・対象コードパス限定で検証し、OS更新に備えてフォールバックを用意
