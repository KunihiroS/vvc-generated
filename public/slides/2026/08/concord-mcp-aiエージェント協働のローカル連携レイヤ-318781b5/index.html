02 / 16

Local-first collaboration

Concord 協働基盤

複数のAIコードエージェントが「同じリポジトリ作業」を安全に引き継ぎできる、ローカルファーストの連携レイヤ（MCP経由）です。

ただのチャットではなく、ownership・handoff・レビュー状態・衝突（overlap）まで“タスクの記憶”として保持します。

problem
03 / 16

Collision & context loss

協働の破綻 頻出

別々のハーネス（実行環境）で動くエージェント同士は、同じ箇所を編集して衝突しやすく、さらに意思決定の文脈がセッション終了で消えがちです。

衝突
編集が“重なったあと”では修復が重い（上書き・矛盾・レビュー不能）。
文脈喪失
会話ログ頼みだと、前提・発見・判断が後から追えない。
metaphor
04 / 16

Not an orchestrator

共通の“作業帳” 共有

Concordは司令塔（オーケストレータ）ではなく、代理人たちが同じ作業帳を参照しながら、順番と責任を明示して引き継ぐための土台です。

ownership
誰が今そのタスクを持つかを明示。
handoff
去る/渡す手続きを残す。
review packet
レビュー準備状態を証跡として扱う。
architecture
05 / 16

MCP message bus + Local state

構成要素 中核

MCP（Model Context Protocol）でメッセージングしつつ、状態はローカルSQLite（.concord/concord.db）を真実の源に統一します。

MCP
エージェントがサーバ機能を呼ぶ規格（start_work / claim / accept / update など）。
SQLite
タスク記憶・衝突判断・レビュー状態を保持し、同一リポジトリ配下の複数エージェントで共有。
evidence
06 / 16

Overlap prevention

衝突検知 前に

編集のあとで“かぶった”と気づくのではなく、start_work と claim/accept の流れで作業の重複を事前に検知・制御します。

開始
start_work が作業登録と所有権（claim）の土台になる。
確認
inspect_work で現在のワークスペース/タスク状態や古いclaim（stale）をフラグ。
enumeration
07 / 16

Ownership & handoff protocol

引き継ぎ 手続き

タスクの責任移譲は、transfer/accept の手続きとして明示されます（単なるメッセージ送信ではない）。

i claim
作業対象と責任を“取りにいく”。
ii transfer/accept
別エージェントへ渡すことを手続き化して合意する。
distinction
08 / 16

Task memory, not chat history

チャットとの 差

Concordは、意思決定・前提・発見をタスクに紐づけて保持し、セッション終了後も文脈を追えるようにします。

Concord
タスク記憶（review packet / evidence）を“成果物の単位”で残す。
会話中心
ログは残っても、判断の所在が構造化されにくい。
結果
レビュー可能性と引き継ぎ品質が上がる。
process

Local control, visible operations

運用の見える化 CLI

CLIやTUI（dashboard）で、衝突・古いclaim（放置）・レビュー準備完了などを可視化し、実務の管理コストを下げます。

重要コマンド
concord setup / concord adapters status / dashboard
管理対象
到達性、セッション状態、stale claim、レビュー状態の整合性。

Best-effort delivery

到達性が 鍵

update_work は、指定したto_agent_idが到達可能でない場合に即失敗し、黙って別ルートへ回さない制約があります。

到達性
“必ず届く”ではなく、reachable endpoint / アダプタ状態に依存。
運用対策
concord adapters status で事前確認が実質的に必須。
evidence
11 / 16

Privacy posture

テレメトリ 方針

テレメトリは送信されますが、コード断片・原ファイルパス・リポジトリ詳細・メッセージ内容を送らない方針が明記されています。

送らない
コード/パス/リポ詳細/メッセージ内容。
注意
サーバ側保持やIP由来情報など、管理面の確認が必要。
無効化
CONCORD_TELEMETRY_DISABLED=1 または DO_NOT_TRACK=1。
comparison
12 / 16

Strengths vs unknowns

評価軸 論点

強みは安全な所有権移譲と衝突制御、運用の見える化。一方で性能・耐障害性・脅威モデルなどの定量情報は不足しています。

強み
Practical: setup/status/dashboard。Safety: claim/overlap制御。Security: テレメトリ抑制。
不足
SQLite同時実行、復旧手順、監査ログ粒度/保持、性能指標、統合失敗事例。
closing
13 / 16

Takeaway

導入の勘所 期待調整

Concord MCPは“確実な自動分業”ではなく、到達性・セッション状態・権限/プライバシーを整えたときに価値が最大化します。

先に adapters status で到達性を確認し、.concord/concord.db を前提とした運用（衝突・stale claim・レビュー状態）を設計するのが近道です。
