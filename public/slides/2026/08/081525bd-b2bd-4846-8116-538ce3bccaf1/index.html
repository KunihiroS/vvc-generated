全部スコアリングの代償
Scale
READMEでは性能上の境界も明示され、メモリが増えるほど設計限界に近づく前提です。
Latency
サブ10msの安定：概ね1万件前後
Upper design
5万超で設計限界に近づく（ベクトルDB領域）
Need
実利用では自組織の規模で再ベンチマーク
Assumption
数千〜数万規模なら速度と取りこぼし低減が成立する考え
近似ではなく全件スコアリング（recall）ゆえのトレードオフ
Ops
12 / 16
運用の注意
Practical
埋め込み器の混在や、ネットワークファイルシステム上のSQLite運用など、前提条件を守る必要があります。
Embeddings
同一DB内で埋め込み器を混在させない（空間比較不能）
File system
NFS/SMBなどネットワークFSは危険（ローカル保存前提）
Concurrency
WALやbusy timeout等の話題があるが、ディスク種別と運用確認が必要
Conflict
コンフリクトは“審判材料”であり、最終判断はエージェント/ユーザに依存
Bilingual: 矛盾（contradiction） / コンフリクト（conflict）
Takeaway
13 / 16
向くチーム
Verdict
remembraneは、少〜中規模のエージェント記憶を“監査可能・説明可能・取りこぼし低減”で運用したいチームに適しています。
Strength
ローカル・監査（explainable / journaling / time travel）・全件スコアリング
Safety
矛盾を黙殺せずコンフリクト提示（likely / possible）
Risk
コンフリクト検出はヒューリスティック（誤検知/見逃し）
Limit
性能上限は“規模と運用条件”に依存（5万超が境界）
結論：用途条件が合えば、信頼性と運用性の両立がしやすい永続メモリ。
