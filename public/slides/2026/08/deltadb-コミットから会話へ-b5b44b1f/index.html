DeltaDB
02 / 16
会話で作る履歴
CommitからConversationへ
Zedが構想する新しいバージョン管理基盤「DeltaDB」は、ソフトウェア開発を“コミット単位”ではなく“会話と編集の連続”として扱います。
Problem
03 / 16
議論が後でズレる
Gitの限界
Gitは基本的に「コミット＝スナップショット」で履歴を結びます。ところが、重要な会話は“実装の途中”に起き、コードとして語れる状態になるのは後になりやすい。
発生タイミング
会話：作業中（進行中）
会話が先 / 編集が途中
接続のズレ
コード：後で（コミット/PR後）
会話と実装がドリフト
Metaphor
04 / 16
地点ではなく軌跡
履歴は軌跡
コミットは点です。しかしDeltaDBが扱いたいのは、点を結ぶ線——会話と編集が同じ“参照軸”で連続する軌跡です。
Gitの見え方
点：コミットごと
差分は参照されるが連続性が弱い
DeltaDBの見え方
線：操作（デルタ）単位
会話→編集の流れを保持
Architecture
05 / 16
DeltaIDが軸になる
デルタDB
DeltaDBでは、作業の“間”に起きるあらゆる操作を細粒度のデルタとして記録し、各デルタに安定したIDを与えます。
単位
操作（デルタ）
参照ID
DeltaID
目的
会話↔コード整合
Evidence
06 / 16
双方向に辿れる
トレーサビリティ
デルタIDにアンカーできるため、過去の会話のどの行からでも当時のコードへジャンプでき、逆に現行コードから“それを生んだ会話”へ辿れます。
会話 → コード 会話（いつ・どこ）から、その時点のコードへジャンプ
コード → 会話 現行の変更点から、「触れた会話／関与したエージェント」へ追跡
Distinction
07 / 16
ドリフトを抑える
会話×編集を同時記録
メッセージ（会話）と編集結果を並行して保存し、後付けの議論や“ズレ”が生まれる余地を減らす設計思想です。
Git的な運用
会話：後から紐づけ
PR/コメント接続が遅れやすい
DeltaDBの狙い
会話と編集：同じ文脈で参照
最初から対応関係を保持
Process
08 / 16
待たない参加
フロー中心
pull requestやpush待ちで議論を再接続するのではなく、作業中に参加し、その場で必要な注釈を行えることを目指します。
i 発生
編集が進む
ii 会話
参加して意図を補足
iii 接続
会話↔デルタが同軸に
Key
09 / 16
協働を前提に設計
AI時代の必須条件
人間に加えてAIエージェントが継続的に編集するなら、編集の連続性と意図の追跡がより重要になります。DeltaDBはこの前提で整合を作り込みます。
i 同時編集
複数人・複数エージェントが同じファイルを編集
ii 参照の一貫性
編集が変化しても会話の対応が崩れにくい
Concurrency
10 / 16
衝突を“扱える”形に
コンフリクトフリー
DeltaDBは「コンフリクトフリー・レプリケートされたワークツリー」を組み込み、分散環境でも同時編集と参照の整合を狙います。
狙い
会話と編集の乖離を減らす
ズレが“履歴の都合”で増えないこと
含意
合成（整合）をワークツリー側で吸収
衝突解決を開発者の儀式にしない
Comparison
11 / 16
中心座標が移る
Git vs DeltaDB
DeltaDBは、共同作業の中心を「コミット経由」から「会話と編集を同一の参照軸で扱う」方向へ移します。
Git（従来）
履歴：コミット（スナップショット）
参照：コミットや差分に依存
DeltaDB（構想）
履歴：操作（デルタ）＋DeltaID
会話：同軸で追跡可能
Caveats
12 / 16
期待と未確証
評価ポイント
記事の思想は筋が良い一方で、本文だけでは実装の具体・検証結果が不足しています。特に運用（性能、セキュリティ、監査、承認）での限界が鍵です。
実務
移行コスト・運用再設計
技術
デルタ粒度/性能/ストレージ
ガバナンス
承認・監査・責任分界
セキュリティ
会話データの機密情報混入
アクセス制御・ログ保持が未提示
倫理/品質
エージェント発話の誤りの扱い
誤った理由として誤用しない設計が必要
Closing
13 / 16
結論：会話が座標になる
ベータを待つ
DeltaDBは「コミットを介した共同作業」から「会話と編集を同一の参照軸で扱う共同作業」への移行を狙うバージョン管理基盤です。短期的にはベータ提供と早期利用が計画されています。
One message
DeltaDB＝デルタで会話と編集を同時に結び、AI時代の“連続性”と“意図追跡”を成立させる。
