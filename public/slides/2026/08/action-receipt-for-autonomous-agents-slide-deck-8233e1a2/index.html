COVER
02 / 14
説明より先に、実行を固定

Action Receipt（行動レシート）

自律エージェントが外部ツールに副作用を与えるなら、事後の言い訳ではなく「実行前に確定する行動レシート」で監査可能性（誰が・何を・どの権限で・状態がどう変わったか）を確保します。

PROBLEM
03 / 14
後付けはズレる

問題は post-hoc

分散システムではタイムアウト、再試行、部分成功が起き、後からログや要約で「筋が通った説明」を作れます。そのズレが、監査や責任追及を曖昧にします。

METAPHOR
04 / 14
境界を作る

説明ではなく commit barrier

行動レシートは、説明の代替ではなく「検証不能なら次に進めない」ためのゲート（commit barrier）です。正しさ保証ではなく、再現可能な責任切り分けを先に固定します。

ARCHITECTURE
05 / 14
最小6フィールド

最低限のレシート

i. actor
実行主体（誰が）/ 実行ID
ii. policy version
適用ポリシー（どの規則）
iii. normalized-input hash
正規化入力ハッシュ（何に基づく）
iv. tool-argument digest
引数ダイジェスト（何を送る）
v. idempotency key
冪等キー（再試行の二重副作用を抑止）
vi. resulting state ID
結果状態ID（状態遷移の同一性）

※日本語：actor（実行主体） / policy（ポリシー） / digest（要約） / idempotency（冪等） / state（状態）

PROCESS
06 / 14
書き込み前にゲート

実行順序（ゲート設計）

前（commit）
1 レシートを耐久ストアへ先に書く
2 レシートが存在しない限りツール副作用を実行しない
後（replay / reconcile）
3 再試行は idempotency key と結びつける
4 結果が確定すれば resulting state ID で照合する

目的：成功応答を「完了」と誤解せず、未確定を次の不可逆処理へ持ち込まないこと。

ENUMERATION
07 / 14
再試行の要点

二重副作用を止める

核心 i / ii
i 冪等キー（idempotency key）で意図を束ねる
ii 引数ダイジェスト（tool-argument digest）で同一性を補強
核心 iii / iv
iii 結果状態ID（resulting state ID）で「同じ結果」を検証可能にする
iv 未確定なら再実行しない（後述）

レシートは「書いたこと」ではなく「再生可能性（replay）」として効きます。

EVIDENCE
08 / 14
保証は万能ではない

それでも重要な理由

監査可能性
誰が・どのポリシーで・どの入力（hash）に基づき実行したかを切り分けできる。
運用の安全
再試行時の判断を型で制限し、二重副作用（注文/支払い/削除の重複）を減らす。
分散の現実
クラッシュや部分成功でログが欠けても、「実行前コミット」が検証の起点になる。
責任の再現
説明が筋が通っていても、実際の状態遷移との差分を追跡できる。
DISTINCTION
09 / 14
正しさ保証ではない

レシート ≠ 正義の証拠

レシートがあっても、適用ポリシーが誤っていれば「間違った行動」も正確に再現され得ます。つまりレシートは正しさの保証でなく、再現可能な責任切り分けです。

改善できる
監査で「何が確定していて、何が不確定か」を境界として扱える。
別途必要
政策評価・テスト・結果判定（アウトカム）など、正しさの検証は別レイヤー。
PROCESS
10 / 14
未確定をファーストクラスへ

outcome unknown（未確定）

成功応答が返っても state ID が確定しないなら、成功/失敗に倒さず outcome unknown として扱い、依存する次の不可逆アクションを止めます。

i / 収集
observed success の記録は保持する。
ii / 停止
次の副作用を実行しない（確定まで待つ）。
iii / 決着
外部照合（reconcile）で state ID を確定させる。
COMPARISON
11 / 14
自己署名問題

レシートは改ざんし得る

強み
監査の起点になる（実行前コミットがある）。
限界
レシートを書いた当事者が改ざんできるなら「自己申告」に退化する。
必要な設計
追記不能ストア、ハッシュ対象の正当性（生入出力）、独立観測や外部検証。
結論
脅威モデルと保証強度を見積もらないと、監査“風”に留まり得る。
EVIDENCE
12 / 14
全ツールに一律は危険

適用範囲を絞る

耐久コミットと外部検証はコスト（レイテンシ、保存量、運用負担）を増やします。全てのツール呼び出しへ一律適用すると破綻し得るため、副作用の不可逆性に応じて分類して適用します。

高リスク
支払い、削除、権限変更（strict）
中リスク
重要変更（commit + reconcile）
低リスク
観測中心（軽量ログ）
CLOSING
13 / 14
実行ゲートが本体

結論：説明より commit

自律エージェントの説明力は監査の代替になりません。価値が出るのは、レシートが「実行ゲート」として強制され、unknown を未確定として止め、外部観測で確定して初めて次へ進める設計にしたときです。

Action receipt：実行前にコミットされる監査可能な行動記録（actor / policy / input hash / argument digest / idempotency key / resulting state ID）。
unknown outcome：成功応答でも state ID 未確定なら outcome unknown として停止し reconcile で決着。
Threat model：自己署名や改ざん耐性の不足があると、レシートは“監査風”に退化し得る。
