Agentic IAM
02 / 16

監査可能な「代理行動」

Identity & Access

AIエージェントが複数の社内システムを操作するとき、「誰が、いつ、なぜ、どの経路で」実行したかを切れずに残す仕組みが要る。

PROBLEM
03 / 16

従来IAMのズレ

Person/Service中心

従来のアクセス制御は「人」「サーバ（サービスアカウント/APIキー）」「単発処理」を前提にしがちで、代理で意思決定する主体（agency）を表現しにくい。

不足
“誰の要求に基づき、どのエージェントが判断したか”が追いにくい
代理行動の帰属（who）
結果
監査・説明責任が弱くなり、権限評価の粒度も崩れやすい
説明可能性（auditability）
PROVENANCE
04 / 16

ホップ越しの欠落

Provenance chain

多段のエージェント連携では、各システムが“直前の呼び出し元”しか見えず、アクタチェーンが途中で欠けると監査が破綻する。

問題
ログ統合が手作業になりがち
影響
インシデント対応が遅れる
影響
権限評価の不整合が起きる
FOUNDATION
05 / 16

検証可能ID

SPIFFE/SPIRE + STS

既存のゼロトラストをエージェントにも拡張し、SPIFFE/SPIREに基づくワークロード検証可能IDを起点に、STSがエージェントごと・ホップごとに短寿命JWTを発行する。

起点
SPIFFE/SPIRE（workload identity）
ワークロードの検証可能ID
発行
STS（Security Token Service）で短寿命・スコープ付きJWT
agent/hop単位のトークン
ACTOR CHAIN
06 / 16

アクタチェーンを埋め込む

JWTで who-did-what

アクタチェーン（ユーザ→エージェント→次ホップ…）をJWTに埋め込むことで、各システムが同じ文脈を前提に監査とポリシー評価を行える。

嬉しさ
監査ログのつぎはぎを減らす
監査の一貫性
嬉しさ
下流サービスも“チェーン前提”で制御できる
ポリシー整合性
SECURITY
07 / 16

使い回し抑止

Single-hop JWT

JWTは単一ホップ向けでAudience（宛先）と短いTTLを持ち、別宛先への転用や再実行（リプレイ）を抑える設計になっている。

Audience
宛先に紐づく
TTL
短寿命
効果
漏えい時の被害範囲を制限しやすい
CONTROL POINT
08 / 16

統制点はMCP Gateway

集中検証で policy

MCP Gatewayを中継点として、JWT検証とポリシー適用をツール呼び出し単位で行い、統制の一貫性を確保する。

理由
認可が分散すると運用・監査が難しくなる
一貫性を失う
手段
AI Guardのような横断対策も適用しやすい
機密・不正の統制
DEV EX
09 / 16

正しい実装を舗装する

A2A standard

A2A（Agent-to-Agent）呼び出しを安全に行える標準クライアントで、STSトークン交換やアクタチェーン保持の“漏れ”を減らす。

従来の問題
手作業の準拠は欠落が起きやすい
実装ギャップ
解決
SDKに統合し、最短で正しい経路へ誘導
paved path
PERFORMANCE

値

利点の整理

3観点 × 実装

結論

人中心→代理の帰属

このアプローチは「AI時代のIAM」を、連鎖認証（アクタチェーン）・統制点（MCP Gateway）・可観測性（observability）で実装する方向性として要約できる。

盗難/転用/監査欠落を抑制
