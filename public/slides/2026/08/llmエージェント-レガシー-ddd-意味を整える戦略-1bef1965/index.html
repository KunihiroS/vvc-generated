COVER
02 / 16
LLMを「成果」へ導く

意味の整備

レガシーコードへLLMエージェントを入れる鍵は、モデル性能ではなく「意味の混乱」を減らす設計（DDD）にあります。
対象 / Legacy
既存コードベース（ブラウンフィールド）では、用語・責務・境界が曖昧になりやすい。
解決 / DDD
ユビキタス言語（ubiquitous language）と境界づけられたコンテキストで、推測領域を削ります。
PROBLEM
03 / 16
壊れるのは「推測」

品質急落

グリーンフィールドではうまくいくのに、レガシーではLLMが誤りやすくなります。原因は能力不足というより、コードが「言葉の意味と境界」を答えられていないことです。
起きる / 発明
モデルが、コードにない綴り・表現・概念を「補って」提案する。
起きる / 勝手に直す
意図して存在しているアダプタ等の有無を誤認し、変更してしまう。
本質 / 意味の不在
用語の採用、所有者、責務境界がコード内に十分に埋め込まれていない。
METAPHOR
04 / 16
モデルの席替え

意味が席

LLMエージェントは「正解」を探すより先に、どの言葉をどの意味で使えるかを確定する必要があります。DDDはその座席表（＝制約）を先に用意します。
Without DDD / 推測
曖昧な用語 → もっともらしい補完 → PRがズレる。
With DDD / 制約
ユビキタス言語・境界・拒否語 → 迷う余地を削る。
ARCHITECTURE
05 / 16
分けて進める

戦略×戦術

本稿は作業を2層に分けます。戦術（実装）はLLMで安くでき、戦略（意思決定）はDDDで土台を作って人が担います。
戦術 / tactical
決めたことをコードへ反映する。機械的作業はLLMが得意。
戦略 / strategic
変更理由・整合性・設計意思決定。LLM単独では不足し、人が関与する前提。
要点
「LLMに全部任せない」ではなく、「DDDでLLMが推測しなくて済む環境」を作る。
PROCESS
06 / 16
最小の宣言セット

.workflow.json

各リポジトリに `.workflow.json` を置き、ドメイン情報・境界づけられたコンテキスト・グロッサリ・エッジ（呼び出し関係と責務）を宣言します。
何を宣言 / Repo
コンテキスト関係、必要チェック、生成時の制約の入口。
なぜ重要 / 制約入力
LLMが「どの言葉を使ってよいか」を理解でき、推測発明を減らす。
出力 / 整合性
CONTEXT-MAP.md
で全体整合性を保ち、各コンテキストの記述へ接続する。
EVIDENCE
07 / 16
生きた辞書

CONTEXT.md

各コンテキストの `CONTEXT.md` には、採用する用語と、意図的に拒否する同義語を明確に書きます。これがLLMの“揺れ”を抑えます。
採用語 / 採用
このコンテキストでの正しい意味（用語の定義）。
拒否語 / 同義語
誤解されやすい表現を「使わない」と宣言する。
効果 / 推測削減
モデルが「どれが正か」を推測せずに済む。
狙い
人間の設計資料であると同時に、LLMにとっての制約付き入力になる。
ARCHITECTURE
08 / 16
全体地図

CONTEXT-MAP

`CONTEXT-MAP.md` により、コンテキスト間のつながりを可視化し、全体の整合性を保ちます。部分的な修正でも“意味の地図”は一貫させます。
役割
コンテキストの関係（エッジ）と配置をまとめる。
効果
生成・レビュー・更新が同じ前提に寄る。
キーワード（英/日）
Bounded Context（境界づけられたコンテキスト）／Ubiquitous Language（ユビキタス言語）
DISTINCTION
09 / 16
一方宣言は危険

エッジ二重宣言

エッジ（近隣コンテキストの呼び出し関係）は両側で宣言します。一方だけの記述はズレの温床になるためです。
片側だけ / ズレ
片方は「こう呼ぶ」と思っているが、もう片方は違う責務で扱う。
両側で / 一致
ジェネレータが不一致を検出し、設計の衝突を早期に見つける。
結果
不一致はDDD issueとして扱い、議論を継続的な検査へ寄せる。
PROCESS
10 / 16
機械的整合性

不一致→Issue

生成器はエッジや用語の整合性をチェックし、不一致をDDDの問題として管理します。後戻りを減らすために“衝突”をPR以前に炙り出します。
入力
.workflow.json
規約
CONTEXT.md
全体
CONTEXT-MAP.md
運用
再実行しても同じIssueを更新する、という更新規律で混乱を抑える。
EVIDENCE
11 / 16
最終的な到達点

推測しないPR

戦略層（意味と境界）を整備し続けると、LLMが作るPRは壊れにくい形に近づきます。結果として、コードベースが“推測に頼る状態”から移行します。
Before
用語・責務・境界が散らばる → 推測で埋める → 事故が起きる。
After
ユビキタス言語と境界が明確 → 制約付き入力 → 事故確率が下がる。
注意
効果は設計と運用次第。数値KPIなどの裏取りは別途必要。
COMPARISON
12 / 16
強みと限界

批判点

本稿の筋は良い一方、導入には初期整備コストがかかります。また、バグ率や回帰検出、セキュリティ検査などの具体指標が本文では不足しています。
強み
LLM導入を「プロンプト最適化」から外し、意味の混乱を構造問題として扱う。
限界
用語確定・エッジ定義・運用合意の負担、品質指標の定量化不足。
要検討リスク
辞書の陳腐化／境界の変化でマップが破綻／定義ミスが誤った制約として蓄積。
CLOSING
13 / 16
実行の指針

第一歩

次にやるべきは「LLMを入れる」ではなく、「意味の土台を作る」ことです。`.workflow.json`、`CONTEXT.md`、`CONTEXT-MAP.md` とエッジ二重宣言で推測領域を削りましょう。
着手（戦略）
Ubiquitous Language（ユビキタス言語）と境界を先に決める。
次に（戦術）
決めたことをLLMで実装・更新し、衝突はDDD issueで吸収する。
ゴール
人間が意思決定し、LLMは制約の範囲で働く。レガシーでも品質を落としにくい運用へ。
