02 / 16
アカウント許可を統一
Agent Policy Manifest
AIエージェントがユーザーの代わりにアカウント作成を行うとき、サイト側が許可条件を機械判読できる形で伝える新しい規格案です。
使う場所
/.well-known/agent-policy.json（例：wkdomains.agent-policy.json）
狙い
高リスクな「状態変更」を、段階的な権限と停止条件で安全に扱う。
用語の目安：permission tiers（権限ティア）= 操作の強さを段階化 / hard stop = 即時停止
problem
03 / 16
robots.txtでは足りない
状態変更が難所
robots.txtのような「クロール（読み取り）可否」は、アカウント作成のような“能動操作”の安全基準を表現できません。
読み取り
公開情報の探索は比較的リスクが小さい。
能動操作
アカウント作成はサーバ側の状態を変える。
結果
濫用検知・認証・同意・支払い等が絡み、制御が破綻しやすい。
metaphor
04 / 16
鍵穴を増やす
allow/denyの限界
単一の許可・拒否より、権限を段階（tiers）にして「どこまでなら自動化してよいか」を機械が理解できる形にするのが核です。
旧式
“入ってよい／だめ”だけでは、作業の重さが表せない。
提案
公開探索→委任付き試行→（停止）…のように段階化する。
bilingual（目安）：permission tier（権限ティア） / hard stop（即時停止）
architecture
05 / 16
/well-knownで宣言
agent-policy.json
サイトは /.well-known/agent-policy.json に「エージェントが何をしてよいか」をマニフェストとして置きます。
サイト側
許可条件・ティア・停止（hard stop）を定義。
エージェント側
ポリシーを読み取り、境界を守って行動。
安全側フォールバック
ファイルが無い場合は「公開探索のみ」（要約は可、登録はしない）。
監査ログ（想定）
行為の痕跡を残し、境界で“人へ引き継ぐ”。
enumeration
06 / 16
権限ティアの例
段階で許す
提案では、単純なallow/denyではなく、行為レベルを複数のティアに分けて扱います。
i. デフォルト
公開情報の探索は許可。
ii. 条件付き
条件を満たす場合のみ「ユーザー委任によるトライアル作成」を許可。
iii. 即停止
hard stop：支払い・法的責任などは停止。
iv. 例
CAPTCHA/ボット検知に引っかかる・偽の身元が必要・契約同意の扱い…等。
distinction
07 / 16
hard stopが境界
止める基準
特に「人の責任に関わる同意や支払い」を含む場合、エージェントは停止して人へ引き継ぐべきだとされています。
停止条件（例）
支払い要求（payment） / 料金 / 反復課金。
停止条件（例）
物質的な法的責任の受諾（legal responsibility）。
停止条件（例）
CAPTCHA・ボット検知（bot mitigation）、電話認証など。
狙い
“取り返しのつかない同意”をエージェントの誤操作で起こさない。
運用
境界で自動行動を止め、ユーザー確認へ切り替える。
evidence
08 / 16
なぜ実装が楽になる
共通言語の価値
この規格が普及すると、サイトごとに個別ロジックを作る負担が減り、エージェント側も安全側の実装を統一しやすくなります。
開発者
個別実装のカスタムを削減し、方針をマニフェストで共有。
プラットフォーム
監査ログ・hard stop・境界の明示を標準化しやすい。
ユーザー
「自分の代わりに何をしてよいか」を透明性のある形で理解。
相互運用
複数サイトでも同じ枠組みで読み取り・判断できる。
comparison
09 / 16
既存標準との違い
robots/llmsとの断層
robots.txtは読み取り中心、llms.txtはモデル利用中心で、ユーザー委任つきのアカウント作成の“行為レベル”を直接制御できません。
robots.txt
クロール（読み取り）可否。
llms.txt
AIモデル利用の補助ガイド寄り。
agent-policy.json
アカウント作成などの能動操作＋権限ティア＋hard stop。
ポイント
“行為（account creation）”と“境界（tiers/hard stop）”を機械判読に載せる。
到達したいこと
サイト横断で一貫した安全制御。
process
10 / 16
エージェントの判断手順
読む→判断→止める
エージェントはポリシーを読み、ティアに従って行動し、hard stopに当たれば停止して人へ渡します。
i. 探索
ポリシー探索（マニフェストの有無確認）。
ii. 適用
許可ティアに該当する操作だけを実行。
iii. 停止
支払い/法的責任/ボット検知などでhard stop。
iv. フォールバック
ファイル無しなら公開探索のみ（登録はしない）。
distinction
11 / 16
委任の線引き
“ユーザー委任”だけ
「完全自動登録」ではなく、人間ユーザーの意図が検証され、透明で追跡可能な形（監査ログなど）で委任が裏付けられる場合に限定します。
委任が必要な理由
同意（consent）や登録結果がユーザーの責任に波及するから。
区別されるポイント（例）
意図の検証 / 身元の透明性 / 追跡可能なメール形式 / 監査ログ可視化。
ここは仕様が運用に直結するため、実装基準の明確化が重要です。
comparison
12 / 16
賛成点と限界
強みは安全・課題は曖昧さ
提案の強みは“安全側設計”ですが、意図検証・監査ログ形式・救済フローなどが詰まっていないと誤解や抜け穴が起きます。
強み
支払い・法的責任をhard stopとして扱い、誤操作リスクを現実的に下げる。
限界
意図検証やログの具体が曖昧になりやすく、普及前は解釈誤りも起こり得る。
追加で必要
意図検証・身元透明性・ログ形式 / 法務・規制との整合 / 相互運用テスト / 誤検知時救済。
結論
万能策ではないが、“共通言語”を作る価値は大きい。
closing
13 / 16
次の標準に向けて
account creationの整合
Agent Policy Manifestは、アカウント作成を“安全に分解して許可する”方向で設計されており、エージェント時代の次の共通枠になり得ます。
要点 i
tier（権限ティア）で段階化。
要点 ii
hard stopで“責任領域”を停止。
要点 iii
ファイル無しは公開探索のみ（安全側フォールバック）。
標準化は実験段階で、期限（2026年11月1日）が示されています。普及には実装例と相互運用性、救済手段の具体化が鍵です。
