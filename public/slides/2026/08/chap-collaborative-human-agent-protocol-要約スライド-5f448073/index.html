CHAPの要点

CHAP（Collaborative Human-Agent Protocol）は、人間とAIエージェントの共同作業で生じる「判断（承認・編集・却下など）」を、後から追跡・検証できる形で保存する公開プロトコルです。

目的：再現性／検証可能性
日本語（JA glossあり）
PROBLEM
03 / 15
判断が散らばる

分散ログ問題

判断がチャットやチケットコメント、アプリの内部ロジックに分散すると、時間が経った後に「何が根拠でどう決まったか」を再構成しにくくなります（推測が混ざる）。

Where
chat / ticket / code
After
追跡が推測になりやすい
Need
問い合わせ一発の検証
解決の方向：構造化 + 連結
One-message / one-slide
CORE IDEA
04 / 15
監査チェーン

内容ハッシュ連結

CHAPは、AIの下書き（artefact）と人間の構造化された上書き（diff / rationale / tags等）を「監査チェーン」として、内容ハッシュで前後をつなぎます。

Artefact
エージェントのレビュー案（下書き）
Override
人間の上書き（diff / rationale / tags）
結果として、後日「何が根拠でどう変えられたか」を、ログ再解釈や推測を減らして検証しやすくなります。
ENVELOPE
05 / 15
override envelope

上書きの器

CHAPの核は「override envelope（上書きのエンベロープ）」です。人間がどのように承認・編集・却下したかを、diff・rationale・tagsなどで表現してチェーンに載せます。

diff（差分）
何を変えたか
rationale（理由）
なぜそうしたか
tags（分類語彙）
どの観点の判断か
Chain link（連結）
前後をハッシュで結ぶ
日本語注：diff=変更差分
rationale=判断理由
INTENT
06 / 15
intent_preserved

修正の種類

intent_preservedは「上書きされた事実」だけでなく、その修正が refining（表現の洗練） か substituting（決定変更） かを判別し、原因の切り分けを助けます。

Refining（洗練）
意図は維持し、表現だけ調整
Substituting（置換）
決定そのものが変わった
同じ「失敗」でも、対策（エージェント側の誤解か／ポリシー側の曖昧さか）が変わります。
TAGS
07 / 15
小さく統制

tagsで集計可能に

tagsは自由入力ではなく、チームで小さく統制することで、3か月後に「どのプロンプト／どのパスで繰り返し間違えるか」を集計できるデータになります（後日の学習・改善の基盤）。

統制
粒度・語彙を崩さない
集計
再現性ある分析軸
改善
対策を“データ化”
自由にすると：粒度が分裂
タグ=分析の次元
WORKING MODEL
08 / 15
監査の問いに答える

“何が根拠？”

CHAPの問いは一つに寄せられます：後日、チェーン上の差分・理由・分類を辿って「何が根拠でどう変えられたか」を検証します。

検証
根拠（rationale）と差分（diff）
追跡
前後をハッシュで連結（再構成の推測を減らす）
ログが散らばっていても、問い合わせ・再生・検証の“統一入口”を作るのが狙いです。
RELATION
09 / 15
併用が基本

MCP / A2Aと役割分担

CHAPはMCPやA2Aの代替ではありません。MCP/A2Aはツール実行やエージェント連携を担い、CHAPは人間が介入した判断を監査可能にする“交通整理”として周辺に位置付けられます。

MCP / A2A
連携・ツール実行の枠組み
CHAP
共同判断の監査チェーン（diff/rationale/tags等）
目的は補完関係
overlapあり

SECURITY
12 / 15
脅威モデル要確認

署名・権限

セキュリティ面では「署名（security-signed / 1.0等）」がオプトインとして示され、SCITTなどの選択肢もある一方、どの脅威モデルに対してどの設定が適切か、設定ミスがどれほど致命的かは追加の実務ガイダンス確認が必要です。

設定
署名は要件次第（常時必須とは限らない）
権限
監査チェーンが漏えい先にもなり得る
また誤ったoverride/diff/rationaleが登録されると、後日の分析が誤誘導されるため訂正の取り扱い方針も重要です。
