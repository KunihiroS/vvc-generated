Effective HTML
02 / 16
成果物で意図を伝える
HTMLスキル
AIエージェントに「何を作るべきか」を明確に渡すため、HTML成果物の種類と検証観点を再利用できる形に整理した考え方です。
成果物
ワイヤーフレーム / プロトタイプ / 計画 / 図まで含む
狙い
品質と有用性を上げる：曖昧さを成果物構造で潰す
Problem
03 / 16
文だけではズレる
曖昧さ
モデルは指示文の解釈が揺れやすく、手戻りやレビュー負荷が増えがちです。
起きること
曖昧な文章 → 誤解 → 差し戻し
解決の方向
意図をHTML成果物・構造・参照で可視化する
Core Idea
04 / 16
fat context + fat artifacts
伝達設計
「現代のモデルは多くできる」前提で、十分な文脈（fat context）と成果物（fat artifacts）を揃え、品質を押し上げます。
fat context
参照フォルダ / 既存アーティファクトなど“判断材料”を十分に
fat artifacts
HTML成果物自体が意図のガイドになる
狙い
曖昧な文章を減らし、手戻りを抑える
Architecture
05 / 16
創造性と信頼性を分離
分業
`design-artifact`で創作上の方向性を、`html-wireframe`や`html-prototype`で構造・挙動の確からしさを担当させる設計です。
design-artifact
見た目を固定せず、主題に合わせた“方向性”を提示
Wire/Prototype
構造検証→実動挙動の担保へ（忠実度を上げる）
（日本語補足）創造性＝デザイン指針 / 信頼性＝品質・挙動の確実さ
Options
06 / 16
6つの選択肢
スキル群
用途に応じて、成果物の種類（見た目の方向・構造・実動・計画・図）を選べます。
design-artifact
創作の方向性（デザイン指針）
html-wireframe
構造検証用（未完成前提）
html-prototype
実動の挙動・状態（可用性）
html-plan
実装の出発点を守る手順・ロードマップ
html-diagram
関係性に最適な可視化モデルを選択
html
広く相談する窓口（目的別に扱う）
Distinction
07 / 16
完成度より設計
未完成
`html-wireframe`は意図的に未完成にし、レビューの焦点を“見た目”ではなく“構造”へ固定します。
議論の中心
階層 / ナビ / フロー / レスポンシブ
期待される効果
後段のプロトタイピングを効率化する
Evidence
08 / 16
動くまで落とす
Prototype
`html-prototype`はワンフローと状態、キーボード対応、レスポンシブまで含めて可用性を担保します。
挙動
ワンフロー / 状態（state）
体験
キーボード対応（access for keyboard）
表示
レスポンシブ（responsive）
Process
09 / 16
前工程を固定
Plan & Diagram
`html-plan`は実装のコミットメント（出発点の拘束条件）を守りつつ手順に落とし、`html-diagram`は関係性の見取り図を作ります。
html-plan
手順・ロードマップ（いつ・何を守るか）
html-diagram
モデルと描画方式を選ぶ（関係性に最適化）
Quality
10 / 16
毎回の要件を明文化
品質
成果物には、レスポンシブ・アクセシビリティ・自己完結性・ブラウザ検証が期待されます。
レスポンシブ
画面幅に追従する設計
アクセシビリティ
使える体験を前提に
自己完結
依存や前提が少ない形で提供
ブラウザ検証
出力を実際に確認できること
Adoption
11 / 16
まず参照、必要なら導入
運用
READMEには「インストールせずに参照できる」前置きがあり、学習・設計の参考から始められる流れが想定されています。
段階1
参照（運用の型を読む）
段階2
必要になってからインストール
Risks
12 / 16
盲信は禁物
注意点
今回の入力では「品質保証の手順・合否基準」が具体化されていないため、導入時は追加のチェックを検討する必要があります。
検証が不明
自動テストや達成基準の詳細は未確認
fat contextの管理
参照が増えると注意が分散し、意図と結果がズレる可能性
セキュリティ
外部通信・依存・DOM操作などの観点は別途必要
再現性
モデル差によるブレへの対策は運用で設計する
Closing
13 / 16
要点まとめ
結論
Effective HTMLは、成果物中心の分業設計で「構造・挙動・計画・図」をレビュー可能にし、fat contextと組み合わせてHTML生成のズレを減らす方向性です。
効く理由
曖昧さを、HTMLの構造（wire）/実動（prototype）で吸収
実務の条件
品質保証の手順・チェック基準・セキュリティを運用で補う
References（参照の考え方）: リポジトリREADMEの要点（fat context / fat artifacts、各スキルの目的、レスポンシブ・アクセシビリティ・自己完結・ブラウザ検証）を根拠に要約。
