Context Design
02 / 16
6か月の再設計が示した核
コンテキスト設計
分析エージェント（LLM等）が正しいSQLや集計結果を出すために必要なのは「情報量」ではなく、編集場所と探索経路と監査可能性を含む“配置と保守”です。

JP / EN

コンテキスト（Context）＝意味・粒度・結合ルール・監査まで含む設計

Key rule

一つの事実（fact）に対して“authoritative home”（唯一の権威ある編集場所）を置く

Problem
03 / 16
なぜ「精度」だけでは足りない
推測が崩す
初期はエンティティグラフや“根拠なしは拒否”の層を作ったが、失敗の根はコンテキスト不足ではなく、各事実の“置き場所”と更新保守でした。

失敗の型

定義・意味・粒度・変換ルールの参照先が曖昧 → 古いコピーや誤参照 → 推論が崩壊

到達点

最終的に残った中核方針は「不確かな回答を推測で作らない」

Core Idea
04 / 16
一元化が保守性を作る
Author once
最重要ルールは「一つの事実には一つの権威ある編集場所（authoritative home）」を割り当てることです。

許容する重複

同じ事実が生成ビューや参照先から複数に見えてもよい

許容しないこと

編集（author）を複数に分散しない（同期ズレ＝driftを防ぐ）

同期ズレ（drift）：複数箇所で定義が更新されず、意味が徐々に食い違う状態
Navigation
05 / 16
辿り方が“根拠”になる
ナビゲーションツリー
採用したのは、ルートから下へ辿れるナビゲーションツリー（内部的にはリンク可能な有向グラフ）です。エージェントはルート領域から開始し、必要に応じてリンク追跡します。

開始

ルート（入口）を読む

探索

関連ノードへリンク追跡

回答

探索経路が指標の根拠フレーミングになる

Effects
06 / 16
混入を抑える設計
探索は 限定 する
ナビゲーションツリーの狙いは、(1)誤った領域の混入を防ぐ、(2)探索経路を説明・検証可能にする、(3)コンテキストバージョンの追跡を可能にする、の3点です。

①混入防止

無関係情報がウィンドウに入る確率を下げる

②説明可能

「なぜその指標か」が経路として示せる

③監査可能

回答に使われた定義セットを追跡できる

RAG vs Graph
07 / 16
検索型より“経路”を固定
RAGは増えるほど揺れる
RAGのように検索結果を大量提示して選ばせるより、決定的なグラフ探索に限定することでコンテキストトークン使用量が大きく減る、という社内テスト結果が示されています。

検索型のリスク

関連性の低い情報も一緒に見て、推論がぶれる

探索型の利点

「どの経路で定義へ辿り着いたか」が説明しやすい

※記事の主張：監査・再現性において、経路固定は検索型より有利
Audit
08 / 16
再現性＝参照ログ
context version
監査可能性は「context version」「参照ノード」「SQL」「実行時間」を、回答の再現性として扱うことで担保します。

必要な記録

どのコンテキストを読んだか／どのノードを参照したか／生成したSQLは何か

得られること

検証・修正が可能になり、「なぜその結果になったか」を追跡できる

Update Safety
09 / 16
更新経路を“見える化”
保守は 経路 と 同期
更新経路の可視化と履歴（バージョン）保持が重要です。平文ルールだけでなく作動例（worked example）が信頼性を高めますが、手作業の冗長化は避けるべきだと整理されています。

冗長化はOK/NG

例：表示のための重複は許容。手作業コピーの“同期ズレ”が危険

実務の解

「作者（author）と生成（generation）を分けて同期」させる

Ruleset
10 / 16
安全に拒否する設計
曖昧は選ばせる
曖昧な質問（例：「active」の定義が複数）には推測しない方針です。社内データでは定義の違いで結果が約4倍ずれることがあったため、根拠付けできない場合は拒否し選択を促します。

拒否条件

根拠（定義・粒度・結合等）に辿り着けない場合

ユーザーへの要求

定義のどれを使うか（どの“意味”を採用するか）を選ばせる

FAQ
11 / 16
用語のズレを潰す
Context ≠ Metadata
この文脈でのコンテキストは、テーブル一覧やカラム名に留まりません。指標定義（active customersの意味）、粒度、結合ルール・カーディナリティ、変換（countryがFRで保存）まで含みます。

定義

active＝何を満たすか

粒度

いつ・誰単位か

変換/Join

countryの保存形式・結合の前提

追加：アクセス制御（権限/行レベルポリシー）は別途必須で、コンテキストだけでは解決しません
Opinion
12 / 16
技術より“運用”の勝ち筋
編集権が根にある
強みは、LLM活用を「情報を与える」から「編集権・参照経路・監査可能性」に落としている点です。author onceはデータ定義が組織に根付くかを左右する“ガバナンス”になっています。

懸念点

再現条件（データ規模/質問分布/モデル構成）が十分に見えにくく、効果の一般化は慎重さが必要

導入で要るもの

承認フロー・責任者・変更管理など組織設計も同時に必要（技術だけでは完結しない）

Closing
13 / 16
持続する設計へ
結論：配置が正しさを守る
コンテキスト設計の要点は、(i)authoritative homeの一元化、(ii)ルートからのナビゲーション探索、(iii)参照ログとバージョンで再現性を担保、(iv)曖昧定義は推測せず拒否/選択させることです。

Checklist

唯一の編集場所 / 辿る経路 / 監査できる記録 / 更新時の同期

Limits

アクセス制御は別途設計が必要。コンテキストは“意味の正しさ”に主に責任を持つ

Bilingual term: authoritative home（唯一の権威ある編集場所）/ drift（同期ズレ）/ context version（コンテキストのバージョン）
