COVER
02 / 17
読める“文脈”を再利用
Graft

コーディングエージェントが毎回ゼロからリポジトリ理解を作り直さないよう、コードベース専用の文脈グラフを生成して再利用します。

Core idea（要点）
Context graph を 再利用可能なファイルにする
context（文脈）/ graph（グラフ）
Outcome（狙い）
探索コスト（$・トークン・ツール）と待ち時間を削減
cost reduction / latency（遅延）
PROBLEM
03 / 17
毎回の“再探索”が重い
Restart

従来のエージェントはタスクごとに検索（grep）やファイル参照を繰り返し、ツール呼び出し・トークン消費・待ち時間が増えやすい課題があります。

Symptom
grep / file walk の反復
探索（search）
Cost
ツール呼び出し・トークンが増える
tokens / $
Delay
レイテンシ（遅延）が伸びる
latency
METAPHOR
04 / 17
地図と配線
Map

Graftは、リポジトリの理解を“リンクされた地図（文脈グラフ）”として作り、必要な場所だけを開けるようにします。

地図（context graph）
markdown ノードのリンクで理解を保持
再利用（reuse）/ node-link
配線（wiring）
エージェントのプロンプトへ“注入する範囲”を決める
configuration（設定）
ARCHITECTURE
05 / 17
何を作るか
Artifacts

Graftは、リポジトリから「context graph（理解）」と「wiring（配線成果物）」を生成し、エージェントが必要部分だけ読む設計です。

context graph
リンクされた markdown ノード群（plain-English / crux 付き）
embeddingsではなく“読めるリンク”
wiring
git差分で扱える成果物（例：.claude/ 等の設定）
レビュー可能（reviewable）
DISTINCTION
06 / 17
類似検索ではない
No-RAG-Index

context graph は embeddings / vector DB の“類似度インデックス”ではなく、エージェントのコード読解動線に近い形のファイル群として作られます。

Graft（基本）
markdown ノードを開き、grep /追跡でコードへ辿る
動線ベース（navigation-first）
対比
ベクトルDBの類似度検索（index-first）ではない
exploration（探索）の転換
PROCESS
07 / 17
決定論 + 要約
Two-Layers

構造部分は tree-sitter 等の決定論的解析で作り、LLMが書く要約ノード（crux 等）と分離して更新コストを抑えます。

Deterministic（決定論）
構文・関係エッジをパースで生成（LLM不要の更新領域）
tree-sitter / parsing
LLM（要約層）
必要部分だけに plain-English / crux を付与（--deep 等）
summary（要約）
ARCHITECTURE
08 / 17
自動同期の方向性
Auto-sync

照会時にグラフを最新化し、ターン末にコードに触れた分だけ再ビルドすることで、未コミット変更も含む“いまの状態”に追随することを目指します。

When（開始）
タスク開始時に参照する文脈を準備
context ready
During（実行中）
必要な範囲だけ注入して探索を削減
less tool calls
After（更新）
変更差分に応じてオンデマンド更新
incremental rebuild
EVIDENCE
09 / 17
削減の主張
Efficiency

Controlled benchmark（Efficiency: 162-run）では、ツール呼び出し約46%、トークン約42%、時間約60%削減が主張されています。

Tool calls
約46%削減
探索往復の減少
Tokens
約42%削減
注入の適正化
Time
約60%削減
レイテンシ短縮
EVIDENCE
10 / 17
正確性も改善
Correctness

Efficiencyだけでなく正確性も改善（66% vs 54%）とされ、SWE-bench Verified（50 instances）でも54%→66%と主張されています。

Controlled
正確性 66%（Graft） vs 54%（ベースライン）
再探索削減の副次効果
SWE-bench Verified
54% → 66%（50 instances）
実課題での伸び
Why（解釈）
典型的な誤り（単一ファイルだけ修正し兄弟ファイルを見落とす）を、Graftが不足分の発見に寄せやすい
context coverage（文脈の覆い）

DISTINCTION
12 / 17
導入時の見落とし
Skeptic

READMEベースの数値は説得力がありますが、モデル選択・タスク特性・失敗パターンで再現性が変わるため、社内PoCが重要です。

Risk（条件依存）
リポジトリ構造、テスト複雑性、依存関係の多さで効果が変わる
条件探索（assumption）
Risk（送信範囲）
LLM層が送る情報（要約・crux生成）がどこまでかは設定/ログで確認が必要
privacy（機密）
Recommendation
(1)言語スタック適合、(2)LLM送信情報の把握、(3)同期頻度/挙動、(4)失敗条件の検証 を小さく試す
PoC（試験導入）
