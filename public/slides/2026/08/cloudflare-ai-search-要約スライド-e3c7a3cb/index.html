ワンストップ検索基盤

AI Search

Cloudflareは、AIエージェントが自社データを参照するための「検索基盤」を、複数機能の寄せ集めなしで素早く作れるようにしました。 仕組み・利用導線・料金プレビューまでを一気に整理します。
前提の用語：インデックス / 埋め込み（embedding） / 再ランク付け（reranking） / ハイブリッド検索 / MCP
問題
03 / 16
検索がボトルネック

導入が重い

従来は Workers AI、AI Gateway、Vectorize、R2、Browser Run などを組み合わせて「自社データ検索」を作る必要がありました。 その結果、エージェント開発で“検索基盤”の実装・運用に時間が奪われがちでした。
従来
複数サービス連携が前提
課題
実装工数・運用リスクが増える
結論
04 / 16
自動で組み立てる

統合して提供

AI Searchは、検索に必要な処理をまとめて提供し、開発者は「どのデータを・どう検索させるか」に集中できます。 目的は、エージェントが関連情報を見つけてより良い回答を生成できる状態を作ることです。
役割
検索エンジン（インデックス化＋検索＋再ランク）
価値
立ち上げを速く・設計の細部を減らす
何が変わる
05 / 16
5つの改善

設計が軽くなる

記事で示された改善ポイントを、導入観点で整理します。
i
データセットをインデックス化しやすい
ii
サイト統合：サイトマップなしでも Discover で取り込み
iii
namespace横断：/search と /mcp を単一公開で提供
iv
公開エンドポイントに自社ドメイン、Cloudflare Accessで非公開化
v
EmDash：プラグインで意味検索を追加
備考
埋め込み・再ランクは選択したWorkers AIモデルで無料枠
仕組み
06 / 16
ingestion → query

2段で動く

インデックス化（ingestion）はデータ取り込み・埋め込み作成・保存を行い、検索（query）は候補抽出→意味検索→再ランク付けで順位を整えます。
インデックス化
取り込み / 埋め込み（embedding） / 検索用整備
検索
候補抽出 / ハイブリッド検索（意味＋キーワード） / reranking
回答には、検索で得た関連断片（チャンク）と引用を組み合わせる前提です。
サイト統合
07 / 16
sitemap不要へ

Discover取り込み

記事では、従来“事実上必須”だったサイトマップに代わり、リンク探索の Discover 解析で取り込み可能になったとされています。 既存サイトが完全に整っていない場合でも導入ハードルが下がる狙いです。
従来の壁
sitemap依存で取り込み失敗・手作業が増える
新アプローチ
リンクを辿る Discover 解析で取り込み
横断検索
08 / 16
/search と /mcp

単一エンドポイント

namespaceを公開URL化すると、複数サイト・複数インスタンスを横断して /search と /mcp で利用できます。 Workerを使えば、既存アプリやMCPサーバへ組み込みやすくなります。
横断
複数インスタンスを /search 一発で検索
接続
/mcp でエージェント連携をしやすく
公開範囲
09 / 16
データ保護

認証・robots

記事では、namespace公開URLはデフォルトで認証なしの /search と /mcp とされていますが、カスタムドメイン配下で Cloudflare Access による非公開化が可能と書かれています。 また robots.txt 等のルールを守る設計だと説明されています。
公開
認証なしの導線（デフォルト）
非公開
Cloudflare Accessで保護
順守
Cloudflare-AI-Searchで robots.txt 対応
料金
10 / 16
コストを見通す

無料枠の考え方

料金プレビューでは、埋め込みと再ランク付けが特定のデフォルト／選択モデルで無料になるなど、予測可能性を高める設計意図が示されています。 ただし最終コストは生成やクエリ内訳などで変動し得ます。
対象
埋め込み（embedding）／reranking
狙い
トークン予測の負担を下げる
記事は“無料条件の前提”を読み取った上で、運用時の試算が必要という含みがあります。
実例
11 / 16
Dev Stack MCP

横断回答

Cloudflare自身の「Cloudflare Dev Stack MCP」を AI Search で動かす例として、複数ドメインごとにAI Searchインスタンスを作り、1つのクエリで横断検索と引用付き回答を実現する流れが紹介されます。
構成
ドキュメント／ブログ／コミュニティ等で個別インスタンス
動作
Workerまたは公開エンドポイントで横断検索
運用面では Browser Run の crawl ベースで、robots.txt 等に従うよう設計される点が強調されています。
見方
12 / 16
良い点／注意点

導入向け

記事の強みは、統合サービスとして“検索基盤”への張り付き時間を減らす設計が明確なことです。 一方、品質指標（誤引用・鮮度・権威性の評価）や、実運用の失敗パターンは十分に示されておらず、依存前の検証が安全です。
強み
導入導線（Discover／/mcp）と横断設計が実務に寄り添う
注意
品質保証・コスト確定の根拠（定量）が不足
結論
13 / 16
次にやること

小さく試す

AI Searchは、エージェントが参照すべき自社データの検索を、実装工数と運用リスクを抑えて開始するための統合基盤です。 ただし品質・コスト・権限（公開範囲）を“使う前提”で確認し、重要業務では検証計画を立てるのが安全です。
手順
Discover取り込み→検索→引用の妥当性確認
安全
Access／公開範囲／robots順守の設計を確定
経済
埋め込み・reranking条件＋クエリ内訳で再試算
用語ミニ：ハイブリッド検索＝キーワード＋意味、MCP＝エージェント連携の枠組み。
