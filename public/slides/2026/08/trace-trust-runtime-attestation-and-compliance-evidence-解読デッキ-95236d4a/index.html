TRACE
02 / 17
検証可能な証拠レコード
Trust Record
TRACE（Trust, Runtime Attestation, and Compliance Evidence）は、AIエージェントの「方針・実行環境・データ分類・ツール呼び出し」を、第三者が検証できる形で残す証拠形式です。
狙い
運用者を信用せず検証
核
署名付き Trust Record
補強
ハードウェアによる実行証明（attestation）と、透明性ログへのアンカー（例：SCITTのreceipt URI）で、改ざん耐性と追跡性を上げる。
PROBLEM
03 / 17
ログは証拠にならない
Audit Gap
監査や説明責任では「何が起きたか」を知りたいが、単なるログ保存だと後から都合よく作り替えられ得ます。
よくある弱点
改ざん耐性が弱い
よくある弱点
運用者依存
よくある弱点
検証手順が不統一
TRACEの答え
証拠の作り方と検証の根拠をレコード仕様として固定し、第三者が自己完結的にチェックできるようにする。
METAPHOR
04 / 17
「何を」ではなく「証明」
Claim → Evidence
TRACEは、監査で問われる事実を「TRACE claim（主張）」に分解し、レコード内の署名・ハッシュ・測定値で裏付けます。
例：モデル
model_id + model.weights_digest
例：実行環境
runtime.platform + runtime.measurement
例：policy
policy.bundle_hash + policy.enforcement_mode
例：透明性ログ
transparency（SCITT receipt URI）
ARCHITECTURE
05 / 17
署名付きTrust Record
One Artifact
TRACEの中心は、AIエージェントの実行内容を「単一の署名付きTrust Record」にまとめることです。
Trust
第三者が検証可能な形で内容を固定
Runtime attestation
測定値（measurement）で実行環境を裏付け
Compliance evidence
policy/データ分類/ツール呼び出しを証拠化
設計思想
「ログ保管」ではなく「検証の根拠をレコードに含める」ことが目的。
ENUMERATION
06 / 17
何を記録する？
TRACE claims
TRACEは、監査観点をclaimへ明確に対応付けし、検証可能な粒度に落とし込みます。
i. モデル
model_id + weights_digest
ii. 実行場所/環境
platform + runtime.measurement
iii. 方針（policy）
bundle_hash + enforcement_mode
iv. データ分類
アクセス範囲をラベル化/証拠化
v. ツール呼び出し
呼び出し要約（transcript）を証拠化
vi. 透明性アンカー
SCITT receipt URI の有無/参照
EVIDENCE
07 / 17
検証の材料
How it’s proven
TRACE claimを検証可能にするため、署名・ハッシュ・測定値・透明性ログアンカーをレコードに含めます。
署名（signature）
Trust Recordの真正性と一意性を担保
ハッシュ（digest/hash）
policy/modelなどの同一性を比較可能にする
実行測定（measurement）
runtime.measurementで実行環境を裏付け
透明性ログ（SCITT）
receipt URIで独立アンカーリング
効果
運用者が都合よく「後追いの主張」を作るコストを上げ、第三者検証を容易にする。
COMPARISON
08 / 17
ただのログとの違い
Log vs TRACE
TRACEは「保存された情報」ではなく、「検証可能な証拠として設計された形式」です。
一般的なログ
改ざん耐性は弱いことが多く、検証手順が統一されない。
結果として運用者依存になりがち。
TRACE
署名付きTrust Record＋runtime attestation＋SCITTアンカーで、第三者が自己完結的に検証できる方向を作る。
ポイント
claim ↔ 証明項目の対応が固定されるため、「何がどこまで証明されるか」が明確。
EVIDENCE
09 / 17
透明性ログの効能
SCITT receipt
TRACEは透明性ログ（SCITT）のreceipt URIを独立アンカーとして扱い、改ざんや後追いの主張を抑止します。
何を参照する
receipt URI
狙い
「その時点の証拠」へ結びつける
嬉しさ
第三者が追跡しやすくなる
注意
アンカーが有効でも、測定値や署名の前提（attestationの成立条件、鍵運用など）が合わないと効果が弱まる。

標準との整合
Built on standards
TRACEはEAT/RATS/SCITTなど既存概念に整合することで、相互運用や理解可能性の見通しを立てています。
EAT
RFC 9711
RATS
RFC 9334
位置づけ

DISTINCTION
12 / 17
採用前の“穴”を見抜く
Limitations first
TRACEは方向性が良い一方で、測定値の粒度、ツール呼び出しの網羅性、データ分類の運用などの前提が仕様だけでは見えにくい点に注意が必要です。
技術
runtime.measurementの保証範囲が実装依存
技術
ツール呼び出し transcript の網羅性
運用
data_class（データ分類）の決定・維持
成熟度
v0.2 / trace-registry未公開 / 本番利用はLIMITATIONS.md確認
提案
自組織の脅威モデルに対して、attestationとアンカーリングのチェーンが成立するか追加検証する。
CLOSING
13 / 17
結論：証拠を流通させる
Verifiable Governance
TRACEは、AIエージェント統治（policy/データ分類/ツール）の“証拠としての流通”を標準化し、運用者を信用しない検証に近づけます。
良い点
claimへの分解が監査に落ちやすい／EAT・RATS・SCITT等の標準整合
確認すべき点
測定値の保証／鍵・アンカー運用／データ分類の責任分界／LIMITATIONSの適用
次の一手（問い）
あなたの利用目的（監査・社内ガバナンス・顧客提示など）と、重視するclaimはどれですか？それに合わせて追加で測定・鍵・アンカーの確認項目を整理できます。
