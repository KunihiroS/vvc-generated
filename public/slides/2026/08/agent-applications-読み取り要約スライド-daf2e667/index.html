Problem

「チャット＝Agent」
チャットUIがあるだけではAgent Applicationにならない、と文書は線引きします。重要なのは“次のイベントが同じ実体へ戻るか”です。
誤解しやすい
会話 UI の存在 ≠ カテゴリ条件
本質
同一インスタンスへ“継続で戻る”
Metaphor
04 / 14
チャットは“単発”
インスタンスは“作業部屋”
Agent Applicationは、作業の土台（ファイル・指示・記憶・コード等）と、仕事の進行（成果物・外部記録・プロセス）を同じ部屋に残します。
Chat / 単発
応答が終わると状態が途切れがち
Agent Application
同じ“部屋”に戻り、継続が残る
Architecture
05 / 14
4性質で分類
カテゴリの核
Agent Applicationは、次の4性質（継続作業・制御・ワークスペース・仕事）が揃う“アプリケーション形”として切り出されます。
i. 持続的実体
Long-lived instance（持続的なインスタンス）
ii. エージェント制御
Agent-led control flow（エージェント主導の制御）
iii. 耐久WS
Durable compute workspace（耐久的ワークスペース）
iv. 耐久的仕事
Durable work（外部記録まで残る）
Evidence
06 / 14
同じインスタンスへ戻る
継続性が判定軸
後続のメッセージやイベントに応答するたび、同一のエージェントインスタンス（同一のプライバシー領域・継続作業）へ戻ることが要点です。
戻る相手
同一エージェント
境界
同一プライバシー領域
仕事の継続
進行中プロセスが残る
Distinction
07 / 14
自動化と違う
状態を推論して分岐
単に既定手順を機械的になぞる完全ワークフローではなく、エージェントが現在の状態を推論して次の行動を選びます。
完全な手順
入力が違っても同じ流れ
Agent Application
状況で分岐（state→decision）
Enumeration
08 / 14
“保持”の範囲が重要
WSと仕事の違い
耐久的な計算ワークスペースは土台（ファイル・指示・記憶・コード等）の保持、耐久的な仕事は結果・影響（成果物・外部記録・継続プロセス）の保持です。
Durable WS
次回に使える“作業の土台”
Durable Work
次回にも残る“仕事の結果”
Architecture
09 / 14
提供側の層
Framework / Platform / Store
実現には複数の部品が必要で、文書はエージェント・アプリケーションの“開発〜実行”を支えるフレームワーク、運用を強制するプラットフォーム、カタログと決済のストアを分けます。
Framework
開発・評価・実行ランタイム
Platform
アイデンティティ/権限/承認/支出制限/ネットワーク宛先
Store
カタログ＋決済（流通）
Process
10 / 14
運用は“ローカル状態”も監査
インスタンス分岐
長寿命インスタンスは蓄積事実や成果物で変化し、プログラム（自然言語指示の追加・編集）まで分岐し得ます。そのためロールアウトや監査、ポリシー適用をインスタンスのローカル状態込みで行う必要があります。
変化の源
事実・成果物・指示編集
運用の帰結
インスタンス別の監査/適用が必要
