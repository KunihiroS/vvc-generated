COVER
02 / 16
確率AIを“決定論”で囲う
locus-engine v1.5.0
AST（構文木）を中心に、検証・自己修復・取引コミットを組み合わせ、AIコード生成の安全性崩れと競合を抑える設計です。
（安全性の崩れ＝誤生成／並行編集／誤反映の連鎖）
PROBLEM
03 / 16
なぜ壊れる？
生成は“確率”
AIコード生成は確率的で、誤生成・同時編集・見落としが起き得ます。さらに複数エージェントが同じ場所を触ると、整合性がサイレントに崩れやすくなります。
AIの事故

React Hooksの規則違反、unsafe unwrap、nullチェーンなど

運用の事故

複数同時編集の衝突、複数ファイルの誤反映、ディスク/ワークスペースのドリフト

METAPHOR
04 / 16
“編集”ではなく“契約”
Symbol Lease
locus-engineは、単なるファイルロックではなく「シンボル（FQN）単位の排他契約」を作ります。契約が切れるまで、そのシンボルを触る権利を限定します。
鍵（ロック対象）

Fully Qualified Symbol Name（FQN）

制約（期間）

TTL付き排他ロック（lease）
acquire_symbol_lease 等

ARCHITECTURE
05 / 16
安全の三段構え
検証 → 修復 → 確定
AIが出した変更は、ASTの決定論的インバリアントで即座に検証されます。違反が見つかれば決定論的自己修復し、最後に取引として原子的に確定します。
Ⅰ 検証

20パスのAST安全不変条件（check_safety）

Ⅱ 自己修復

未閉タグ、nullチェーン、Hooks違反など（auto_remediate）

Ⅲ 確定

ACIDライクなワークスペース取引（begin_tx/stage_tx/commit_tx）

ENUMERATION
06 / 16
20パス安全検証
ASTインバリアント
“リンタを回す”に留まらず、AST根拠で危険パターンを検出し、反例（カウンターエグザンプル）を返す志向があります。
狙う事故

SQLインジェクション、危険な unwrap、危険な動的実行、Hooks規則違反

手触り

決定論的・高速（目標：低遅延）
※ただしベンチ条件はSPEC/テスト確認が必要

PROCESS
07 / 16
壊れ方に強く直す
Auto Remediate
典型的な不整合（未閉タグ・null伝播・Hooksの配置ミス等）を検知すると、決定論的に“修復パッチ”へ寄せます。
修復例

未閉タグ（構文を成立させる） / nullチェーン / Hooks持ち上げ

安全側の発想

修復“後”も検証を通す前提（verified_patch/取引コミット）

ARCHITECTURE
08 / 16
変更を“段階”で扱う
ACID的ワークスペース
複数ファイルにまたがる変更は、影（シャドー）で段階検証し、最後に原子的にコミットします。これで壊れた中間状態やドリフトを防ぎます。
段階

begin_tx → stage_tx → commit_tx

狙い

ディスク破損・半端な書き込み・検証漏れの連鎖を抑える

EVIDENCE
09 / 16
“検証対象”を絞る
Taint × コンテキスト
クロスファイルの taint（未検証入力）やnullの伝播を追跡し、さらに骨格化・スライスで影響範囲を制御してトークン節約を狙います。
Taint解析

未検証入力の追跡（cross-file污染の抑制）

骨格化

skeletonize：全投げを避ける

影響範囲

blast-radius：不要な修正を減らす

DISTINCTION
10 / 16
“単機能”と何が違う？
統合パイプライン
locus-engineは、ロック・検証・修復・取引・解析・検索を“境界条件込み”で連結し、事故の連鎖を工程ごとに断ちます。
よくある対策

ビルド/テストだけ、またはリンタだけ

locus-engine

AST検証（反例志向）＋自己修復＋ACID的確定＋シンボル排他

COMPARISON
11 / 16
注意点も明確
“安全”の範囲
README抜粋だけでは、ルール網羅性・攻撃耐性（回避手段）・意味論の正しさまで確定できません。SPEC.mdやtestsの確認が必須です。
検証の網羅性

20パスが“全て”を保証するとは限らない（SPEC/テストで確認）

自己修復の副作用

誤修復で意味が変わる可能性はゼロではない（verified_patch/契約検証の程度確認）

CLOSING
13 / 16
結論
事故確率を下げる
locus-engineの強みは、AIが壊しやすい工程（マルチエージェント編集、コンテキスト肥大、未検証生成物の書き込み）に対して、安全・整合メカニズムを具体的に用意している点です。
導入時は必ず、SPEC.md・tests/・既知の回避ケースを確認し、あなたの組織の規約/脅威モデルに合わせて運用ルール（lease更新・修復の保守性・契約検証の強度）を調整してください。
