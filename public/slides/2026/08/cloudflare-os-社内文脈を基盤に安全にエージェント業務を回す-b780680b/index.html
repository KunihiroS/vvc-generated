社内文脈 × 安全な実行基盤

Cloudflare OS

チャット止まりではなく、社内の用語・手順・スキルを土台に、エージェントがドキュメントやアプリ、ワークフローを“仕事として”進めるオープンプラットフォームです。

キーワード：エージェント・ワークスペース、MCP、Gatekeeper、観測ログ、AI Gateway

PROBLEM
03 / 14

実運用の壁

“動く”だけでは足りない

従来のエージェント活用は、コードは動いても「文章・分析・社内連携をどうスケールさせるか」が難所でした。

Scale gap / スケールの断絶
エンジニア中心になりがちで、組織全体へ再現性ある形で展開しにくい。
Leak path / 漏えい経路
入力制限（参照制御）だけでは、出力共有や副作用で機密が広がり得る。
METAPHOR
04 / 14

安全な“作業場”

ガード付き ワークベンチ

Cloudflare OSは、エージェントを“勝手に触れる工具”ではなく、権限と監査で区切られたワークスペース上で働かせます。

Workspace / 作業場
社内文脈（用語・手順・ベストプラクティス）を参照して仕事を進める。
Request / 依頼
必要なリソースを要求→許可/拒否で段階付与。
Audit / 監査
観測ログにより“何を見たか”を後続の共有・出力で検証。
ARCHITECTURE
05 / 14

中核コンセプト

エージェント ＋ ワークスペース

エージェントは、会話ではなく成果物（ドキュメント、アプリ、ワークフロー）へ“変換され続ける仕事の単位”として動きます。

Agent / エージェント
社内文脈とスキルを参照し、調査・作成・実行を行う。
Workspace / ワークスペース
用語・手順・ベストプラクティスを保持し、品質と再現性を上げる（文脈ライブラリ）。
ENUMERATION
06 / 14

安全設計の順番

ゼロアクセスから 能力付与

エージェントは最初からアクセス権を持たず、必要に応じて能力（capability）として限定的に付与されます。

i. Start safe / 初期状態
“最初からゼロアクセス”で攻撃面と誤操作を抑える。
ii. Type binding / 型付きバインド
触れられるのは許可された特定リソースだけ（能力ベース）。
iii. Network boundary / ネット制限
外部ネットワーク到達を遮断し、明示的な能力がない限り外へ出ない。
iv. Gate mediated / 仲介認可
副作用や共有の経路をGatekeeperが媒介する。
EVIDENCE
07 / 14

MCPの安心範囲

MCPで“呼べる道具”を整える

MCP（Model Context Protocol）は、エージェントが利用できるツールを定義する助けになります。

MCP / ツール境界
「エージェントが呼べるツール」を揃えて、統合をしやすくする。
But / しかし残る穴
ツール制限だけでは「観測した具体的リソース」を制御できない、という課題が残る。

そのギャップを埋めるのが Gatekeeper と観測ログの設計です。

DISTINCTION
08 / 14

Gatekeeperの役割

Gatekeeper＝認可＋監査＋出力制御

Gatekeeperは、外部サービスごとに認可・監査・フィールド制御・承認フロー・レート制御を担います。

AuthZ / 認可
誰が何を操作できるかをルールで判定。
Audit / 監査
行ったことを追跡可能にする（後で検証できる状態に）。
Output guard / 出力防壁
生成物の共有や外部書き出しを、後段でチェック。
EVIDENCE
09 / 14

観測ログが鍵

“見たもの”を記録して守る

観測ログ（観測したリソースの記録）を保持し、その記録に紐づいて後続の共有可否を判断します。

観測ログ / Observation log
例：参照したDBのテーブル、どの行/列相当か、などの“具体”を記録。
漏えいを止める / Leak prevention
閲覧者に権限があっても、生成物が別ユーザーに共有される経路を抑制する。
PROCESS
10 / 14

仕事の流れ

要求→許可→成果物化

エージェントは必要なリソースを要求し、Gatekeeperの認可と検証を通って、仕事として成果物を生成します。

i. 作業着手
ワークスペースの文脈を参照してタスク開始。
ii. リソース要求
必要なデータ/ツールを要求（能力として付与）。
iii. 生成と共有
観測ログに基づき、共有・出力をGatekeeperが判定。
ARCHITECTURE
11 / 14

アプリとコストを統合

Workerで個別アプリを回す

ドキュメントだけでなく、クライアントUI＋状態＋APIを持つフルスタックアプリとして生成・共有できます。

App / アプリ
個別に改造可能な“業務用ランタイム”を作り、継続運用へ。
AI Gateway / 推論統制
モデル選択と推論コストを一元制御（タスク難度で使い分け）。

結果：予算・性能・ガードレールをまとめて設計しやすい。

COMPARISON
12 / 14

鍵の渡し方が違う

APIキー直渡しより 管理可能

APIキーをエージェントへ直渡しすると制約・監査・安全な共有が難しくなりがちです。

キー直渡し / Risk
長寿命化しやすく、広範な権限になりがちで監査が重くなる。
Gatekeeper介在 / Control
鍵を持たせず、認可を介して限定操作＋副作用/外部公開の制御を実現。
CLOSING
13 / 14

導入判断の要点

評価すべき点／確認すべき点

Cloudflare OSは「安全を前提にしたエージェント基盤」という一貫性が強みですが、保証の強度と運用負荷は追加確認が必要です。

Strong / 強い
ゼロアクセス、能力ベース、外部ネット遮断、Gatekeeper、観測ログで“共有経路”まで抑える。
Verify / 確認したい
観測ログ粒度、ポリシー判定（ABAC/RBAC等の近さ）、監査の運用負荷、統合手順、脅威モデルの網羅度。

開発体験や粒度まで知りたい場合は、観測ログの“行/列レベル”やポリシー言語、監査ログの保管/検索方法を確認すると意思決定が速くなります。
