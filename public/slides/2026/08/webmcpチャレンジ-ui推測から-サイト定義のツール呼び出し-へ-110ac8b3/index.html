新しい“Web行動契約”

WebMCP チャレンジ

UIを見て推測する代わりに、サイトが用意した「呼び出し可能なツール」をエージェントが実行する――その方向性を確かめる試験的イベントです。

PROBLEM / 課題
03 / 16
UI依存の限界

クリック推測

従来多くの自動化は、画面の見た目（UI）からクリック位置や手順を当てにいくため、失敗・不整合・再現性不足が起きやすくなります。

問題

見た目に依存

同じ意図でもUI変更で手順が崩れる。

影響

失敗しやすい

EC・予約・開発者向け機能で特に厳しい。

METAPHOR / 比喩
04 / 16
“合図”で動く

ツール呼び出し

WebMCPは、画面を読ませるのではなく「実行してよい操作」を名前付きの関数として渡し、エージェントがそれを呼び出して進めます（関数＝道案内）。

従来（推測）

見た目を読み取り

ボタン位置・順序を推定。

WebMCP（指示）

サイトが定義

例：ツール名＋入力で実行。

ARCHITECTURE / 構造
05 / 16
ブラウザ内で共有

JS文脈実行

ツール実行はバックエンド接続ではなく、同一のブラウザセッションで行う設計です。導入の摩擦を下げる一方、権限・安全性の設計が重要になります。

どこで実行

既存ブラウザ文脈

ユーザーセッションを共有して操作。

前提

セキュリティ設計

誤操作・不正利用・復旧を考慮。

ENUMERATION / 要点1
06 / 16
UI→契約へ

移行の狙い

主眼は、エージェントが「ページを見て手順を推測する」必要を減らし、サイトが公開する操作に基づいてタスクを完了することです。

i

推測の削減

クリック位置・順序を当てに行かない。

ii

再現性

同一ツール呼び出しで結果を揃える。

iii

実用性

EC/予約/機能連携に効く可能性。

DISTINCTION / 違い
07 / 16
MCPの“まだ一部”

限定仕様

現行は「呼び出し可能ツール」中心で、MCPのより広い要素（資源・プロンプト・サンプリング等）は含まれていません。期待が大きいほどギャップが出ます。

含む

ツール呼び出し

サイトが提示する関数を実行。

含まない

広範統合

資源・プロンプト等の一括連携は未成熟。

PROCESS / チャレンジ
08 / 16
10日間の試験

WebMCPチャレンジ

OpenAI主導の「10日間のWebMCPチャレンジ」は、エージェントがWeb上で実行できる行動を、サイト側が明確に公開する流れを普及させるための試験です。

目的（主張）

導入の加速

“サイト定義の操作”を増やす。

読み替え

市場シグナル

仕様完成の勝負より、実装意欲を測る色。

EVIDENCE / 根拠の置き方
09 / 16
“速い/正確”は要確認

定量材料不足

記事中の利点は主に「期待される効果」として提示されており、独立評価やベンチマークの結果は読み取れません。採用判断には追加の検証が必要です。

必要な指標

完了率・失敗率

従来（UI推測）との比較が鍵。

安全側の論点

復旧・制御

誤操作時にどう戻すか。

DISTINCTION / ブラウザ
10 / 16
互換性が揺れる

対応偏り

対応ブラウザが均一ではないため、短期コンテストの結果をそのまま“標準の覇権”とは見なせません。動く範囲の違いが採用を左右します。

見落とし注意

コンテスト＝覇権?

実利用の前提（互換性）が不足し得る。

代替の見方

採用意欲を見る

各社がどこまでプロダクト化するか。

ENUMERATION / エコシステム
11 / 16

参加企業

Chromium（Chrome系）、Cloudflare、Shopify、Vercel、Render、Netlifyなどが関与し、審査にも代表的な関係者が入っています。実装志向の強さが示唆されます。

基盤

Chromium / Cloudflare

ブラウザ・配信側の近さ。

EC

実運用の価値領域。

DISTINCTION / 私見
12 / 16
方向性は筋が良い

次の確認点

UI推測から“行動契約”へ切り替える設計は有望です。ただし、効果の検証データと、安全性・権限管理・復旧の詳細が不足しています。

強み

安定完了を狙える

ツール呼び出しで手順ブレを減らす。

弱み/未解決

ガバナンス不明

権限逸脱・誤操作復旧の設計度。

CLOSING / まとめ
13 / 16
結論：重要だが慎重に

追うべき観測点

WebMCPチャレンジは、Webインターフェースが「人のクリック」から「構造化された行動」に移る可能性を示します。採用判断には、セキュリティ設計・互換性・定量評価を今後の公開結果で確認すべきです。

見るべきもの

互換性と指標

失敗率/完了率、安全性要件。

判断の姿勢

標準確定ではない

実験段階として段階的に評価。
