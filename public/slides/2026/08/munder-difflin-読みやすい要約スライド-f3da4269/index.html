02 / 18

ローカルで動く“複数開発”ハーネス

Munder Difflin

既存のターミナル型AI開発CLI（Claude Code等）を、ローカルで複数同時に走らせる“実行基盤”です。作業配分と承認を上位オーケストレータが統括し、運用設計（安全・連携・可観測）まで含めて作られています。

目的：不在でも開発を継続し、必要な判断だけ人へ返す／英：turns CLI agents into a multi-agent work floor

03 / 18

“チャット増やすだけ”問題

運用が 破綻 する

マルチエージェントは、並列実行・ログ・連携・停止条件が弱いと暴走、無駄な課金、失敗の見落としが起きやすいです。Munder Difflinは、その失敗モードを前提に回路（ブレーカー）とゲート（承認）を設計しています。

Failure mode
暴走 / 無限ループ
Failure mode
破壊的操作 / 課金
Failure mode
連携不良（メールが起床しない）
Failure mode
環境差（Apple Siliconの不具合など）

オフィス運用の比喩

エージェントは 社員

各エージェントは“自分の作業フロア”で動き、結果は封筒（メッセージ）で受け渡されます。上位のGOD（Michael）が、割当・承認・必要時のエスカレーションを行います。

ルーティング＋承認判断
日本語補助：Mailbox＝受信箱／GOD＝調停者・割当者（Human gateとも接続）

可観測性とプライバシー方針

ログは“匿名寄り”

バックエンドはイベントログ、永続ストレージ（SQLite）、OTelによる可観測性などを取り込みます。テレメトリは匿名の利用イベントに限定し、コードやファイル、出力は送らない説明がある一方、初期導入時は設定確認が必要です。

“確実さ”は万能ではない

断定せず 検証前提

入力文には「メールが確実に届く」「暴走を確実に止める」といった成功率の定量評価は見当たりません。結果は、モデル/プロバイダ、予算設定、トリガ設定、環境差（OS/CPU/GPU）で変わり得るため段階導入が妥当です。

不明点
成功率・失敗率の指標
条件
環境差（OS/モデル/設定）
推奨
小さなタスクで検証→拡大
安全運用の前提：承認フロー、ログ確認、停止手段を理解してから強い自律へ。

導入の考え方（読み手向け）

“小さく試し、見える化する”

最初は破壊的操作や課金が必要になりやすい条件を避け、ログと承認キューの動作を確認しながら使うのが現実的です。v0.4.5の修正点（コスト/Apple Silicon/メール監視）に合わせ、あなたの環境で挙動を確かめてください。

Step 2
