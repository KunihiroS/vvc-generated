家計アシスタント オフラインRAG

Goal / 目的

Key idea / 核
grounding（根拠）を先に作って渡す
Tech / 技
Cache Storage + 小型LLM + JSON修復
Bilingual: offline RAG（オフラインRAG）= 外部検索せず、手元の集計根拠で回答精度を上げる。

03 / 16
何が難しい？
ローカル実行 の落とし穴
WebでローカルLLMを動かすと、モデル取得（2GB級）、ブラウザ制約（トークン/計算/ストレージ）、算術ミス、ストリーミング断片JSONが問題になります。
Model / モデル
初回DL失敗・更新管理・オフライン継続
Accuracy / 正確性
小型モデルは算術ハルシネーション（足し算誤り）
Tokens / 文脈
会話のトークン上限（3ターン運用など）
Streaming / 出力
途中のJSONが壊れてUI崩れしがち
これらを、アーキテクチャ（キャッシュ、grounding、会話管理、jsonrepair）で潰します。
metaphor
04 / 16
“計算はアプリ”
LLMは 語る、真値は 渡す
家計の“数値の正しさ”はアプリで先に集計し、LLMには月次/日次/カテゴリ内訳などの根拠（ground truth）を埋め込みます。
Before / 先にやる
合計・内訳をアプリ側で計算（grounding作成）
After / LLMにさせる
根拠を読み、文章化・要約・示唆を生成（推測を減らす）
Bilingual: grounding（根拠提示設計）/ ground truth（真値）。RAG（外部検索）は“同類の考え方”として扱い、検索はしません。
architecture
05 / 16
完全オフライン
モデル重みを Cache に
Gemma 4 E2Bの重み（約2GB）をブラウザのCache Storageに保存し、以後はネット無しで推論できるようにします。
Step i
初回：重みをDLしてCache Storageへ保存
Step ii
以後：ネット無しでもモデル読み込みが可能
Result / 結果
接続不安定でも“動く”体験（オフライン推論）
LiteRT（エンジン） + Gemma 4（モデル）をブラウザ内で組み合わせる前提。
architecture
06 / 16
grounding設計
真値の数表を プロンプトへ
LLMの算術誤りリスクを下げるため、月次合計・日次合計・カテゴリ別内訳などをアプリで集計し、プロンプトに埋め込みます。
埋め込む例
月次合計：2026-08 = 123,456
日次合計：2026-08-12 = 4,321
カテゴリ内訳：食費=56,789 / 交通=12,345
効く理由
小型モデルは計算で誤り得るため、足し算の責任をアプリ側に移す
Bilingual: arithmetic（算術）/ hallucination（ハルシネーション・誤生成）。
process
07 / 16
会話管理
3ターンでリセット 再プライミング
ブラウザLLMはトークン上限があるため、一定条件（3ターン）で会話をリセットします。 ただし直近のクエリを保持し、固定の家計根拠データと共に再投入して連続性を狙います。
Step i
3ターン到達でリセット
Step ii
直近クエリをクライアントメモリに保存
Step iii
根拠データ + 再プライミングで“途切れ感”を抑制
限界：保持できる範囲が狭いので、長文文脈は設計上の制約になります。
evidence
08 / 16
JSONストリーミング
途中断片は 壊れる前提
ストリーミング出力は断片ごとに届くため、途中のJSONが不完全になり得ます。 通常の`JSON.parse()`だと崩れやすいので、補正しながら解析します。
問題
逐次到着のJSONが“未完成”でパース不能
対策
jsonrepairで不完全断片を補正し、UI更新を継続
体験の要点：ユーザーの画面が止まらず、途中からでも表示が進む。
architecture

データの置き場所
取引データは IndexedDB/ローカル
家計データはブラウザのローカル保存（例：IndexedDB）に置き、外部送信せずオンデバイスで扱います。 目的は「プライバシー重視」と「オフライン価値提供」です。
保存先
IndexedDB（家計データ）
保存先
Cache Storage（モデル重み）
原則
外部送信を避け、ローカル処理で完結
Bilingual: on-device（端末内）/ data leak risk（情報漏えいリスク）。
distinction
10 / 16
RAGとgroundingの違い
検索RAGではなく 根拠埋め込み
通常のRAGは外部情報を検索してLLMへ渡しますが、ここでは「手元の取引から計算・集計した根拠を渡す」設計が中心です。 そのため“RAG”より“grounding設計”が本質になります。
通常RAG / 典型
外部検索 → LLMへ情報投入 → 生成
本設計 / 今回
ローカル集計 → 真値の根拠投入 → 生成（数値の誤り抑制）
結論：家計の“計算部分”をアプリが担い、LLMには言語化・説明に寄せる。
comparison
11 / 16
得意・苦手の分担
小型LLMの弱点を 設計で補う
小型モデルの算術誤りは“仕様として起きうる”ため、合計や内訳など厳密性が必要な部分はLLMに丸投げしません。 代わりに、先に集計した値（ground truth）を根拠として提示します。
LLMに任せる
要約、説明、言い換え、カテゴリの意味づけ
アプリが保証する
月次/日次/カテゴリ別内訳などの集計値
Risk管理：算術に起因する誤回答（ハルシネーション）を構造的に抑制。
evidence
12 / 16
議論：安全性の盲点
“送らない”だけでは 十分でない
記事の強みはサーバー送信を避ける点ですが、安全性の全体像（暗号化、消去、端末共有時、XSS等のWebセキュリティ）が十分に説明されていない可能性があります。 実運用では追加確認が必要です。
Pros / 良い点
外部送信ゼロで漏えい面を縮小
Needs / 必要情報
ローカル暗号化・削除手段
Threats / 脅威
端末盗難・共有・セキュア実装不足
Personal finance（個人財務）は機微情報。保護は保存先の選択だけで完結しません。
closing
13 / 16
結論
実務的なオフラインRAG の型
Cache Storageでモデルをオフライン化し、家計の数値はアプリがground truthとして先に計算。 さらに会話リセット、ストリーミングJSON修復で、ブラウザ制約下でも破綻しない体験を狙います。
Core stack / 中核
LiteRT + Gemma 4（E2B） / Cache Storage
Core safeguards / 保護策
grounding（先集計） / 3ターン管理 / jsonrepair
Bilingual: offline（オフライン）/ privacy-first（プライバシー優先）/ grounding（根拠提示）。
