COVER
02 / 16
出荷のための“所有”基盤
Agentic Ship
AIコーディングエージェントの成果を、デモではなく“ちゃんと出荷できる”形に整える、検証ゲート付きツールキットです。
PROBLEM
03 / 16
Hosted builderの罠
続かない
ホスティング型は開始が速い一方で、離脱時にルール・バックエンド規約・検証が“手元に残らない”問題が起きやすくなります。

速度

立ち上げは簡単だが、運用の契約が外部化されがち

所有

“できた”は残っても、“壊れない条件”が残らない

METAPHOR
04 / 16
AIを指揮する
検証契約
Agentic Shipは、エージェントに“書かせる”だけでなく、pnpm verifyのような合否で出荷可否を決める契約を同梱します。

指示

AGENTS.mdのルールを守る

検証

テスト・静的チェック・視覚レビュー等で合否

ARCHITECTURE
05 / 16
成立させる固定
スタック固定
Node 20+、Next.js 16、React 19、Tailwind v4、Convex、Better Auth、Stripe、Resend、PostHog、Netlifyなどを前提としてピン留めします。

前提

runtime/フレームワーク

背骨

Convex + 認証/課金/メール

運用

Netlify主導のデプロイ

iv

品質

DISTINCTION
08 / 16
Hosted vs Own repo
主導権
差はコストではなく“所有と離脱”にあります。定義済みの“done”を自前のCI/検証で担い続けられるかが鍵です。

Hosted builder

外部の規約・検証に依存しやすい

Own repo toolkit

コードと検証ゲートが自分のGitに残る

EVIDENCE
09 / 16
セキュリティの要件
閉域の準備
依存監査、CSPを閉じた本番事前準備、production preflightなど、運用前のチェックを前提にしています。

事前

production preflight（本番前点検）

監査

依存監査 + 設定の整合

DISTINCTION
10 / 16
接続の設計
consent / revocation
サービス接続はベンダのOAuthに任せつつ、同意（consent）と取り消し（revocation）を設計要件として明示します。

Consent

誰が何に同意したかを前提化

Revocation

接続を取り消せる前提で構成

Bilingual: consent（同意）/ revocation（取り消し）
COMPARISON
11 / 16
採用判断の要点
強みと懸念
強みは“検証でdoneを定義すること”。懸念はバックエンド中核などのスタック固定による置換コストの増加です。

強み

pnpm verify + テスト/レビューで品質を契約化

懸念

Convex等への依存が増え、スワップ見積が必要

自社要件の適合

ii

iii
