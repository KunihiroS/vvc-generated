モデルではなく境界

プロンプト越境

プロンプトインジェクションを「モデルがだまされる」ではなく「信頼境界の崩壊＝権限付き書き込みが生まれる失敗」として捉えます。

読み（read）を安全とみなしても、ツール実行（execute）に接続されると脅威になります。

LLM agents / multi-tenant
PROBLEM
03 / 16

言語の錯覚

read-only でも書き込む

外部ページ等の未信頼テキストがコンテキスト窓に入り、ツール呼び出しの引数形成へ影響すると「読み」が「実行」を誘発し得ます。

前提
未信頼データが同じ共有領域（context）に入る
日本語：共有バス / 英語：shared bus
結果
ツール実行の引数・選択が「良い形」に整えられ越境
日本語：権限借用 / 英語：capability borrowing
METAPHOR
04 / 16

柵は窓じゃない

コンテキスト＝共有バス

境界は「区切りタグ」や「注意書き」ではなく、実行を許可する場所（capability 境界）に置かないと破れます。

分離：テナント境界（multi-tenant）
接続：コンテキスト窓（shared context）
決定：ツール実行ゲート（dispatcher / broker）
本質：provenance-to-authorization の変換

（デリミタはシートベルトであってブレーキではない）

06 / 16

confused deputy

混乱した代理人

モデルが“正しそうな提案”をしても、その結果がツールの権限成立根拠として使われると越境が起きます（confused deputy）。

誤りの原因
推論結果が「承認（authorization）」として扱われる
設計の要点
承認はモデル外（policy broker）で固定
日本語：政策ブローカー / 英語：policy broker

本質は責任分界

対策レイヤの順位

この議論の一貫した結論は「プロンプト防御・検知は補助で、主戦場は実行ゲート」です。

i. 推奨
ツール呼び出しで capability 境界を fail-closed
英語：fail-closed / 日本語：拒否側で閉じる
ii. 補助
注意文・フィルタ・検知（後回しになりがち）
EVIDENCE
08 / 16

read-only がシアター

「拒否条件」がないと崩壊

プロベナンス（出所）をラベル化しても、執行時に拒否へ結び付かなければ「安全の演出」になります。

不足
provenance を“覚える”だけで、authorization に使わない
必要
provenance-to-authorization を執行直前で強制
日本語：執行拒否 / 英語：reject condition
DISTINCTION
09 / 16

taint は拒否へ

taint 追跡は万能でない

要約・コンパクションで taint が失われると拒否根拠が弱まり、境界が“紙の上”でしか機能しません。

成功の条件
taint が維持される
失敗の条件
要約でビットが飽和/消失
求める着地
実行ゲートで fail-closed

10 / 16

境界の置き場所

拒否は dispatcher で

特に重要なのは実行時（tool-call / dispatcher）で拒否できる境界を作ることです。

手前
retrieval 時点でスコープ付与（要らない権限を先に減らす）
直前
ツール引数・宛先テナント・目的に対し reject 条件を評価
COMPARISON
11 / 16

フィルタ vs 実行ゲート

検知は止められない

注意文・プロンプト改善は「どう言うか」を抑える発想ですが、必要なのは「何をどの権限で許すか」を制御することです。

プロンプト対策
検知・説得はできても、authorization の最終決定を変えにくい
能力ブローカー
capability スコープと拒否条件を fail-closed で固定
日本語：能力境界 / 英語：capability scope

委譲が越境する

multi-agent のハンドオフでは、汚染が“テキスト”ではなく“委譲アーティファクト”として権限越境に寄与し得ます。

scope の単調縮小（縮めるほど安全）

疑問への要点

Q&A：芯は拒否

Q1
注意文・フィルタだけでは不十分：拒否（reject）がない
Q2
taint は万能でない：要約で失われ、拒否根拠が弱まる
Q3

境界はサマライズ後ではなく、実行直前で強制するのが重要。

私の評価

方向性は妥当、設計粒度が不足

最大の強みは実装寄りに問題を再定義して責任分界を明確にする点です。一方、粒度（どの単位まで taint/provenance を保持し拒否するか）や例外運用が未定式化です。

強み
「コンテキスト＝共有バス」「拒否は実行ゲート」「read-only は崩れる」を一本化
限界
性能・誤拒否・例外許可・監査の設計までのガイドが不足
CLOSING

実装チェック

棚卸し→拒否条件

まず「未信頼情報がどのタイミングでツール引数・宛先テナントへ接続されるか」を棚卸しし、次に capability broker の fail-closed 条件（provenance-to-authorization）を検証してください。

検証 1
retrieval後/要約後でも taint/provenance が“拒否判定”に到達しているか
検証 2
誤拒否率と性能コストを運用目標に落とし、例外は“境界の外”で管理
