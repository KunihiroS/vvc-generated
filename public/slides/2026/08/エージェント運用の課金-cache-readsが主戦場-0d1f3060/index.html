02 / 14
課金の見落とし

cache read 主戦場

エージェント運用では、入力/出力トークンの単価よりも cache reads（キャッシュ読み出し） がコストを支配しやすい。

“長く回すほど”見積もりが崩れるので、閾値（cliff）と課金ルールを前提に再計算しよう。

PROBLEM
03 / 14
単価だけだと破綻

安さ判断 近視眼

従来は「1Mトークン当たりの料金（入力/出力）」だけでモデルを選びがちだが、エージェントでは別の課金要素が効いてくる。

盲点
tool呼び出しを繰り返すと、同じコンテキストを“毎ターン読み直す”必要が生まれる。
結果
読み出しの対象になる KVキャッシュ に由来する cache reads が総コストを押し上げる。
METAPHOR
04 / 14
読む回数がコスト

同じ本 何度も

長い議事録（コンテキスト）を、ターンごとに再読するイメージだ。入力や出力が少なく見えても、再読回数が増えると負担が跳ねる。

ターン
in：少し追加
ただし
cache read：過去を参照
累積
100ターン級で“比率”が逆転
ARCHITECTURE
05 / 14
KVキャッシュの所在

高速化の 状態

モデルは推論を速くするため、過去情報を KVキャッシュ（推論高速化用の状態） として保持・圧縮する。

圧縮
KVキャッシュは圧縮され、同じ意味でも実メモリ使用量を下げられる可能性がある。
配置
GPU/メモリ/SSD/NVMeなど、どこに置くかで“性能と実コスト”が変わる。
ENUMERATION
06 / 14
見積もりの観点

見るべきは 3つ

i
入力/出力単価（ベース）
ii
cache reads（参照量）
iii
閾値による再価格設定（cliff）

長時間エージェントでは、ii と iii が見積もりを支配しやすい。

EVIDENCE
07 / 14
ターン数で崩れる

20→100 比率逆転

記事の主張は、「20ターンでも cache reads が大きく見える」「100ターンでさらに顕著になる」という傾向。

直感
追加は数千トークンでも、読み出し対象（過去部分）が毎ターン“積み上がる”。
結論
「平均ターンあたり追加トークン量」だけでは足りず、参照回数（ターン設計）を織り込む必要がある。
PROCESS
08 / 14
コストを下げる設計

往復回数 減らせ

tool呼び出しの回数やターン数を減らす工夫は、結果として cache reads が発生する“回数”を減らしやすい。

例
(1) tool呼び出しをバッチ化して往復を圧縮
例
(2) より専門化した専用ツールで意思決定回数を削減
狙い
「少ない往復で完結」→ cache reads の発生ターンを減らす
示唆
記事では、ターン数を10%減らすとコストが約16%減る可能性に言及
COMPARISON
09 / 14
安いモデルが逆転

価格表 そのまま ではない

同じ“モデル名”でも、課金ルールが入力閾値を超えると再計算され、価格表の単純比較が崩れる。

例（GPT 5.6 Sol）
一定の入力トークン閾値を超えると、入力=2倍、出力=1.5倍のように単価が跳ねるケース。
対比（Anthropic）
同一レートのまま、という主張が引用されている。

長時間セッションほど“cliff（段差）”が効いてくる。

EVIDENCE
10 / 14
KVが小さくても別問題

実コスト と 課金がズレる

KVキャッシュが圧縮で小さくなり、さらにSSD/NVMeへオフロードできるなら、プロバイダ側の実コストは相対的に抑えられる可能性がある。

推測
その結果、 cache reads が利益率の高い収益源になり得る、という見立て。
注意
通信・同期・運用の複雑さなど、実コスト増もあり得るため確定ではない。
DISTINCTION
11 / 14
“採用前”に検証

ログで 当てる

読み手は記事の計算をそのまま採用せず、自分のプロンプト設計・ターン設計・実ログで cache reads と閾値挙動を確認するべきだ。

Q
cache readsとは？：KVキャッシュを参照して“読み出す量”として課金される場合がある。
Q
なぜ入力/出力だけで足りない？：既存コンテキストを再読するコストが勝つため。
Q
ターン数を減らすと？：キャッシュ参照が起きる“回数”を減らせる。

Bilingual（概念）：cache reads（キャッシュ読み出し） / KV cache（KVキャッシュ）

ENUMERATION
12 / 14
誤差の原因

同じ数式で 同じ結論 にならない

記事の示唆は強いが、実際はプロバイダのcache read仕様、キャッシュヒット率、toolの挙動などで結果が変わる。

変動要因
キャッシュヒット率／セッション境界／再計算の有無
設計要因
ターンごとのトークン推移、並列度、tool設計（往復回数）

特に長期実行では、cliff（閾値）を“必ず”チェックする。

CLOSING
13 / 14
意思決定の要点

モデル比較は 参照込み で

エージェント運用の費用最適化は「単価が安い」だけでは足りない。cache reads と閾値による再価格設定（cliff）を前提に再見積もりしよう。

行動
tool統合・バッチ化・往復削減でターン数を下げる
確認
自社ログで cache reads 比率と閾値超えの有無を検証

（まとめ）cache read主戦場／長期は二次的に高騰／単価比較だけに頼らない。
