会話を短く、仕事は続ける
Compactionコンテキスト圧縮
Codex CLI（Rust）における会話履歴の圧縮設計を、トリガー／方式／保持ルール／拡張点の観点で整理します。
対象：コンテキスト制限（token / context window）
Focus：設計思想 × 実装の全体像
problem
03 / 16
なぜ圧縮が要る？
コンテキスト上限
LLMへ送れる履歴には上限があり、会話が伸びるほど「全部をそのまま再送」できません。 そこで、必要情報を残しつつ古い履歴を要約や再構成で短く保つ必要があります。
Constraint
token / context window の上限
Goal
継続性（continuity）を維持
トレードオフ：情報保持 vs 情報損失
手段：要約・再構成
architecture
04 / 16
核となる思想
Mementoメメント
要約は「削除」ではなく、別のLLMが引き継いで再開するためのスナップショットとして位置づけられます。 これで圧縮後もタスク継続の論理が崩れにくくなります。
Reframe
要約＝ハンドオフ（handoff）
Outcome
継続性を守る（整合性）
Bilingual：Memento（メメント）
核心：責務分離された再開設計
enumeration
05 / 16
方式は3系統
Three3Modes
Codex CLI の Compaction は状況に応じて、ローカル要約・専用API・ストリーミング連動のいずれかを使います。 方式ごとに「コスト／保持範囲／遅延」が変わります。
i
Token Budget Compaction（要約なし）
ii
ローカルコンパクション（要約生成）
iii
リモート v1/v2（専用API/連動）
自動選択：provider / 状況 / 設定
目的：性能とコストの釣り合い
process
06 / 16
発動は段階的
90%閾値トリガー
自動コンパクションの中心閾値は「コンテキストウィンドウの90%程度」です。 さらにその前に Token Budget Reminder（事前警告）で段階的に管理します。
Before
Token Budget Reminder（警告）
At
~90%到達で Compaction（強制）
狙い：突然の挙動変化を抑える
安定性＝推論品質＋UX

Hooksフック
コンパクションの前後で pre_compact_hooks / post_compact_hooks が実行でき、ログ記録や連携処理など外部介入が可能です。 「観測性」と「拡張性」を両立する設計です。
pre
pre_compact_hooks
post
post_compact_hooks
可能：監査・連携・計測
不透明になりがちな圧縮を可視化

08 / 16
保持されるもの
Rulesルール
Compaction後に「何が残るか／何が要約に置き換わるか」は方式ごとに定義されています。 そのため、情報損失の範囲を見える化しやすい点が重要です。
Local
ユーザーメッセージ中心（最大20,000 token相当）
v2
保持対象を条件化（保持予算上限 64,000）
古いアシスタント/ツール出力等は置換され得る
保持の設計が品質を左右
evidence
09 / 16
方式ごとの違い
Zero/Local/Remote
Token Budget Compactionは要約生成をせず、コンテキストを切り替えて履歴をクリアし再注入します。 一方、ローカルやリモートは要約（または圧縮済み履歴）を生成・返却します。
Token
要約なし（context切替）
Local
要約生成（ローカル処理）
Remote
専用APIで圧縮（v1/v2）
性能：遅延・コストの最適化余地
運用：provider適応
distinction

v2の狙い
Streaming連動
v2は Responses API のストリーミング呼び出しに CompactionTrigger を追加し、応答と同時期に圧縮を進める設計です。 保持トークン予算（例：RETAINED_MESSAGE_TOKEN_BUDGET）や保持条件も細かく管理します。
Timing
応答ストリームと並行に進行
Budget
RETAINED_MESSAGE_TOKEN_BUDGET
狙い：遅延・タイミング制御の最適化
設計：保持範囲を条件化

11 / 16
情報損失と安全
Trade-off
要約ベースの方式では情報が欠落し得ます。加えて、保持/破棄ルール（例：developer メッセージ）が方式によって変わるため、重要指示の取り扱いに注意が必要です。
Risk
要約の正確性・細部の落ち
Safety
developer/system 指示の保持条件次第
推奨：保持条件の確認と回帰テスト
推奨：圧縮の観測（監査ログ）
problem
12 / 16
運用で効く要点
Predict & Verify予測と検証
90%閾値・Token Budget Reminder・保持予算が具体的なので、「いつ圧縮されるか」を運用設計に落とせます。 ただし品質（成功率・再実行率等）は本メモだけでは確定できないため、回帰テストと観測設計が必要です。
Practical
設定値で運用に組み込める
Quality
失われた情報の影響を実測で評価
観測：なぜ圧縮されたか／方式は何か
安全：方針遵守の間接要因を潰す
closing
13 / 16
結論
Mementoで継続
Codex CLI の Compaction は、Memento による継続設計と、段階的トリガー／方式別ルール／フック拡張で実運用に寄せた全体像になっています。 採用・運用では「保持される情報」を確認し、圧縮が品質に与える影響を検証するのが最重要です。
