変更権限を契約化する
Trusted Base

AIコーディングエージェントに「どこまで書いてよいか」を、プロンプトではなくレビュー可能なGitベース契約として渡す。

Problem
03 / 18
テストは通っても
範囲逸脱

目的どおり実装できても、認証ミドルウェアの共有部やDBテーブル、デプロイ設定まで触れてしまう可能性がある。

誤解
「指示どおり」＝「承認済み境界内」
ギャップ
技術的正しさ ≠ 人の許可の根拠
Core Idea
04 / 18
プロンプトは意図
Permission

permission（許可）は、プロンプトや探索結果ではない。書き込み可能な境界を含む「権限契約（permission contract）」として固定する。

日本語対応：permission（許可） / classification（分類）
Architecture
05 / 18
契約＝書き込み境界
Permission Contract

承認された設計変更（engineering change）を、バージョン管理された契約として表現し、エージェントが読む前に trusted base から取得する。

対象
書き込み可能なパス群（path policy）
制約
停止条件・技術的義務・検証者（verifiers）
根拠
承認済み履歴（trusted base）に結び付く
Flow
06 / 18
読み取りは広く
書き込みは限定

エージェントはリポジトリを広く読むことは許容されるが、書き込み権限は契約で指定された境界に限定される。

Read（読む）
調査・影響把握のために許可
Write（書く）
契約が指定した場所だけ
Distinction
07 / 18
許可と分類を分離
No Confusion

classification（分類）は「差分をどう観測したか」の説明にすぎない。permission（許可）そのものではない。

classification
current-change classification（現状差分の分類）
permission
契約が許す“その差分を作る権限”
Failure Mode
08 / 18
「分類できた」罠
Future Permission

classificationが許可を意味すると誤解すると、verificationが“未来の許可”を捏造する危険がある。EngineeringSpecはここを切り離す。

分類（観測）＝許可（根拠）ではない、という責任分界を維持する。
Governance
09 / 18
自己拡張を防ぐ
Stop & Amend

契約範囲を超える必要が判明したら、停止→ブロッカーを説明→追加のレビュー済み権限（amendment）を取得してから続行する。

停止
勝手に範囲を広げない
説明
ブロッカーの明示（何が足りないか）
改訂
追加レビューされた権限を取得
RC17
10 / 18
運用面の整合
RC17 Improvements

RC17は権限モデルを変えず、エージェント向けチケット表示をコンパクト化し、permissionとclassificationを明確に分離する。

表示
permission（許可）とclassification（分類）の分離
導線
ブロック時の“実行可能な診断コマンド”を含める
Verification
11 / 18
検証の射程
Boundary Check

verification（検証）は「権限境界との整合」を確認するもので、ソフトウェア品質やセキュリティの保証そのものではない。

確認する
権限契約とルーティングの妥当性
保証しない
動作正しさ・受入基準の達成・安全性
Pilot
12 / 18
生産性は未確定
Paired Task

モデルが本当に生産性・安全性を高めるかは十分な証拠がないため、paired-taskによる外部パイロットで検証する姿勢を取る。

“設計上合理的”と“実運用で改善”は別問題として扱う。
Takeaway
13 / 18
要点を一文で
Permission First

EngineeringSpecは、許可（permission）をレビュー可能な契約として固定し、分類（classification）と分離し、範囲逸脱を停止と改訂で封じる。

一線
プロンプト≠許可
分離
分類≠許可
回復
Stop → Amend
My View
14 / 18
合理性 vs 摩擦
Balanced Skepticism

権限と分類を分離し、verificationを品質保証に誤って拡張しない点は強い。一方で、契約粒度やamendment運用コストは定量不足で不確実性が残る。

強み
監査可能性と逸脱検出の期待
懸念
停止回数・契約改訂頻度で速度低下
References
15 / 18
参照（整理）
Next Checks

導入判断には、paired-task結果だけでなく、停止頻度・契約粒度・失敗ケース分析の定量も確認する。

Repro / Pilot
paired-task（同一条件で生産性・安全性を比較）
Ops Metrics
amendmentの回数、ブロッカー復旧の成功率、導入摩擦
Boundary Cases
契約改訂が必要になった失敗例と、修正に要した情報
