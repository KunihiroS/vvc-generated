Shelf Protocol
02 / 18
AIの買い物前確認
安全に
事前許可
AIエージェントが商取引に進む前に、各商店の「買ってよい条件」を検証済みで参照（lookup）します。 DNS検証と仕様化で、無断スクレイピングより安全で安価な導線を狙います。
Problem
03 / 18
無断購入の不安
無検証
AIがオンラインで購入するとき、誤購入・悪用・価格上限の悪意ある上書きが起き得ます。 そこで「事前に許可を取り、許容範囲だけ動く」仕組みが必要になります。
リスク
プロンプト改ざんや誤設定で検証がスキップされる
原因
購入条件がコードやスクレイピング側に“散らばる”
Architecture
04 / 18
lookupで許可
Shelf
商店は shelf.json を公開棚（shelf）として登録し、AIは購入前にレジストリへ1回問い合わせます。 返ってきた「検証済み情報」と制限にもとづき、許容範囲内で自動購入します。
商店（merchant）
shelf.json 登録
検証（verification）
DNS TXTでドメイン所有確認
AI（agent）
lookup → can_buy() → 自動購入
Core
05 / 18
手順は短く
lookup
AIの導入は「問い合わせ1回」で済む設計です。制限（上限額・許可エージェント等）だけを機械的に守る形になります。
step i
domainを指定して Shelf Protocol へ lookup
step ii
verified情報と制限を受け取り、can_buy(domain, amount_usd) を評価
Verification
06 / 18
DNS TXTで固定
verified_domain
登録直後は提案に近く、DNSのTXTレコード（_shelfprotocol.<domain>）で所有を確認した後に verified_domain=true になり、can_buy() が自動購入を許可します。
未検証
勝手に“買える状態”を作れない（自動購入が拒否）
検証済み
ドメイン管理者の意図が確認でき、範囲内購入が可能
Catalog
07 / 18
壊れたデータを混ぜない
Strict
カタログ更新（shelf-catalog.json のクロール）では品質検証を行い、SKU重複などがあれば全更新を拒否します。 静かな欠損や不整合の混入リスクを抑えます。
検証
HTTPSのみ、リダイレクト禁止、タイムアウト、サイズ上限
整合性
SKU一意性、価格の非負、必須項目
失敗時
1件でも失敗 → 全体拒否、422で理由を返す
shelf.json
08 / 18
商店が宣言する条件
Constraints
商店は shelf.json に、購入可能条件（例：agents_allowed、 max_autonomous_order_usd）と参照先（checkout.endpoint、catalog.feed_url）を宣言します。
例：許可範囲
agents_allowed / max_autonomous_order_usd
例：参照先
checkout.endpoint / catalog.feed_url
Security boundary
09 / 18
検証回避を潰す
can_buy()
MCPツールの can_buy(domain, amount_usd) には、無検証を許す設定（例：require_verified=false 相当）がないと明記されています。 そのため、プロンプト注入で「検証をスキップ」させるリスクを下げる意図があります。
設計意図
検証“強制”に寄せ、誤実行を抑制
SDKとの差
SDKは require_verified を指定でき、意図的なオプトアウト余地がある
Seeding
10 / 18
空の問題を解く
seeding
空のレジストリ問題を避けるため、公開フィードから取り込み、検索可能に“露出”させます。 ただし最初は verified_domain=false かつ自動購入上限を$0にして不活性化します。
最初
verified_domain=false
自動購入
max_autonomous_order_usd = $0
開始条件
claimフローでDNS検証を完了
Tooling
11 / 18
MCP / LangChain / CrewAI
呼び出し
エージェント統合では、lookup結果の“検証済み制限”を前提にツール呼び出しします。 フレームワークが違っても、最終的な安全境界は「検証の有無」に強く依存します（読み取り実装が鍵）。
MCP
検証回避しにくい（require_verified系の引数なし）
実装注意
SDKはオプトアウト余地があるため、運用で固定する必要
Operations
12 / 18
現実の運用前提
Rate & Limits
レジストリには読み取り／書き込みのレート制限があり、超過時は 429 と Retry-After が返ります。 ローカルデモではDNS検証をオフにできる環境変数も用意されており、本番では有効化徹底が重要です。
429
IP単位の抑制 → 再試行待ち
検証チェック
環境変数で切れるなら、本番誤設定を防ぐ統制が必要
Business
13 / 18
標準化×課金
Growth
無料枠（登録・lookup）と、検証済みバッジの商店課金、閲覧回数に応じた従量課金、エンタープライズ向け優先掲載・リッチデータ提供を述べています。 公開テンプレートへの早期組み込みが、ネットワーク効果の起点になります。
無料
登録・lookup
課金
検証済みバッジ / 従量閲覧
企業
優先掲載 / リッチデータ
Concerns
14 / 18
“完全性”は別途
Security Gaps
抜粋からは、DNS TXTトークンの強度、漏洩時の影響範囲、監査ログ粒度、チェックアウト連携の真正性などの追加情報が不足しているように見えます。 さらに lookupが基盤になるため、DoSや列挙攻撃への対策も別確認が必要です。
未確認項目
監査ログ / チェックアウト真正性 / キー漏洩の影響
運用の難所
レート制限設定・削除/抑制の手順を誤ると意図しない挙動
Takeaway
15 / 18
導入の結論
事前許可
Shelf Protocolは、DNS検証と厳格な失敗時挙動で「未検証の自動購入」を抑え、標準化とネットワーク効果を狙います。 一方で、実運用では本番設定（DNS検証・レート制限・監査/真正性の確認）が成功要因です。
