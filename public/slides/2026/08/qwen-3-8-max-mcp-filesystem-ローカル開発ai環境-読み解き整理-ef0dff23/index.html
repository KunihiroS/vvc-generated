Cover
02 / 13
無料で“ローカル体験”
Qwen 3.8-Max
Qwen Studio（クラウド実行）＋ MCP Filesystem（ローカル実行）で、AIが手元ファイルを読み書きしながらコーディング支援する環境を、注意点込みで整理します。
Bilingual（用語）: MCP = Model Context Protocol（モデル文脈プロトコル）/ Filesystem = ファイル操作
Problem
03 / 13
便利さと引き換え
データ境界
モデルはクラウドで動き、MCP Filesystem側はローカルでも、読み取ったファイル内容がクラウドへ送信される可能性があります。
できること
ファイルの読み取り・書き込み・編集（ローカル開発フローを拡張）
気をつけること
機密/著作権/社内データは、プライバシーポリシーと送信範囲を確認してから扱う
結論: “ローカルっぽい”体験でも、情報統制は必須です。
Architecture
04 / 13
分業が鍵
クラウド × ローカル
Qwen 3.8-MaxはQwen Studio経由でクラウド実行し、MCPのFilesystemサーバーだけを手元PCで起動します。
Qwen Studio
AI推論はクラウド
(入力/文脈が送られる可能性)
MCP
外部ツール連携で文脈を拡張
(Model Context Protocol)
Filesystem MCP
ローカルでファイル操作
(アクセス範囲を絞れる)
安全設計の主役は、Filesystemが触れるフォルダの“絞り込み”です。
Metaphor
05 / 13
“手”はローカル
AIは読者、触るのは手元
AI（読者）が質問し、Filesystem（手元）がファイルを取得して返すことで、編集まで進みます。
流れ i
AIが「必要なファイル/差分」を要求（文脈が形成される）
流れ ii
Filesystemがローカルから読み取り→変更→差分を返す（ただし内容はクラウド側で扱われ得る）
誤解しがちポイント: “手元で動く＝機密が外へ出ない”ではありません。
Process
06 / 13
最小手順
設定は2段
Qwen StudioでQwen 3.8-Maxを選び、次にMCP設定でFilesystemサーバーを有効化します。
段 i（モデル）
Qwen StudioでQwen 3.8-Maxを利用開始
段 ii（MCP）
Filesystem MCPを起動し、アクセス対象フォルダを指定
起動の要点（例）
Node.js が必要
npx で Filesystem MCP サーバーを起動
args でアクセス範囲（フォルダ）を絞る
導入ボトルネック: Node.js未導入だと止まります。
Enumeration
07 / 13
運用ベスト
3つの統制
この環境は強力ですが、誤変更・情報漏えいの両方を抑える統制が必要です。
i（範囲）
アクセスを必要最小限のフォルダへ限定
ii（確認）
プライバシーポリシー/利用規約で送信範囲を確認
iii（品質）
変更は必ず差分レビュー（必要ならテスト/検証も）
結論: “自動化”より前に“人間の承認”を設計します。
Comparison
08 / 13
得意と限界
速いが保証は別
README/入力要約から分かる範囲では、AI編集の速度と便利さは高い一方、品質保証の自動化までは読み取れません。
向いている
読み取り→理解、新規作成、既存コードの文脈に応じた編集、ファイルナビゲーション
不確実/要追加
依存関係解決、テスト実行、ビルド、静的解析などの品質工程は別途設計が必要
結論: “作業は速くなるが、検証工程は別途”が現実的です。
Evidence
09 / 13
FAQ要点
重要な5問
入力データに基づく、判断に直結する要点だけを抜粋します。
Q1 無料？
無料とされるが、Free tierはポリシーに従い変動し得る
Q4 自分のコード？
クラウド実行が前提で、MCP経由のファイル内容が送信される可能性
Q3 MCPの役割
AIが外部ツール（今回はFilesystem）と連携し文脈を拡張
Q5 得意タスク
読み取り理解〜文脈編集、ただし依存/テスト自動化は要確認
Q2（モデル詳細）とQ6（セキュリティ）は、実運用前に公式情報で補完が必要です。
Closing
10 / 13
最終結論
試す価値は高い
セットアップの道筋は分かりやすく、無料枠でローカル開発体験を拡張できる可能性が高いです。
導入前
プライバシーポリシー/規約で送信範囲を確認し、扱うデータを限定する
導入後
変更は必ず差分レビュー、必要な検証工程（テスト等）を別で用意する
運用判断に不足: データ保持期間、送信粒度、MCPログ挙動、テスト/検証連携は入力データだけでは確定できません。
