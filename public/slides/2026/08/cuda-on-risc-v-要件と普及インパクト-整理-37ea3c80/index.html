Hot Chips 2026

CUDA on RISC-V

NVIDIAの狙いは「RISC-VのCPUを挿せば動く」ではなく、GPU計算を成立させるプラットフォーム全体の前提を満たすことだ。

Key message / ひと言
当面はサーバ中心（要件未達が多い）
Why it matters / 何が効く
ACPI / PCIe coherency / peer-to-peerが普及の壁
Problem
03 / 18
CPU命令だけではない

互換性の定義

CUDAはGPU単体の話ではなく、CPU側のメモリ整合性・電源/熱制御・割り込み/管理・通信（PCIeなど）まで一連で整合する必要がある。

Correctness / 正しさ
キャッシュとDMAの整合
Performance / 性能
無駄な経路・同期の削減
Operability / 運用
電源・熱・保守性（RAS）
Thesis
04 / 18
有望だが条件付き

結論

CUDAをRISC-Vへ拡張する計画は前向きだが、当面は多くのRISC-Vが満たさないサーバ級要件が前提になりやすい。

i
NVIDIAはまずRISC-V側のサーバSoC/プラットフォーム仕様（RAS・セキュリティ等）を満たすことを求める。
ii
その上で、CUDA最適化に必要な追加要件（ACPI / PCIeなど）が残る。
iii
既存のRISC-V普及機では要件未達の確率が高く、サーバ中心に寄りやすい。
Architecture
05 / 18
成立の土台

要件の階層

CUDA対応には「命令セット」より先に、サーバとしての基礎（信頼性・可用性・保守性）と、OSが把握できる管理情報が要る。

Layer 1 / 土台
RISC-VサーバSoC/プラットフォーム（RAS・セキュリティプロセッサ等）
Layer 2 / 追加
ACPI / PCIe coherency / PCIe peer-to-peer

日本語補助：RAS（Reliability, Availability, Serviceability）＝信頼性・稼働率・保守性。

Evidence
06 / 18
ACPIが鍵

電源・熱・性能

ACPI（Advanced Configuration and Power Interface）は、OSが電源・性能・熱などの管理情報を掴むための仕組みで、CUDAの制御前提になる。

What it governs / 管理
電源・性能・熱（power / performance / thermal）
Why CUDA / CUDA理由
GPUの動作制御と熱・電力最適化の不確実性を下げる
Status / 状況
2025年：RISC-V ACPIサポート追加、BRSにも取り込み

ポイント：標準が整っても、実装が広がるまで時間差が出る。

Distinction
07 / 18
coherencyは妥協しにくい

PCIe coherency

PCIe coherencyがないと、CPUキャッシュとDMA/GPUアクセスの整合が崩れ、読み書きの正しさと性能の両方にリスクが出る。

Failure mode / 破綻例
CPUキャッシュ更新がDMAに反映されず、GPUが古いDRAMを読む
Why hard / 難しさ
CUDAスタックに「キャッシュ無効化」のような対処を組み込みにくい

結論：保証としてのcoherencyを、サーバCPUの標準機能として求める。

Comparison
08 / 18
速度だけじゃない

PCIe peer-to-peer

peer-to-peer PCIeは、速さ（直接転送）だけでなく、CPU経由による経路・同期の増加を抑えて構成の単純さにも効く。

No P2P / P2Pなし
CPUメモリ経由になり、バッファ転送＋同期が増えて性能低下・複雑化
With P2P / P2Pあり
デバイス間で直接転送、CUDA/NCCL系の通信設計がシンプルに
Process
09 / 18
ソフトスタック依存

NCCL / DOCA

CUDAに加えて、通信ライブラリ（例：NCCL）やネットワーク/オフロード（例：DOCA）の成立にも要件が波及し、プラットフォーム要求が強まる。

NCCL / 通信
データ並列・集団通信の性能設計が前提要件に依存
DOCA / ネット
オフロード/デバイス連携が整合して動くことが重要
CUDA以外も / 波及
CUDAと通信スタックは同じプラットフォーム前提を食う
Architecture
10 / 18
協業設計の色

NVLink Fusion

NVLink Fusion（他社チップでNVLink IPを使う）では、IP統合の複雑性が高く、ソフト/通信スタックまで含めた緊密な協業が前面に出る。

Goal / ねらい
互換だけでなく、通信スタックを一体で最適化できる構図
Implication / 含意
RISC-V単独導入より、周辺エコシステムの共通化が進みやすい

ここが強いほど、対応は「早い普及」より「要件を揃えたサーバ」へ寄りやすい。

Market
11 / 18
普及の条件

どこで動くか

筆者の見立てでは、既存のRISC-V普及機（特にコンシューマ）で要件未達になりやすく、CUDA対応はサーバ中心に寄る可能性が高い。

Consumer RISC-V
ACPI/PCIe coherency/P2Pの実装が追いつかない可能性
Server RISC-V
RAS・管理・検証が前提化しやすく、要件吸収が進む
Outcome / 結果
「手頃なボード」ではなく「構成が揃った環境」へ
Risk
12 / 18
コミュニティ阻害

試せる範囲

要件が厳格すぎる場合、趣味層・研究コミュニティによる試行（部分構成での実験）が抑制され、エコシステムの立ち上がり速度に影響しうる。

i
必須要件の境界が不明だと、導入判断の見積もりが難しい。
ii
最初の利用機会がサーバに限定されると、試作・検証の母数が減る。
iii
結果として「いつ・どの構成で恩恵」が掴みにくくなる。
Skepticism
13 / 18
見積もりが難しい

必須度とロードマップ

記事中では要件の概観は掴めるが、「どこまで満たせば実用か」や、必須/推奨/将来緩和の区分が分かりにくい点が弱点になりうる。

Missing / 不足
必須度（必須/推奨/将来緩和可能）や数値目標の粒度
Effect / 影響
外部から「実用化のタイミング」と「必要コスト」が読みづらい

補足：普及には要件だけでなく、互換性範囲と緩和のロードマップが効く。

Takeaway
14 / 18
次に見るべき

判断軸

CUDA対応RISC-Vの現実は「CPU命令セット」より「プラットフォーム整合性」が決める。見極めには、ACPI・coherency・P2Pの実装有無と、その検証体制が要点になる。

i. ACPI / 管理
電源・性能・熱をOSが把握できるか
ii. coherency
キャッシュ整合が保証されるか（正しさ＋性能）
iii. peer-to-peer
デバイス間直接転送で経路・同期を抑えられるか
日本語補助：coherency＝複数の記憶階層でデータが食い違わない性質。
