実行ファイル＝データベース
SELF SQLite化
実行ファイルを“ただのバイト列”ではなく、SQL（SELECT/INSERT/UPDATE）でクエリできる容器として扱う発想です。（実際に動くプロトタイプ例として self-httpd が示されます）
核心
コードと状態を同一SQLiteに
routes / visits / presses 等
狙い
デプロイ・監査を“SQL操作”へ寄せる
INSERT…SELECT / sqldiff
problem
03 / 14
分離が“運用の重荷”
分けるほど 面倒
通常のアプリは「コード（実行ファイル）」と「状態（/var, /tmp, /home, 外部DBなど）」を分けて管理します。結果として、デプロイ・更新・監査の単位がズレやすくなります。
コード
実行ファイル（更新が別工程）
状態
ログ/DB/ファイル（永続領域）
運用
移行・整合性・監査の工数
SELFはこの分離を弱め、同一ファイル内のSQLで“状態の移し替え”や“更新の一貫性”を狙います。 (ただし安全性・失敗モードの情報は不足)
metaphor
04 / 14
実行＝クエリ
起動中に SELECT
SELFでは“起動したプログラムが自分のファイルをSQLiteとして開き”、テーブルを読み取って動作を決めます。さらにUPDATE/INSERTで同じファイルを更新できます。
読み取り
routes や body を SELECT して応答生成
GET → SELECT → HTML
書き込み
visits/presses を INSERT して状態保持
POST/クリック → INSERT → 永続化
ここでの言い換え（JP gloss）: container＝容器、self-update＝自己更新
architecture
05 / 14
binfmt_miscで切替
カーネルが 解釈器
binfmt_misc のような仕組みで、SELF形式にマッチした実行時に“別の解釈器（interpreter）”へ切り替えます。そこでSQLiteテーブル行をセグメントとして扱い、エントリポイントへジャンプします。
起動
カーネル → interpreter 呼び出し
argv[0] を SELFファイルとして扱う
実行
SQLテーブルから状態/資産を取得
routes / visits / presses
SELFの狙いは「形式（バイトレイアウト仕様）」を「データベース（クエリ可能）」へ読み替えることです。
evidence
06 / 14
self-httpdの実演
1ファイルで Web
self-httpdは証明コンセプトとして、SQLiteが1つの実行ファイルを“Webサーバ”に見立てます。ファイル内テーブルを読み取り、訪問やボタン押下を同ファイルへINSERTして状態を保持します。
routes
ルーティング（path→実装/ body）
visits
訪問ログ（INSERTで増える）
presses
ボタン押下（押した回数/履歴）
外部永続領域（/var, /tmp, home 等）を介さず、自己完結した状態管理を狙えるのがポイントです。

トランザクションで整合
UPDATEは 巻き戻せる
SQLiteのUPDATE/COMMIT/ROLLBACKにより、再起動なしの“ライブ更新”が可能になります。本文では routes.body 等を書き換えて、失敗すれば巻き戻す挙動が示唆されています。
例：内容更新
routes.body を UPDATE → GET結果が変化
self ← UPDATE ← self
例：失敗時
トランザクション境界で整合性を維持
COMMIT / ROLLBACK
ここが“単なる自己書換”ではなく、整合性を守る仕組みとして重要です。

08 / 14
デプロイがSQLへ
scp1本 vs SQL移行
通常のデプロイは「新コード」と「旧ログ/状態」を別物として扱いがちです。SELFは、同形式のSELF同士で状態テーブルをINSERT…SELECTで移す方向に寄せます。
従来
コード更新＋状態移行（工程が分離）
backup/restore, migrations
SELF
同一SQLite形式間で状態を移送
ATTACH old → INSERT INTO … SELECT
監査も sqldiff により差分を要約できる、とされています。
distinction
09 / 14
handlersが実装になる
SQL行が ルーティング
handlersテーブルのように、SQLの行（パスとSQL）をルーティング実装そのものとして扱える例が挙げられます。これにより、プログラム構造がDBスキーマやクエリに寄っていきます。
宣言
INSERT INTO handlers で path と実行内容を紐づけ
handlers(path, sql, …)
実行
GET/POST が対応行を参照して応答生成
SQLが“分岐表”になる
Bilingual（JP gloss）: routing＝経路指定、schema＝構造定義
distinction
10 / 14
実運用は未解決
安全性が 未提示
SELFの魅力（自己更新・SQL統一）に対して、運用上の安全性に関する情報が本文では十分でないと指摘されます。並行アクセス、破損耐性、復旧手順、権限、改ざん耐性、スキーマ移行などが課題になり得ます。
自己書換の失敗モード（電源断・クラッシュ時の復旧）
複数プロセスでの同時書き込み制御
ファイル権限/読み取り専用/署名検証との整合
DDL（スキーマ変更）を含む更新互換性
外部入力がSQLに影響する場合の対策
監査ログの完全性と攻撃面の増加
トランザクションは助けになりますが、工学的ガバナンス（復旧・検証・安全設計）までセットで評価が必要です。
closing
11 / 14
結論：研究価値大
次は 検証する
SELFは「データベースの道具立て（クエリ・トランザクション・監査・FTS）を実行ファイル側の能力として再利用する」方向性を示しています。self-httpdのように“1ファイルで完結する”デモがあり、可能性は強いです。
強み
コード/状態の統合、デプロイのSQL移行化、監査（sqldiff）、FTS5の内蔵可能性
判断に必要
同時実行・破損復旧・権限/署名・スキーマ進化・セキュリティ境界の体系的検討
