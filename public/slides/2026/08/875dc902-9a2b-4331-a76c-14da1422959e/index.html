diffusion型開発ワークフロー
拡散して固める
NAWCは、粗いアイデアを段階的に精密化し、意思決定と根拠をノートに蓄積しながら実装チケットへ落とし込むプロセスです。
Key
意図と証拠（evidence）保持
圧縮ではなく、判断の追跡可能性を残す。
Flow
refine → evidence → ticket-ready → implement
質問→検証→決定→実装へ橋渡し。

04 / 18
diffusionの比喩
粗い考えを広げる
diffusion（拡散）とは、最初の粗い考えが少しずつ広がり、最終的に堅牢なノートや実装計画になる流れです。
i
粗いアイデア
粗案（あらあん）
ii
refineで精緻化
段階（だんかい）
iii
証拠へ変換
検証（けんしょう）
変化は失敗ではなく、ワークフロー内で“育てる材料”として扱われます。
diffusion / 拡散from rough → robust
ARCHITECTURE
05 / 18
基本構成
ノートが意思決定の場
NAWCでは、ノート・チケット・プロトタイプ/テストを軸に、設計の決定と根拠を結びつけます。
ノート（notes）
判断と根拠の蓄積
質問→回答→意思決定を記録。
チケット（tickets）
実装の独立単位
依存関係つきで分解し、readyへ。
証拠（evidence）
プロトタイプ/テスト
実行可能例・テストで検証。
Implement
決定事項に従う更新
コード/ノートを変更しチェック。
Artifacts / 成果物notes • tickets • evidence

PROCESS
07 / 18
ブロッキング質問
疑問を1つずつ
refineでは、重要な論点に対してブロッキング質問を1つずつ投げます。回答は意思決定としてノートに記録されます。
なぜ分割？
矛盾と負担を減らす
一度に大量の質問は破綻しやすい。
得られるもの
意思決定（decision）
後で追跡できる形で残る。
各回答は「設計上の選択」として扱われます。
Questioning as designblocking • 1-by-1

証拠への変換
decisionsをevidence
重要な判断は、プロトタイプ・実行可能例・テストなどの“検証物”に変換されます。これが根拠（evidence）になります。
Prototype
interactive prototypes
試して学ぶ形で設計を確認。
Example
runnable examples
実行できる形で挙動を確かめる。
Test
tests（検証）
期待通りかを機械的に確認。
「なぜその仕様か」「何が確認されたか」を追跡できます。
evidence traceabilityprototype • examples • tests

ENUMERATION
12 / 18
NAWCの“伸び”ポイント
5つの要点
NAWCの中心価値は、粗い案を検証可能な設計に育て、意思決定と根拠を保持し続けることです。
i
粗案→検証可能へ
refineで質問と回答を通じて具体化。
ii
decision×evidenceを残す
プロトタイプ/例/テストで追跡。
iii
チケットで文脈保持
分割の利点を活かし、理由を失わない。
iv
implementはチェック付き
ready後に更新し、整合性を確認。
v
ノート語彙と補助スキル
interactive prototypes等で整合を上げる。
意図保持が中核
単発指示の文脈喪失を抑える。
Value summarykeep intent • keep evidence

14 / 18
批判的な見方
コストは見えにくい
refineの往復（質問→検証→再質問）が増えると進行が遅れるリスクがあります。また、成功指標・失敗時の扱いがこの抜粋だけでは明確ではありません。
Risk
質問と検証の増加
“いつ終えるか”が不足すると遅延。
Missing
ガードレールが不明
上限設定やready判定の基準は別資料確認が必要。
導入時は関連ドキュメントで運用基準を必ず確認してください。
cost managementguardrails • stop criteria
