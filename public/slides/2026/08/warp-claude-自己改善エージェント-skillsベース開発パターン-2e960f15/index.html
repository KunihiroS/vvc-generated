Skillsで“学習”を開発に接続

Warp×Claude

自己改善型エージェントを、プロンプトではなく Skills（スキル） の更新として運用する設計パターン。
内側：base skill（実行）／外側：improver skill（観察・編集）で、フィードバックを次回に引き継ぐ。
problem
03 / 18
“残り20%”がノイズ化

セッション消失

最初のプロンプトで約80%はできても、残り20%がノイズになりユーザー体験が悪化する。
根本
フィードバックが次回へ届かない
セッション終了後に評価・修正意見が消え、同じミスを繰り返す。
結果
単発対応ではスケールしない
応急処置（その場の調整）では、改善が蓄積されない。
metaphor
04 / 18
“学習”をPRにする

改善は積み上げ

自己改善を「学習アルゴリズムのブラックボックス」にせず、スキル更新として増幅させる。
中心
フィードバック → 編集案
人間の結果・評価を観察し、base skillへ“最小で的確”な編集を提案する。
運用
PRで承認・マージ
変更履歴を追跡し、「何を採用したか」を説明可能にする。
architecture
05 / 18
二層ループ

base と improver

base skillは安定した実行知識、improver skillは観察と編集案の生成役として分離する。
i. base skill（内側）
業務ドメインの手順
例：PRレビューの作法・判断軸。
ii. 実行
エージェントが作業
成果物（コメント等）を生成する。
iii. improver（外側）
人間フィードバックと突合
編集提案をbase skillへ。
process
06 / 18
スケジュール実行

次回へ持ち越す

改善ループは「セッションの外」で回し、蓄積されたフィードバックでスキルを更新する。
入力（人間）
レビュー結果・修正意見
どこが良くないか／どう直すべきか。
出力（システム）
base skillへの提案
最小編集案→PRレビュー→マージ。
二度目以降は更新されたbase skillを参照し、時間とともに精度が上がる（学習の継続）。
evidence
07 / 18
“ファイル化”の力

Skills＝更新可能な設計

スキルをプロンプトへベタ書きせず、参照させることで更新・レビュー・統合を既存フローに乗せる。
従来の課題
プロンプト修正は履歴が曖昧
誰が・何を・なぜ変えたかが追いにくい。
改善点
スキル更新がPRになる
レビュー可能で、採用理由も説明しやすい。
enumeration
08 / 18
運用のコツ

小さく・原則で

品質向上には「原則中心」「whyの説明」「フィードバックを入れやすく」「スキルを小さく」「improverへ工数」が効く。
設計
原則中心で書く
判断基準を一貫させ、ばらつきを減らす。
説明
理由（why）を明示
フィードバックが“改善に変換”されやすい。
データ
フィードバックを入れやすく
摩擦が高いとデータが集まらない。
構造
スキルを小さく保つ
変更単位が管理しやすくなる。
improver側に工数をかける（観察→編集案の質を上げる）。
distinction
09 / 18
量より質

シグナル設計

サムアップだけでなく「なぜ良くないか／どう直すか」を含むフィードバックほど価値が高い。
良いフィードバック
理由・修正方針がある
改善に直結しやすい（編集案が具体になる）。
悪いフィードバック
“良い/悪い”だけ
根拠が弱く、改善根拠の学習が進みにくい。
さらに、PRやIssueなど「既に作業している場所」に導線を作ると、自然にデータが残る。
comparison
10 / 18
検証可能性で評価を変える

verifiable対応

ドメインが検証可能なら自動評価で調整し、検証不能なら人間評価は専門家に限定してノイズを避ける。
検証可能
参照コーパス／ゴールデン出力
自動評価→調整。
検証不能
人間評価は専門家に限定
洪水入力を避ける。
目的は「誤った学習（ノイズ学習）」のリスクを抑えること。
architecture
11 / 18
適用範囲を拡張

レビュー以外へ

このパターンは、仕様書作成・レビュー・トリアージなど複数のエージェントへ拡張された。
文書
仕様書作成
原則とwhyで品質を安定させる。
品質
レビュー
フィードバック→スキル更新。
運用
トリアージ
判断軸の改善で誤検知を抑える。
distinction
12 / 18
Skills と メモリ

別物として運用

Skillsは「手順や方針（どうやってXするか）」を保持し、意図的に更新する安定要素。
Skills（スキル）
更新・レビュー・統合が主役
参照され、改善ループの対象になる（運用できる学習）。
メモリ
推論時に自動で書かれがち
常に変化し、Skillsと同粒度では扱いにくい。
comparison
13 / 18
懐疑も必要

誤強化の恐れ

自己改善ループは魅力的だが、フィードバックが偏るとスキルが誤った方向へ強化される。
記事の抑制策
間違う前提＋人間の関与
そのまま従わず、文脈で妥当性をチェック。
未確定点
採用基準と評価の頑健性
どの誤りでどう収束するかの具体は不足。
evidence
14 / 18
導入価値は“統制”

PRでガバナンス

スキル更新をPRレビューに載せることで、変更を統制し、監査に耐える形で改善を回せる。
Practical（実務）
運用が“通常の変更”になる
承認プロセスに適合。
Risk（リスク）
権限・誤入力の混入
専門家限定・フィルタ・最終レビューが必要。
Governance（統治）
人間が最終承認
マージされたスキルだけが次回へ反映。
さらに、因果検証（テスト／ゴールデン／AB／メトリクス）の用意を最初に確認すべき。
closing
15 / 18
要点まとめ

次回に効く改善

自己改善の本質は「セッション後に消える問題」を、Skills更新の開発プロセスとして解消すること。
核心
base（実行）× improver（編集）
観察→最小編集→PR承認→マージ。
条件
量より質／検証可能性で評価
ノイズ学習と誤強化を抑える設計。
この型は、レビューだけでなく仕様書作成・トリアージにも横展開できる。
