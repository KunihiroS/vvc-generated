本番の壁を越える
Agent × 分散設計

エージェントはHTTPの寿命に閉じ込めると壊れやすい。QueueとWorkflowで「実行の寿命」と「意思決定の履歴」を分けて、復旧可能にする。

problem
03 / 17
HTTP待ちが危険
タイムアウト地獄
エージェントは長時間稼働・状態保持・非決定的（同じ入力でも分岐し得る）。この性質をHTTPリクエストの“待ち”に結び付けると、信頼性が崩れる。
起きること
タイムアウト / 接続寿命 / 中断 / 途中クラッシュ
結果
重複実行 / 復旧不能 / 期待と違う挙動
architecture
04 / 17
寿命を分離する
Web-Queue-Worker

APIは実行開始だけを行い、ジョブをQueueに投入する。ワーカーが非同期に実行し、進捗はDBへ記録することでHTTPと寿命を切り離す。

API
開始受付 → Queue投入 → 即応（HTTP）
Worker
実行・ツール呼び出し・進捗更新（非同期）
distinction
05 / 17
Queueは正しさをくれない
冪等性が要る

Queueは“ある程度”の実行を保証するだけで、論理的に何を途中までやったかまでは面倒を見ない。at-least-onceでは重複実行が起きる前提で冪等性が必須になる。

前提
at-least-once（重複実行し得る）
設計
副作用に“同じ結果になる境界”を設ける（idempotency）
enumeration
06 / 17
失敗時の巻き戻し
補償（Saga）

途中停止や部分成功に備えて、補償（compensation）を設計する。サーガ（Saga）では「戻す/整える」手順を副作用ごとに用意する。

ステップ
外部操作・課金・通知などを副作用として分離
失敗
どこまで成功したかを基に分岐
補償
部分失敗の扱い（全部巻き戻す/続行する）を要件化
process
07 / 17
分岐が増える
Workflow導入

分岐と復旧が増える局面ではWorkflowが必要になる。実行履歴を保持し、クラッシュ後に“同じ履歴に基づいて”再実行できるようにする。

履歴
実行ログ / ステップ結果 / 意思決定の根拠
再開
再起動しても履歴と矛盾しない
architecture
08 / 17
意思決定と副作用
分離が鍵

Workflowでは「意思決定（コーディネータ）」と「副作用（ステップ）」を分ける。コーディネータは同じ履歴なら同じ判断をするべきだと強調される。

コーディネータ
履歴から次アクションを決める（clock/乱数は注意）
ステップ
モデル呼び出し・外部操作は記録される副作用
再開時に、外部時間や揺らぎへ依存すると履歴と矛盾し得る（＝再現性の設計が必要）。
evidence
09 / 17
並列は一筋縄でない
fan-out / fan-in

並列化（fan-out / fan-in）では成功基準・失敗方針・統合の設計が重要になる。単に多重投入すると、待ち続けたり、結果の統合が壊れる。

失敗方針
成功しきい値 / 続行 / 中断を明示
同期
失敗が混ざる統合（Promise.allSettled相当の発想）
競合制御
レート制限・DB接続プール・バックオフ
comparison
10 / 17
自作配線 vs 構築済み
Render Workflows

Render Workflowsは、実行配線（キュー/ワーカー/ステータス/リトライ等）を抽象化する。タスク関数として書いたものをプラットフォームがチェーン実行する。

あなたが書く
タスク（関数）と、必要な意味論
平台が担う
実行・可観測性・再試行・分離の配線
distinction
11 / 17
肩代わりには限界
Semanticsは残る

Renderが簡素化しても、冪等性・補償・アーティファクト保管・承認境界・コスト上限・レート制御など“何を進捗とみなすか”はアプリ側の責務として残る。

プラットフォーム側
実行・履歴・リトライの運用レイヤ
アプリ側
意味論（整合性/安全性/ビジネス要件）
architecture
12 / 17
成熟した責務分担
三つの役割

成熟したアプローチは「インフラは運ぶ」「ワークフローは進捗を保存」「エージェントは次の行動を選ぶ」。責務の違いを保ったまま、運用負担を減らす。

Queue / infra
実行寿命の切り離し、配送
Workflow
履歴・再開・意思決定の再現
Agent
次のツール/行動を選ぶ（非決定性と向き合う）
closing
13 / 17
チェック姿勢
設計を詰める

パターンは“そのまま適用”ではなく、要件（部分失敗の許容、課金/通知の一貫性、承認、コスト上限）に合わせて責務分担を決める必要がある。

Q（要件）
何を成功とし、何を巻き戻すか？（idempotency / compensation）
S（運用）
再開時に同じ履歴で同じ判断になるか？（再現性）
