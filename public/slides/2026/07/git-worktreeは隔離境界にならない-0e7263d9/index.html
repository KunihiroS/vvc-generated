隔離境界
02 / 17
worktreeは“境界”じゃない
Git worktree
AIコーディングエージェントを並列実行するなら、worktreeを隔離境界として扱うのは危険です。
結論

隔離したいなら clone（特に --shared） を選ぶべき、という主張が中心です。

問題設定
03 / 17
並列エージェント
事故の種
複数のエージェントが同じリポジトリ由来で動くと、共有部分があるだけで“普通の操作”が他者に波及し得ます。

期待

worktreeで作業ディレクトリやHEADは分かれるはず。

実際

共有される .git の中身が隔離にならない。

見かけ
04 / 17
境界の錯覚
worktreeの穴
worktreeは分離しているように見えますが、隔離境界は “worktreeの外側にある .git 側” で決まります。

分離される

作業ツリー、HEAD/index、チェックアウト先の状態など。

分離されない

objects、refs、config、stash、hooks。

核構造
05 / 17
.git が支配する
共有 .git
hooksやrefsなどは .git側の状態として存在するため、worktree内の操作が他者に波及し得ます。

hooks

共通の実行入口。書き換えが危険。

refs

ブランチや参照の共有。更新が波及。

config/stash

作者情報や退避が混入・衝突し得る。

最大リスク
06 / 17
コード実行
hooks共有
worktreeから共有hooksを書き換えると、次回のコミット操作でホスト側権限で実行され得ます。
なぜ危険？

hooksは“コミット等のトリガー”なので、隔離したはずのエージェントがホスト上でコード実行を誘発し得る点が致命的です。

データ汚染
07 / 17
configの混入
作者情報
共有configにより、エージェントが user.email などを上書きすると“あなたのコミット”に混入する可能性があります。

期待

エージェント用の設定で完結。

実際

共有configを通じて利用者リポジトリへ影響。

作業衝突
08 / 17
stashの争奪
refs/stash
stashはリポジトリ単位で共有（refs/stash）に近く、別エージェントの stash pop が作業を奪取・上書きし得ます。

起こること

退避スタックの共有で、復元先がズレる。

結果

意図しない差分の適用・作業損失。

波及範囲
09 / 17
refsの連鎖
強制更新
refsやブランチ名が共有されると、強制更新や reset、gc など“普通のコマンド”で他worktreeへ影響が及び得ます。

例

branch -f / reset --hard

例

git gc / 参照の削除

反論処理
10 / 17
コスト神話
cloneは重い？
「cloneは重いからworktree」は誤解で、ローカルclone（hardlink）や --shared を使えばworktreeと同等レベルの負担で済む、という反証が提示されています。
選ぶ基準

性能ではなく“隔離境界の正しさ”を優先する、という方向性です。

推奨策
11 / 17
隔離の境界
clone（推奨）
並列エージェントの隔離には、worktreeより clone（特に git clone --shared）を推奨する、というのが結論です。

目的

共有される状態が減り、衝突面を縮小。

注意

完全無条件ではない（オブジェクト寿命など）。

運用チェック
12 / 17
落とし穴
--sharedの条件
clone（特に --shared）でも、オブジェクトストアへの参照依存があるため、寿命管理を要します。

影響

参照元が削除されると不整合の余地。

注意

強い gc が巻き込む可能性。

選択肢

--dissociate 等で独立させる余地。

まとめ
13 / 17
Takeaway
境界は .git
worktreeは作業面を分けても、共有される .git（hooks/config/stash/refs）が隔離を壊し得ます。
最短指針

並列エージェントの隔離境界は worktree ではなく clone（特に --shared、必要なら dissociate）として設計する。
