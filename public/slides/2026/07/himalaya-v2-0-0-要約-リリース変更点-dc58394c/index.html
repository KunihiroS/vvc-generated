Release Summary
02 / 16
v2.0.0 の要点を一気読み
himalaya v2.0.0変更点
メール操作CLI「himalaya」の v2.0.0 で、認証・コマンド構造・出力仕様・設定作法がどう整理されたかを要約します。
目標は「拡張しやすい土台」＋「運用での安全性」。 一方で破壊的変更も同時に入り、移行コストが発生し得ます。
Why change
03 / 16
統一インターフェース強化
共通化で 拡張を楽に
プロトコル差（IMAP/JMAP/Gmail REST/Microsoft Graph）を吸収しつつ、機械可読性（JSON Schema 等）と運用安全性を引き上げる再設計が入っています。
Claim
REST（Gmail/Graph）を本格統合
Claim
設定出力と入力の扱いを整流化
Claim
DNS/プロキシ/疎通の順序見直し
Claim
コマンド体系のフラット化
Architecture
04 / 16
認証を一本化
OAuth bearer前提
Gmail REST / Microsoft Graph REST は OAuth 2.0 の bearer token を単一トークンとして扱う設計で統合されています。
Gmail REST
profile / labels / messages / attachments / drafts / threads / history / settings
Gmail REST：表現力のある領域を追加
Graph REST
profile / mail-folder / message / attachment
Graph REST：メール基礎＋添付をカバー
Wizard
05 / 16
設定を stdout へ
TOML 出力の透明化
アカウントウィザードは、生成した設定を「ディスクへ書かず stdout に TOML」として出します。
Before（傾向）
勝手にファイルへ書く／出力が見えにくい運用
After（狙い）
コピー＆ペースト / リダイレクトで反映し、変更管理を容易に
さらに「存在するが目的アカウントがない config はウィザード再実行なしでハードエラー」のように挙動が明確化されています。
CLI Model
06 / 16
入力を一本化
MessageArg 統一raw
raw-message の扱いが MessageArg に一本化され、ファイル指定／インライン／stdin を共通の入口へ統合します。
source
file（ファイル）
source
inline（本文直指定）
source
stdin（パイプ）
IMAP コマンドツリーのフラット化や、旧フラグ（例：--file など）の置換の可能性もあるため注意が必要です。
Command Tree
07 / 16
imap をフラットに
階層整理 破壊的変更
IMAP のサブコマンド構造がトップレベルの動詞へフラット化され、コマンド呼び出し順やフラグ前提が変わり得ます。
狙い
学習コストの低減・実装の統一でバグ源を減らす
影響
スクリプト自動化／旧オプション依存ユーザーは移行調査が必要
例：imap の呼び出し順、messages add の旧 --file フラグ 等が変化対象になり得る
Networking
08 / 16
DNS は鎖で試す
漏洩回避 運用配慮
DNS は Cloudflare へ直行せず、まず system DNS resolver を試す鎖に変更されています。
DNS fallback
system DNS →（続く）フォールバック
Socket proxy
unix:///path 形式でソケットプロキシ経由の接続をサポート
SASL ネゴシエーションを行わない（既に認証済みセッションが来る）前提も明確化されています。
Output
09 / 16
JSON Schema で検証
機械可読 品質向上
structured-output の検証用途として json-schema <DIR> が追加され、スキーマファイル生成が可能になりました。
--json
下流ツールで期待形式をチェック可能
json-schema
型安全なパイプライン構築に寄与
Behavior
10 / 16
bare の意味が変わる
“bare himalaya” 変更影響
サブコマンド無しで実行したときの挙動が変化し、従来の envelope 一覧表示からアカウントウィザード起動へ置き換わります。
旧
デフォルトアカウントの envelope 一覧表示
新
アカウントウィザード起動
「一覧だけ見たい」人は、明示的な envelope listing コマンドへ移行が必要です。
FAQ
11 / 16
よくある疑問
移行判断の 要点まとめ
v2.0.0 は「追加」も「仕様変更」も同時にあるため、判断軸を先に押さえるのが近道です。
IMAP
不要ではない（REST は選択肢として追加）
stdout TOML
上書き抑制・原因追跡のしやすさに寄与
OAuth token
Gmail/Graph は bearer token が唯一の前提
IMAP ID-after-auth は RFC 2971 関連の癖を v1.2.0 系へ復元する趣旨で触れられています。
Opinion
12 / 16
強みとリスク
堅牢化 するが学習も必要
方針としては拡張性・透明性・運用安全性が同時に上がるのが強みですが、複数の破壊的変更が同時に入っています。
Strength
stdout TOML / DNS fallback / socket proxy / MessageArg 統一 / json-schema
Risk
bare 挙動・imap 階層・--file 削除・設定作法の変更で移行調査が必要
REST 導入では権限・仕様差（ラベル/フォルダ/添付粒度等）と例外時の挙動検証も重要です。
Closing
13 / 16
チェックリスト視点
次に見る
v2.0.0 は「共通インターフェース強化」と「運用品質の底上げ」。ただし移行は “どこが変わったか” を先に洗い出すのが安全です。
まず確認
1) bare 挙動 2) imap 階層 3) MessageArg 入力 4) wizard の stdout TOML
次に検証
1) Gmail/Graph の bearer token 運用 2) REST権限/例外 3) DNS/プロキシ環境
目的は同じ：メールを扱うCLIを 壊れにくく、拡張しやすくすること。
