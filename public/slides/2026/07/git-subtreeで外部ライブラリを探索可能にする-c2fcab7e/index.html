導入手順（概略）

4ステップ

導入は「取り込み→境界線→パターン化→運用設計」の順で組み立てます。実装探索を“読みやすい状態”として固定します。
i. 取り込み
Git subtree でリポジトリをサブディレクトリへ
ii. ガバナンス
AGENTS.mdで参照目的・編集禁止・import禁止
iii. 成果物化
agent-patterns等で再探索を削減
iv. 運用設計
更新頻度・互換性・破壊的変更の扱いを決める

Q&Aを圧縮

subtreeの効果

subtreeにより改善されるのは、主に「文脈の欠落」です。ローカルで抽象のつながりや期待挙動を確認しやすくなり、断片検索よりイディオムに沿った実装になりやすいです。
ポイント：探索（code exploration）として理解できる度合いが上がる
Why：設計意図・周辺構造がローカルに存在するため

11 / 16

見落としの典型

node_modules問題

npmのnode_modulesにソースがあっても、足りない場合があります。構造が失われる/探索設定でnode_modulesや.gitignore配下が参照されにくい/結果として“読みやすい形”に到達しにくいことがあります。
理由（1）
コンパイルやフラット化で構造が消える
理由（2）
探索除外（node_modules / .gitignore配下）
Security/License：記事本文は深掘り不足（別途運用が必要）

負債も同時に

トレードオフ

vendoringはプロジェクト肥大化と更新責任を伴います。品質向上の見返りはある一方、陳腐化を防ぐ更新フローや破壊的変更への対応設計が必要です。
コスト
サイズ増 / 更新の手間 / CI・レビュー負荷の可能性
前提
更新ポリシー（頻度・安全性・互換性）を別途用意

参照ガイド（記事要旨）

読み替え

以下は本文から抽出した参照ポイントの要約です（外部URLは記載しません）。必要なら、あなたのプロジェクトでのAGENTS.md/更新ポリシー雛形に落とし込んでください。
1) “推測”ではなく“既存実装の探索”で品質を上げる
2) subtreeを推す理由：運用の煩雑さ（submoduleの初期化/間接化/.gitmodules）回避
3) AGENTS.md等で境界線（参照用途・read-only・編集禁止・import禁止）を明示
4) agent-patterns等でパターン集を作り再探索コストを削減
5) トレードオフ：肥大化と更新責任。更新フローを設計して陳腐化を防ぐ
Bilingual: 境界線 = boundary（境界線） / 更新ポリシー = update policy（更新ポリシー）
