失敗の原因

制御ループ

観測・検証契約
エージェント（自律ツール実行）の失敗は「推論力」より「フィードバック設計」を疑え。決定的な状態差分を返せないと、ログが詩（poet）になり事故に進む。
Agent failure ≠ reasoning failure → feedback control loop failure
PROBLEM
02 / 14
何が起きるか

詩が増える

ツール実行の後に返る結果が曖昧（または遅い）だと、次の行動の根拠が足りない。モデルは「たぶんこう変わったはず」と物語化し、incident channelにpoetが出現する。
兆候
成功ログは積み上がるのに、状態遷移が現実とズレる
根因
観測が遅い／前提が古い／自己申告の成功を採用する
METAPHOR
03 / 14
制御として見る

次の一手

エージェントは「計画して実行する存在」ではなく「状態を観測して更新する制御器」だ。成功とは“実行した”ではなく“状態が契約通りに変化したと検証できる”こと。
Pre
事前状態（pre-state）を同じ基準で観測
Tool
ツール実行（API呼び出し、外部ゲート含む）
Post
事後状態（post-state）差分で確定
ARCHITECTURE
04 / 14
必要な契約

状態差分

各ツール境界で「決定的なstate delta（状態差分）」と「境界付きsuccess（成功/失敗/unknown）」を返す。0/1成功ビットだけでは、分岐の契約にならない。
State delta
検証可能な差分（observed post-stateが境界）
Bounded signal
上限付き成功：success / failure / unknown を型で
Decision step uses contract, not model “story”
ENUMERATION
05 / 14
型で返す

三分類

successだけで前進させない。重要なのは機械が次の行動を選べる分類を返すこと（unknownを“許可なし”として扱う）。
success
適用が確定（差分が検証可能）
failure
差分が検証できず、理由カテゴリも型で
unknown
次の意思決定に進む権利なし（再観測/隔離へ）
EVIDENCE
06 / 14
なぜ0/1不足か

検証できない

0/1成功は“理由”も“次の分岐”も足りない。差分が再現可能で、かつ成功の定義が機械検証可能である必要がある。
ダメな例
「200 OKだから成功」＝観測不能なまま次へ
必要
pre/postの同基準観測＋効果境界で合意
DISTINCTION
07 / 14
境界を分ける

200≠成功

ツール側の“受け付け（accepted）”と、業務上の“適用（applied/confirmed）”は一致しない。非同期・外部ゲートでは特に、効果境界（effect boundary）で検証が要る。
Tool boundary
呼び出し結果（accept、受付、キュー投入）
Effect boundary
状態が変わった事実（適用済みの確認）
PROCESS
08 / 14
観測の鮮度

provenance×freshness

署名（provenance）があっても安全ではない。観測時刻・経路・キャッシュ/サンプル条件（freshness/admissibility）を分離してゲートする。
provenance
出所の信頼性（誰が/何で観測）
freshness
鮮度（sampled_at、期限、整合性）
admissibility
意思決定に使ってよいかの適格性
DISTINCTION
09 / 14
二重のずれ

観測×効果

観測レイヤ（何を見たか）と実効レイヤ（何が起きたか）がズレると、検証は意味を失う。だから“検証可能な差分”は観測の出所と効果の境界にまたがる。
観測のズレ
古い前提、キャッシュ、サンプル条件の混入
効果のズレ
受け付けのみで、業務状態は未確定
ARCHITECTURE
10 / 14
不可逆を制御

effect class

決定的差分でも、不可逆な結果へ進めば事故になる。rollback可否や効果の種類（idempotent / compensatable / irreversible）を契約として表現し、誤った楽観を遮断する。
idempotent
再実行しても同一効果
compensatable
補償（相殺）が可能
irreversible
取り返し不可→ゲート厳格化
PROCESS
11 / 14
リトライの契約

再試行を限定

リトライは“推論で許す”のでなく、ツール/効果契約に基づき限定する。retriability や lease（期限付き許可）を状態差分・境界と一体で返す。
retriability
再試行してよいケースだけを許可
lease
許可の期間と失効条件を契約化
EVIDENCE
12 / 14
規制で必須

金融・規制

TRID/ECOA、レートロック、DTI閾値などでは、鮮度のズレや根拠の欠落が違反や損失に直結する。ここでは「思想」ではなく生存条件として、観測・検証契約が要る。
TRID/ECOA
根拠と時点が意思決定に直結
レートロック
期限/条件の鮮度が結果を決める
DTI
閾値判定は前提の妥当性が命
COMPARISON
13 / 14
導入の注意

コストも増える

契約化にはツール実装コストと独立verifier（検証レイヤ）が前提になる。既存APIが境界・差分・型付き失敗を満たさない場合は、アダプタや追加観測が必要。
リスク
過度な厳格化で unknown が増え、探索/運用が止まる
追加負担
検証の同期/非同期設計、責任分界（SLA/オンコール）
CLOSING
14 / 14
最小単位へ

漸進的に

全部を決定的にするより「次の意思決定に影響する部分だけ」を厳密に契約化する。unknown/隔離で誤前進を抑え、効果境界とstate deltaを核に据える。
優先
state delta＋bounded success（success/failure/unknown）
抑止
effect boundary・effect class・provenance/freshnessで誤進行を遮断
（参考）Agent / control loop / feedback design を制御工学・分散システムの視点で見直す
