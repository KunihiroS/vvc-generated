資源で読む、7エージェント
省資源選び方
同一コンテナ・同一スクリプト前提の「harness resource bench」を、起動・メモリ・CPU・ディスク・TUI/headless・アイドル残りまで分解して読み解きます。
Bench（資源）
Startup / Memory / Install
起動時間・開始時メモリ・インストールサイズ。
運用（長期）
CPU / Idle / Disk
セッション中CPU・長時間のメモリ増・アイドル時のCPU・ディスク消費。
注：機能差により「資源が少ない＝総合が良い」とは限りません（同一でない可能性が明記）。
Problem
03 / 16
同じ勝負に見えて
前提が違う
同じ環境で同じ作業をしていても、エージェントは内部機能が完全一致しないことがあり、資源差の原因が「最適化」以外になり得ます。
比較の強み
コストの内訳が見える
起動・メモリ・CPU・ディスクを同じ測り方で分解。
比較の限界
成功率・品質は不明
資源効率だけで「完了率」や「出力の正しさ」は確定できません。
結論：資源ベンチは「選定の土台」には強いが、「総合断定」には追加データが必要。
Metaphor
04 / 16
資源＝燃料、仕事＝距離
燃費で見る
同じ距離（同じ作業）でも、車（エージェント）ごとに必要燃料（CPU/メモリ/ディスク）が違います。あなたの制約（待ち時間、CPU上限、ストレージ、放置運用）で最適車が変わります。
短期回転
Startup軽量
都度起動→短作業で効く。
制限下CPU
TUI/CPU最適
描画やストリーミング負荷を抑える。
長時間放置
Idle安定
作業後の無駄な負荷を抑える。
“headless / TUI”は、燃料の種類（UI描画コスト）に相当します。
Architecture
05 / 16
何を見ているか
指標地図
このベンチの「資源」は、起動コスト・常駐/初期常用・実作業コスト・長期挙動・保存コストの5系統に分けて解釈できます。
立ち上げ
Startup / Init memory
例：起動時間（ms）、開始時メモリ（MiB）。
導入と残骸
Install / Session disk
例：インストールサイズ（MiB）、ディスク消費。
処理中
CPU time / CPU use
TUI・streaming・Terminal CPU time など。
長期運用
A long session / Idle
長時間のメモリ増、アイドル時CPUの残り方。
“UIあり/なし”で、CPUが別系統として現れやすい点が重要。
Evidence
06 / 16
fx：最軽量で先頭
起動が勝つ
fxは起動時間・開始時メモリ・インストールサイズで最小クラスで、「都度起動して回す」ワークフローに強い傾向です。
Startup
7.0ms
“立ち上げ待ち”を最小化。
Start memory
5.8MiB
初期の常駐が小さい。
Install size
12.2MiB
導入フットプリントが軽い。
fxは「短い作業の回転率（回すほど効く）」に適性。
Evidence
07 / 16
pi：TUIとディスクが軽い
UIコスト抑制
piはTUI関連のCPU時間が最小クラスで、実作業中のCPU負荷やセッションのディスク消費も相対的に軽い傾向です。
TUI CPU time
1.36s
描画・表示の燃費が良い。
Disk footprint
7.4MiB
ログ/履歴の増え方が抑制。
作業中CPU
相対的に低め
ストリーミング処理の寄与が軽い可能性。
piは「CPU上限」「ログ膨張」「保存制約」がある現場向け。
Evidence
08 / 16
smelt：headless×長時間
放置に強い
smeltはheadless運用でのCPU時間、長時間セッションのメモリ増、アイドル時CPUの低さが目立ち、「暴れにくい」運用に向きます。
Headless CPU
121ms
UIなしの処理が軽い。
Long session
64ターン付近
メモリ増の最小域がある。
Idle CPU
0.5ms
放置時の無駄負荷が小さい。
smeltは「端末UI不要」「長く回す」「待ち時間がある」運用向け。
Comparison
09 / 16
勝ち軸が違う
3系統整理
fx / pi / smeltは、それぞれ「起動」「UI/ディスク」「headless/長期」へ軸足があり、総合ではなく“用途で選ぶ”のが筋です。
fx
Startup最軽量
都度起動・短期回転。
pi
TUI/ディスク軽量
CPU上限・保存制約。
smelt
headless/Idle安定
長時間・放置運用。
Claude Code / opencodeは資源軸で不利に見える点があり得るが、総合は別途検証が必要。
Distinction
10 / 16
TUIとheadlessは別物
描画がCPUになる
headlessは端末UIを使わず、TUIは端末上の表示/出力描画を含みます。さらに Terminal CPU time（tmux描画コスト）が分かれている点が、差の出方を決めます。
headless（無UI）
表示コストを削減
CPU時間の見え方が変わる。
TUI（端末UI）
描画がCPUに転換
TUI時CPUやTerminal CPU timeが支配しやすい。
→ piがTUI寄りで強く、smeltがheadlessで強い、という整合が取れます。
Process
11 / 16
選定の手順
用途から決める
資源ベンチを「どこがボトルネックか」の答えに使います。最初に運用形態（短期/長期・UIあり/なし・放置あり/なし）を固定しましょう。
i / 短期
fx（Startup優先）
都度起動で待ち時間を減らす。
ii / 端末UI
pi（TUI/CPU/ディスク）
描画や履歴の増加が制約。
iii / 長期・放置
smelt（headless/Idle）
無UIで長く回し、アイドル負荷を抑える。
iv / 最終確認
成功率・品質も見る
資源だけで総合最適を断定しない。
ローカル環境：Ryzen 9 7900Xでの傾向として解釈する（他環境では再確認）。
Distinction
12 / 16
“Resource”で分かること
できること/できないこと
このベンチは主にコスト（CPU時間、メモリ、ディスク、起動など）を測ります。成功率や出力品質、再現性はこの情報だけでは確定できません。
わかる
計算・保持・保存の負担
CPU/メモリ/ディスクの内訳と長期の増え方。
わからない
成果系（成功率・品質）
完了までの回数、仕様遵守、レビュー工数は別指標が必要。
中央値中心
分散が読みづらい
最悪ケースの体感は別途。
機能差
同一比較でない可能性
資源が少ない理由が能力以外のことも。
補うべき
完了率・品質
再現性（別日/別負荷条件）も。
“資源効率＝総合勝者”は誤りになり得ます。
Closing
13 / 16
最終結論
用途適合
このベンチが一番強く示すのは「どの運用形態で使うか」です。fxは起動、piはTUI/ディスク、smeltはheadless/長期・Idleで、それぞれ“効く場所”が明確です。
fx
Startup最軽量
短期回転の第一候補。
pi
TUI/ディスク軽量
CPU上限・保存制約で有利。
smelt
headless/Idle安定
長時間・放置運用に向く。
次に欲しい追加情報：成功率（完了率）、出力品質（不具合/レビュー工数）、再現性。
