アイドル時間で“夢”が効く

Claudeの agent memory

記憶は保存ではなく、整理・検証・表現設計・階層化まで含むシステムとして設計されるべきだ――という主張を、dreaming中心に圧縮します。
（日本語補助）dreaming＝夢のような再整理 / salience＝重要度 を軸に読みます。
Problem
03 / 17
ログは増えるだけ

保存の罠

単に過去ログやノートを溜めるだけだと、誤り・陳腐化が混入し、探索コストが増えて性能が下がり得ます。
Failure mode / 崩れ方
無差別保存 → 記憶が古くなる・探すのに時間がかかる
Core fix / 核
dreamingで再構成→誤り修正→将来参照しやすい形へ整理
Metaphor
04 / 17
人間の分業に近い

記録と睡眠

人の脳では「その場での記録」と「睡眠中の整理（統合・修正）」が分かれます。記事も同様に、AIの長期記憶へ役割分担を持ち込みます。
Writing / 書く
セッション中：重要候補をメモリに残す（ただし誤り得る）
Sleeping / 夢見る
アイドル時間：dreamingがログ/逐語記録を照合し、整合性を上げる
Architecture
05 / 17
書く・読む・直す

memory hierarchy

agent memoryは階層（上位に短く・下位に詳細）を取り、上位注入は小さく抑えて、必要時に下位へ誘導します。
Up / 上位
小さな“注入コンテキスト”（毎回載せる量を抑える）
Dreaming / 夢
詳細を再整理→誤り修正→参照しやすい表現へ
Down / 下位
トランスクリプト/逐語ログや根拠、wikiへのリンク

salienceが勝負

重要度 salience

記憶ノートは初期に誤りや陳腐化を含み得ます。そこで、何を残すかの判断（salience）が性能を左右します。

Sonnet 3.7：膨大なメモリ → 状態変化で古くなる → 探索に時間が奪われ停滞
Fable 5

失敗→ルールへ

学習ループの 閉路化

記憶を単なるメモにせず、失敗の分析を検証済みルールとして保存すると、長期タスクで伸びが出ます。
CL-Bench
正誤を受けて“失敗分析→ルール化→次へ再利用”したモデルほど改善
記録内容
「なぜ判断できるか」「罠の警告」まで含めると再利用性が上がる（Opus 5系）

08 / 17
dreamingの位置づけ

予測ではなく整合性

記事の趣旨は、dreamingが次の行動を直接予測するというより、アイドル時間にログ/逐語記録を再整理して誤りを直す後処理に近い、という点です。
入力
セッションのトランスクリプト（逐語ログ）
出力
誤り修正された記憶＋将来参照用の表現（wiki等）

ゲーム攻略の分岐

Mt. Moonの罠

dreamingは誤った記憶を逐語ログと照合して修正できるため、ゲーム攻略の分岐を外さない改善につながります。
without fix
誤りが残る → 次セッションで同じ罠に再突入
with dreaming
ログ照合 → 誤記修正 → 分岐ミス回避

wikiが“地図”になる

表現（wiki）を 育てる

wikiのような“記憶表現”をdreamingで段階的に構築すると、複数文書を跨ぐ質問や法務系タスクで検索単独より成績が上がることがあります。
Stainless
大量文書コーパスでwikiを育成 → セッションとともに質問回答が伸びた
Harvey LAB
wiki利用は検索単独より有利な場面がある（複数文書結合が必要）
条件
単一文書で足りるタスクでは効果が薄いこともある
Comparison
11 / 17
注入はトークンを食う

上位注入 vs 根拠リンク

上位レイヤへ毎回載せる情報を増やすとトークンを消費し、誤った内容の“持続”リスクも上がります。だからdreamingで階層を調整し、上位を小さく保つのが要点です。
増やしすぎると
探索を減らす代わりに、トークン消費↑＋誤り注入が毎セッション参照され得る
設計方針
上位は短く（要点のみ）／詳細は下位へリンク／dreamingで誤りを下ろす
Takeaways
12 / 17
設計チェックリスト

“部品”で考える

agent memoryは「書く・読む・直す・表現する・階層化する」の組み合わせで性能が決まり、dreamingはその統合を支える裏側の計算です。
i Writing / 書く
何を残すか：salience判断をタスクに合わせる
ii Dreaming / 夢
ログ照合で誤り修正し、整合性を上げる
iii Representation / 表現
wiki等で参照しやすくし、リンクで階層を作る
Closing
13 / 17
一般化の注意

“夢＝常勝”ではない

dreamingを入れれば常に良くなるわけではなく、タスク特性（変化しやすさ、検索で足りるか、複数文書統合が必要か）を見極める必要があります。
