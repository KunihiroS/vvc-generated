02 / 16

checkout不要の発想

gitfold / ブランチを“フォルダ化”

Gitのブランチやコミットを、コピーや checkout なしで「ファイルとして見せる」仕組みです。

中心アイデア

FUSE（仮想ファイルシステム）でマウント

向く場面

巨大モノレポ / 並行ブランチ / エージェント

problem
03 / 16

“展開コスト”が死活

checkoutの重さ

通常の Git は、ブランチ/コミットを見に行くたびに checkout（作業ツリー展開）や worktree を作ります。

問題

巨大モノレポだと展開時間・ディスクが膨らむ

並行で悪化

並行レビュー/エージェントが増えるほど相対的にコスト増

metaphor
04 / 16

コピーではなく“直参照”

読み取りを 先送り

gitfoldは「データを複製して持つ」のではなく、「必要になったら読む」方向で設計します（コピー回避）。

Git側

オブジェクトDBからスナップショットを読ませる

FUSE側

ファイルシステムをユーザー空間で仮想化

ユーザー側

ディレクトリ（フォルダ）として扱える

architecture
05 / 16

2種類のディレクトリ

@<rev> と <branch>

gitfoldはスナップショット（読取専用）とワークスペース（編集可能）を分け、変更コストを最小化します。

スナップショット

@<rev>：読取専用（GitオブジェクトDB参照）

ワークスペース

<branch>：編集可能、変更分だけ .git/gitfold/ に保存

architecture
06 / 16

コストは“変更分だけ”

差分保存が 要

編集していないファイルはオブジェクトDB側を参照し、変更した分だけ実ファイルを持ちます。

読み取り

未変更は参照（参照コスト中心、複製しない）

書き込み

変更分のみ .git/gitfold/ に退避（差分コスト）

process
07 / 16

“linked worktree”風

既存ツールに 寄せる

gitfoldは linked worktree として振る舞うように登録し、エディタや `git status`、`rg` などの体験を近づけます。

運用感

編集・保存を通常の作業ツリーに近い感覚で

相互作用

commit / push などGit操作とも整合を狙う

検索

`rg`（ripgrep）でコード探索しやすくする

enumeration
08 / 16

並行タスクの分離

セッションごと ワークスペース

エージェント（例：Claude Code）向けに、セッションごとにワークスペースを用意する発想が示されています。

目的

レビュー/タスク並列で衝突を減らす

仕組み

プラグインが worktree作成やツール利用前にフック

comparison
09 / 16

強みは“開く速さ”

高速起動 × ディスク削減

読み取りは Git オブジェクトDBから直参照するため、巨大リポジトリでも「開くまでが速い」「ディスク使用量が抑えられる」と主張されています。

checkoutの代替

展開コストを回避し、並行数が増えるほど効きやすい

設計思想

スナップショット（読取）＋差分保存（編集）

distinction
10 / 16

万能ではない

checkoutと 完全一致しない

FUSE経由の書き込み遅延や、LFS/フィルタ/サブモジュールなどの差分があるため、置換はワークロード依存です。

性能

書き込みはネイティブより遅い

レイテンシ

初回アクセスは decompression 等で遅くなり得る

互換差

LFS/フィルタ/サブモジュールで挙動が異なる

evidence
11 / 16

制約が“具体的”

LFS / .gitattributes / submodule

説明上の差分として、LFSファイルはポインタ扱い、`.gitattributes` フィルタを反映できず、サブモジュール初期化ができない等が挙げられます。

Git LFS

ファイルがポインタとして扱われる

フィルタ

`.gitattributes` フィルタを適用できない

サブモジュール

初期化ができない

process
12 / 16

導入前に見たいこと

自社ワークロードで 検証

期待通りになりにくい点があるため、書き込み量・初回レイテンシ・LFS/サブモジュール依存を先に確認するのが重要です。

必須チェック

LFS有無 / `.gitattributes` フィルタ / サブモジュール利用

体感への影響

小ファイル大量生成・CIビルド・起動頻度（短命ジョブ）

closing
13 / 16

結論

“置換”ではなく 適材適所

gitfoldは巨大リポジトリ×並行開発×エージェントで強く、checkoutの完全代替ではなく制約込みで判断するツールです。

向く

コピー回避・差分保存・複数リビジョン同時アクセスが多い環境

注意

書き込み遅延 / LFS・フィルタ・サブモジュール差分がボトルネックになる場合
