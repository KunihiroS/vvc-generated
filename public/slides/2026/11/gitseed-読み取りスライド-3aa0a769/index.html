信じない前提
GitSeedが目指す あなたが支配する SDLC
AIエージェントを“実行対象”として使いながら、権限と検証責任を分離し、署名付きガバナンスで監査可能にするコントロールプレーンです。（Japanese gloss: 信頼できないAI = trusted-less agent）
problem / 問題
03 / 14
AIには権限が危険
信用問題
AIコーディングエージェントはアイデアは強い一方、悪用・情報漏えい・不正コミットの可能性が常に残ります。さらに監査不能になると、後から「何に基づいて何が入ったか」を追えなくなります。
リスク
権限過剰 / 監査不能 / 情報漏えい / 不正PR
必要条件
隔離・検証・署名・承認ゲート
architecture / 全体像
04 / 14
3相コンテナで隔離
prepare → agent → finalize
開発を3相に分け、エージェント側にGit資格情報を持たせないなどで権限を分離します。コミットや検証はfinalize側で確定し、検査→PR反映の経路をクリーンに保ちます。
i prepare
入力（Seed）を準備し、実行条件を整える
ii agent
創造的生成（ただしGit credsなし等の制約）
iii finalize
blocked_paths / 秘密スキャン / 確定処理
狙い
“信用しないAI”でも、責任の所在を人間側へ寄せる

05 / 14
5段階 + 速度ルート
Ideate→Plan→Execute→Review→Merge
基本は5段階で追跡し、急ぎのバグ修正向けにFast-Track（Execute→Review→Merge）も用意されています。どちらもfinalize側の検査や署名・承認ゲートを維持する設計です。
通常

Fast-Track

PRを“出所証明”へ
Ed25519 Governance Receipt
PRごとに、ロックされた仕様、使ったモデル、支出モード、セキュリティ検査、そして人間の承認状況を署名レシート化します。CLIでオフライン検証できるため、監査性が大きく上がります。

07 / 14
AIに鍵を渡さない
隔離設計の要点
エージェント側でGit資格情報やdocker socketを持たせず、コミット・検証はfinalize側へ寄せます。さらにblocked_pathsチェックや追加行の秘密スキャンを実施してからPRへ反映します。
agent側
Git credsなし / docker socketなし / non-root UID制約など
finalize側
blocked_paths / 秘密スキャン / 確定（クリーンな経路）
distinction / 二系統運用

人間の承認ゲート
レビュー前に止める
通常フローではReviewで観測し、承認ゲートを通してからMergeへ進めます。Fast-Trackでも短縮しつつ、署名・検査・承認の“最後の関門”を残します。
ゲート
最終的な反映は人間の承認＋署名レシートの確認後
観測

最大3モデルで比較
同じステージで複数モデル/エージェント案を比較し、承認へ進む前に差異を洗い出します。単発生成より見落とし低減に寄与する可能性が狙いです。

12 / 14
権限の境界
Personal Modeの制約
Personal Mode（cli_oauth）は単一ユーザーに紐づき、owner_user_idによって他ユーザーが接続・実行・閲覧できない設計です。無効化設定（GITSEED_ALLOW_PERSONAL_CLI_OAUTH=false）もあり、チーム利用やCIはAPIキーや推奨構成へ寄せます。
仕組み
owner_user_idでアクセス境界（接続・実行・閲覧）
運用
チーム/CIはAPIキーや別手段を推奨（Personalは限定）
closing / 結論
13 / 14
方向性は良い
導入は精査から
GitSeedは「信用しないAI」を明確に前提化し、3相コンテナ、署名付きレシート、レビューゲートで監査可能な開発へ寄せています。一方で、README入力だけでは検出精度や残存リスクの具体数字が不足するため、SECURITY.md等で評価結果を確認し、PoCで検証するのが安全です。
強み
権限分離 / 署名レシート / レビューゲート / SSRF対策の考え方
要確認
秘密スキャンの偽陰性 / blocked_pathsの網羅性 / 攻撃耐性の評価ログ
Takeaway：アイデアはAIに任せ、確定と検証は“人間の管理下の経路”に集約する。これがGitSeedの狙いです。（Japanese gloss: あなたが支配するSDLC = human-controlled SDLC）
