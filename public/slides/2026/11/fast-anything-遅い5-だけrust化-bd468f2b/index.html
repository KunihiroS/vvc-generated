遅い一部だけ移植

fast-anything

大規模アプリを全面的に Rust 化せず、ボトルネックの“遅い部分”だけを部分移植します。実データで同等性（値一致）を確かめてから差し替えます。
鍵
Proof, not vibes（証拠）
目的
速い・安全・可逆
Problem
03 / 16
全面移行は重い

なぜ難しい

全面 Rust 化はコスト（移行・検証・運用）が大きく、回帰リスクも増えがちです。そこで狙うのは「遅い一部だけを、元と一致させて差し替える」現実解です。
よくある失敗
正しそうだが遅い / 稀な入力で壊れる
必要条件
値一致の検証＋差し替えの可逆性
Architecture
04 / 16
段階的・可逆

scan→port→verify

fast-anything は、時間がかかる関数を特定し、Rust クレートを生成し、記録した呼び出しをリプレイして一致確認します。有効化は `enable`、戻すのは `disable` です。
scan
プロファイルで候補をランキング
port
最大500件の呼び出しを記録→1関数だけ移植
verify
リプレイして値・境界条件・エラー一致
enable
条件を満たしたときだけ差し替え
disable
局所的に元へ戻す（リスク管理）
Workflow
05 / 16
“どれを”決める

移植対象の選定

候補は「時間へのインパクト × 移植しやすさ」でランキングされます。コアは“外側ループを Rust 側へ運ぶ”ことで、Rust への呼び出し回数を減らす点です。
ポイント
インパクトが大きい“外側のループ相当”を狙う
注意
内側だけ移植すると FFI 往復で遅くなり得る
scan → port [id] → verify → enable / disable
Evidence
06 / 16
値一致で判定

“同じ結果”

バイト列一致ではなく、計算結果としての同等性を重視します。浮動小数は許容誤差（例：1e-9）内で比較し、エラーや境界値も一致させます。
浮動小数
許容誤差 1e-9、NaN / ±infinity / -0.0 も対象
境界条件
エラーの種類・発生条件、非ASCII、空/最大など
Testing
07 / 16
記録＋追加生成

検証を厚くする

最大500件の“実際の呼び出し”を記録します。加えて、tiny / random slices や境界入力を追加して、単なるリグレッション固定を避けます。
実呼び出し
最大 500 件（portの対象関数1つ）
追加ケース
tiny / random slices（入力サイズ縮小）
狙い
稀な落とし穴（境界・文字・例外）を拾う
Distinction
08 / 16
正しさだけでは不十分

遅くなるなら無効

移植結果が正しくても、FFI 往復コストや呼び出し回数次第で遅くなることがあります。fast-anything は「速くないポートは有効化しない」方針です。
理屈
Rust 呼び出し回数が増えると境界往復が支配
運用
性能逆転を検知→差し替えを見送る
Comparison
09 / 16
内側 vs 外側

効果は移植単位

ベンチマークでは、内側のレベンシュタイン“計算だけ”より、外側ループを移植した方が大きく速くなりやすいと説明されています。理由は Rust 側へ呼ぶ回数が激減するためです。
内側だけ
呼び出し頻度が高く、FFI 往復が増えがち
外側ループ
境界往復をまとめ、実効性能が伸びやすい
Results

実測で示す

fuzzy dedupe

提示例では、Python / TypeScript / PHP / Go / Ruby / C# / JavaScript などの「fuzzy dedupe」系処理で大幅な高速化が示されています。Java は JVM 起動コストの影響が出る可能性も言及されています。
対象例
fuzzy dedupe 系
言語例
Python / TS / PHP / Go / Ruby / C# / JS
補足
Java は起動コストが影響し得る
FFI
11 / 16
クロス言語設計

Cブリッジ方式

fast-anything は FFI で Rust 側を呼びます。C の入口関数 1つを JSON の入出力で接続し、各言語から共通のブリッジ経由で呼び出す方式が採用されています。
接続
FFI → Rust ライブラリ（Cの入口 + JSON）
成否要因
Rust化の単位／検証条件／遅くなるケースの扱い
Risk
12 / 16
導入時の論点

保証の限界

検証は強いですが、完全保証ではありません。記録期間の入力分布が代表的でない場合や、長期運用特有の並行性・タイミング依存のバグは検知しきれない可能性があります。
要確認
記録期間の代表性、稀入力、並行負荷、巨大データの上限
設計上の注意
JSON/シリアライズが支配してメリットが縮む場合も
（SYCL / デバイス実行はホスト関数側が対象で、期待効果が限定され得る）
Closing
13 / 16
結論

5%だけRust化

fast-anything は「部分移植＋実データ検証＋可逆な差し替え」で、雰囲気最適化を避けるアプローチです。導入では“どの関数を移植するか”と“検証の代表性”を押さえることが重要です。
得られるもの
同等性の根拠（値一致）と性能安全性（遅ければ無効）
