safe でも起きる

信頼の置き違い

Rust 標準ライブラリの unsafe が守るべき前提（安全契約）が崩れると、ユーザの safe Rust からでも未定義動作が誘発され得ます。

（Japanese gloss）信頼の置き違い：前提（contract）を誤って期待してしまうこと

Problem
02 / 16
なぜ“safe”で事故？

標準の unsafe

Rust 言語は所有権・借用・型で多くを防ぎますが、標準ライブラリ内部は性能のために unsafe を多用します。

言語保証
safe API の安全契約が破られない前提
現実
unsafe が前提を守ることで成り立つ（前提破りで崩れる）
Metaphor
03 / 16
契約＝座標

unsafe は前提で走る

unsafe は「ここでは決して起きない」「必ず整合する」といった条件を信じて高速化します。信じる座標（不変条件）がズレると安全は成立しません。

信じる
不変条件（invariants）
崩れる
panic / unwind、実装者の契約違反
結果
未定義動作（Undefined Behavior）誘発
Evidence
04 / 16
AI が“穴”へ

FORGE Lab の探索

Microsoft FORGE Lab は AI 支援スキャナ（Hyenas / MDASH 系）で、Rust 標準ライブラリ内の unsafe 実装に起因するメモリ安全性バグを報告しました。

観測
多くは safe Rust のみで誘発し得る
示唆
標準が保持する前提が崩れると保証が完全には移らない
Architecture
05 / 16
3パターンで整理

“信頼”の置き違い

バグの構造は主に 3 領域に整理できます：panic/unwind、ユーザ提供実装（trait 等）、OS/C 境界の状態です。

i
panic が起きないと信じる
ii
呼び出し元の実装を正しいと信じる
iii
OS / C と共有状態が維持されると信じる
Distinction
06 / 16
i: panic safety

早期脱出の穴

panic が「そのタイミングでは起きない」と信じ、不変条件を一時的に壊したままユーザコードや破棄処理が走ると危険です。

何が起きる？
panic / unwinding により、通常経路とは別のタイミングで drop が実行される
なぜまずい？
“壊れた状態のまま” メモリ操作や不変条件前提の処理へ進むと未定義動作になり得る
Distinction
07 / 16
ii: trait 契約

safe でも正しくない

ユーザが提供する trait 実装・比較関数・パターンなどが、論理契約を満たすと仮定すると破綻します（safe でも“正しさ”は保証されない）。

危険な前提例
比較が整合している／返り値が契約を満たす
破綻の方向
unsafe 側が検証せず高速パスへ → 前提違反 → 未定義動作
（例示の文脈：sort のように非整合でも未定義動作にならない領域もあり、設計差が鍵）
Distinction
08 / 16
iii: OS/C 境界

外部状態が揺れる

sigaltstack、environ、exit のクリーンアップなど、プロセス全体の状態が期待通り維持されると信じると見落としが起きます。

例1
シグナルスタック無効化×メモリ解放（munmap）の噛み合い
例2
exec / environ のロック整合
難所
型システムが直接追跡できず、並行性・タイミング依存
Process
09 / 16
どう設計で潰す？

契約を明文化して守る

実務上の焦点は「unsafe が信じている前提を、どこで検証／保持／ガード／型で封じるか」です。

panic/unwind
panic が来ても不変条件が壊れたまま drop へ渡らない設計（ガード、ManuallyDrop 等）
trait/外部実装
“safe でも正しくない” 前提を置き、必要なら検証・制限・設計で無効化
OS/C 境界
境界条件を仕様化し、探索可能な状態空間としてモデル化して継続検証
全体
高速化と安全契約（invariants）を切り分け、守る箇所を固定する
Comparison
10 / 16
言語 vs 実装

どこが保証される？

Rust は safe を守る言語仕様を提供しますが、標準ライブラリは unsafe 契約に依存するため「周辺コード・実装者・OS 境界」が結果を左右します。

Rust 言語
安全性の枠組み（所有権・借用・型）
標準ライブラリ
unsafe による高速化＋不変条件の維持
外部要因
panic/unwind・ユーザ実装・OS/C 状態
Closing
11 / 16
学びの中心

“危険”ではなく設計前提

本報告の主価値は、個別 issue よりも「unsafe が置く前提がどこで破綻するか」を再発しにくい設計観として三分類した点です。

強み
前提（契約）のズレを抽象化して共有可能にした
注意
発火確率・影響度・回帰リスクの比較データは限定的
結論：安全性の一般化より「前提が危うくなる領域」を学習する
