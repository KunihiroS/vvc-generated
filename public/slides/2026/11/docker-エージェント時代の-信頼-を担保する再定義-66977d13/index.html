軸

Problem
03 / 16
なぜ今「信頼」か
信頼の欠如
エージェントは状況を見て判断し、外部アクセスや変更を行います。だから「安全・統治・制御」を失わずに使えるかが本質になります。
問い i
安全を保ったまま活用できるか
問い ii
統治（governance）を組み込めるか
問い iii
信頼できる状態にできるか
Context
04 / 16
コンテナの強み
継承
Dockerは「どこでも同じように動く」移植性・再現性で10年以上の信頼を獲得してきたと主張します。
レガシー
再現性・標準化は継続
宣言
コンテナ中心のコミットは変えない
Core
05 / 16
Workloadではない
Actor
コンテナは従来の「処理実行（workload）」向け。エージェントは「判断・アクセス・変更」を伴う行為者（actor）です。
Workload
手順どおりに回る
Actor

必要なガードレール
隔離 / 統制
エージェントの自律性が増えるほど、セキュリティ、隔離（isolation）、ガバナンス（governance）が従来以上に重要になります。
Security
権限暴走・サプライチェーン対策
Isolation
ホストや他実行からの分離
Governance
ポリシー・監査・制御

Docker SandboxesはマイクロVMとして説明され、コンテナではなく「分離された実行環境」を提供する方向です。
特徴 i
各サンドボックス独自カーネル
特徴 ii

特徴 iii

Architecture
10 / 16
統制を掛ける
AI Governance
Docker AI Governanceは、サンドボックスのネットワークやファイルアクセスをポリシーで統制し、監査の可視性も扱うとされています。
統制対象
Network / Fileアクセス
運用要素
監査可視性・MCPガバナンス
MCP（Model Context Protocol）の組織横断統制に言及あり。
Distinction
11 / 16
何が違う
Trustの中身
Dockerが掲げるtrustは、単なる「安全な実行」ではなく「監査・制御・サプライチェーン安全」まで含む広い概念として扱われます。
セキュリティ
隔離＋権限の暴走抑制
ガバナンス
ポリシーで許可を設計
可視性
監査できる（検証可能）状態
Caution
12 / 16
導入時の見極め
評価は別
記事だけでは、境界条件・監査粒度・脅威モデルへの対応関係などが検証できません。導入判断は追加資料と実測評価が必要です。
足りない可能性
trustの保証範囲・限界
求めるべきこと
テスト設計 / 第三者検証 / 運用責任
Closing

次の一歩

コンテナの価値を土台にしつつ、エージェント時代のtrustを「隔離＋ガバナンス＋監査」へ具体化するのがDockerの方向性です。
