02 / 16
Agent Optimization Toolkit
AOT Kit
LLMエージェントの改善を「エビデンス（証拠）駆動」で試せるようにする、Claude Code向け最適化ツール群の概要です。（最適化＝optimization）
重要点：良さそうな案を並べるのではなく、各改善に「適用条件・計測・必要な証拠レベル」を紐づけます。
problem
03 / 16
なぜ“計測”が要る
Eval 必須
エージェント改善は、変更の効果が「主観」になりやすく、再現性も崩れます。AOT Kitは“何を見れば良いか”を設計の一部として扱います。
よくある問題
評価が曖昧 / 失敗の再現ができない / いつ効くか不明
AOT Kitの狙い
シグナル→測定→証拠→意思決定 を一つの単位にする
architecture
04 / 16
知見と生成を分離
Library / Skill
知見はlibraryに集約し、生成物（Claude Codeスキル）はそこから自動生成する、という分離設計です。更新時の整合性とレビューの焦点が整理されます。
library
最適化（optimization）知見の本体：測定・根拠・影響
skill
libraryから生成する実装の器（現状はplaceholder）
運用
make render / make check で更新の整合性を維持
enumeration
05 / 16
段階的に試す
Tier 設計
変更の性質に応じて Tier 1〜4 を使い分け、危険な構造変更をいきなり推奨しません。まずは小さく安全に、次に効果と信頼性を確認します。
Tier 1
Hygiene（手堅い衛生改善）
Tier 2
Reliability（失敗率など信頼性改善）
Tier 3 / 4
Tuning（調整） / Restructuring（構造変更）
※Status: placeholders とされており、自動の検知→適用→測定は未完の可能性に注意。
process
06 / 16
改善の“単位”
Evidence First
各optimizationは、適用条件・観測するシグナル・測定方法・証拠レベル（evidence tier）をセットで記録します。これで「試すべき変更」と「測り方」がズレません。
適用条件
いつ効きそうか / どんな状況で当てるか
シグナル
エージェントコード上の何を見ればよいか
測定 / 根拠
どう測るか / どの出典・数値が支えるか
enumeration
07 / 16
改善の例（抜粋）
Bound & Stop
例として、ツール入出力を上限で縛る・ループやスタールを検知して早期停止するなどの“失敗耐性”系があります。
bound-tool-output
ツール出力の上限で暴走・肥大化を抑制
detect-loops-and-stalls
ループ/スタール検知→早期停止（fail-fast）
どちらも「実行予算・挙動制御」と相性がよいタイプです。
comparison
08 / 16
品質を上げる段取り
Verify
単に生成を整えるだけでなく、引用の真偽検証のように“答えの根拠”を後段で扱う発想が入っています。これで誤りを回収しやすくなります。
verify-citations
引用の真偽を検証して信頼性を上げる
restructure-system-prompt
不要要求を減らすためにシステム部を再構成
verifier cascade
多段検証で誤りを段階的に落とす
enumeration
09 / 16
安全・信頼の最適化
Fail-safe
LLMエージェントの事故はコスト・リスクに直結するため、不可逆アクションのゲートや未検証入力の封じ込めなどが重視されます。
fail-soft
失敗しても全停止せず、影響を小さく収める
contain-untrusted-input
未信頼入力を囲い込み、危険な拡散を抑える
（入力→実行までの間に“検査”を置く設計に近い考え方です）
architecture
10 / 16
複数エージェント分担
Breadth
単一エージェントの深掘りだけでなく、多段検証（cascade）や複数エージェントによる分担で探索幅を広げる方針も含まれます。
multi-agent for breadth
複数役割で探索を分散し、見落としを減らす
verifier cascade
“検証”を段階化してコスト対効果を調整
意思決定
Tierとevidence tierで推奨段階を管理
evidence
11 / 16
強み：再現可能な改善
Scientific→Practical
AOT Kitの最大の強みは、改善案を“知識”ではなく“測定設計”込みで扱い、属人的な試行錯誤を減らす方向に寄せている点です。
Scientific
測定方法・証拠が最適化に紐づく（主観評価を抑制）
Safety / Reliability
ループ・タイムアウト・検証・ゲート等を厚く扱う
（さらに運用面では、library/生成物分離で更新とレビューを整える設計です）
distinction
12 / 16
注意：プレースホルダー
未完リスク
この抜粋ではStatus: placeholdersであり、スキルがあっても“エージェント検知→適用→測定”の一気通貫自動フローは未整備の可能性があります。導入前に評価基盤の準備度を確認してください。
不足し得る点
evidence tierの厳密定義 / 指標の式・閾値 / 実行時限界 / evalの再現手順
導入判断の観点
ログで失敗モードを把握できるか / evalを再現できるか / Tier 1から検証できるか
closing
13 / 16
次の一歩
Tier 1 から
AOT Kitは「エージェント改善を、エビデンスとともに運用へ落とす」ための枠組みです。まずはTier 1（Hygiene）から、シグナル計測とevalの再現性を満たす形で段階的に試すのが妥当です。
①ログ確認（失敗モード）
②eval設計（測定）
③Tier検証（推奨段階）
