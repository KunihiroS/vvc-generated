Agentic Coding性能・効率レポート
高効率の 密型
Ricursive Intelligence は Ripple-65B Preview（オープンウェイト）を公開し、TerminalBench 2.1 で 80.52（米国SOTA相当）と主張しています。 「コード生成」だけでなく、ツール実行や修正を含む“手順”の遂行能力が主題です。
推し所は、(1) MoEを避けたdense設計、(2) SFT→RL＋合成データで効率化、(3) 学習レシピの段階改善、です。

Architecture choice
05 / 16
MoEなしの密型
Dense Transformer
技術の核は、MoEを避けた密型（dense）Transformerを採用し、学習・提供のインフラ複雑性を抑えつつ推論効率を確保する方針です。 “提供しやすさ”と“再現性”を意思決定として強調しています。
なぜMoE回避？
MoEは性能面の利点があり得る一方、運用・最適化の難度が上がりやすいです。 denseはサービス化の障害を減らしやすい、という論理が読み取れます。
推論設計の方向
低遅延・効率重視を狙い、さらに学習レシピも「計算効率」に重心を置くと説明されています。

SFT → RL、段階的改善
Model laddering
学習は SFT から RL へ進み、さらにモデルラダーリング（学習レシピの段階改良）で改善を積み上げたとされています。 4B以降でも効く介入があり、単発の工夫ではなく検証の反復が示唆されます。
i
SFT→RLの段階適用
ii
計算効率重視のRL設計
truncated IS / score centering / length penalty
iii
モデルラダーリングで介入を累積
pre+post norm / global NoPE / FFN等
iv
合成データパイプライン＋品質フィルタ
購入データ依存を抑制（と説明）

“学習データ設計”が効く
合成 × フィルタ
ポストトレーニングデータを購入せず、自前の合成データパイプラインと品質フィルタで効率化したと述べられています。 これは「性能×価格」の両方に影響しうる設計要素です。
合成データ
パイプライン構築

品質フィルタ
ノイズ削減
quality control / 誤り抑制
重要なのは、合成が“量”で勝つのではなく、品質指標とカバレッジ指標で学習の有効性を上げる狙いが示されている点です。

Takeaway
11 / 16
結論（今できる判断）
有望だが検証を前提に
Ripple-65B Preview は、Agentic coding向けに「dense設計・SFT→RL・合成データ・段階改良・長コンテキスト」を組み合わせ、性能と効率の両立を狙ったリリースです。 一方で、比較条件の詳細や $32M 主張の検証可能性、推論速度・メモリ条件が不十分なので、導入前のPoCを推奨します。
