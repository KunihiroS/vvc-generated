Agent Experience を“実行”で改善
Gauge CLI
自社プロダクトを使うAIコーディングエージェントが“どこで詰まるか”を実行ベースで特定し、修正→再テストまで回すオープンソースCLIです。 （エージェント体験 / Agent Experience）
読みどころ：ローカルで閉ループ（修正→計測→再テスト）を回せること、そして修正候補が Skill/ヘルプ/コード/ドキュメント等に広がり得ること。
読み取り要約（出典：Gauge CLIの説明文・README要約、利用シナリオ、FAQ、考察）
problem
03 / 16
“テストでは見えない詰まり”
Why Gauge?
ユニットテストだけでは、AIエージェントが実際にSkillやドキュメントを読んで実行する際の“滞留ポイント”は見えません。 Gauge CLIは実行を通じて、どこで失敗・迷走するかを記録します。
従来
レビュー/単体テスト中心で、実行上の導線ズレを見落としがち。
Gauge の狙い
“使って詰まった箇所”を evidence として集め、改善ループへ。
前提：エージェントは指示（Skill等）を元に作業し、評価（eval）と分析（findings/judgments）を保存し、修正後に再計測します。
metaphor
04 / 16
詰まりを“デバッグ”する
Hillclimb ループ
Gaugeが回す中心は hillclimbing：修正→計測→再テストで、結果が本当に良くなったかを確かめます。 失敗だけでなく、改善の有無も同じケースで検証します。
i. 実行
エージェントがケースを走らせ、どこで詰まるかを観測。
ii. 記録
evidence（runs等）を保存し、findings/judgments を作成。
iii. 改善
修正→同ケース再走で、アウトカムの変化を評価。
狙いは“それっぽい修正”ではなく、改善が再現可能かを運用意思決定に使うことです。
architecture
05 / 16
ローカルで完結 / ホストで拡張
二つの モード
Gauge CLIはローカルモードで Docker 等により実行環境を立ち上げ、アカウントなしでも評価ループを回せます。 ホスト型ではセッション継続、共有、並列性、PRチェック等の運用機能が増えます。
ローカル
Dockerで実行。作業ツリーの変更や保存済みevalを使い、SQLite（.gauge/）に残せる。
ホスト型
共有・自動ジャッジ・測定のスケジューリング。認証済みMCP/API、Webフィクスチャ等。
FAQ要点：ローカルは Gauge account 不要、ホスト型はサインインが必要です。
evidence
06 / 16
評価と分析を“証拠”化
eval → findings
Gaugeは「何が起きたか」を evidence として保存し、criteria（判定基準）に照らして成功/摩擦の有無を評価します。 修正案の当たり外れを、読み物ではなく再計測で見にいきます。
Saved evals
評価（再実行）に必要な状態を保存（ローカルは .gauge/gauge.sqlite）。
Cases
実行条件・観測を保持する“ケース”。共有は gauge-cases/ 配下。
judgments
criteriaに基づきアウトカムを判定し、改善の有無を示す。
共有ケースは gauge.json でプロジェクト入力や自動化宣言を行う、と説明されています。
comparison
07 / 16
“詰まり”の典型
よくある 失敗
Gaugeが見つける問題は、単なるバグよりも“実行上の判断”に近いものが多いです。 そのため修正は多方面（Skill/ヘルプ/コード/ドキュメント/エラー）に及びます。
対話停止
対話的コマンドがエージェントの行動を止めてしまう。
古い依存
古いコマンドやAPIパターンに依存して進めない。
Skill不使用
必要なSkillがタスクで使われない（導線/説明不足の可能性）。
誤った制約主張
存在しない制約を自信満々に主張する。
意図WF破綻
複数コマンドにまたがるワークフローを理解できない。
原因の広さ
エラーメッセージ/Skill/ヘルプ/コード/ドキュメントのどれでも原因になり得る。
“正しい修正”は一つとは限らないため、Gaugeは修正案を事前に再検証する前提を置きます。
process
08 / 16
修正→再テストの現場手順
実行 サイクル
ローカルでは、作業ツリーのバージョンを投入し、共有ケースや保存済みevalと組み合わせて同一タスクを再計測します。 これにより“改善したつもり”を“改善だった”へ変換できます。
入力
Skill/CLI/SDK/MCP/API/ドキュメント（ケース定義に紐づく）。
観測
どこで詰まったかをトランスクリプト等として正規化し保存。
評価
criteriaに基づき outcome を判定（成功/摩擦/新規問題）。
修正
該当箇所（説明・ヘルプ・コード等）を直し、同ケースを再実行。
補足：Claude Code / Codex / Pi / OpenCode 等のイベントを共通形式に正規化する旨が述べられています。
distinction
09 / 16
共有と継続追跡
ローカル vs ホスト
ローカルは手元で完結し、手触りの改善に向きます。 ホスト型は共有・自動ジャッジ・継続追跡・拡張機能で、チーム運用を楽にします。
共有
共有ケース（gauge-cases/）でCIや他者に渡しやすい。
継続
ホストはセッションが継続し、追跡や結果共有が容易。
拡張
PRチェック・並列実行・認証済みMCP/API・Webフィクスチャ。
Webフィクスチャ：未公開のページでもエージェントが遭遇する内容をテストする目的。
enumeration
10 / 16
要点4つ
価値の 核
Gauge CLIの価値は、単発のレビューではなく“反復による改善の証明”にあります。
i hillclimbing
修正→計測→再テストをローカルで閉ループ化。
ii 正規化
複数エージェントイベントを共通トランスクリプトにして原因探索を効率化。
iii 修正範囲
Skill/ヘルプ/コード/ドキュメント/エラーまで“広く原因”を想定。
iv 分業
ローカルとホストで役割分担：自分で回す vs チームで回す。
一言：改善が“良くなったか”まで到達する設計思想が、意思決定に直結します。
evidence
11 / 16
運用の論点（読み取りの限界）
導入前の 確認
README情報だけでは、精度の担保範囲・実コスト・保存データの扱い・セキュリティ要件を判断しにくいです。 特にチーム運用では、ケース定義の誤りが“未改善の誤判定”につながり得ます。
コスト/性能
ホスト型のクレジット消費、並列実行、長期運用の性能指標は要追加確認。
データ/永続化
どのデータを永続化し続けるか、バックアップやクリーンアップ方針が不明。
セキュリティ
テレメトリは引数/プロンプト/ファイル内容を除外とされるが、Webフィクスチャ等で注意。
criteria
改善判断ロジックは設定依存。社内基準に合わせた criteria 設計が重要。
ベースライン測定があると、品質指標として運用しやすい（という示唆）。
problem
12 / 16
FAQを短く
よくある 質問
重要な前提だけ押さえると導入判断が速くなります。
Q1: アカウント要る？
ローカルは Gauge account 不要。ホスト型は login が必要。
Q2: Saved evals と cases
Saved evals は評価状態、ケースは実行条件/観測。共有ケースは gauge-cases/。
Q3: Webフィクスチャ
未公開ページ等、エージェントが遭遇する内容をテストするため。
Q4: テレメトリ
コマンド使用（コマンド名/タイムスタンプ/CLIバージョン/ランダムID）を収集。無効化：telemetry disable または GAUGE_TELEMETRY_DISABLED=1。
Q5（判断）：evidenceを criteria に照らし、元問題が消えたか/成功したか/新摩擦がないかを見る（詳細ロジックは設定依存）。
closing
13 / 16
導入の結論
Agent体験を資産化
Gauge CLIは、エージェントの“詰まり”を実行ベースで見つけ、修正→再テストで改善を証明するための基盤です。 criteria設計と機密管理を固めれば、プロダクトの導線/説明/実装品質を継続改善できます。
Practical（実用）
Dockerローカルで再投入テストが回しやすい。
Operational（運用）
SQLite (.gauge/) と共有ケース（gauge-cases/）でモデルが明確。
Safety（安全性）
テレメトリ無効化と、ホスト連携のデータフロー確認が要点。
次の一歩：小さな shared case を作り、ベースライン→criteria→修正→再計測で“改善の証拠”を積み上げる。
