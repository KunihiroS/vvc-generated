検証ループで 品質 を担保
Claude Codeチームの技術記事を、読みやすい形に圧縮しました。狙いは「テストを回す」ではなく、「doneを証拠で定義する」運用設計です。

03 / 16
並列化の壁
検証 がないと詰む
エージェントを大量に並列で回すには、成果物を人が全確認する手が破綻します。検証ループを自動化・形式化すると、品質確認の仕事が「証拠を見る」に置き換わります。
Without loop
人手で差分を追う必要が増え、並列化が成立しない
With loop
生成より検証がボトルネック化し、改善が回る
metaphor
04 / 16
“裁判”として設計する
テスト＝ 証拠
テストは単なる合否判定ではなく、学習信号（次の修正の根拠）でもあります。だからこそ、失敗の質（フレーク/遅い/軽すぎ）まで設計します。
Flaky
再試行の学習が歪み、「直した」ではなく「たまたま」が強化される
Too slow
探索回数が減り、原因特定が難しくなる
Too light
通るが本質が壊れる状態を許し、自己確認が信用できない
architecture
05 / 16
3つで“失敗モード”を潰す
E2E / Property / Diff
重要なのはテスト数ではなく、失敗しやすい観点ごとに異なる検証手段を組み合わせることです。記事では投資価値が高い3種を推奨します。
分類 狙い 見つけやすいズレ
E2E（End-to-End） ユーザー視点の実行フローで破綻を確認 完了条件の崩れ、繋ぎ目の破綻（ユニットの“通過”を覆す）
Property（不変条件） 必ず成り立つ制約を大量入力で破る 境界ケース、round-trip / idempotency / equivalence系の見落とし
Diff（差分） 新旧の挙動同等性を“旧をオラクル”に比較 移行・リライト時の意味のズレ、誤検知/見逃しの増減
evidence
06 / 16
E2Eが最優先になりがちな理由
E2E は“本筋”を掴む
E2Eは実際のユーザーの経路を通し、破綻の有無がはっきりします。ユニットが通っても全体が壊れる「部分正しさ」を見落としにくい点が決定打です。
Done condition
完了条件が明確で、成功/失敗の判断が“騙しにくい”
System integrity
繋ぎ目・副作用・フロー全体の破綻を拾う
distinction
07 / 16
Propertyは“仕様の骨格”で殴る
Property テストの効きどころ
プロパティは「壊れてはいけない制約（不変条件）」を言語化し、それを大量入力で破ろうとします。仕様が曖昧でも、制約として明確化できる部分に強いです。
round-trip
往復して元に戻る（変換の一貫性）
idempotency
繰り返しても結果が変わらない
equivalence
同等性（別表現でも同じ意味）を保つ
comparison
08 / 16
Diffは“旧が答え”のとき強い
差分テスト＝ oracle
差分テストは、移行やリライトで「新旧が同等であるべき」局面に有効です。逆に、振る舞い変更が前提なら、許容差設計を誤ると誤検知/見逃しが増えます。
When valid
本質的挙動が同等（旧システムがオラクルとして働く）
When risky
仕様が変わる（許容差・正規化・承認済み変更の設計が要る）
evidence
09 / 16
検証の“自己改竄”を防ぐ
検証ルールは 固定 する
検証コード（チェック）が改変できるなら、検証は無意味になります。記事では、レビュー/ゲート側のルールをベースブランチ側から参照し、自分で自分を裁けない設計にしています。
bilingual
anti-rationalization＝自己正当化/自己改竄を抑える設計（“チェックが信用できる状態”を守る）
process
10 / 16
停止条件で“自動化の限界”を切る
失敗が続くなら 人 へ
Claudeは失敗したら修正を試みますが、3ラウンド経ってもダメなら人に引き継ぐと線引きします。無限ループや過剰推論コストを運用側で抑える考え方です。
i
生成（Agent）→ローカル/ゲート検証
ii
失敗なら修正して再検証（ラウンド継続）
iii
3ラウンド後も失敗→人が判断・対応
enumeration
11 / 16
検証層も“監査”して改善する
verifier の チューニング
監査側（verifier）自体も定期的に調整されます。差し戻しやリバート等の実績を追跡し、判断基準を育てることで誤検知を減らします。
Record
レビュー判断・リバート・差し戻しをログ化
Improve
誤りのパターンを検証側へ反映（ルールを更新）
distinction
12 / 16
記事の結論：doneを“ルール”へ
検証層を 別システム に
検証を独立した層として扱い、証拠にもとづくdoneを定義します。さらに学びをルールへ昇格させつつ、過剰に肥大化させず維持するのが要点です。
Principle 何を守る/作る
done を定義 「通った」ではなく根拠（evidence）が揃った状態を完了条件にする
検証層の分離 成果物を作る層と、裁く層を混ぜずに責務を保つ
ルール昇格 失敗→学び→検証ルール更新を回し続ける
