agentbadge
01 / 16
Lighthouse for agents
AIエージェント準備度
リポジトリが、Claude Code / Cursor のような自律エージェントにとって「最初の60秒で理解・立ち上げ・検証」しやすいかを、0〜100で静的に採点し改善まで支援します。
（Agent Readiness / エージェント準備性）
problem
02 / 16
文脈不足が失敗を増やす
暗黙知の非表示
人間なら README、既存ドキュメント、対面の引き継ぎで暗黙知を補えますが、エージェントは「生ファイル」から推測するため、セットアップ手順や安全策を誤りやすくなります。
その結果、同じ失敗を繰り返しがちです。
solution
03 / 16
診断→スコア化→改善
agentbadgeの狙い
リポジトリを静的に監査し、準備度を決定論的に 0〜100 点へ分解して可視化します。さらに不足点に応じて改善アクション（主に AGENTS.md）までつなげます。
architecture
04 / 16
5つの柱で分解
Context / Setup / Verification / Guardrail / Tooling
スコアは5柱に分解され、エージェントが「何に詰まりやすいか」を機械的に切り分けます。改善の優先順位が立てやすい設計です。
（五本柱 / 5 pillars）
enumeration

評価の視点

導線は3つ
--badge / --fix / --json
ただ診断するだけでなく、README掲載用のSVG、AGENTS.mdの改善パッチ、CI/CDゲート用の機械可読出力を用意して、改善を運用に乗せます。
Badge

Fix

JSON
--json：CI/CD用の機械可読

08 / 16
重要なのは冪等
--fixの設計思想
不足点の修正を「冪等（重ねても重複が増えない）」方針で行うため、継続運用してもドキュメントが壊れにくいことが強調されています。
Before
人が分かっているが機械に伝わらない
After
AGENTS.mdを機械が理解しやすい形へ寄せる
comparison
09 / 16
一回の改善で終わらない
Lighthouse的な継続品質
スコアを可視化して PR/CI に組み込むことで、準備度の改善が継続する設計になります。品質指標としての扱いがしやすい点が実務的です。
変化を観測
スコア・柱別評価で差分が見える
行動に接続
--fix / --badge / --json で改善導線がある
distinction
10 / 16
強みと制約
対象技術の前提
提示情報では JS/TS 最適化が明示され、Go/Rust/Makefile 基盤の検知はロードマップとされています。導入時は「スコア妥当性（検知カバレッジ）」を確認する必要があります。
得意
JS/TS（検知・改善の一貫性が期待）
課題
Go / Rust / Makefile（現状はロードマップ）
risk
11 / 16
安全性の根拠は追加確認
誤検知・誤修正の扱い
静的監査は便利ですが、実行可能性（依存が揃うか、テストが確実に回るか）を完全には保証しません。さらに --fix が意図とズレた場合の運用（レビュー/ロールバック等）の詳細はこの抜粋からは不明です。
スコアの限界
30秒で回る保証は未確定
修正の限界
誤って安全策を弱める可能性はゼロでない
opinion
12 / 16
おすすめの入れ方
段階導入が安全
実運用では、まず PR ベースで導入し「スコアの再現性」と「パッチの安全性」を検証するのが現実的です。自動化の恩恵を得つつ、失敗時の安全網を用意できます。
Step i
スコアを測ってベースラインを取る
Step ii
--fixはレビュー前提で適用範囲を絞る
Step iii
ゲート（--json）へ拡張し、ロールバック運用を用意する
closing
13 / 16
結論は明確
文脈を“品質”にする
agentbadgeは、AIエージェントに必要な「機械向け文脈」を品質指標に変換し、可視化と改善導線（バッジ/パッチ/CI出力）まで用意します。導入前の注意点は、適用範囲と安全運用の設計です。
Value
作業しやすさを定量化し、改善を加速
Caution
検知カバレッジと修正の安全網は要確認
