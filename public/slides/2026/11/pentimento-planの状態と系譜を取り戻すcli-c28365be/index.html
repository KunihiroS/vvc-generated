Cover
02 / 17
planの記憶を取り戻す
pentimento。
AI開発支援ツールが残す plan を、本文だけでなく〈状態・意図・系譜〉として再構成するCLIです。
何がつらい？
planファイル名がランダムで、進行中・完了・不要の見分けがつきにくい。
何をする？
関連するトランスクリプトも手がかりに、派生情報を補い「木構造の履歴」に戻す。
Bilingual: 状態(state)・意図(intent)・系譜(lineage) / 既存plan群から推定・補完（backfill）。
Problem
03 / 17
探索コストが増える
ランダムなplan
planは残っても、どれが終わりで、どれが続きで、どれが方針転換なのか判別できません。“探す”時間が積み上がります。
問題1
ファイル名は意味を持たない（進捗が見えない）。
問題2
状態(status)は本文に書かれていないことが多い。
問題3
分岐（系譜）が残らず、意思決定の文脈が消える。
Bilingual: どれを追う？ / Which plan to continue? を見分けにくい。
Metaphor
04 / 17
失われた文脈を補う
pentimentoの役割
画の下絵を“下から見えるようにする”ように、plan群から状態と系譜の手がかりを掘り起こします。
状態（status）
進行中・完了・不要などを派生で復元。
意図（intent）
なぜその枝を切ったかを再解釈。
系譜（lineage）
parent（親）関係で履歴を木構造に。
backfill
欠けた派生フィールドを補い、以後の参照を安定化。
Bilingual: lineage(系譜) / intent(意図) / status(状態) 。
Architecture
05 / 17
二層：フロント＋派生
frontmatterと派生
planは手で編集できるMarkdown（frontmatter）を土台にし、status/lineage等は複数シグナルから派生（derived）して補います。
土台（手で編集）
フロントマターはプレーンなMarkdownとして残り、読み取り可能性を確保。
派生（derived）
Progressのチェック、Cursorのtodos、本文の文脈などを読み取り「最初に一致した規則」を採用。
補強（enrich）
トランスクリプトがあると精度が上がる。ない場合はフォールバックへ縮退。
上書き（set/pin）
必要なら set --status で明示的に修正し、pinで固定も可能。
Bilingual: derived(派生) / fallback(縮退) / pin(固定)。

何を根拠に復元？
シグナルの束
status/intent/parentは、plan本文だけでなく周辺の“痕跡”から推定します。トランスクリプトが鍵になります。
本文
他章の文脈、本文参照、supersededの扱い方。
Progress
チェックボックスの状態が進捗ルールとして効く。
Cursor/ todos
Cursorのtodosがstatus推定に寄与。
トランスクリプト
Cursor/Antigravityの作業記録から意図を補完（backfill材料）。
ファイル時刻
mtimeなどへフォールバックして運用継続。
推定の決定
複数候補の中で“最初に一致した規則”が採用される。
Bilingual: evidence(根拠) / heuristic(推定) / signal(シグナル)。
Process
07 / 17
整える道筋
list → tree → check
pentimentoは「閲覧」だけでなく、検索・ツリー可視化・整合性検証・補完まで一連で行います。
探索（find）
list / show / 検索で候補を絞る。
系譜（view）
tree <id> / --ancestors で枝をたどる。
補完（backfill）
欠けた intent/created/project/parent を埋めて以後を安定化。
検証（check）
vocabulary/lineage/status/tags の整合性を検査し、矛盾を検出。
Bilingual: process(手順) / integrity check(整合性検証)。
Distinction
08 / 17
置換も捨てない
supersededの思想
superseded（置換済み）をゴミとして上書きせず、意思決定の“記録”として木に残す設計です。
ありがちな失敗
過去の分岐を消してしまい、なぜ置き換えたかが追えない。
pentimentoの方針
長期案件で分岐を残し、後で見返せるようにする。
木の機能
tree <id> で置換前の枝も文脈込みで復元。
復元の目的
過去の回答が“既に存在する”状態を横断検索で再発見。
Bilingual: decision log(意思決定ログ) / superseded(置換済み)。
Evidence
09 / 17
実務で効く3点
回収できる価値
pentimentoが“探索から回収へ”切り替える、具体的な効能を3つに絞ります。
1. 過去の枝
長期インフラ移行のサブプランなど「後で必要になる過去」を再取得。
2. 後で戻る
完了したが今は追わない計画を、タグ/intentで管理して再発見。
3. 理由の横断
他プロジェクトの意思決定理由まで含めて、横断検索で見つけ直す。
Bilingual: discover(発見) / retrieve(再取得) / cross-project search(横断検索)。
Comparison
10 / 17
“ビューア”とは違う
役割の差
cc-plan-viewerのようなリアルタイムtodo表示とは異なり、pentimentoはplan全体の系譜推定・一覧・ツリー可視化を狙います。
pentimento
plan群の状態/系譜を推定し、木構造で履歴を取り戻す。
cc-plan-viewer
Claude Codeのtodo進捗をリアルタイム表示するデスクトップビューア。
違い
“進捗の見える化”よりも、“決定の履歴を再利用”することが中心。
今回の焦点
status/intent/parentを派生し、checkで矛盾も検出。
Bilingual: progress(進捗) / history(履歴) / reuse(再利用)。
Distinction
11 / 17
うまくいく理由
backfillと耐障害
トランスクリプトの形式が将来変わっても、frontmatterはプレーンMarkdownとして残り、派生はフォールバックで運用継続を狙います。
耐障害（fallback）
トランスクリプト不足でenrich精度が下がっても、mtimeや本文参照へ縮退。
上書きルール
statusはbackfill/フックが勝手に上書きしないなど、仕様上の意図を明確化。
検証（check）
dangling-parent / underivable-status 等の矛盾を検出し、修正へ導く。
運用設計
単なる表示で終わらず、set/backfillでデータを整えられる導線。
Bilingual: durability(耐障害性) / consistency(整合性) / repair(修復)。
Comparison
12 / 17
限界と注意点
精度・共有・透明性
トランスクリプト形式への依存、並行・共有・多作者のスコープ外、派生ルールが原因究明に必要なケースがあります。
リスク1
未公開トランスクリプト形式の変更で推定精度が低下する可能性。
リスク2
1オペレータ・1台のローカル前提。チーム共有には別途設計が必要。
リスク3
派生ルールとユーザー意図のズレで誤分類。原因追跡には診断情報が鍵。
Bilingual: risk(リスク) / scope(スコープ) / troubleshooting(原因究明)。
