Agents 連携の安全

transitive policies

ツール権限は各エージェントで設定しても、受け渡しで制約が落ちると機密漏えいが起き得る。 必要なのは「連携をまたいで強制できる」ポリシーの保持だ。

でも漏れる
各エージェントが「自分に割り当てられたツール権限の範囲内」で動いていても、チケット（要求）から始まる情報の組み合せで漏えいが成立する。 問題はモデルの区切り理解ではなく、受け渡しでの制約の保持だ。

04 / 18
権限は合成されない
composeしない
Writer / Reader / Sender のように役割別に許可しても、委任（delegation）の鎖（chain）では「制約が自動で合成されない」。 そのギャップを埋めるのが transitive policies（連鎖的ポリシー）だ。
Writer
チケット作成だけ
Reader
顧客DBの読み取りだけ
Sender
検証済みアドレスへ送信だけ
それでも攻撃者のチケット起点で、要約＋機密＋外部通信が一本の流れになる。

強制の場所
runtime
delimiters（区切り）をモデルが認識できても十分ではない。 権限（authorization）や情報流制約、行動履歴を「執行可能な形」で保持・検証するのは runtime（信頼できる実行基盤）の責務になる。

runtime寄り

06 / 18
transitive policies
3要素
transitive policies は「委任をまたいで生き残り、次のエージェント/ツールへ到達しても強制可能」な振る舞い制約だ。 最低でも次の 3 つを揃える。
i / Authorization
誰が何のために開始し、何が許可されるか
開始者・サービス/取得の範囲
ii / Info-flow
機密性・完全性の制約をラベルとして維持
要約しても“落とさない”
iii / Action history
参照回数や上限などのシーケンス制約
状態管理で追跡する
evidence

漏えいの成立条件
“一本化”
チケットが起点になり、要約（summarize）・転記（transcribe）・返信（reply）で情報が結び付くと、局所的に許された操作の組み合わせで漏えいが成立する。 重要なのは“命令の形”に見える受け渡しだ。
攻撃の起点

結び付ける要素
要約/転記/返信＋機密＋外部通信

理解 ≠ 強制
delimiters
区切り（delimiters）はモデルの解釈には役立つが、制約が守られないのは runtime が意味と制約をメタデータとして保持・検証しないからだ。 “区切りが示す承認範囲”が落ちると危険になる。

エンベロープで運ぶ
policy metadata
作者の立場は、エージェント間メッセージの中身ではなく「エンベロープ（ポリシーのメタ情報）」としてラベルと履歴ID等を保持すること。 同じ情報由来なら、テキスト表現が変わっても制約を変えない。
入力
開始者/目的（Authorization）
変換
要約・転記してもラベル維持（Info-flow）
出力

distinction
10 / 18
送信先の“検証”の罠
entitlement
送信先が検証済み（verified address）でも、受取人がその機密情報を受け取る資格（entitlement）を持つかは別問題。 runtimeは実データ流（どのラベルが含まれ、誰へ行くか）でブロックすべきだ。
検証（verified）
そのアドレスが誰に紐づくか
identity/ownership
資格（entitlement）
その情報を受け取る権利
confidentiality permission
enumeration
11 / 18
履歴がないと破れる
action history
「1日あたり10件まで」のような制約は、単発メッセージのラベルだけでは追跡できない。 runtimeが認証済み依頼者と紐づけ、セッションを跨いで上限を守る必要がある。
必要
依頼者ID＋参照/送信の状態管理
目的
回数制限・連続手順制約の強制

既存の委任標準は？
OAuth / MCP
RFC 8693（OAuth token exchange）は“confused deputy”を抑える方向性を持つが、統一的な機密ラベル伝播や委任チェーン全体での検証まで明確に規定されない可能性がある。 そのため、主張の中心（委任の受け渡しでのメタデータ保持と検証）は実装者の負担になり得る。

13 / 18
運用観点（筆者の論評）
チェックリスト
transitive policies は抽象要件として有用だが、運用ではラベル設計・相互運用・監査可能性・履歴状態管理まで詰めないと理論が現場で機能しない。 “由来の追跡”の粒度や、人間の例外承認の基準も重要になる。
Security
局所安全が連携で崩れる（confused deputy）
Operational
complete mediation（完全仲介）の導入負担
Governance
同意・規約・監査と直結（entitlement）
closing
14 / 18
結論
設計の芯
transitive policies は「連携をまたぐ制約の保持」を、モデルではなく runtime がエンベロープで強制するための枠組みだ。 最低でも Authorization / Information-flow restrictions / Action history をメタデータとして伝播し、実データ流で検査する。
Takeaway： “権限と機密ラベルは、テキスト変換後も生き残らせる。”
