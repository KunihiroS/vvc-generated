ボトルネック
推論待ち / 確認待ち

結果
並列化しにくい
METAPHOR
04 / 16
“賢さ”より“分業”

Excelのように組む

マルチエージェントは、モデルの賢さだけでなく「分解・引き継ぎ・検証」を作業設計として組み込む。著者は、それが“現場の基盤”になる可能性を示唆する。
単体AI（イメージ）
相談 → 生成 → 待つ → 修正
マルチAI（イメージ）
調査 / 実装 / 検証 / PR作成を分業
ARCHITECTURE
05 / 16
工程を分担する仕組み

オーケストレーション

成功の中心は、複数段の検証・監視・人の介入ポイントを含む“明示的なオーケストレーション層”。工程全体を回す設計が必要になる。
Step i
調査（ログ/テスト/差分理解）
Step ii
実装案（修正方針→コード生成）
Step iii
検証・PR（テスト/品質/監査用情報）

移植・改善が得意

価値は新規生成だけでなく、既存テストやログを手掛かりに“整合するように直す”能力にある。移植や性能改善など、地味だが広い作業で効く。
狙う入力
テストスイート / ログ / 仕様の痕跡
狙う出力
差分の修正案 / 整合性 / PR生成
COMPARISON
07 / 16
“人が書く”が縮む

役割が管理へ寄る

単体AIは人が最終的に書く比重が残りやすいが、マルチエージェントでは「チーム（AI部隊）が進め、必要時に人が判断」が増える。結果、人のスキル要求も変わる。
単体AIの傾向
実装中心 / 人の確認がボトルネック化
マルチAIの傾向
設計・承認・例外処理が中心になる

Opsも主語になり得る

監視・突合作業・照合ブレイクの原因調査などをOpsに寄せ、エージェントがログ解析から修正案まで進める未来像がある。チケット文化や作業形態が変わる可能性を示す。
領域
Observability（可観測性）
入力
ログ / アラート / 実行履歴
出力
原因候補 / 修正提案 / 手順案
DISTINCTION
09 / 16
金融は“統制”が本丸

信頼・統制が成否

エージェントが誤った意思決定をしたときの損失を現実の問題として扱う。監査、分離、手続き、レッドチーミングなど、事故時の設計が必要になる。
i
損失の現実：悪い判断は“可能性”ではなく“規模”が問題になる
ii
統制の設計：監査・分離・権限・手続きで暴走の確率を下げる
iii
検証の前提：どこまで自動化し、どこから人が止めるかを明確にする

推論コストは増える

inference費用が壁

推論コストが無視できず、運用設計次第でボトルネック化し得る。採用は技術進歩だけでなく、コスト構造とインセンティブの相互作用で進む。
コスト増の源
複数エージェント / 複数段検証 / 繰り返し
運用の示唆
バッチ化・呼び出し頻度制御・必要時のみ実行
PROCESS
11 / 16
PoCの勝ち筋を先に決める

導入は検証計画から

方向性は魅力的でも、成立条件の切り分けが不足しがち。小規模PoCで、失敗モード・責任分界・評価基準・ロールバック可能性を先に設計する。
検証 i
失敗頻度 / 検知速度 / 再現性
検証 ii
責任分界 / 自動停止 / 監査証跡
検証 iii
コスト最適化 / 実行回数 / 平均修正回数
CLOSING
12 / 16
結論：技術＋統制＋経済性

“導入できるか”ではなく“運用できるか”

マルチエージェントは、作業分解と統制設計を含むパラダイム転換になり得る。一方で勝ち筋は、技術だけでなくプロセス設計・統制・コスト最適化・人の役割定義で決まる。
One-liner
“AIが書く”から“AI部隊が進めて人が裁く”へ。
Key phrase
統制とコスト・リスクが導入の前提。
