AIネイティブCRMの輪郭
Relaticle 整理
本レポートは、README相当の情報から「仕組み・強み・注意点」を読みやすく圧縮した要点整理です。
Problem
02 / 12
CRM運用の“次”
AI連携
人がCRMへ入力するだけでなく、AIエージェントがCRMデータを読み書きし、分析まで回す運用が求められます。
課題
認可・権限・監査の設計が重要になる
課題
エージェント向けに“使える形”のAPIが必要
Core
03 / 12
中心思想
MCP / REST 主役
Relaticleは、AIエージェントがCRMデータを扱うための接続手段として、MCPサーバとREST APIを中心機能に据えます。
MCP
Model Context Protocol プロトコルで“つなぐ”
REST API
HTTP endpoints 読み書き・分析を実装
狙い
CRUDとスキーマ参照を提供しやすくする
Architecture
04 / 12
自己ホストの形
Docker + 権限
自己ホスト（Docker）で動かし、マルチワークスペース隔離とRBACで権限境界を意識した設計を示しています。
隔離
マルチワークスペース
管理
RBAC（Role-Based Access Control）
Data
05 / 12
CRMを“伸ばす”
カスタム項目 移行なし
移行なしで独自項目を追加でき、項目単位で暗号化も可能という主張がされています。
拡張
移行なしで項目追加
保護
項目単位暗号化（方式は要追加確認）
AI Workflow
06 / 12
エージェント作業
フルCRUD + 分析
REST APIやMCPサーバ経由で、作成・読取・更新・削除に加え、活動履歴やパイプライン分析が扱える方向性です。
CRUD
Create / Read / Update / Delete
履歴
活動履歴の追跡
分析
パイプライン分析
Use case
07 / 12
想定ユースケース
営業“チームなし”
営業チームを持たず、特定の企業リストに対して販売活動を行うケースで、AIがCRM更新と分析を支援する想定があります。
入力
企業リスト（対象範囲）
出力
CRM更新・状況分析（半自動化の焦点）
Strengths
08 / 12
強み：筋が良い
設計の“前提”一致
「AIエージェントがCRMデータを扱う」前提を、APIと運用の形まで一貫させようとしている点が強みです。
価値
エージェント実装を相対的に独立しやすい（MCP/REST）
価値
権限（ワークスペース隔離・RBAC）を最初から重視
Risks
09 / 12
注意点：README限界
安全性は要追加確認
提示情報は主にREADMEであり、実装の安全性・監査・バックアップ・暗号化方式などは不足している可能性があります。
セキュリティ
認可・認証・監査ログの粒度
暗号化
方式と“検索/集計”への影響
運用
バックアップ/復旧、鍵管理、脆弱性対応フロー
Legal
10 / 12
法務：ガードレール明示
AGPL + 例外
ライセンスは基本AGPL-3.0で、Cloudパッケージ（relaticle.com側）には別扱いがあり、商標ポリシーも触れています。
要点
AGPL-3.0（基本）
別扱い
Cloudパッケージのみ例外（詳細は要精読）
Decision
11 / 12
導入判断の軸
確認すべき論点
導入前に、セキュリティと運用責任の詳細を“埋める”ことで、自己ホストCRMのリスクを下げられます。
認可
MCP/REST経由で書ける範囲（RBAC粒度）
監査
誰がいつ更新したか（監査ログ）
運用
バックアップ、復旧、更新手順（鍵管理含む）
Closing
12 / 12
結論
魅力は明確、鍵は実装
AIエージェント連携を前提にした筋の良い設計が期待できる一方、暗号化・監査・運用の具体は追加調査が必要です。
