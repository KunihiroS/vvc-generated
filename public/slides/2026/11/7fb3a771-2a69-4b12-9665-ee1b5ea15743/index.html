COVER
02 / 16

バトラー/ガーデナー

責任を分ける

AIエージェントを「誰に仕えるか」で分類し、実装・運用の混乱（品質低下・衝突）を防ぐための指針。

PROBLEM
03 / 16

混同のコスト

役割が滲む

バトラーもガーデナーも「目標に向けてツールを使うwhileループ」に見える。けれど責任範囲（personかplaceか）が違うため、混同すると不具合が増える。

曖昧化
参照品質と整合性が崩れやすい
結果
矛盾更新・品質低下が蓄積→連鎖
METAPHOR
04 / 16

庭と召使

二類型だけにする

バトラー（butler）は「特定の1人に仕える」。ガーデナー（gardener）は「共有の場所（リポジトリ/知識ベース）を世話する」。

バトラー / butler
個人の好み・前提を学び代行
ガーデナー / gardener
制度的記憶を保ち整合性を維持
ENUMERATION
05 / 16

責任分界

中核は誰か/何か

決めるべき最重要軸は「仕える対象（personかplaceか）」。これを曖昧にすると、エージェントが勝手に領域へ手を伸ばす。

i
person責任：バトラー
ii
place責任：ガーデナー
iii
混在は衝突・矛盾の原因
ARCHITECTURE
06 / 16

バトラーの形

個人最適が得意

バトラーは一人用（シングルプレイヤー）であるほど設計しやすい。期待値や作業スタイルを学ぶほど成果物の質が上がる。

学習対象
好み・前提・作業スタイル
成果物例
PR / スライド / ドキュメント
ARCHITECTURE
07 / 16

ガーデナーの形

長期整備で守る

ガーデナーは「雑草を取る」ように、長期計画で共有の場所を整える。目的は今の正解ではなく、将来に参照できる状態を保つこと。

責務
institutional memory（制度的記憶）維持
対象
共有リポジトリ / CRM / 知識ベース
DISTINCTION
08 / 16

相互不適合

触る範囲を変える

バトラーが庭を直接いじると、矛盾更新や品質低下が蓄積しやすい。逆にガーデナーが個人に結びつくと、個人最適が暴走しうる。

NG: バトラー→place
直接更新で整合性が崩れやすい
NG: ガーデナー→person
組織ではなく個人最適に寄りやすい
EVIDENCE
09 / 16

汚染の連鎖

参照品質は全員を左右

低品質な参照データは、複数のバトラーに波及して誤作業を増幅する。だから検証・型・整合性チェックなどの防御が必要になる。

1
汚れたknowledge-base
2
バトラーの誤生成が増える
3
誤作業がさらに増幅
PROCESS
10 / 16

未来の更新

PR的な意図へ

バトラーが群れとして増える将来では、共有空間への変更は直接書き込みではなくプルリクのように「意図」を渡す形に移行する。採否と最終判断は庭側（ガーデナー）が担う。

提案側
intent（意図）を提示
判断側
ガーデナーが取り込み可否
COMPARISON
11 / 16

要点比較

どちらが何を守る

バトラーは個人文脈の実行最適化、ガーデナーは共有状態の整合性維持。役割を対応づけるだけで、運用の論点が一気に整理される。

バトラー
個人最適（UX成立）
/ single-player
ガーデナー
共有空間最適（参照品質）
/ institutional memory
EVIDENCE
12 / 16

筆者の見立て

採用価値は高い

この分離は「境界」を設計原則として言語化しており、マルチエージェント化のカオスを抑えられる可能性がある。

強み
変更責任を分け、衝突・矛盾を構造的に抑制
注意
完全二分ではなく、権限・ゲート・復旧まで具体化が必要
CLOSING
13 / 16

次に考える

設計に落とす

次は「どの操作がどのゲートを通るか」を権限・検証・監査ログ・失敗時リカバリまで拡張することが必要。意図（intent）と最終判断者を分ける発想を、運用フローへ実装する。

検証
型・整合性チェック
承認
ガーデナーの採否ゲート
記録
監査・復旧（リカバリ）設計
参考（本文内の裏付け・文脈）

・curator agent：他エージェントのノートを後からまとめて見直すことで共有知識を更新
