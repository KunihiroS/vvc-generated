COVER
02 / 16
MCPが“仕事”へ拡張
Claude連携の MCP進化
MCPは、ツール接続に加えて「長い手順・承認・ファイル受け渡し」を扱える方向へ進みました。要点は Skills / Tasks / Elicitation / File Uploads の組み合わせです。
New
Skills over MCP：知識（段取り）も同梱
Run
Tasks：長時間処理をバックグラウンド化
Control
Elicitation：ユーザー確認で事故を抑制
さらに File Uploads で PDF/画像/スプレッドシートを実運用のまま渡しやすくなります。
PROBLEM
03 / 16
“ツール”だけでは足りない
連携は 点 になりがち
従来のMCPは、サーバーが提供する「ツール名と説明」をClaudeへ提示します。しかし現場では、どの順で何を確認し、例外にどう対処するかが成功率を左右します。
不足
手順・ベストプラクティス（段取り）が伝わりにくい
結果
多段階の“仕事”が組み立てづらく、品質がばらつく
METAPHOR
04 / 16
Skills＝段取りの同梱
関数だけでなく 作業手順 まで
Skills over MCP は、ツールを使うための“ノウハウ（ガイド・ワークフロー）”を一緒に提供します。Claudeは必要時にそのスキルをロードして、多段階の仕事を進めやすくなります。
Tool
何ができるか（API/機能）
Skill
どう進めるか（手順・確認・例外対応）
一体で出荷でき、開発者は“ツールと知見の別管理”を減らせます。
ARCHITECTURE
05 / 16
MCPが“オーケストレーション基盤”へ
段取り・待機・承認・文書を 一つに
今回の拡張は、外部に依頼し結果を受け取って前へ進む運用に合わせて設計されています。Tools（機能）だけでなく、手順（Skills）と実行制御（Tasks/Elicitation）とデータ受け渡し（File Uploads）を扱います。
Skills（技能）
必要時にロードして実行
Tasks（仕事）
バックグラウンドで進行
Elicitation（確認）
承認ポイントで入力を取得
File Uploads により、PDF/画像/表などを“そのまま”渡しやすくします。
ENUMERATION
06 / 16
4つの拡張が噛み合う
Skills / Tasks / Elicitation / Uploads
“長い仕事”をプロダクション運用するために、4つの機能が役割分担します。Claudeが必要なタイミングで介入し、ユーザー承認とデータ受け渡しが成立する構造です。
Skills over MCP
手順・段取りを同梱（Toolの不足を補う）
Tasks
待ち続けず、結果を後から受け取る
Elicitation
削除/課金などの合意が必要な点で確認
File Uploads
PDF・スプレッドシート・画像をサーバーへ
EVIDENCE
07 / 16
Skillsが成功率を上げる
“段取り”が 知識 になる
ツール定義（名前・説明）だけでは、順番・確認・例外処理が伝わりません。Skillsを同梱すると、Claudeが多段階の作業をより適切に組み立てられます。
Before
実務の運用ノウハウがサーバーに閉じない
After
外部提供側が“成功手順”を知識として提供
結果として、失敗率低下と品質の一貫性に直結しやすい点が重要です。
PROCESS
08 / 16
Tasksで“待つ”をやめる
時間がかかる処理は 裏で
Tasksにより、Claudeがツール呼び出し完了まで止まる必要が減ります。外部サーバーがバックグラウンドで進め、準備ができたら結果を受け取って続きを進めます。
i
Claudeがタスク開始を指示
ii
サーバーがバックグラウンド実行
iii
結果受領後に会話/作業へ復帰
会話体験と運用効率が改善しやすい、という方向性です。
DISTINCTION
09 / 16
Elicitationは“止めて確認”
自動化の境界を 設計 する
削除や課金など、意思決定が必要な操作はElicitationで途中入力を求めます。その後も処理は継続でき、ガバナンスや安全設計に寄与します。
狙い
“止める→確認→続ける”を仕組み化
対象
金銭支出 / 削除 / 合意が必要な操作
安全性は機能だけで決まらず、対象操作の選定とUI/文言も重要です。
EVIDENCE
10 / 16
File Uploadsで“現場データ”へ
PDF/画像/表を 押し込まない
PDFや画像をテキスト化して長文コンテキストに詰めるのはボトルネックになりがちです。File Uploadsにより、文脈容量を圧迫せずサーバーへ渡せます。
Before
テキスト化・長文化が必要で非効率
After
ファイルをそのままサーバー連携
置き換えではなく“適材適所”。テキストで十分ならテキスト、ファイルならファイルです。
COMPARISON
11 / 16
Tool提供とSkills提供の違い
“できること”と “進め方”
ツール提供は「このサーバーは何ができるか」を知らせます。Skillsは「目的を達成するための手順・ベストプラクティス」を同梱でき、複数手順の組み立てを助けます。
ツール（Tool）
機能の提示：名前・説明中心
スキル（Skills）
運用の提示：手順・確認・ワークフロー
必要なときにだけロードする想定で、常時大量情報を抱え込む設計ではないと説明されています。
DISTINCTION
12 / 16
導入時の論点（意見）
前進は確か、でも 責任 は設計する
Skills/Taks/Elicitation/File Uploadsは“技術デモ”から“業務運用”へ引き上げる改良です。一方で、承認粒度、スキルの更新互換性、誤案内時の責任分界などは別途検討が必要です。
Practical
時間・承認・データ形式の現実的な詰まりを解消
Safety
Elicitationは事故抑制に寄与（ただし設計依存）
Governance
ログ/監査、承認フロー、ロールバック戦略が必要
自動化を強めるほどガバナンス設計の重要度が上がる、という注意点が残ります。
CLOSING
13 / 16
結論：エージェント連携の実務化
MCPは “仕事全体” を扱う
単発ツール利用から、手順・承認・ファイル搬送まで含む“仕事”へ拡張されます。MCPがエージェントのオーケストレーション基盤として強固になっていく、というメッセージです。
Takeaway
Skills：成功手順を同梱 / Tasks：待ちを削減 / Elicitation：確認 / File Uploads：実データ連携
Ready check
導入前にログ・監査、承認フロー、更新影響、責任分界を確認する
