Higher Order Harness

Endoとは

Endo（HOH）は、複数のLLM/プロバイダを同じプロトコルと同じ“スレッド体験”として束ねるためのハーネス設計です。 途中でエージェント（別CLI/別ベンダ）へ切替しつつ、会話の履歴や運用を保つことを狙います。
PROBLEM
03 / 16
AIを選び続ける負担

選択コスト問題

プロバイダが増えるほど、モデル切替に伴う挙動差・履歴差・ツール呼び出し差が運用を重くします。 結果として「会話の本線」や「同じ手順の再実行」が崩れやすくなります。
i
切替で体験が分断
ii
履歴・ツール差が事故要因
iii
再実行が属人化
iv
ガバナンスの根拠が散らばる
METAPHOR
04 / 16
関数合成の発想

HOHの比喩

Endoの見立ては「単発のハーネス」ではなく、ハーネス同士（エージェント）を“高階の部品”として合成することです。 同じプロトコル体験を保ちながら、途中で差し替え可能にします（編集可能な会話）。
HOH ≒ agent（部品）を組み合わせて返す：プロバイダやCLIが違っても、スレッド体験を揃える。
ARCHITECTURE
05 / 16
統一プロトコル

“同じ体験”への道

Endoは各プロバイダのCLIを、Endoの1プロトコルへストリーミングして取り扱います。 そのためモデル切替時にも、履歴・ツール呼び出し・許可プロンプト等の挙動差を揃えやすい設計です。
入力
Codex / Claude Code / Grok / OpenCode 等のCLI
変換
Endoプロトコルへ統一（ストリーム取り扱い）
効果
切替しても会話と運用が破綻しにくい
狙い
学習コスト削減・事故（想定外挙動差）低減
EVIDENCE
06 / 16
会話の編集

途中切替 + 履歴引継ぎ

1つのスレッドで、別エージェント（別ベンダ/別CLI）へ途中から切替しても履歴を引き継ぐ前提が提示されています。 また Dig In で別スレッドを“隣に開き”、本線を汚さず深掘りできます。
切替
Codex → Claude Code 等へ途中で差し替え
引継ぎ
Each agent picks up the full history（前提）
Dig In
フォーカス用の“隣スレッド”で本線維持
※ただし詳細な履歴の範囲・機密情報の扱いはREADMEだけでは確定できないため、事前検証が必要です。
PROCESS
07 / 16
構造化ワークフロー

TypeScriptで運用化

ワークフローはTypeScriptで定義し、agent() / parallel() / phase() などで段階化・並列化・制御します。 これにより単発の相談ではなく、同じ手順を繰り返す運用（再実行・スケジュール）へ接続できます。
表現の核（概念）
agent() / parallel() / phase()
→ parallel・phase・session id
→ 後続の再実行 / スケジュール実行
ARCHITECTURE
08 / 16
状態とルールの共有

Resource / Drizzle / Effect

Resourceの導入により、状態を Drizzle テーブルと Effect Schema で統一し、エージェント間で同じデータ・同じルールを共有する構想があります。 推論だけを散らばらせず、意思決定の基盤（データ）を揃える狙いです。
Resource
状態・ルールを定義（ガバナンスの軸）
統一
Drizzleテーブル + Effect Schema
共有
エージェント間で“同じ状態”を参照
効果
一貫性・再現性・説明可能性の向上
COMPARISON
09 / 16
“単発”との違い

ハーネス運用の差

Endoは「エージェントを単体で回す」だけでなく、スレッド体験の維持・編集、TSワークフローによる再実行、Resourceによる状態統一をまとめて狙います。 その結果、AIを“使う”から“運用する”へ重心が移ります。
通常の運用
切替ごとに履歴/挙動/手順がズレやすい
Endo（HOH）
統一プロトコル + 履歴引継ぎ + 編集可能スレッド
手順
属人化しやすい
Endo
TSで構造化（parallel/phase/session id）→再実行可能
DISTINCTION
10 / 16
価値の中心

3つの柱

Endoの価値は、(1)統一プロトコルで体験差を抑える、(2)HOHで会話を編集しつつ履歴を維持する、(3)TSワークフローで並列・段階・スケジュールへ拡張する、の3点に集約されます。
i
統一プロトコル：切替の挙動差を吸収
ii
HOH：途中切替 / Dig Inで本線維持
iii
TSワークフロー：parallel/phase/session idで再実行
iv
Resource：状態/ルールの一元化で一貫性

安全と運用の確認

READMEは全体像中心のため、権限・保存・失敗時の扱い・外部送信範囲などの具体が不足している可能性があります。 导入前に“安全に使うための最低限”を先回りで確認する必要があります。

保存

失敗時
リトライ/タイムアウト/部分失敗の扱い
送信範囲
どの情報が各プロバイダへ渡るか

導入の現実

0.1.xの変動リスク

Endoは0.1.xで破壊的変更があり得ると明記されているため、仕様の変動（ワークフロー互換性や挙動差）を織り込む必要があります。 推奨は「小さく検証→必要な権限/保存/送信範囲を確認→段階的に拡張」です。
i
ローカルで小さなワークフロー検証
ii
非機密データで挙動確認
iii
権限範囲・保存/送信範囲の明確化
iv
本番データへ段階移行

要点まとめ

結論：運用基盤

Endoは「AIを選び続ける」負担を減らし、「会話の合成・構造化・再実行」まで含めた運用基盤（HOH）を提供する方向性です。 ただしセキュリティ境界などの詳細はREADMEだけでは確定しないため、導入前の安全確認が鍵になります。
推奨する使い方
編集可能スレッド + TSワークフロー + Resourceで統一運用
最優先の確認
権限・保存・外部送信・失敗時の扱い（監査含む前提）
用語（bilingual）：HOH（高次ハーネス）/ harness（ハーネス）/ agent（エージェント）/ subscription（購読）/ provider（プロバイダ）
