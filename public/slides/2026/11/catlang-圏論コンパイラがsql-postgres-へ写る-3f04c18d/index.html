写像する コンパイラ

catlangは、カテゴリ理論（型と矢印）の構造でプログラムを組み立て、コンパイラがそれをPostgresのSQLに変換して実行結果を得ます。
計算の核
射合成 ⊗ 直積 ⊕ 余積（分岐）
実行の器
巨大SELECT ＋ 再帰CTE（ループ）

04 / 16
中間表現

ILは 射の式

catlangの中間表現（IL）は、変数名よりも「射の合成」「直積・余積の操作」「分岐」「cochoice」で計算を記述します。
例（直積）
prj₁ / prj₂、合成（⨟）、△（直積の構築）
例（余積）
inl / inr、▽（join）、分岐（▽）
NO FUNCTION APPLY
05 / 16
関数適用を回避

「渡す」ではなく 合成

catlangでは通常の「xを関数に渡す」発想（関数適用の($)）を避け、矢印合成・直積・余積の操作で計算を組み立てます。
考え方
データ依存と分岐を、矢印と（直積/余積）で表す
副作用
読みやすさは下がるが、名前消し→変換が簡単になる
EXAMPLE
06 / 16
countの罠

常に 100 を返す

記事の例のcountは入力に依らず100を返しますが、内部では「n=abs(n-100)を調べ、条件で次の反復値を決める」遠回りな構造で書かれています。
見かけ
どの入力でも結果は100
実装
ループ（cochoice）で反復し、最後に最終状態を抽出

07 / 16
脱糖 → IL

名前を消して 射へ

ソースコードはdesugarされてILになります。ILでは変数名がほとんど登場せず、直積はprj₁/prj₂、余積はinl/inrとjoinで表されます。
直積（△）
構築：△、分解：prj₁ / prj₂
余積（Either）
構築：inl / inr、合流：join（▽）
結果
「構造」がそのままSQL断片へ対応

08 / 16
ループ＝cochoice

cochoiceは 抜き差し

cochoiceは「Eitherの上の射を外して、最終的にLeftが返るまで反復する」操作として説明されます。これがSQLの再帰CTEに写像されます。
意味
Left＝完了、Right＝継続（擬似コードでも再帰で回す）
実行
再帰CTEで反復結果を表として積み上げる
DATA REPRESENTATION
09 / 16
Eitherを列へ

余積を NULL で識別

Eitherの値はSQLの都合に合わせて（例として）複数列へフラット化し、「どちらの構築子か」をNULLの有無で管理します。
変換
型 (Int, Either Int Int) → 3列の表現
論点
NULLの伝播・3値論理・整合性が安全性ボトルネック
RISK
10 / 16
最後の行

抽出に hack

再帰CTEが返す行の「最終」を素直に決めにくいため、記事ではclock_timestampをstep列として使うハックが含まれます。
なぜ必要
Postgresの順序/多重集合的性質のため、最終行が曖昧
将来の破綻
行生成が増えるプリミティブ導入で意味が崩れる可能性
COMPARISON
11 / 16
何が強い

変換の 変換 が楽

ILの操作が規則的で単純（合成・直積・余積・cochoice）だから、各操作に対応するSQLを割り当てれば、ターゲットをSQL以外へ広げやすいと主張されます。
i
ILは「意味の単位」が小さく固定
ii
バックエンドは機械的に対応表を作れる
iii
名前消し（スタック/射）で転用性が上がる
LIMITS
12 / 16
実用の壁

巨大SELECTのコスト

SQL生成は「巨大なSELECT（さらに再帰CTE）」でループを表現するため、規模が大きくなると性能問題や最適化不足が現実的になります。
性能
インデックスやクエリプラン次第で再帰ステップが高コストになり得る
意味保存
NULL表現やstepハックは、拡張で破綻するリスクがある
