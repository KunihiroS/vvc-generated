SWE-CoWork
02 / 14
研究が示す現実
追跡が鍵
SWE-CoWork は、AI が要求（仕様・未決事項）を「見つける」だけでなく、 開発の全期間で整合的に「完了まで運用できるか」を測ります。
二言語用語：要求追跡 / requirement tracking（英）／要求追跡（JP）
Problem
03 / 14
単なるコード生成ではない
仕事の完了
評価対象は、途中で判明した保留（未決事項）や要求更新を 確認→実装→検証→引き継ぎまで矛盾なく持ち越せるかです。
Input
要求の断片（仕様・意図・保留）
Goal
最後の引き継ぎまで整合維持
“完了”＝定義された成功状態（Pass rate）
Metrics
04 / 14
指標が分けるもの
F2P と Pass
F2P（部分成功）は新しい要求の通過度合い、Pass rate（全体成功）は同一実行で全条件を同時達成した割合です。 そのため両者は一致しません。
F2P
新規要求：部分的に満たせた度合い
Pass rate
全検証ノード：一度で同時達成
Bilingual：部分成功（F2P）/ partial success（英）
Core claim
05 / 14
起きるズレ
高評価でも落ちる
F2P が高くても Pass rate が低くなり得ます。 つまり「途中まで良い」が「最後の整合性」まで続かない失敗が残っていることを意味します。
途中
要求の取りこぼし減
終盤
反映漏れ／不整合で失敗
判定
Pass rate は厳格（同時達成のみ）
メッセージ：最後までの“追跡”が弱い
Evidence
06 / 14
切り分けの実験
Oracle-Spec
Oracle-Spec（完全仕様を最初に提示）でも全体成功（Pass rate）が大きく改善しないなら、 ボトルネックは「情報不足」だけではありません。
仮説A
情報が足りないから失敗
観測
Pass rate はほぼ伸びない
結論へ：得た情報を状態として運用し続ける必要
Interpretation
07 / 14
能力の別物
聞けても完了できない
質問相手の選定（要求取得）は比較的うまくいっても、 未追跡の保留・未反映要求・不合格変更などの“最終段階の管理”で落ちます。
取得
誰に聞くか／何を問うか
完了
反映・検証・報告の一貫性
“要求追跡”＝追跡（tracking）と運用（maintenance）の両方
Process
08 / 14
追跡の連鎖
状態管理
研究の中心は、要求（未決事項や更新）を“どこかに残す”のではなく、 開発全期間で更新し続け、最後の受け入れ判定まで整合させることです。
i. 発見
保留（未決）を特定し記録
ii. 確認
担当者に確認し内容を更新
iii. 運用
実装→検証→引き継ぎで整合維持
関連英語：requirement tracking（要求追跡）
Limitations
09 / 14
批判的見方
同一障壁か？
失敗の性質は示唆的ですが、デジタル同僚（26人）はルール化されたシミュレーションで、 人間組織の政治・暗黙知・非定型交渉を完全には再現しません。
代表性
組織政治・暗黙知が不足し得る
結論の強さ
“確定”には追加検証が必要
別の要因（評価判定の主観性など）もあり得る
Takeaway
10 / 14
設計への示唆
ゲート設計
現場導入では、最後までの完了判定（ゲート）と、 再実行・再質問・差戻しなどの修正ループを設計しないと事故につながり得ます。
狙い
Pass rate を守る
仕組み
追跡ログ（要求状態）
運用
検証ゲート＋修正ループ
一言：賢い対話より“忘れない運用”
