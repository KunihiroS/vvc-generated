macOS向け運用最適化

agweb 単一ウィンドウ

macOS（macOS 26以降）で、複数の開発エージェントがWeb操作を同時に回せるよう最適化されたブラウザです。

一番の狙いは「複数タブを1ウィンドウにまとめつつ、フォーカスを奪わないこと」。
Problem
03 / 16
エージェント現場の詰まり

なぜ困る？

coding agents がブラウザを操作するとき、フォーカス競合・ヘッドレス差・状態追跡・ログインMFA/CAPTCHAがボトルネックになります。

Focus
キーボード/入力フォーカスの奪い合いで、操作の正しさと人間の作業が壊れる。
Headless差
ヘッドレスでは挙動が変わり、失敗理由が分かりにくい。
State追跡
どこがどう変わったかを毎回取り直すと、観測コストが高い。
Login難所
ログイン・MFA・CAPTCHAは自動化が不完全で、手渡し導線が必要。
Metaphor
04 / 16
“邪魔しない観測窓”

同時運用の前提

agwebは「タブを1つのウィンドウに集約」し、サイドバーとダッシュボードで全エージェントの状態を見える化します。

運用
⌘D のダッシュボードで全タブの状態を同時に確認。
設計
常に前に出ない／前に出る必要がないため、フォーカス奪取を抑える。
Architecture
05 / 16
複数エージェント導線

workspace×tab×dashboard

各エージェントは workspace を持ち、タブはサイドバーで管理されます。人が“観測”し、必要に応じて“介入”できます。

i 入口
エージェントごとに workspace を分けて実行。
ii 管理
サイドバーでタブを整理し、迷子を減らす。
iii 視認
⌘Dで全体状態を俯瞰し、次の判断に直結。
Evidence
06 / 16
CPUとメモリを抑える

idleを止める

アイドル時のタブはCPU使用率 0% に近づけ、スロットリング→サスペンドで負荷を抑える設計です。

例
5つ開いたページが 0% CPU 近くになる例が示されている。
比較
agweb 約590MB / headless Chrome 約730MB / Playwright Chrome 約1.6GB（紹介記事の再掲）。
※数字は紹介記事ベースで、運用条件で変動します。
Process
07 / 16
観測コストを削減

snapshot/ref/diff

毎回“丸ごと取得”を避け、snapshot に参照ID（ref）を付与し diff / find で必要箇所だけ返すことで、トークンと観測コストを下げます。

snapshot
要素に参照ID（ref）を付けて追跡可能にする。
diff / find
差分・必要情報のみを返して、意思決定を効率化。
クリックの返信に観測が含まれるため、二度目の snapshot が不要になるケースがある。
Distinction
08 / 16
秘密情報を出さない

profile共有とsecret-cmd

ログインは一度行い、named profile を複数エージェントで共有できます。パスワードは transcript に出さない仕組みで運用します。

named profile
ログイン状態を複数エージェントで再利用して加速。
fill --secret-cmd
秘密をトランスクリプトに出さずに入力（運用・監査に寄与）。
手渡し
login/MFA/CAPTCHA は “ask hands” でユーザーへタブを渡す。
フォーカス
タブ渡しでもフォーカス奪取しにくい設計意図。
Architecture
09 / 16
ネイティブ操作寄り

クリック/キー入力をmacOSイベントへ

UI操作（クリック・キー入力・ポインタ移動）をネイティブ macOS イベントとして扱い、ホバーやドラッグ&ドロップが機能しやすいよう配慮されています。

hover
ホバー状態に依存するUIが壊れにくい方向。
DnD
ドラッグ&ドロップの成功率を上げる狙い。
Problem
10 / 16
正直な制約

できないこともある

agwebはWebKitのみで、Chrome DevTools Protocolや拡張の期待通り動作が難しい場合があります。広告ブロックや route mock にも制約が明記されています。

WebKitのみ
Chrome DevTools Protocol（CDP）が使えない。
拡張
拡張機能が期待通り動かない可能性。
adblock
uBlock Origin の“スクリプト”実行ができず壁を突破できない場合。
route mock
静的リソースの扱いに制約がある、とされる。
Comparison
11 / 16
Playwrightと併用前提

移行は段階で

READMEの主張は「可能な限り同じコマンド体系」ですが、WebKitのみ・CDPなし・サイト/拡張制約があるため、必要に応じてPlaywrightを併用します。

agwebの強み
フォーカスを奪いにくい／実ウィンドウで観測しやすい／同時運用の運用設計が厚い。
併用の理由
Chrome依存・ヘッドレス判定・拡張・CDPが必要な場面では互換が崩れる。
Enumeration
12 / 16
導入判断のチェック

評価軸5つ

導入時は「改善できる点」と「地雷」をセットで棚卸しすると安全です。ここでは実務判断に直結する軸を整理します。

i フォーカス
複数エージェントで入力競合が起きていないか。
ii 可視化
⌘Dで状態を俯瞰でき、原因切り分けが速いか。
iii 観測コスト
snapshot/ref/diffでトークン削減が効くか。
iv ログイン
MFA/CAPTCHAを “ask hands” で処理できるか。
v 互換
WebKitのみ・adblock/拡張/CDP制約が運用サイトに刺さるか。
closing
13 / 16
結論

agweb は運用道具

agwebは「複数エージェント同時運用の現場課題」に最適化されたブラウザで、フォーカス抑制・リソース制御・観測効率・秘密情報非表示が核です。

主な価値
同時可視化（workspace/⌘D）＋idle抑制（スロットリング/サスペンド）＋snapshot差分（ref/diff）。
主な制約（英→日）
WebKit-only（WebKitのみ） / No CDP（CDPなし） / Adblock limit（広告ブロック限界）。
References（要約）: Show HN / daily.dev 紹介記事 / 併せてテキスト記載の制約（WebKit・CDPなし・拡張/広告/route mock）を根拠に整理。
