条件付き採用

個人・信頼済みチームの自己ホスト型自動化基盤として、隔離設計を理解した上で評価導入する価値がある。一方、相互に信頼できないテナント、第三者がワークフローを書ける SaaS、強い秘密分離を必須とする本番用途には現状のまま採用しない。最大の条件は、ワークフロー編集権限を本番資格情報の利用権限と同等に扱うこと、Code node を信頼境界に使わないこと、Docker Compose の本番構成から外さないことである。

Go 条件: (1) 単一信頼ドメイン、(2) Compose 構成・runner 内部ネットワーク・read-only/cap-drop を維持、(3) agent token/MCP 認可を強い管理対象にする、(4) 本番前に実機で隔離・復旧・負荷を再現、(5) 資格情報の送信先制約を外部統制またはコード追加で補う。

No-Go 条件: 不特定ユーザーが TOML を編集できる、資格情報名を知るだけで利用可能な状態が許容できない、Code script 同士の同一 VM 共有が許容できない、監査ログ・HA・バックアップ/RPO/RTO が必須だが別途整備しない、のいずれか。

根拠 — README.md:205–223要約: runner は外部アクセス・DB・資格情報を持たない一方、「code node code can potentially interact with other code node code within the sidecar」を最大の未解決問題と明記し、効率を優先して残している。
根拠 — specs/090_workflow_files.md:34–39要約: ワークフロー作者は {{ creds.ANY_NAME }} を HTTP node に置いて任意送信できる。per-credential allowed-host lock は未実装。

2) 深ぼるべき理由（目的・評価対象）

PurpleFlow は「AI が編集する TOML」「強力な HTTP/SSH/Postgres/Code node」「本番資格情報」「ファイル書込可能な agent/MCP」を一体化する。したがって通常のワークフロー UI より、編集者→資格情報→任意宛先という権限連鎖と、任意 Elixir 実行の隔離境界が採否を左右する。

  • 評価対象: Code runner、ワークフローローダー、dufs/MCP ファイル面、credential 暗号化・展開・redaction、run file、watchdog/heart、性能主張、spec-test-code の整合。
  • 評価対象外/不明: 実環境の reverse proxy/TLS/WAF、運用者の token 保管、Postgres のバックアップ、ホスト/カーネル堅牢化、CI の実際の直近成功状態、依存パッケージの現時点脆弱性。静的読解だけでは保証できない。
  • 重要な前提: リポジトリ自身も「power tool」と定義し、制約を強制せず選択肢として提供する方針。その哲学は柔軟性と引き換えに誤設定耐性を下げる。
根拠 — AGENTS.md:26–38要約: “PurpleFlow is a power tool”; hard-coded limits や危険用途の禁止を避け、利用者の設計判断を優先する。
根拠 — README.md:402–431要約: agent token と MCP 認可は workflow files の read/write を許し、workflow は資格情報を使える。つまりファイル編集権限は間接的な秘密利用権限である。

3) アーキテクチャ設計サマリ（隔離・権限・データフロー）

Internet/User/Agent └─ app (Phoenix, admin/agent/MCP auth, credentials decrypt, DB access) ├─ Postgres (runs + encrypted credentials) [purple_flow network] ├─ files/dufs (workflow RW, .git masked) [internal files network] └─ runner TCP :4100 (source+input+steps) [internal runner network] └─ same BEAM VM shared by all Code executions workflow host dir ─ro→ app; ─rw→ dufs; runner has no mount run-files volume ─rw→ app only; deleted at run end / swept at boot

Code node → app/DB/Internetrunner は専用 internal network のみ。秘密 env、DB URL、workflow mount なし。app は runner subnet 起点の HTTP を拒否。release distribution 無効。強い初期設計。ただし Docker/host kernel escape は対象外。dev/test の in-VM runner は隔離なし。
Code node 間各 script は process/group leader で終了処理されるが、同一 runner VM・同一 OS namespace を共有。未解決。BEAM 内の他 process/共有状態への干渉可能性を README/TODO が認識。
workflow filesapp は read-only、dufs は read-write、runner は未 mount。.git は read-only tmpfs で覆う。ホスト git hook 脱出対策を含み良い。dufs への書込権限は強権限。
資格情報AES-256-GCM at rest。app のみ master key 保有。Template 展開後に node へ渡し、保存結果を値一致ベースで redact。DB dump 対策は妥当。送信先・workflow scope は未制限。短い秘密は redact されない。
run filesUUID/UUID 形式参照、専用 volume、終了時削除、起動時全 sweep。一時性は明確。ただしクラッシュ後再起動まで残る。永続成果物には不向き。
根拠 — docker-compose.yml:62–99, 163–173runner は秘密なし、read_only、tmpfs、全 capability drop、no-new-privileges、512 MB/1 CPU/256 PID、internal network のみ。
根拠 — docker-compose.yml:100–139dufs は workflow volume を RW mount する一方、実 .git を read-only tmpfs で隠し、専用 internal network・cap-drop を使う。
根拠 — lib/purple_flow/runner/server.ex:178–245各 request を process で Code.eval_string し、group leader を割り当て、終了後 script/leader を kill して Reaper に残存 process の削除を依頼する。

6) 性能主張の妥当性（README記載ベンチの根拠確認）

判定: 根拠資料はあるが、マーケティング主張を一般性能として採用判断に直結させてはいけない。

  • README の「10,000 one-second jobs / 3.2 s / runner 512 MB」「n8n は100で2 GB」は docs/n8n_case_study.md の test log（PF-S6/S7, N-S5/S6）へ追跡でき、sample workflow/script への参照もある。数字が完全に無根拠ではない。
  • 測定は 2026-09-27、単一 cloud VM、ほぼ各条件1回、PurpleFlow は release でなく mix run dev、n8n は公式 image・SQLite・non-queue mode。処理単位も PurpleFlow 1 step 対 n8n 1 workflow execution で同一ではない。
  • 「200x memory efficient」は 29 KB/script と約7 MB/execution の比に対応するが、同等機能・同等永続化・同等分離の一般比較ではない。自社 workload（HTTP、DB、ファイル、長時間処理、失敗、保存量）で再測定が必要。
  • runner 512 MBだけでなく app peak 約334–339 MB、DB は別。README の短い表現だけを「全体512 MB」と読んではならない。
根拠 — README.md:301–311主張値と case study / samples/testing へのリンク。
根拠 — docs/n8n_case_study.md:24–414 CPU/15 GB の1台、runner 512 MB/1 CPU、PurpleFlow は dev build、n8n は SQLite、各 test は原則1回。
